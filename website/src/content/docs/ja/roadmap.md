Cairn は[日付ベースのバージョン](/ja/spec/versioning-editions/#101-ターゲットはコンパイル時のパラメータ) `YYYY.M[.PATCH]` で、**毎月マイナーリリース** を出します。毎月、準備ができたものをリリースし、区切りのよい「1.0」を待って何かを出し惜しむことはしません。月ごとの予定とは別に、名前付きのマイルストーンを 6 つ設けています。カレンダーの日付よりも変わりにくい目標なので、コントリビューターも利用者もこれを目安に計画を立てられます。

> スケジュールは計画であり、約束ではありません。コンパイラはオープンに開発しているので、予定が遅れることもあります。実際に何がリリースされたかは [CHANGELOG](https://github.com/kage1020/Cairn/blob/main/CHANGELOG.md) (英語) で確認してください。

## 現在の状況

コンパイラは最初の計画よりずっと先に進みました。M1・M2・M4・M5 がコンパイラに求める機能は 2026.8.0 までにすべて入り、そのうち 3 つは予定より何か月も早く入りました。それ以降のリリースでは、入ったものを仕様に照らして固めてきました。ただし M2 はロックファイルの形式を Stable にするマイルストーンでもあり、ロックファイルは M2 の機能が入った後も変わり続けました。2026.9.0 で `lock_schema_version` が加わってレジストリパックのハッシュの組み立て方が変わり、2026.10.0 ではパレットの正規化ですべての `resolved_ir_hash` が変わっています。そのため M2 は、Stable の約束が始まる 2026.11.0 で達成とみなします。残るマイルストーンは 2 つです。

- **M3** で、言語はドラフトを抜けます。すべてのサンプルは、すでに Java 向けには警告なしでコンパイルでき、Bedrock 向けにもビルドできます。M3 にまだ必要なものは[ドラフトを外すまで](#ドラフトを外すまで)にまとめています。
- **M6** で、レッドストーンが構造ファイルに入ります。合成と配置配線は `--experimental-logic-synth` を付けた `cairn synth` で動きますが、配線済みの回路を成果物に書き出す処理はまだなく、回路をシミュレートするものもありません。

## リリースの周期

- **毎月のマイナーリリース** (`YYYY.M.0`) は毎月 1 日に出します。リリース PR は cron ジョブが自動で作り、人がレビューしてからマージします。
- **パッチリリース** (`YYYY.M.N`、`N ≥ 1`) は必要に応じて出します。メンテナが同じリリースのジョブを手動で動かすと、`canary` からリリース PR が作られます。主なきっかけは、レジストリパックや制約パックの更新、リグレッション、セキュリティ修正です。1 か月あたりのパッチの回数に上限はありません。
- **チャンネル** は `stable` の 1 つだけです。nightly や beta を別に運用することはしません。まだ安定していない挙動は、リリースチャンネルではなく[互換性ティア](/ja/spec/compatibility/)で区別します。
- **バックポート** はしません。サポート対象は最新のリリースだけです。古い `YYYY.M.*` の系列には、それ以上パッチを出しません。

## マイルストーン

各マイルストーンは「Cairn が X を確実にこなせる」ことを示す関門で、X ができるリリースが出た時点で達成とみなします。ある対象を Stable にするマイルストーンは、その対象の Stable の約束が始まった時点で達成とみなします。バージョン番号とは別に名前を付けておくことで、月ごとの予定がずれても、ロードマップで使う言葉は変わりません。

| マイルストーン | 状況 | 達成するとできること |
|---|---|---|
| **M1, source parses** | 2026.7.1 で達成 | `examples/` のすべてのファイルについて、`cairn parse` が AST を出力する |
| **M2, minimal build** | 2026.11.0 で達成 (機能は 2026.7.1 で実装) | 床と壁だけの 1 部屋の構造について、`cairn compile` が Java の `.nbt` とロックファイルを書き出し、ロックファイルの形式が Stable になる |
| **M3, examples work** | 2027.1.0 の予定 | `examples/` のすべてのファイルが `--edition java` で警告なしにコンパイルでき、Minecraft で読み込める。仕様がドラフトを抜け、[互換性ティア](/ja/spec/compatibility/#c2-マイルストーンごとのティア表)が M3 に挙げる対象が Stable になる |
| **M4, Java/Bedrock parity** | 2026.8.0 で達成 | 同じ DSL ソースから、両エディション向けに有効な出力ができる。エディション対応表が埋まり、エディション別のテーマのフォールバックが動く |
| **M5, developer experience** | 2026.8.0 で達成 | `cairn-lsp` が、少なくとも 1 つのエディタ (VS Code) で診断と補完を提供する |
| **M6, redstone simulates** | 2027.4.0 の予定 | `cairn compile` が `logic` のグラフを構造ファイルに配置し、tick シミュレータが、組み上げた回路に対して `redstone-door` のアサーションを検証する |

## ドラフトを外すまで

仕様の題は `2026.06 (ドラフト)` です。このラベルは M3 で外します。そのとき、[互換性ティア](/ja/spec/compatibility/#c2-マイルストーンごとのティア表)が M3 に挙げる対象が Stable になります。`.crn` の構文 (5〜9 章と §10.7)、`cairn compile`・`check`・`info` のフラグ・JSON スキーマ・終了コード、診断コード、tier-1 のマテリアル語彙です。それ以降、仕様はそれを含むリリースのバージョンを名乗り、最初は `2027.1` です。これらの対象を壊す変更には、`W_DEPRECATED` による猶予期間が必要になります。

それまでに片付けることは次のとおりです。

- **tier-1 のトークンを示す。** [正規トークン](/ja/spec/materials-themes/#72-正規トークン)は、どのトークンが tier-1 なのかをまだ示していません。tier-1 の行は、Stable になる対象の 1 つです。
- **診断コードを固める。** M3 の後は、コードを足しても何も壊れませんが、既存のコードの意味を変えると破壊的変更になります。後者の変更は 2027.1.0 より前に済ませます。仮置きのコードが、その代わりをしていた構文の実装によって出なくなる場合は、コードを足すのと同じ扱いです。たとえば `W_STATE_LITERAL_UNCHECKED` が `E_STATE_DOMAIN` に置き換わる場合や、`E_UNKNOWN_KEYWORD` が `spawn` に出なくなる場合です。仮置きのコードの意味は変わらず、代わりに入るのは仕様がもともと定めている挙動で、[互換性「ティアの対象外」](/ja/spec/compatibility/#c4-ティアの対象外)はこれを破壊的変更に数えません。互換性の章にも、M3 までにそう明記します。

## スケジュールを守る仕組み

リリースの手順そのものを自動化しています。

1. **毎月のマイナーリリースの PR** は、毎月 1 日の `04:17 UTC` に GitHub Actions の cron が作ります。GitHub Actions の cron は毎時 0 分ちょうどに遅れたりスキップされたりしやすいので、あえて時刻をずらしています。パッチでは、同じジョブを手動で動かします。使うバージョンを指定することもできます。
2. **バージョン** は既存のタグから計算します。`vYYYY.M.*` のタグがまだなければ次は `YYYY.M.0`、すでにあればその月の次のパッチになります。計算したバージョンは、ワークスペースの `Cargo.toml` に書き込みます。
3. **release-plz** がコミットから changelog の節を書き、リリース PR を開きます。続けてジョブが、tree-sitter と VS Code のマニフェストを同じバージョンに揃え、パーサを生成し直し、`changelog.d/` のフラグメントを `CHANGELOG.md` にまとめます。
4. **人によるレビュー** を経て、リリース PR を `canary` にマージします。パッチでもマイナーでも同じです。
5. **公開** は、このマージをきっかけに実行します。`xtask` 以外のすべてのクレートを crates.io に `cargo publish` して `vYYYY.M.N` のタグを打ちます。Linux・macOS・Windows の `x86_64` と `aarch64` 向けのバイナリを、ターゲットごとのランナーでビルドします。すべてのアーカイブを SHA-256 のチェックサムとともに GitHub Release に添付し、Windows の `aarch64` 版を除く各アーカイブには sigstore の署名バンドルも添えます。署名付きの CycloneDX 形式の SBOM も添付します。tree-sitter の文法を npm に公開し、最後に `canary` を `main` に反映する PR を開きます。

このスケジュールを通じた互換性の扱いは、別に[互換性ティア](/ja/spec/compatibility/)で定めています。ロックファイルの形式は M2 を達成する 2026.11.0 から、LSP のワイヤプロトコルは M5 から **Stable** です。`.crn` の構文は M3 で、レッドストーンの DSL は M6 で続きます。Rust の API はずっと **Internal** のままで、それ以外のほとんどは当面 **Evolving** とします。
