## 6.1 既定では導出し、上書きで昇格する

既定では、コンパイラが位置と隣接するブロックからブロックステートを導出します。階段の向き、ドアの向き、ガラス板・フェンス・壁のつながり、チェストの左右などです。

現時点で導出するのは、このうち階段の向きと形、梁・ドア・チェスト・トラップドア・看板・ベッド・レッドストーン部品の向き、ガラス板・フェンス・壁・レッドストーンダストのつながり、チェストの連結です。`roof` は、置かれた位置から階段の `facing`、`half`、`shape` を得ます。軒の `stair` が位置から得るのは、置かれた面に応じた東西南北の `facing` だけで、`half` と `shape` は行に書いた値か、既定の `top` と `straight` です。つながりと連結は、すべてのメンバーを塗り終えたあとで設定します ([つながり](#つながり))。`waterlogged` は、水の `fill` がブロックと重なるところで設定します ([§6.3](#63-waterlogged))。下で述べる入れ替えは、トーチのものも看板のものも導出します。

`door` は、切り抜いた開口に 2 段の高さのドアのブロックをはめます ([構文 §5.4](/ja/spec/syntax/#54-セレクタ))。開口の段に `half=lower`、その上の段に `half=upper` を置きます。`facing` は構造の内側を向くので、閉じたドアは壁の外面に収まり、内側へ開きます。ドアは閉じた状態 `open=false` で組み上げます。`hinge` は、すべての開口を切り抜いたあとで、隣の壁から読み取ります。左右は外から見た向きで、ドアの左は `at=left` の側です。左右それぞれについて、ドアが立つ 2 段のうち、隣のセルにまだ `walls` メンバーのブロックが残っている段を数えます。また、ドアの下半分の隣に別のドアの下半分が立っていれば、その側にドアがあるとみなします。左にドアがあって右にないとき、または右の壁が左より多いときは蝶番を右に、それ以外は左に付けます。途切れのない壁のドアは左に、窓の隣のドアは壁の側に、並んだ 2 枚のドアはそれぞれ外側に蝶番が付き、両開きの組として開きます。ドアの行に書いた `hinge=left` か `hinge=right`、`open=true` か `open=false` は、導出した値に代わります。

`chest` は、壁を背にしてチェストのブロックを 1 つ置きます。置くセルは、同じ `at=`、`offset=`、`y=` を書いた `pressure_plate` が取るセルと同じで、`at=inside.<side>` なら壁の 1 ボクセル内側、`at=<side>.outside` なら 1 ボクセル外側です。感圧板の行が拒否される、または先送りされる場合には、チェストの行も同じように扱われます ([レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング))。`facing` は背にした壁から離れる向きで、内側に置いたチェストは構造の内側を、外側に置いたチェストは外側を向きます。行に `facing=` を書くと向きを変えられます。`in` は構造の内側、`out` は外側、`left` と `right` は壁に沿った向きで、左右は壁の外から見た向きなので、`left` は `offset=0` の側です。チェストは隣のチェストと連結し ([つながり](#つながり))、`size=single` を書くと単体のままになります。`facing=` や `size=` にそれ以外の識別子を書くと `E_INVALID_MEMBER` で、`facing=` に東西南北の方角を書いた場合は、壁から見てチェストをその向きにする語をメッセージが示します。`size=2x3` のように識別子でない値は `W_IGNORED_ARGUMENT` で、そのキーを書かなかったものとして読みます。チェストの `mat_slot=` はチェストのブロックを指し、`mat_slot=` のないチェストはレジストリパックの `@chest.default` で組みます ([マテリアルとテーマ §7.2](/ja/spec/materials-themes/#tier-1-のトークン))。ブロックはチェスト、つまりレジストリパックの `connections` コンポーネントがチェストとして読むブロックでなければなりません (MUST)。これは `type` が `single`、`left`、`right` のいずれかを取るブロックで ([バージョンとエディション §10.3](/ja/spec/versioning-editions/#103-バックエンドはデータテーブル))、エンダーチェストはチェストではありません。パックが答えられないときは、ID が `chest` であるか `_chest` で終わるブロックをチェストとみなします。それ以外は `E_INCOMPATIBLE_MATERIAL` で ([リント](/ja/spec/lint/))、エラーと並んで `@chest.default` でチェストを組みます。チェストは中身を持ちません ([エンティティ §8.3](/ja/spec/entities/#83-どこで線を引くか))。

`lever`、`button`、`daylight`、`observer`、`lamp`、`piston`、`dispenser` は、チェストと同じ方法でセルを取ります ([レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング))。レバーとボタンは壁に掛かり、`face=wall` と、壁から離れる向きの `facing` を持ちます。これは行の何によっても上書きされません。オブザーバー、ピストン、ディスペンサーも、行の `facing=` で向きを変えない限り壁から離れる向きを向きます。使える語は、チェストの 4 つの語に `up` と `down` を加えたものです。どれも動力のない状態で組むので、`powered`、`lit`、`extended`、`triggered` は書き出しません。

Tier 0 の部品 (`repeater`、`comparator`、`redstone_torch`、`redstone_dust`) は、[レッドストーン §14.1](/ja/spec/redstone/#tier-0-の部品) のとおりにセルと向きを取ります。リピーターとコンパレーターの `facing=` は駆動する向き、つまり前面が向く方向で、ゲームの `facing` は背面が向く方向なので、ブロックには逆の向きを書きます。壁のそばに置いたトーチと、3 つ組の位置に `facing=` 付きで置いたトーチは壁付きトーチで、`facing` は指す向きです。3 つ組の位置に `facing=` なしで置いたトーチは、立てたトーチです。リピーターの `delay` とコンパレーターの `mode` は行に書いた値、書かれていなければ `1` と `compare` です。どの部品も何からも動力を受けていない状態で組むので、`powered`、`locked`、`lit`、`power` は書かず、ブロック自身の既定のステートのままです。リピーターは動力もロックもなく、コンパレーターは動力がなく、トーチは点灯し、ダストは信号強度 0 です。

`trapdoor` は、トラップドアのブロックを 1 つ置きます。壁のそばに `at=<side>.outside` か `at=inside.<side>` と `offset=`、`y=` で置くときは、同じ `at=`、`offset=`、`y=` を書いたチェストが取るセルを取り、チェストの行が拒否される、または先送りされる場合には、トラップドアの行も同じように扱われます。`facing` は壁から離れる向きなので、トラップドアはセルの壁の側に蝶番が付き、開くと壁にぴったり沿います。`facing=` に `in`、`out`、`left`、`right` を書くと、チェストと同じように向きを変えます。座標の 3 つ組 `at=x,y,z` で置くときは、Tier 0 の部品と同じセルを取り ([レッドストーン §14.1](/ja/spec/redstone/#tier-0-の部品))、`facing=` は東西南北の方角 `north`、`south`、`east`、`west` です。書かなければブロック自身の `facing` のままです。トラップドアは閉じた状態でセルの下半分に、つまり `open=false` と `half=bottom` で組み、行に書いた `open=true` や `half=top` はそれぞれに代わります。動力のない状態で組むので、`powered` は書き出しません。`facing=` や `half=` にそれ以外の識別子を書くと `E_INVALID_MEMBER` で、壁のそばで東西南北の方角を書いた場合と、3 つ組の位置で壁から見た向きを書いた場合も同じです。識別子でない値と、真偽値でない `open=` は `W_IGNORED_ARGUMENT` で、そのキーを書かなかったものとして読みます。トラップドアの `mat_slot=` はそのブロックを指し、`mat_slot=` のないトラップドアはレジストリパックの `@trapdoor.default` で組みます。ブロックはトラップドア、つまり ID が `trapdoor` であるか `_trapdoor` で終わるブロックでなければなりません (MUST)。それ以外は `E_INCOMPATIBLE_MATERIAL` で、エラーと並んで `@trapdoor.default` でトラップドアを組みます。

`beam` は、柱状のブロックを横に寝かせて一列に並べます。種類は `kind=pillar` の 1 つです。`at=<side>.top` は、その `level` の下の壁の最上段、つまりレベルの最初の段を含む `walls` の積み段の最後の段に、壁の 2 つの角のあいだのセルにわたって梁を渡します。`at=<id>.top` は、同じ本体のうちその `id=` を持つ `door` か `window` の上、開口の最上段の 1 段上に、開口の列と左右に 1 列ずつ多くわたって梁を渡します。これも壁の角のあいだに限ります。窓の `repeat=` の連なりと `sym=true` の鏡像は、窓の行が切り抜くとおりにそれぞれ覆います。面の名前は ID より先に読みます。開口の上に渡す梁は、梁自身の `level` では動きません。梁の `axis` は壁に沿い、前面と背面では `x`、左右の面では `z` です。行に `axis=` で `x`、`y`、`z` を書くとそれに代わるので、`axis=y` ならブロックを立てて帯にします。梁は `envelope` で、載る壁の上に置き、あとからそこを通る開口は `openings` で切り抜きます ([コンパイルモデル §4.1](/ja/spec/compilation/#41-フェーズ評価))。`kind=` がないか知らない種類であるもの、どちらの形でもない `at=`、本体のどの `door` や `window` も持たない ID、角のあいだにセルを持たないほど短い壁、どの `walls` メンバーも届くように書かれていない段、`axis=` のそれ以外の識別子は `E_INVALID_MEMBER` です。届くように書かれた `walls` メンバーが塗らない段と、自身の行が位置を決めない開口は `W_DEFERRED_MEMBER` で、識別子でない `axis=` は `W_IGNORED_ARGUMENT` です。梁の `mat_slot=` はそのブロックを指し、`mat_slot=` のない梁はレジストリパックの `@beam.default` で組みます。ブロックは柱状のブロック、つまり固定したターゲットで `axis` が `x`、`y`、`z` を取るブロックでなければなりません (MUST)。バージョンを固定しない lowering はどのブロックも柱状とみなし、固定したターゲットではそれ以外が `E_INCOMPATIBLE_MATERIAL` で、エラーと並んで `@beam.default` で梁を組みます。梁は体積の大きさを決めません。

`note_block` は、座標の 3 つ組 `at=x,y,z` が示すセルに音符ブロックを 1 つ置きます ([構文 §5.1.1](/ja/spec/syntax/#511-リテラルと区切り))。音符ブロックはどちらも向かないので、壁を基準にした位置は取りません。`note=` は 0 から 24 の整数、`instrument=` は楽器の名前で、どちらもブロックのステートに書きます。行が書かないステートは書き出さないので、ブロック自身の既定のまま、つまり `note` は 0、`instrument` はゲームが音符ブロックの下のブロックから決めるものになります。ゲームはそのブロックが変わるたびに楽器を決め直すので、書いた楽器が鳴るのはそれまでです。音符ブロックがどの楽器を取るかはターゲットが決めます。固定したバージョンで、音符ブロックが取らない `instrument=` (後のバージョンで加わったものなど) は、その値に対する `E_STATE_DOMAIN` で、音符ブロックは組みません。0 から 24 の外の `note=` と、3 つ組でないか struct の外にある `at=` は `E_INVALID_MEMBER` で、種類の違う値は `W_IGNORED_ARGUMENT` です。音符ブロックは動力のない状態で組むので、`powered` は書き出しません。ブロックはレジストリパックの `@note_block.default` で、行の `mat_slot=` は `W_IGNORED_ARGUMENT` です。Bedrock は音符ブロックの音をブロックエンティティに持ち、書き出しがそれを埋めます ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階))。楽器は下のブロックから決めるので、Bedrock のビルドは楽器を書き出さず、行が楽器を書いたときは `W_INTENT_DEGRADED` でそのことを知らせます ([バージョンとエディション §10.7](/ja/spec/versioning-editions/#107-java--bedrock-の可搬性))。

`sign` は、看板のブロックを 1 つ置きます。壁のそばに `at=<side>.outside` か `at=inside.<side>` と `offset=`、`y=` で置くときは、同じ `at=`、`offset=`、`y=` を書いたチェストが取るセルを取り、チェストの行が拒否される、または先送りされる場合には、看板の行も同じように扱われます。そこでは看板は壁の面に掛かった壁の看板で、`facing` は壁から離れる向きです。そのため `facing=` が選ぶものは残っておらず、行に書くと `E_INVALID_MEMBER` です。座標の 3 つ組 `at=x,y,z` で置くときは、Tier 0 の部品と同じセルを取ります ([レッドストーン §14.1](/ja/spec/redstone/#tier-0-の部品))。`facing=` がなければ下のブロックの上に立つ看板で、`rotation=0` と書き、表は `front` の壁のほうを向きます。`facing=` に `north`、`south`、`east`、`west` を書くと、後ろのブロックに掛かった壁の看板になり、表はその向きを向きます。`facing=` にそれ以外の識別子を書くと `E_INVALID_MEMBER` で、識別子でない値は `W_IGNORED_ARGUMENT` で、そのキーを書かなかったものとして読みます。行が書いた文字は、看板のブロックエンティティに持たせます ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階))。看板の `mat_slot=` は立てた看板を指し、`mat_slot=` のない看板はレジストリパックの `@sign.oak` で組みます。掛けた看板は、その看板の壁の看板で組みます。立てた看板の ID の終わりの `sign` か `standing_sign` を `wall_sign` にした ID のブロックです。`spruce_sign` は `spruce_wall_sign` として、Bedrock の `spruce_standing_sign` は `spruce_wall_sign` として掛かり、既定のものは `@sign.oak_wall` として掛かります。ブロックは、ターゲットに壁の看板がある立てた看板でなければなりません (MUST)。つまり ID が `_sign` で終わり、`wall_sign` でも `hanging_sign` でも終わらず、その壁の看板を固定したターゲットが宣言しているもの、バージョンを固定しないときはエディションのどれかのバージョンが宣言しうるものです。それ以外は `E_INCOMPATIBLE_MATERIAL` で、エラーと並んで既定のもので看板を組みます。

`bed` は、ベッドの 2 つのブロックを置きます。頭は `at=` が示すセルに、足は頭の後ろのセルに置き、それぞれに `part` (`head` か `foot`) と、頭が向く `facing` を持たせます。壁のそばでは、頭はチェストが取るセルを取り、ベッドは頭を壁に付けて横たわります。`facing` は壁のほうを向き、壁の内側からなら struct の外へ、外側からなら struct の中へ向きます。`facing=` に `left` か `right` を書くと、チェストと同じように壁に沿って向きを変えます。頭を壁から離す向き、つまり内側からの `in` と外側からの `out` は足を壁の中に置くことになるので、`E_INVALID_MEMBER` です。座標の 3 つ組で置くときは、頭は Tier 0 の部品と同じセルを取り、`facing=` は東西南北の方角 `north`、`south`、`east`、`west` です。どちらに横たわるかを決める壁がないので、`facing=` は書かなければなりません (MUST)。足は、頭が置かれうるところになければなりません (MUST)。壁の内側の頭なら壁の輪の内側、壁の外側の頭なら struct の足場の外でブロック配列の中、3 つ組の頭なら足場の上です。それ以外の場所の足、3 つ組で `facing=` がないこと、`facing=` のそれ以外の識別子は `E_INVALID_MEMBER` で、ベッドはどちらの半分も組みません。識別子でない `facing=` は `W_IGNORED_ARGUMENT` で、壁のそばのベッドはそのキーを書かなかったものとして読みます。ベッドは誰も寝ていない状態で組むので、`occupied` は書き出しません。ベッドの `mat_slot=` はそのブロックを指し、`mat_slot=` のないベッドはレジストリパックの `@bed.default` (赤いベッド) で組みます。ブロックはベッド、つまり ID が `bed` であるか `_bed` で終わるブロックでなければなりません (MUST)。それ以外は `E_INCOMPATIBLE_MATERIAL` で、エラーと並んで `@bed.default` でベッドを組みます。色はブロックのものですが、Bedrock はそれを半分それぞれのブロックエンティティに持ちます ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階))。

建築上の意図になりうるブロックステートは、どれも上書きできます。そして **書いた時点で、そのステートは意図 (intent) に昇格します**。「導出できるものは作者に書かせない」という厳しい考え方は採りません。ルールは「既定では導出し、意図になりうるブロックステートはすべて上書きできる」です。

次のものは、どれも意図になりうるので、上書きできなければなりません (MUST)。

| 分類 | ステート |
|---|---|
| 階段 | `facing` (椅子や飾りとしての階段)、`half=top` (逆さにした軒)、`shape` |
| 家具 | `chest size=single` (隣接による自動の結合は禁止)、`bed facing`、`door hinge` / `open` |
| 向き | `log` / `pillar axis` (水平の梁)、`trapdoor open` / `half`、`glazed_terracotta` の回転 |
| 個数 | `snow layers`、`candle count` |
| レッドストーン | `redstone_dust connect`、`repeater delay`、`comparator mode`、`observer` / `piston` / `dispenser` / `repeater` / `comparator facing`、`note` / `instrument` |

彩釉テラコッタの `facing`、雪の層の `layers`、ろうそくの `candles` には、メンバーを設けません。そうしたブロックの置かれた位置からは何も導出できないので、メンバーには導出するものがなく、ブロックのステートのリテラル以上に言えることもないからです。これらはブロックを指すマテリアルに `@white_glazed_terracotta[facing=east]`、`@snow[layers=3]`、`@candle[candles=3]` のように書き、`floor`、`walls`、`fill`、生のブロックが書いたとおりに置きます ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))。固定したターゲットでは、`E_STATE_DOMAIN` がそれぞれの組を検査します。

見落としやすいものが 2 つあります。これらは意図ではなく導出に属します。`torch` と `wall_torch`、`sign` と `wall_sign` は、取り付ける面に応じて自動的に入れ替わります。トーチや看板を置くメンバーは、どれもこの入れ替えをします。`redstone_torch` と `sign` は、位置の指定と `facing=` が示す形を取り、回路が敷くトーチはどれも後ろのブロックの側面に掛かります ([レッドストーン §14.5](/ja/spec/redstone/#145-配置配線-place-and-route))。

下の例は、どの行も上書きを書いています。

```
stair id=eave   kind=stairs mat_slot=roof side=front half=top facing=out shape=outer_left  # 軒
beam  id=lintel kind=pillar mat_slot=frame at=front.top axis=x                             # 水平の梁
chest id=store  at=inside.back offset=2 size=single
trapdoor id=hatch at=inside.left offset=1 y=2 half=top open=true
note_block at=2,1,2 instrument=bit note=12
bed   id=cot    at=inside.back offset=1 y=1 facing=left
```

### つながり

本体のすべてのメンバーを塗り終えると、その中のガラス板、鉄格子などの格子、フェンス、壁、フェンスゲート、レッドストーンダストは、隣のブロックからつながりのステートを得ます。ゲームがブロックを置いたときに設定するのと同じ規則です。チェストは下に挙げる Cairn 独自の規則で連結します。ゲームはチェストを置いた順に連結しますが、ビルドには置く順がないからです。ブロックの面は、ブロックのモデルがその面を隙間なく覆うとき **頑丈 (sturdy)** です。完全なブロックはすべての面が、下付きのハーフブロックは底面が、正立した階段は底面と背面が頑丈です。葉、シュルカーボックス、バリア、スイカ、カボチャ、くり抜かれたカボチャ、ジャック・オ・ランタンには、面でつながることはありません。

- ガラス板の `north`、`east`、`south`、`west` は、頑丈な面、ガラス板、壁の側で `true` になります。
- フェンスの同じステートは、頑丈な面、同じグループのフェンス、その側を横切る向きのフェンスゲートの側で `true` になります。木のフェンスのグループは木のフェンスで、ほかのフェンスはすべてもう一方のグループです。この分け方はゲームの `wooden_fences` タグに従います。
- 壁の各側は、頑丈な面、壁、ガラス板、その側を横切る向きのフェンスゲートとつながります。何ともつながらない側は `none` です。つながる側は、上のブロックがその側を覆えば `tall`、覆わなければ `low` です。
- ブロックが下の壁の部分、つまり柱か側を覆うのは、そのブロックのモデルのうち底面に接する箱が、上から見てその部分を覆うときです。部分の取り方はゲームの `WallBlock` の判定に従い、柱はセルの中央の 2×2 の正方形、側は中央からその縁までの同じ幅の帯です。完全なブロックや下付きのハーフブロックは柱とすべての側を覆い、ランタンや植木鉢は柱だけを覆います。上につながるブロックがあるときは、そのつながりのステートで読みます。ガラス板とフェンスは柱とつながる各側を、壁はつながる各側と、自分の柱が立っているかどれかの側がつながるときの柱を、閉じたフェンスゲートは柱と自分がまたぐ側を覆います。開いたフェンスゲートは何も覆いません。
- 壁の `up`、つまり柱は、柱の立った壁の下、どの側もつながらない場所、そして端や角や分岐のように、ある側がつながるのにその反対側がつながらない場所で立ちます。それ以外では、向かい合う 2 つの側がともに `tall` なら立たず、残りの場所では、ゲームの `wall_post_override` タグが挙げるブロック (松明や看板など) か、柱を覆うブロックの下でだけ立ちます。
- フェンスゲートの `in_wall` は、向いている方向を横切る隣に壁が立つとき `true` になります。
- チェストの `type` は、チェスト自身から見て左か右の隣にある、同じブロックで同じ `facing` のチェストと連結させます。そうしたチェストが並んだ列は、チェスト自身から見て左の端から 2 つずつ組になります。壁の内側から構造の内側を向く列なら `offset=0` に近い端からです。列の長さが奇数なら、もう一方の端のチェストは `single` のままです。自身の右に相方がいるチェストが `left`、その相方が `right` です。`size=single` のように `type` を書いたチェストは、どのチェストとも連結しません。
- レッドストーンダストの `north`、`east`、`south`、`west` は、ゲームがダストをつなぐ隣のブロックの側で `side` になります。ダスト、その側に沿って置かれたリピーター、背面をダストに向けたオブザーバー、そしてどの側にも信号を出すブロック (コンパレーター、レッドストーントーチ、レバー、ボタン、感圧板、日照センサー、レッドストーンブロックなど) です。隣のセルの 1 段上にあり、上面が頑丈なブロックの上に載ったダストに向かう側は、そのブロックのこのダストに向いた面も頑丈なら `up`、そうでなければ `side` です。隣のセルの 1 段下にあるダストに向かう側は `side` です。ゲームは上面が頑丈でないホッパーとトラップドアにもダストを登らせますが、この登りは導出しません。斜めのつながりは、何もないセルを通るときだけ成り立ちます。1 段上へは、このダストの上のセルを、1 段下へは隣のセルを通ります。そこにブロックが立っていると、ダストを通すか断つかを、ゲームはそのブロックが伝導するかどうかで決めますが、それを記録した表はないので、斜めは断たれたものとして導出します。導出のあと、ある軸のどちらの側ともつながらないダストは、もう一方の軸の両側とつながります。孤立したダストは十字になり、1 つの側だけとつながったダストはまっすぐ通り抜けます。`connect=none` は 4 つすべてを `none` (点) に、`connect=all` は 4 つすべてを `side` (十字) にし、隣に何があっても変えません。

ブロックのマテリアルや行が書いたステートはそのまま残し、ほかのステートだけを導出します。`@glass_pane[north=true]` は `north=true` を保ち、ほかの側は上の規則でつながります。生のブロックは、書いたかどうかによらずすべてのステートを保ちます。隣のブロックはほかのブロックと同じように生のブロックを読みますが、生のブロック自身のステートは 1 つも導出しません ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))。導出したステートは resolved state であり、意図にはなりません ([§6.2](#62-intent_state-と-resolved_state))。

隣のブロックとして見るのは同じ `struct` か `place` の本体のブロックだけで、その配列の外にあるものは数えません。各ブロックがこれらの規則にとって何であるかは、ターゲットのレジストリパックから得ます ([バージョンとエディション §10.3](/ja/spec/versioning-editions/#103-バックエンドはデータテーブル))。バージョンを固定しない lowering は、規則がブロックに尋ねること (つながるブロックの種類、頑丈な面、底面が覆うもの、ダストがつながる面など) をそれぞれ、そのブロックを宣言するすべてのバージョンが一致する内容として読み、一致しないものは何もないものとして読みます。種類が一致しないブロックは、規則にとって何でもありません。パックがなければ何も導出しません。Bedrock のターゲットは、ブロックを、そのステートマップが挙げる正規のブロックのうちそのブロックのステートを取るものとして読み、書き出すときは導出したステートをほかのステートと同じように写します。パックが答えられないブロックは、規則にとって何でもありません。どの正規のブロックにもならないもの (Bedrock の `border_block` など) や、なりうる正規のブロックどうしが食い違うものがそれです。Bedrock はチェストの連結をステートではなくブロックエンティティに持ち、書き出しは 2 つの半分をそこで連結します ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階))。ブロックの側面のステートをステートマップが一つも持たないバージョン (1.26.60 より前の Bedrock の板ガラス、フェンス、ダストなど) では、側面はゲームが隣のブロックから決めます。lowering が導出した側面はそこで何も失いませんが、素材や行が書いた側面 (`@glass_pane[north=true]` やダストの `connect=`) は保たれず、ビルドはこれも `W_INTENT_DEGRADED` で知らせます。ブロック配列はパレットのエントリごとに、そのエントリを持つすべてのセルで lowering が導出したステートを記録しており、書き出しはこれで両者を見分けます。struct の下に組み上げる回路のブロックはどの行も書かないので ([レッドストーン §14.5](/ja/spec/redstone/#145-配置配線-place-and-route))、回路だけが持つエントリのステートはすべて導出したものです。

面と、ブロックが覆う部分は、リリースのクライアントが描くブロックのモデルから読みますが、ゲームが読むのは当たり判定の形で、いくつかのブロックでは両者が食い違います。ハチミツブロック、サボテン、粉雪は、隙間なく描かれますが当たり判定は内側に収まります。チェストや頭のようにゲームがコードで描くブロックと、モデルのないバリアは、ここでは何も覆いません。キャンプファイアや 2 本のろうそくのように、当たり判定がモデルの描く部品を囲む 1 つの箱であるブロックは、ここではその部品が覆う部分だけを覆います。床に付けたボタンや 1 層の雪のように、底面に接しながら当たり判定のないブロックは、ここではモデルが覆う部分を覆います。

## 6.2 `intent_state` と `resolved_state`

```yaml
member:
  id: eave
  type: block | block_entity | entity      # IR では型を持つ。区別するのはコンパイラの仕事
  primitive: stairs
  intent_state:   { half: top, facing: out, shape: outer_left }  # 作者の意図
  resolved_state:                                                # 導出した値。塗りに由来するステートもここ
    - state: { id: minecraft:oak_stairs, properties: { facing: south, half: top, shape: outer_left } }
      runs: [{ from: [0, 4, 0], len: 1 }]
```

Minecraft 自身の用語である「blockstate」と紛れないよう、あえて別の名前にしています。導出や塗りに由来する resolved のステートを、作者が書いた intent のステートと混ぜないことで、編集が安定します。

メンバーの `intent_state` には、そのキーワードが名前を挙げるブロックステートのキーだけが入ります。`stair` なら `half`、`facing`、`shape`、`waterlogged`、`beam` なら `axis`、`door` なら `hinge`、`open`、`chest` なら `facing`、`type` を行の上で綴った `size`、`waterlogged`、`trapdoor` なら `facing`、`half`、`open`、`waterlogged`、`note_block` なら `note`、`instrument`、`observer`、`piston`、`dispenser`、`redstone_torch`、`sign`、`bed` なら `facing`、`repeater` なら `facing`、`delay`、`comparator` なら `facing`、`mode`、`redstone_dust` なら `connect` です。ほかのキーワードが挙げるキーはありません。行に書いたそれ以外の `key=value` は、メンバーの引数になります。例外は `id`、`class`、`mat_slot` で、これらはそれぞれ専用のフィールドになります。キーがどちらに入るかはキーワードで決まります。`stair` の `shape=` は意図ですが、`window` の `shape=` は開口の輪郭を表す引数です ([エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約))。

lowering は、組み上げる block-array の隣に、各メンバーの `resolved_state` を記録します。本体を塗り終えたときにメンバーのセルが持つすべてのステートと、それを持つセルの組です。セルは `x` 方向の連なりにまとめ、それぞれの最初のセルと長さで、block-array の順に並べます。セルは最後に塗ったメンバーのものになるので、ドアのブロックははめ込まれた壁ではなくドアに記録され、セルが 1 つも残らないメンバーは何も記録しません。`cairn lower --format json` は、この記録を `members` の下に、`structures` と同じキーで出力します。これで 2 つのビルドをメンバーごとに比べられます。本体はメンバーを、それぞれが持つ最初のセルの順に並べます。そのため、セルを共有しない行を並べ替えても、格子と同じく記録も変わりません ([コンパイルモデル §4.8](/ja/spec/compilation/#48-同一フェーズ内の衝突とパレット))。記録は本体を lowering するたびに作ります。ブロック ID は、テーマのエディション別の変種や固定したバージョンの上書きも含めて、その lowering のターゲットが解決したものです。プロパティの名前は正規の語彙のものです。

メンバーは `type` の代わりに、キーワードから分類した `role` を持ちます。

`bed` は IR の型を整理しておくために、エンティティではなくブロックのメンバーとして扱い、`sign` も同じです。どちらのブロックについても、ブロックエンティティに持つものはブロック配列の格子と並べて持ちます ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階))。

## 6.3 `waterlogged`

**変更の余地あり。** 流水はまだ組み上げられません。`water` は `E_UNKNOWN_KEYWORD` で、`fill` が注ぐのは水源だけです ([互換性ティア](/ja/spec/compatibility/#変更の余地あり))。下の例では、`water` は `E_UNKNOWN_KEYWORD` になります。

既定では、塗りから決まります。`fill fluid=water` が水浸しにできるブロックと重なると、コンパイラが `waterlogged` を立てます。

`fill` は、向かい合う 2 つの角 `from=` と `to=` で箱を指します。2 つの角はどちらが先でもよく、どちらも箱に含まれます。それぞれの角は座標の組で、struct の 1 つのセルを指します ([構文 §5.1.1](/ja/spec/syntax/#511-リテラルと区切り))。`mat_slot=` を書いた `fill` は、`massing` で箱のすべてのセルをそのマテリアルで塗ります。既定のブロックはないので、マテリアルが解決しない `fill` はセルをそのままにします。`fluid=water` を書いた `fill` は、水を含められるブロックを置き終えたあと、`fluids` で水を注ぎます ([コンパイルモデル §4.1](/ja/spec/compilation/#41-フェーズ評価))。箱のセルのうち、ブロックのないセルには水源 `minecraft:water[level=0]` を置きます。水浸しにできるブロックで、ステートに `waterlogged` を書いていないものは `waterlogged=true` になり、もとのメンバーのものであり続けます ([§6.2](#62-intent_state-と-resolved_state))。それ以外のブロックは塗られたままなので、水は箱の中に立つものの周りだけを満たします。

ブロックが水浸しにできるのは、ターゲットのレジストリパックが、そのブロックに `true` を取る `waterlogged` のステートを与えていて、ステートに水の入る余地があるときです。`type=double` と書いたハーフブロックはセルを埋め、ゲームも水を入れないので、水浸しにできません。Java に対応するブロックのない Bedrock のブロックのように、パックがステートを持たないブロックも水浸しにできず、水はそのブロックを塗られたままにします。バージョンを固定しない lowering は、[つながり](#つながり) と同じく、ブロックを宣言するエディションのすべてのバージョンが一致する内容としてブロックを読み、パックがなければどのブロックも水浸しにできません。導出した `waterlogged` は resolved state であり、意図にはなりません。Bedrock のバックエンドは、水浸しのブロックの水を構造の第 2 レイヤーに持たせます ([バージョンとエディション §10.7](/ja/spec/versioning-editions/#107-java--bedrock-の可搬性))。

流体は `water`、種類は `kind=source` だけで、`kind=` を書かない `fill` も水源を注ぎます。`mat_slot=` と `fluid=` を両方書いた `fill`、ほかの流体や種類、ない、または座標の組でない `from=` や `to=`、struct の外にある角は `E_INVALID_MEMBER` です。`fluid=` のない `fill` に書いた `kind=` は `W_IGNORED_ARGUMENT` で、`mat_slot=` も `fluid=` もない `fill` は `E_MISSING_MATERIAL` です ([リント](/ja/spec/lint/))。`fill` は体積を決めません ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出))。書かれたとおりの struct が届き、組み上げた struct が届かない段に及ぶ `fill` は `W_DEFERRED_MEMBER` になり、その段を組み上げるはずのメンバーを待ちます。

`waterlogged=auto|true|false` の 3 値で指定することもできます。水槽の中に空気の空間を残す (明示的な `false`)、水源と流水を区別する、水浸しにできるブロックの一覧がバージョンによって違うことに対応する、といった用途のためです。`stair`、`chest`、`trapdoor` では、`waterlogged=true` と `waterlogged=false` をブロックのステートに書いてそのまま残し、`waterlogged=auto` は、`waterlogged=` を書かないときと同じく、水の `fill` に設定させます。それ以外の語は `E_INVALID_MEMBER` です。流水は `flow=` と `level=` で明示します。

[§6.1](#61-既定では導出し上書きで昇格する) の上書きと同じく、`waterlogged=` は、ブロックを 1 つ置き、そのブロックのステートを行に書くメンバーに書きます。コンパイラが知っているキーワードのうち、水を含められるブロックについてそうするメンバーは `stair`、`chest`、`trapdoor` だけです。`door` と `pressure_plate` のブロックは水を含めず、`roof` と `window` は置くブロックのステートをすべて導出し、上書きを取らないので、この 4 つのどれに書いた `waterlogged=` も `E_UNKNOWN_ARGUMENT` になります。

```
fill fluid=water kind=source from=1,1,1 to=5,3,5    # 重なったフェンス・階段・看板は自動で waterlogged になる
trapdoor id=shutter at=inside.front offset=2 y=2 waterlogged=false  # 水槽の中の空気の窓
water id=stream from=.. flow=east level=4
```
