## 12.1 順方向の変換

block-array IR をシリアライズすると、`.nbt` / `.litematic` / `.schem` / `.mcstructure` が出力されます ([アーキテクチャ](/ja/spec/architecture/))。各形式はシリアライザで、既存の形式は、ピボットの周りに追加するバックエンドという位置付けです。現在は 4 つすべてのシリアライザがあります。

`cairn compile --edition bedrock` は `.mcstructure` を書き出します。`--edition java` は `.nbt` を書き出すか、`--structure-format` が指定した形式で書き出します。

| `--structure-format` | 書き出すもの | `site` の書き出し方 |
|---|---|---|
| `nbt` (既定) | struct、配置、通路ごとに 1 つのバニラ構造ファイル | 配置ごと、通路ごとに 1 ファイル ([§9.3.4](/ja/spec/components-editing-sites/#934-出力ファイル名)) |
| `litematic` | struct ごと、site ごとに 1 つの Litematica schematic ([§12.1.1](#1211-litematica)) | 1 ファイルにまとめ、配置ごと、通路ごとに 1 つのリージョン |
| `schem` | struct、配置、通路ごとに 1 つの Sponge Schematic ([§12.1.2](#1212-sponge-schematic)) | 配置ごと、通路ごとに 1 ファイル。それぞれ site の中の原点だけずらす |

形式で変わるのはファイルだけです。block array は同じで、成果物は同じ規則で名付け、同じ衝突で拒否し、ロックファイルはどの形式で書き出してもバイト単位で同じです。Bedrock の構造形式は 1 つだけなので、`--edition bedrock` と一緒に `--structure-format` を指定すると使い方の誤り (終了コード 2) になり、ソースを読む前に拒否します。

### 12.1.1 Litematica

`.litematic` は、Litematica が保存して読み込む、gzip で包んだ Java の NBT です。struct はそれだけで 1 ファイルになり、struct の名前を付けて (`cottage.litematic`)、原点に 1 つのリージョンを置きます。site は site の名前を付けた 1 ファイル (`hamlet.litematic`) になり、配置ごと、通路ごとに 1 つのリージョンを、ソルバーが決めた原点に置きます。この原点はロックファイルに記録するものです。リージョンには、その配列を `.nbt` に書き出すときのファイル名を付けます (`home1`、`hamlet_walkway_home1_entry__home2_entry`)。リージョンはそれぞれ、読み戻すと 1 つの struct になり、その名前と角を来歴として残します ([§12.4](#124-取り込み時の記録と落とし穴))。同じ名前の site と struct は 1 つのファイルに書き出すことになるので、`.nbt` のファイル名が重なる 2 つを拒否するのと同じく、何も書き出す前に拒否します。

ルートには次のものを入れます。

- `MinecraftDataVersion` はターゲットの DataVersion、`Version` はそのリリース向けの Litematica が読める schematic のバージョンで、1.20.5 の DataVersion (3837) より前なら 6、それ以降なら 7 です。`SubVersion` は 1 です。
- `Metadata`: ファイルの名前にあたる `Name`、ソースには作者を書かないので `Cairn` とする `Author`、空の `Description`、`RegionCount`、リージョンのボクセル数を合計した `TotalVolume`、そのうち air、cave air、void air 以外の数を数えた `TotalBlocks`、すべてのリージョンを囲む箱の大きさの `EnclosingSize` です。作成時刻、更新時刻、プレビュー画像は入れません。そのため、同じソースからは常に同じバイト列が書き出されます。
- `Regions`: 各リージョンには、最小の角にあたる `Position` と、どの軸も正の `Size` を入れます。`BlockStatePalette` には、リージョンのブロック状態を air を先頭にして並べ、どの DataVersion でも `Name` と `Properties` のキーで書きます。構造ファイルが `id` と `properties` に切り替わる版でも、Litematica はこのキーのままだからです。`BlockStates` には、各ボクセルのパレット番号を `(y, z, x)` の順に、最大の番号に必要なビット数 (2 ビット以上) で、各 long の下位から詰めます。1 つの long の残りに収まらない番号は、次の long にまたがります。`TileEntities` には、各ブロックエンティティを `.nbt` の書き出しが `nbt` に書くのと同じ形で入れ、リージョンの角からの `x`、`y`、`z` を加えます。`Entities`、`PendingBlockTicks`、`PendingFluidTicks` は空です。

### 12.1.2 Sponge Schematic

`.schem` は、WorldEdit が保存して読み込む、Sponge Schematic Specification の gzip で包んだ Java の NBT です。Cairn はバージョン 3 で書き出します。struct、配置、通路はそれぞれ 1 ファイルになり、`.nbt` と同じ名前を付けます (`cottage.schem`、`home1.schem`)。そのため site は、`.nbt` で書き出すときと同じファイルの組になります。各ファイルの `Offset` には、その配列が site の中で置かれる位置、つまりロックファイルが記録する原点を入れ、struct では `[0, 0, 0]` とします。site のファイルをすべて同じ地点に貼り付けると、site が組み上がります。

バージョン 2 ではなくバージョン 3 で書き出す理由は次のとおりです。

- WorldEdit は 7.3.0 からバージョン 3 を読み書きでき、7.3.0 以降の WorldEdit は、Cairn が出荷する Java のターゲット (1.20.4 から) のどれでも動きます。
- バージョン 3 のブロックエンティティは、フィールドを `Id` と `Pos` と並ぶ `Data` コンパウンドに入れます。block array がブロックエンティティの id とフィールドを分けて持つのと同じ形です。バージョン 2 はフィールドを `Id` と `Pos` と同じ階層に並べるので、どちらかと同じ名前のフィールドがあると衝突します。
- バージョン 3 は、Minecraft 自身のデータファイルと同じく、schematic を名前のないルートの中に入れます。

`.schem` の読み込みはどちらのバージョンも受け付けるので、バージョン 2 しか書き出さないツールのファイルも読めます。

ルートには `Schematic` コンパウンドを 1 つ入れ、その中に次のものを入れます。

- `Version` は 3、`DataVersion` はターゲットのものです。
- `Metadata`: ファイルの名前にあたる `Name` と、`Cairn` とする `Author` です。保存した日時は入れません。そのため、同じソースからは常に同じバイト列が書き出されます。
- `Width`、`Height`、`Length` は、配列の x、y、z 方向の大きさです。どれも符号なし short で保存するので、いずれかの軸で 65535 を超える配列は拒否します。
- `Offset` は前述のとおりです。
- `Blocks`: `Palette` は、各ブロック状態をプロパティを名前順に並べた `namespace:id[name=value,...]` の綴りで書き、block array のパレット (air が先頭) での番号に対応付けます。プロパティの値にカンマを含むものなど、綴りを読み戻すと別の状態になってしまうものは拒否します。`Data` には、各ボクセルの番号を `(y, z, x)` の順に varint で入れます。`BlockEntities` には、各ブロックエンティティを `Pos`、`Id`、そして `.nbt` の書き出しが `nbt` に書くフィールドを入れた `Data` として入れます。

バイオームとエンティティは書き出しません。

## 12.2 逆方向の変換: コンパイラは写し取り、LLM がリフトする

コンパイラは、ボクセルを見て「これは壁だ」と判定するようなコンピュータビジョンは作りません。保守できなくなるからです。コンパイラが実装するのは、堅牢で忠実な写し取り、検証、ボクセル単位の差分です。意味を付けて引き上げる作業 (リフト) は、raw を中心にした DSL を LLM がリファクタリングする形で行います。言語を自分で使って確かめることにもなり、P5 の自己修正ループとも一致します。

```text
cairn import house.litematic --mode raw    → house.raw.crn     # fill/raw_block 中心
(LLM が house.raw.crn を意味 DSL にリファクタ) → house.lifted.crn
cairn compile house.lifted.crn --edition java --target 1.21.4
cairn diff-blocks house.litematic house.lifted.crn             # voxel XOR → 自己修正へ
```

最初の段階はできています。`cairn import FILE --mode raw` は `.nbt`、`.litematic`、`.schem`、`.mcstructure` のファイルを読み、その隣に `<stem>.raw.crn` を書き出します。`--out` を指定したときはそのパスに書き出します。どちらも、すでにあるファイルは置き換えます。形式は拡張子が決め (大文字と小文字は区別しません)、エディションは形式が決めます。`.mcstructure` は Bedrock の形式で、ほかの 3 つは Java の形式です。どれにもあたらない拡張子は使い方の誤り (終了コード 2) で、ファイルがない場合や、`--out` が取り込むファイルそのものを指す場合も同じです。モードは `raw` だけです。L1 がコンパイラにできる上限で ([§12.3](#123-写し取りの-3-段階))、リフトはそれが書き出したものをリファクタリングする作業だからです。

ソースは書き出す前に検証します。記録するターゲット ([§12.4](#124-取り込み時の記録と落とし穴)) でコンパイルし、ファイルとセルごとに比べるので、そのターゲットでの `cairn compile` はファイルにあるブロックを組みます。`cairn import` が最後に出す note は、それを組む `--edition` と `--target` を示します。2 つのブロックは、ターゲットが組むとおりに比べます。どの値でもターゲットが同じに組むステートは比べず、Bedrock では、ブロックはステートマップがそれとして読む正規のブロックとして比べます。記録するターゲットが宣言していないブロックを持つファイルは、コンパイルが出すエラーで拒否します。エラーにはそれぞれ書き出すはずだった行を添え、そのリリースでファイルを保存し直すと、古いリリースが別の綴りで書いたブロックの名前が変わる、という注記を付けます。ファイルのとおりに組む生のメンバーがないセルがあれば、誤ったものを書き出さずに取り込みを拒否します。どちらの拒否も、形式の読み込みが受け付けないバイト列も、終了コード 1 で、何も書き出しません。

最後の段階でループが閉じます。`cairn diff-blocks` は、構造ファイルに記録されるターゲットでリフトを組み、両者をセルごとに比べ ([§12.2.1](#1221-リフトの差分))、食い違うセルの領域をそれぞれ考えられる原因とともに示し ([§12.2.2](#1222-領域とその原因))、組んだものをファイルに近づける `edit` の行を提案します ([§12.2.3](#1223-修正案))。取り込みと差分のあいだのリファクタリングは LLM の仕事で、ループはリフトが収束するまで続きます。

```text
house.litematic against house.lifted.crn at java 1.21.4, the shipped target the file was saved at
block IoU       0.962  converges at >= 0.985
state_accuracy  1.000  converges at >= 0.995
residual raw    0%     converges at <= 5%
1 region differs:
  missing house (12,4,3)..(18,6,3): 12 cells of minecraft:glass_pane → likely `window[id=front_windows]` `repeat=3` too small
suggested patch, reaching block IoU 1.000, state_accuracy 1.000, residual raw 0%:
  edit window[id=front_windows] set repeat=4
error[E_DECOMPILE_DIFF]: block IoU = 0.962 < threshold 0.985
```

リフトは、block IoU ≥ 0.985、`state_accuracy` ≥ 0.995、残った raw ≤ 5% で収束します。完全な一致は求めません。残差は `raw_fill id=residual_* origin=imported` として明示的に残します。

### 12.2.1 リフトの差分

`cairn diff-blocks STRUCTURE FILE [--format text|json]` は、STRUCTURE を `cairn import` と同じように読みます。拡張子が形式とエディションを決め、[§12.4](#124-取り込み時の記録と落とし穴) の規則でターゲットを記録します。次に、そのターゲットで `cairn compile` が行うすべての段階を通して FILE を組み、組んだブロックを STRUCTURE にあるブロックと比べます。記録されたターゲットで組むので、比較は 1 つのエディションと 1 つのバージョンの中で行われます。

どちらの側も、いくつかの本体からなります。STRUCTURE の本体は取り込みが書き出すもので、Litematica ならリージョンごとに 1 つ、ほかの形式ならファイルに 1 つです。ストラクチャーヴォイドは空気として読みます。FILE の本体は、その `struct` と `site` です。`site` は 1 つの本体として並べます。配置と通路を `site` の中の位置に置き、後の配列のブロックは前の配列のブロックを上書きし、後の配列の空気は何も上書きしません。最も低い角が `(0, 0, 0)` になるよう動かします。両側に本体が 1 つずつしかなければ、名前にかかわらずその 2 つを比べます。それ以外では、本体は反対側の同じ名前の本体と組になり、同じ名前のものがない本体は何もないものと比べます。組になった 2 つの本体は、それぞれの `(0, 0, 0)` のセルからそろえ、両方を含む箱の範囲でセルごとに比べます。

セルは、本体の外にあるか、`minecraft:air`、`minecraft:cave_air`、`minecraft:void_air` のどれかであるとき以外は、ブロックを持ちます。2 つのブロックは ID が同じとき一致し、記録されたターゲットが組むとおりにすべてのプロパティが一致するとき、ステートが一致します。

- 両側が書くプロパティは、値が同じなら一致します。
- 片側が省いたプロパティは、ターゲットがそれに組む既定値として読みます。Bedrock ではステートマップが示す既定値、`waterlogged` はどちらのエディションでも `false` です。水のないところでは lowering がこれを省くからです。
- STRUCTURE が書き、組んだ側が省いたプロパティは、そのような既定値がなければ比べません。ゲームが保存したファイルはブロックのすべてのプロパティを書き、ソースは設定したものだけを書くからです。
- 組んだ側が書き、STRUCTURE が省いたプロパティは、そのような既定値がなければ食い違いです。
- ターゲットがどの値でも同じに組むプロパティは比べません。

差分は、すべての組について、STRUCTURE がブロックを持つセル、FILE がブロックを組むセル、両側がブロックを持つセル、両側が同じ ID を持つセル (*一致した*セル)、一致したセルのうちステートも一致するセルを数えます。組んだセルは、本体を組み終えたときにそのセルを持つメンバーが `raw_block` か `raw_fill` (`raw_repeat` の複製を含む) であれば、行に `origin=imported` の印があるかどうかにかかわらず *残差*です。これらの数から次を求めます。

- **block_iou.** block IoU です。一致したセルの数を、どちらかの側がブロックを持つセルの数で割ります。2 つが異なる ID を持つセルは、和集合には入り、積集合には入りません。どちらの側もブロックを持たないときは 1 です。
- **state_accuracy.** ステートも一致するセルの数を、一致したセルの数で割ります。異なる ID を持つセルは block IoU を下げ、こちらには数えません。一致したセルがないときは 1 です。
- **residual_ratio.** 残った raw です。残差のセルの数を、FILE がブロックを組むセルの数で割ります。FILE が何も組まないときは 0 です。

3 つすべてが閾値を満たすとき、リフトは**収束**します。閾値とは丸める前の値で比べます。満たさないとき、差分は `E_DECOMPILE_DIFF` を報告します ([lint §11.1](/ja/spec/lint/#取り込み))。

指標は任意の 2 組の本体について定義され、ライブラリは、評価のハーネスなど、どの呼び出し側にも同じものを計算します ([評価フレームワーク §13.2](/ja/spec/evaluation/#132-逆変換の補助指標))。2 つのエディションや 2 つのバージョンのあいだでは、綴りを置き換えません。ID はそれぞれの側が書くとおりに比べるので、一方のバージョンで名前が変わったブロックや、もう一方のエディションでは別の綴りのブロックは、置き換わったものになります。片側が省いたプロパティは、STRUCTURE のターゲットの既定値として読みます。`cairn diff-blocks` は FILE を STRUCTURE に記録されたターゲットで組むので、この場合にはあたりません。

### 12.2.2 領域とその原因

食い違うセルは、STRUCTURE がブロックを持ち組んだ側が持たなければ *missing*、組んだ側が持ち STRUCTURE が持たなければ *extra*、2 つが異なる ID を持てば *replaced*、同じ ID でステートが一致しなければ *state* です。1 つの組の中で、種類と ID (STRUCTURE のものと組んだ側のもの) が同じセルは、どの軸でもほかのセルから 2 セル以内にあれば 1 つの領域になります。つまり、あいだにほかのものが 1 セルあっても領域は分かれません。

領域は、その種類、本体 (組んだ側の名前、なければ STRUCTURE の名前)、最も低い角から最も高い角までの箱、その中で食い違うセルの数、ブロック (STRUCTURE のもの。extra の領域では組んだ側のもの) を示します。replaced の領域では組んだ側のブロックも、state の領域では食い違うプロパティを両方の値とともに示します。領域は、セルの多い順に並べ、次に組、上の順の種類、最も低い角 (`y`、`z`、`x` の順)、ブロックの順に並べます。

原因は、組み終えたときに領域のセルを持つメンバーから読みます。最も多くのセルを持つメンバー、同じ数なら先に書かれたメンバーです。

- **built_by.** extra、replaced、state の領域は、それを組んだメンバーを示します。
- **cleared_by.** セルをメンバーが持つ missing の領域は、そのメンバーを示します。そのメンバーがセルを空気にしたからです。
- **short_of.** セルをどのメンバーも持たない missing の領域は、そのブロックを組むメンバーのうち、2 セル以内で最も近いものを示します。1 段足りない壁や、1 列狭い fill です。
- **walkway.** `site` の通路が領域のブロックを置きました。
- **no_member.** そこにそのブロックを組むメンバーがなく、missing の領域では 2 セル以内にもありません。
- **unpaired.** 領域の本体には、組になる本体が反対側にありません。

メンバーは、キーワード、行が書いていれば `id=`、書かれた本体の中でのアドレス ([コンポーネント、編集、複数の建物 §9.2](/ja/spec/components-editing-sites/#92-編集モデル))、行で示します。`def` のメンバーは、`site` がどこに配置しても、その `def` の中で示します。

### 12.2.3 修正案

修正案は、FILE の末尾に加えると組んだものを STRUCTURE に近づける、最大 3 行の `edit` です ([§9.2](/ja/spec/components-editing-sites/#92-編集モデル))。どの行も推測だけでなく、その行を加えて組むことで見つけます。

1. 領域は並んだ順に扱います。原因が FILE のメンバーを示し、そのメンバーをそれより前の領域が示していなければ、その領域を試します。それ以外の領域は飛ばします。
2. メンバーの候補は次の順に試します。raw のメンバーの replaced か state の領域では、`mat=` を、領域のセルの多くが STRUCTURE で持つブロックにします。state の領域では、キーワードが受け取るステートの引数をそれぞれ STRUCTURE の値にします。replaced の領域では、`mat_slot=` を、領域のブロックを組むメンバーが読むほかのスロットのそれぞれにします。行が書く整数のそれぞれを 1 増やし、1 減らし、2 増やし、2 減らします (0 未満にはしません)。キーワードが `repeat=` を受け取り、行がそれを省いていれば `repeat=2` と `repeat=3` を試します。`from=` と `to=` は、隣の missing の領域まで広げるか、箱を 2 つの軸にわたって覆い残りの軸の一端にある extra の領域を除いて縮めます。
3. 候補はそれぞれ、すでに残した行の後に、1 行として FILE に加えます。その文字列を、記録されたターゲットで `cairn compile` が行うすべての段階を通して組みます。構文解析できない候補、エラーを出す候補、スコープを落とす候補は捨て、それ以外の候補の組んだものを STRUCTURE と比べます。
4. 食い違うセルが最も少なくなる候補を、それまでに残した行より少ないときに残します。同じ数なら先の候補です。数えるセルは、片側だけがブロックを持つセル、2 つが異なる ID を持つセル、一致したセルのうちステートが一致しないセルです。
5. 3 行を残すか、48 の候補を組むか、食い違うセルがなくなったところで探すのをやめます。

残した行は、見つけたときの領域とともに示し、その領域の原因は行が加える変更として読みます。整数 1 つなら `` `walls[0]` `height=3` too small ``、行が省いたキーなら `` `walls[0]` without `repeat=2` ``、それ以外なら `` `raw_fill[0]` `mat=minecraft:granite` where `mat=minecraft:stone` builds it `` です。修正案は行を順に並べ、すべてを加えたときに FILE が達する指標を添えます。役に立つ候補がなければ、修正案はありません。

### 12.2.4 レポート

まず FILE を組み、その診断を `cairn compile` と同じように stderr に出します。エラー、ビルドが塗るブロックを宣言するどのターゲットも満たさない `@requires` の下限 (`E_REQUIRES_CONFLICT`)、組むときに落ちたスコープ ([lint §11.1](/ja/spec/lint/#lowering))、記録されたターゲットが満たさない下限 ([バージョンとエディション](/ja/spec/versioning-editions/)) は、この順に比較を拒否します。このコマンドは `--target` を受け取らないので、最後の拒否は、記録されたターゲットを示す note で終わります。

テキストのレポートは stdout に次を出します。

- `STRUCTURE against FILE at EDITION VERSION, REASON`。REASON は、バージョンを選んだ [§12.4](#124-取り込み時の記録と落とし穴) の記録の規則です。
- 指標とその閾値。block IoU と `state_accuracy` は小数第 3 位まで切り捨て、残った raw は百分率で小数第 1 位まで切り上げます。指標が満たさない閾値を、出力した値が満たして見えることはありません。
- 2 つ以上の組を比べたときは、組ごとの指標を 1 行ずつ。
- `no cell differs`、または食い違う領域の数と、最初の 10 個 (1 行に 1 つ)、残りの数。
- 修正案と、それで達する指標。

リフトが収束しないとき、stderr には、閾値を満たさない指標を並べた `error[E_DECOMPILE_DIFF]:`、閾値を示す note、次にすることを示す note を出します。次にすることは、修正案を加える、領域が示すものを編集する、またはすべてのセルが一致して残った raw だけが足りないときは、raw のメンバーが組むものに名前を付ける、のどれかです。

`--format json` は stdout に 1 つの文書を書きます ([lint §11.2](/ja/spec/lint/#112-機械可読ペイロード))。

| キー | 値 |
|---|---|
| `structure` | STRUCTURE のファイル名。 |
| `target` | `edition` と `version`。FILE を組んだ記録のターゲット。 |
| `saved` | STRUCTURE が保存されたバージョン。取り込みのヘッダーと同じ書き方。 |
| `converged` | リフトが収束するかどうか。 |
| `code` | `"E_DECOMPILE_DIFF"`。収束しないときだけある。 |
| `block_iou`、`state_accuracy`、`residual_ratio` | 丸める前の指標。 |
| `thresholds` | 3 つの閾値。キーは同じ。 |
| `counts` | `structure_blocks`、`built_blocks`、`both_blocks`、`matched`、`states_matched`、`residual`。指標の元になるセルの数。 |
| `bodies` | 組ごとに、`structure` と `source` (それぞれの側の本体の名前。本体がない側にはない)、その指標、その `counts`。 |
| `regions` | すべての領域。`kind`、`body`、`[x, y, z]` の形の `from` と `to`、`cells`、`mat`。replaced の領域では `built`。state の領域では `states` で、`key` ごとに `structure` と `built` の値 (書かない側は `null`)。`cause` はその `kind` と、メンバーを示す 3 つでは `member` (`keyword`、書かれていれば `id`、`address`、`line`)。その領域で見つけて残した行があれば `patch`。 |
| `patch` | 行を残したときだけある。順に並べた `edits`、達する指標、その `counts`。 |

FILE が記録されたターゲットで組めないとき、文書は `cairn lower` が書くのと同じ、診断を並べた `{"diagnostics": [ ... ]}` です。矛盾する下限、落ちたスコープ、記録されたターゲットが満たさない下限のような実行全体の拒否では `{"diagnostics": []}` を書き、残りは stderr で伝えます。

終了コードは、リフトが収束すれば 0 です。収束しないとき、FILE が構文解析できない、エラーを出す、スコープを落とす、記録されたターゲットより後のターゲットを必要とするとき、または STRUCTURE がその形式として読めない、出荷するどのターゲットより後に保存されたときは 1 です。どちらかのファイルが見つからないとき、STRUCTURE の拡張子がこのコマンドの読む形式を示さないときは 2 です。

### 12.2.5 エディタでのレポート

言語サーバーは、エディタで開いている文書に対して、同じ答えを `workspace/executeCommand` のコマンド `cairn.diffBlocks` として返します。引数は 1 つのオブジェクトで、開いている文書の `uri` と、構造ファイルの `file:` URI である `structure` を持ちます。結果は、`cairn diff-blocks --format json` がその 2 つに対して出力する文書です ([§12.2.4](#1224-レポート))。つまり、レポートか、記録されたターゲットでソースが組めないときの `{"diagnostics": [ ... ]}` の文書で、実行全体の拒否では空です。次の 2 つの入力は、コマンドラインではなくエディタから受け取ります。

- ソースはエディタが保持するテキストで、保存したかどうかは問いません。編集しているそのままのリフトを比べるので、`uri` はファイルを示していなくてもかまいません。
- 構造ファイルは、`cairn diff-blocks` が STRUCTURE を読むのと同じく、ディスクから読みます。

`cairn diff-blocks` が stderr に書くもの、つまり報告して先へ進む診断、実行を拒否した理由、文書が `code` として持つ `E_DECOMPILE_DIFF` は送りません。コマンドが読めない引数、エディタで開いていない文書、ローカルのファイルを示さない `structure`、構造ファイルとして読めないファイルには、どれであるかを示す `InvalidParams` エラーで答えます。

## 12.3 写し取りの 3 段階

写し取りとリフトの境界は、名前を付けるかどうかです。

| 段階 | 内容 | 上限 |
|---|---|---|
| **L0: raw セル** | 1 行に 1 ボクセル。LLM の文脈には大きすぎるので、中間表現としてだけ使う。 | — |
| **L1: 空間的な圧縮** | fill への集約、AABB によるパレット圧縮、`resolved_state` をそれを組み直せる最少のステートへ戻す逆変換 (`minecraft:oak_stairs[facing=east,half=top]`。ガラス板の側面はつながりの規則に任せる)、周期性の `raw_repeat` への畳み込み。**名前は付けない。** | コンパイラにできる上限。 |
| **L2: 意味のリフト** | fill → `wall`、repeat → `def` / `use`、具体的なブロック → `mat_slot` + `theme`。 | LLM にできる上限。 |

```
# L1: 名前を付けない。決定的
raw_repeat count=5 step=3,0,0
  raw_fill mat=minecraft:glass_pane from=0,2,0 to=1,3,0 origin=imported
# L2: LLM が名前を付け、意味を与える
window id=front_windows side=front mat_slot=glass repeat=5 ...
```

### 12.3.1 取り込みが書き出すもの

`cairn import --mode raw` は L1 を書き出し、1 つのファイルは常に 1 つのソースになります。

- **本体。** ファイルが持つ構造はそれぞれ 1 つの本体になります。`.nbt`、`.schem`、`.mcstructure` ではその 1 つの構造が、`.litematic` では各リージョンが、ファイルの順に本体になります。本体には、ファイルの stem またはリージョンの名前を識別子にしたものを付けます。小文字にし、ASCII の英字と数字以外の文字が続くところをそれぞれ 1 つの `_` にし、両端には `_` を残しません。空になった名前は `structure` とし、数字で始まる名前には接頭辞 `structure_` を、トップレベルのキーワードや Windows が予約している名前には接尾辞 `_structure` を付け、前の本体がすでに使った名前には `_2`、`_3` と付けます。
- **ヘッダ。** ソースは 3 行のコメントで始まります。ファイルと、それが保存されたバージョン、記録するターゲットとその理由 ([§12.4](#124-取り込み時の記録と落とし穴))、そして続くものが意図ではなくブロックとその規則性であることです。その後に `@cairn`、`@requires <edition> version>=<target>`、`@intended_targets ["<target>"]` が続くので、ソースは記録したターゲットで組め、それより前では拒否されます。本体の上のコメントには、ファイルが示す本体の位置を残します。リージョンの名前と schematic の中での最小の角、`.schem` の `Offset`、`.mcstructure` の `structure_world_origin` で、後の 2 つは `0,0,0` でないときだけ書きます。
- **箱。** 本体のブロックは、それぞれ 1 種類のブロックからなる箱に切り分けます。1 セルの箱は `raw_block`、それ以外は `raw_fill` です。セルは `x` を最も速く、次に `z`、次に `y` の順にたどり、まだどの箱にも入っていないセルごとに、箱を `x`、`z`、`y` の順に、取り込むセルがすべてそのブロックである限り伸ばします。air は書き出しません。ただし最上段に届く箱がないときは、struct がファイルと同じ高さになるよう、最上段の最初のセルに `raw_block mat=minecraft:air` を 1 つ書きます。
- **繰り返し。** ブロックと大きさが同じで、角が一定の間隔で並ぶ箱は `raw_repeat` に畳み込み、箱を 1 度だけ書きます ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))。まだ畳み込んでいない箱を切り分けの順に、同じ種類の続く 32 個の箱のどれかを 2 つ目とする並びの 1 つ目として試し、最も長い並びを畳み込みます。間隔は負にならないので、並びは最も低い位置のコピーから見つかります。回数と間隔が同じ並びの箱は、まとめて 1 つの `raw_repeat` の下に書きます。
- **ステート。** ブロックは、それを組み直せるステートだけを書き、ほかのステートは書きません。Java では、ファイルが保存しているステートをすべて書きますが、つながりの規則が隣のブロックから導き直すつながりのステートは除きます ([ブロックステート §6.1](/ja/spec/blockstate/#つながり))。その導出を求めるのが `origin=imported` です。Bedrock では、まずブロックを、ステートマップがそれとして書き出す正規のステートとして読み戻し ([§12.4](#124-取り込み時の記録と落とし穴))、ターゲットが組む既定値のステートと、どの値でもターゲットが同じに組むステートも除きます。規則が別のつながりのステートを導いてしまうセルは、つながりのステートをすべて書き、すべてのセルが一致するまで検証を繰り返します。
- **チャンク。** 幅か奥行きが 48 ブロックを超える本体は、`struct` ではなく `def` を並べた `site` になります。本体の高さいっぱいで、幅も奥行きも 48 以下の柱に分け、`x` と `z` に沿った位置で `<body>_x<i>_z<j>` と名付けます。`site` はそれらを元の位置に、`east_of=`、`north_of=`、`gap=0` で隙間なく並べます。`place` はテーマを指定するもので、生のメンバーはテーマを読まないので、何も割り当てない `theme imported` の下に置きます。チャンクはそれぞれ単独でリフトできます ([§12.4](#124-取り込み時の記録と落とし穴))。

## 12.4 取り込み時の記録と落とし穴

取り込むときは、`(edition, version)` と来歴 (provenance) を、取り込みが書き出すソースに記録します (`.nbt`、`.litematic`、`.schem` → java、`.mcstructure` → bedrock)。これによって、取り込んだものも再現できるようになります ([バージョンとエディション](/ja/spec/versioning-editions/))。バージョンはビルドが出荷するターゲットで、ファイルが保存されたと示すバージョンによって選びます。

| 形式 | 保存されたバージョン |
|---|---|
| `.nbt` | `DataVersion` |
| `.litematic` | `MinecraftDataVersion` |
| `.schem` | `DataVersion` |
| `.mcstructure` | パレットのブロックが持つ最も新しい `version`。ブロックステートのバージョンで、複数のリリースが共有する |

- 出荷するターゲットの `DataVersion`、またはそのブロックバージョンで保存されたファイルには、そのターゲットを記録します。ブロックバージョンを共有するターゲットが複数あるときは、ステートマップがファイルのすべてのブロックに正規のステートを持つもののうち最も古いもの、そういうものがなければ最も古いものです。
- 出荷する 2 つのターゲットの間で保存されたファイルには、その後で最も近いターゲットを記録します。ゲームは古いリリースが保存したファイルを、その後に変わった名前を付け替えながら読み込むので、後のターゲットはゲームと同じようにファイルを読みます。そのリリースがもう使わない綴りのブロックをファイルが持っていれば拒否し ([§12.2](#122-逆方向の変換-コンパイラは写し取りllm-がリフトする))、そのリリースでファイルを保存し直せば名前が付け替わります。
- 出荷するどのターゲットより前に保存されたファイルには、同じ条件で最も古いターゲットを記録します。
- 出荷するどのターゲットより後に保存されたファイルは、このビルドが出荷するどのターゲットもそのブロックを検証できないので、終了コード 1 で拒否します。拒否のメッセージは最も新しいターゲットを示します。
- パレットがバージョンを持たない `.mcstructure` には、そのエディションの `latest` を記録します。

ヘッダは、保存されたバージョンをファイルにあるとおりに示します。ビルドがそのリリースを知っていれば `DataVersion 3955 (1.21.1)` のようにリリースを添え、Bedrock のブロックバージョンは 4 バイトを並べて `block version 1.21.60.33` と示します。そのうえで、上のどの規則で記録するターゲットを選んだかを示します。

**取り込みを「作者の意図の復元」として見せてはいけません。** これが最大の落とし穴です。復元できるのはボクセルと一部の規則性だけで、CLI はそのことを示します。取り込みのたびに `W_SEMANTIC_LOSS` で警告し、まず意図ではなくブロックを復元したことを、次に、ファイルが持っていてソースが持たないものの種類ごとに 1 回ずつ、それがある本体とともに示します。

- ブロックエンティティのデータ。チェストの中身、看板の文字、コマンドブロックのコマンドなどで、どの生のメンバーも持てません。id ごとのブロックエンティティの数を添えます。
- エンティティ。取り込みはブロックしか書き出さないので、id ごとの数を添えて示します ([エンティティ](/ja/spec/entities/))。
- ストラクチャーヴォイド (structure void)。`.nbt` の `blocks` が何も挙げないセルと、`.mcstructure` の 1 層目の `-1` です。配置するとワールドのそのセルをそのまま残しますが、取り込みは air として書き出すので、配置するとそのセルを空にします。
- `.nbt` の 2 つ目以降のパレット。配置するときは、その中から 1 つがランダムに選ばれます。
- Bedrock では、ステートマップに正規のステートがないブロック (id だけで書き出し、そのブロックの既定のステートで組みます)、`waterlogged` として水を持てないブロックの位置にある水 (書き出しません)、ファイルの 2 層目に水がない位置にある、常に水の中にあるブロック、そして 2 層目の水以外のブロック (どの生のメンバーも書き出しません)。

ほかの規則:

- 取り込みが書き出す行には `origin=imported` が付き ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))、設計用の第一級の DSL と区別します。この行は体積を決め、書いていないつながりのステートを隣のブロックから得ます。手で書いた生のメンバーはどちらもしません。リフトは生のまま残すものにこの印を残すので、残差は明示的なままです。
- Litematica のリージョンは、平坦化せずに来歴として残します。各リージョンはそれぞれ 1 つの struct になってリージョンの名前を持ち、その上のコメントにリージョンの名前と schematic の中での最小の角を書きます。リージョンは `site` の配置としては読み戻しません。`place` の行は本体を別の本体の隣に置くもので、schematic が示す角には置けず ([コンポーネント・編集・複数建築 §9.3.2](/ja/spec/components-editing-sites/#932-原点セレクタ))、2 つのリージョンが重なることもあるからです。
- エンティティを含む schematic では、block IoU だけで成功と判定してはいけません。エンティティ用の指標を別に持ち、第一級のエンティティ ([エンティティ](/ja/spec/entities/)) だけを取り出します。
- 巨大な schematic (幅か奥行きが 48 ブロックを超えるものや村全体) を一度にリフトすると、LLM の文脈に収まりません。ストリーミングでパースしながら、チャンクへの分割 → チャンクごとの L1 → 部分ごとのリフト → `site` での結合、という流れをまとめて制御する必要があります。取り込みは最初の 2 つを行います。そのような本体はチャンクを並べた `site` として書き出し ([§12.3.1](#1231-取り込みが書き出すもの))、各形式の読み込みはファイルをストリーミングで読んで、それを表す NBT ではなくグリッドを保持します。
- 1.13 のフラット化より前の、数値 ID の `.schematic` は v1 では扱いません ([目的とスコープ](/ja/spec/overview/))。`cairn import` は、読まない拡張子として拒否します。
