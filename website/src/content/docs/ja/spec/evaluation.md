---
title: "13. 評価フレームワーク"
---

仕様の品質は、好みではなく数値で評価して改善します。評価には、Minecraft 本体に依存しないヘッドレスなジオメトリシミュレータを使います。語彙や構文の議論は好みの問題になりがちなので、先に評価の仕組みを固めておきます。

```text
テストプロンプト集 (~50)
  → zero-shot 生成
  → ヘッドレス lint (構文 + AABB ジオメトリ: 「壁外の窓」「空中のドア」など)
  → 行番号付きエラーを返し、最大 3 ターン自己修正する
```

このループは、リポジトリの評価ハーネスが回します。`cargo eval run` は `eval/prompts/` にあるプロンプト集のすべてのプロンプトをモデルに尋ね、返答をこのチェックアウトの `cairn` で検査して、下の指標を収めた [実行の記録](#135-実行の記録) を書き出します。`cargo eval compare` は 2 つの記録を並べて比べます。実行のしかたは [開発者ガイド](/development/#the-evaluation-harness) (英語) にあります。

lint の段階は、実行のターゲットでの `cairn check` と `cairn compile` です。そのため、ループには作者が見るものがそのまま見え、ハーネスが独自にジオメトリを調べることはありません。上の 2 つのジオメトリの不具合のうち、壁外の窓は `E_INVALID_MEMBER` になります。空中のドアは、ジオメトリの区分のうちまだどのコマンドも検査しない部分なので ([lint](/ja/spec/lint/#意味カテゴリ))、これを含むプログラムも合格し得ます。`cairn check` がこれを報告するようになれば、ハーネスを変えずにループがそれを見るようになります。

## 13.1 主要な指標

| 指標 | 測るもの |
|---|---|
| **Zero-shot compile rate** | 1 回目でエラーなしにコンパイルできる割合。仕様の分かりやすさを表す。 |
| **Fix convergence rate** | 3 ターン以内にエラーなしまで収束する割合。エラーメッセージの伝わりやすさを表す。 |
| **Token efficiency** | 展開後のブロック数 ÷ DSL のトークン数。 |
| **Edit stability** | 「2 階の窓だけアーチにする」のような追加の編集をしたとき、AST と NBT の差分がどれだけ小さいか。 |

指標は、次の用語の上に成り立ちます。

- **プロンプト**: プロンプト集の 1 ファイルです。あるトピックのもとで、平易な英語で書いた依頼です。トピックは、壁、開口部、屋根、階、メンバー、テーマ、`def` と `repeat`、レッドストーン、柱とアーチ、内装です。**生成プロンプト** は建築を依頼します。**編集プロンプト** は生成プロンプトの 1 つを base として名指しし、そのプロンプトが収束したプログラムの変更を依頼します。
- **会話**: モデルには、短い前置きとこの仕様の英語のすべてのページをシステムプロンプトとして与え、リポジトリからはそれ以外に何も与えません。最初のメッセージは `cairn compile` のコマンドラインでターゲットを示し、プロンプトを伝えます。編集プロンプトの最初のメッセージは、base のプログラムも引用します。base が収束しなかった編集プロンプトは飛ばします。
- **試行**: 1 つの返答です。そのプログラムは、`cairn` か `crn` と印を付けた最後のフェンス付きコードブロックです。試行が **合格** するのは、プログラムを含み、`cairn check` がエラーを報告せず、`cairn compile` がビルドでき、ビルドにブロックが 1 つ以上あるときです。警告では試行は不合格になりません。不合格の試行には、`cairn check` か `cairn compile` が出力したものをそのまま返すか、返答にプログラムがなかったこと、またはブロックを 1 つも作らなかったことを伝える文を返します。
- **収束**: 会話が **収束** するのは、最初の 4 回の試行 (1 回目と、最大 3 回の修正) のどれかが合格したときです。会話は合格した試行で終わります。
- **ブロック**: `cairn compile` がターゲットで書き出す構造の中の、空気以外のセルです。`cairn lower --target` が出力する形で、構造、位置、ブロック ID、ブロックステート、ブロックエンティティを持ちます。エンティティはブロックではありません。
- **DSL のトークン**: [字句](/ja/spec/syntax/#51-字句) のトークンのうち、行末と、入れ子が作るインデントとデインデントを除いたものです。コメントはトークンではありません。`slot wall -> @cobblestone` は 5 トークンです。
- **AST のノード**: 先頭の `@` ディレクティブ、トップレベルの項目自身の行、本体の 1 行です。深さを持ち、引数はキーの順に並べ、下に入れ子になった行は含みません。

これらの用語で、指標は次のとおりです。

- **Zero-shot compile rate** は、1 回目の試行が合格した生成プロンプトの数 ÷ 生成プロンプトの数です。
- **Fix convergence rate** は、収束した生成プロンプトの数 ÷ 生成プロンプトの数です。
- **Token efficiency** は、収束したプログラムのブロック数 ÷ DSL のトークン数で、どちらも生成プロンプト全体で合計します。そのため、大きな建築は小さな建築より重く数えられます。
- **Edit stability** は、収束した編集プロンプトごとの 2 つの比で、それぞれをそれらのプロンプトで平均します。小さいほど安定しています。
  - **AST の差分**: (取り除いたノード + 加えたノード) ÷ (前のノード + 後のノード)。残ったノードは、2 つのプログラムのノードの最長共通部分列です。引数の並べ替えや、コメントと空白の変更は変化に数えません。行を別の行の下へ移すことは変化に数えます。
  - **NBT の差分**: ブロックが異なるセルの数 ÷ どちらかのビルドが埋めるセルの数。ファイルから読み戻すのではなく、`cairn compile` が書き出すブロックで比べます。板ガラスのつながりのような、コンパイラが導出するブロックステートも数えます ([編集モデル](/ja/spec/components-editing-sites/#92-編集モデル))。

編集プロンプトの結果は base のプログラムに左右されるので、2 つの率は生成プロンプトだけを数えます。実行の記録は、生成プロンプトをトピックごとにも集計します。

## 13.2 逆変換の補助指標

逆変換の品質 ([エコシステム連携](/ja/spec/ecosystem-interop/)) は主要な評価から外し、補助的な指標として扱います。情報の欠落を許容する方針と合わせるためです。測るのは「形を再現できたか」ではなく、**「編集しやすい DSL になったか」** です。

- `block_iou`、`state_accuracy` (facing / shape / waterlogged の一致)、`entity_accuracy` (額縁 / 看板 / 村人 / display の保持)。
- `residual_ratio`: リフト後に残った raw の体積。`compression_ratio`: ボクセル数 ÷ トークン数。
- `editability_score`: 名前付きメンバーの数、スロット化の割合、安定したアドレスの割合。
- `theme_extraction_score`: 具体的なブロックがインラインで書かれず、スロットとテーマに分離されているか。
- `symmetry_score`: `repeat` / `mirror` / `def` に畳み込まれた割合。`version_portability`: 正規トークンの割合。

## 13.3 運用のルール

語彙の追加や構文の変更は、これらの指標、特に fix convergence rate と edit stability を改善する場合にだけ採用します。「モデルに仕様だけを与えて生成させ、どこでエラーが出るかを観察する」実験を回せば、構文や語彙をめぐる議論のほとんどは実データで決着します。

提案は 2 つの実行を示します。分岐元のコミットでの **ベースラインの実行** と、提案の先頭のコミットでの **提案の実行** です。どちらも、同じモデル、プロンプト集、エディション、ターゲット、`max_tokens` で尋ねます。プロンプト集を変える提案は、ベースラインも提案のプロンプト集で実行します。提案は、2 つの記録を `spec_pages` と `prompt_set` のハッシュとコンパイラのバージョンで示し、それらに対して `cargo eval compare` が出力したものを引用します。この比較は、同じことを尋ねていない 2 つの記録を拒否し、token efficiency と edit stability は両方の実行が収束したプロンプトだけで比べます。モデルは毎回同じようには答えないので、1 組の実行で決着するのは大きな差だけです。差がプロンプト数個分の提案は、より多くの組を示します。

逆変換の評価ハーネスは、コミュニティの schematic を集めたコーパスから、`def` / `theme` の標準ライブラリを育てる仕組みにもなります。

```text
コーパス → 取り込み → 正規化(エディション/バージョン) → L1 圧縮 → クラスタリング(形/マテリアル)
  → LLM リフト候補 → コンパイル/diff → 人手レビュー → def/theme ライブラリ
```

## 13.4 レッドストーンの検証

ヘッドレスのジオメトリシミュレータは、tick 単位のレッドストーン論理シミュレータへと拡張します。ターゲットのエディションごとに合成した回路をシミュレーションし、宣言された真理値表、レイテンシ、時相のアサーションと照合します (synth → sim → diff → patch)。レッドストーンのシミュレータはあり、回路を組み上げるどのコマンドも、`assert truth` と `assert always` に対してこれを実行し、レイテンシの上限の tick は合法化した回路で数えます。破れたアサーションはエラーで、ハーネスのループはほかの報告と一緒にそれをモデルへ返します。レイアウトそのものを直すものはありません。[レッドストーン](/ja/spec/redstone/#147-検証) を参照してください。

## 13.5 実行の記録

1 回の実行は、1 つの JSON の記録を書き出します。記録は、実行が何を尋ねたかを示します。記録の `format`、チェックアウトの `compiler_version`、`model` の ID、`edition` と `target`、各リクエストが持つ `max_tokens`、そして 2 つのハッシュです。`prompt_set` はプロンプトとハーネスが送る固定のメッセージの sha256、`spec_pages` はシステムプロンプトが持つ仕様のページの sha256 です。記録はさらに、[§13.1](#131-主要な指標) の指標、実行が送ったリクエストとそれが使ったトークン、プロンプトごとの結果を持ちます。結果には、各試行の返答、判定、診断、それに返したものと、収束したプログラムとその DSL のトークン数とブロック数、編集プロンプトならその差分が入ります。

記録は、尋ねたモデルを示します。ハーネスには既定のモデルがないので `--model` は必須で、どの実行もモデルを 1 つ名指しします。
