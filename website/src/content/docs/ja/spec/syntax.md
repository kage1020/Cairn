## 5.1 字句

1 行が 1 つのコマンドで、`#` から行末まではコメントです。行はコマンドのキーワードで始まり、**それ以降の引数はすべて `key=value` の形でなければなりません (MUST)**。コマンドが次の行以降に続いてよいのは、真理値表の波括弧の中だけです ([リテラルと区切り](#511-リテラルと区切り))。

```
window side=front mat_slot=glass offset=2 y=2 size=2x2 sym=true   # OK
window front G 2 2 2x2                                            # 禁止 (位置引数)
```

位置引数を使うと、引数の順番を覚えておく必要があります。LLM は順番を取り違えたり、引数を書き落としたりします。`mat_slot=` や `side=` のようなキーは、モデルの注意を向ける目印 (attention のアンカー) になり、生成を安定させます。キーに使うトークン以上の価値があります。

位置引数を読まない行に裸の値があると、`E_UNEXPECTED_POSITIONAL` になります。位置引数を読む形式は `connect FROM.PORT to TO.PORT` だけで、その形は代わりに `E_CONNECT_ARITY` が検査します。

パーサは、`key=`、`-> binding`、`[selector]` のどれでもないトークンを、すべて位置引数のリストに入れます。`=` を書き忘れた引数も、ここに入ります。`walls mat_slot=wall height 3` は、高さが低い `walls` になるのではなく、まったく作られません。

ヘッダ、`theme` のルール、`assert` の行も位置引数のリストを持つので、そこにある裸の値でパースが終わることはありません。ヘッダのリストに入るのは、名前のあとから `:` の前までにある裸の値です。`struct s size=3x3: tall` のように `:` のあとにある裸の値は `E_PARSE` になり、`:` より前の値の中にあるブロック ID も、ブロック ID は `key=` の値なので、それ自身の `:` の位置で `E_PARSE` になります ([リテラルと区切り](#511-リテラルと区切り))。`struct` と `def` のヘッダ、`theme` のセレクタのルールは、裸の値を `key=value` の引数と並べて持つので、`struct s size 3x3` は `size 3x3` の位置で `E_UNEXPECTED_POSITIONAL` になり、`size=3x3` と書けば直ります。`site` と `theme` のヘッダは名前のあとに何も読まず、`slot` の行は束縛する値のあとに何も読まず、`assert` の行は形の終わりのあとに何も読みません。そこにある裸の値は同じ診断になり、そこにある `key=value` は `E_PARSE` になります。名前だけの語を束縛する `slot` の行は、`slot floating_text -> text_display scale=2.0` のように、そのあとにメンバーの形の `key=value` の引数を読みます ([マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット))。`=` を書き落とした `logic` の行 (`logic sig.a sig.b or sig.c`) は、名前のあとの式を読んだうえで何も束縛せず、行全体で `E_UNEXPECTED_POSITIONAL` になります。中置プリミティブで始まる式はないので、`logic sig.a or sig.b` は `=` の書き落としとして `or` の位置で `E_PARSE` になります。

### 5.1.1 リテラルと区切り

`key=` の値は `-` で始まらないので、負の数はパースできません。`offset=-1` と `scale=-1.5` は `E_PARSE` です。**整数** は 10 進の数字の並びです。上限は 2^63 − 1 で、`assert always` の `within`、`assert latency` の `<=`、`pulse(sig.ring, 4)` のようなマクロの段数の上限だけは 2^32 − 1 です。段数は 1 以上です ([レッドストーン §14.1](/ja/spec/redstone/#141-2-つの層と-v1-の範囲))。

**小数** は、10 進の数字の並び 2 つを `.` でつないだもので、`scale=1.5` のように書きます。指数も型の接尾辞も持たないので、`1.5e3`、`1.5f`、`1.5.2` のように数字の先へ続く並びは、サイズの場合と同じくそのリテラルの位置で拒否します。`.` の後に数字がない `1.` も、前に数字がない `.5` も拒否し、診断は `1.0` と `0.5` を示します。小数は、整数が値として書ける場所に書けます。キーの `=` の後、値のリストの中、裸の値です。小数は整数ではないので、座標の組の成分、サイズの寸法、段数、アサーションの上限、ブロックステートのリテラルの値は、どれも小数をそのリテラルの位置で拒否します。パーサは小数を書かれた数字のとおりに保ち、double の範囲 (およそ 1.8 × 10^308) を超える小数はそのリテラルの位置で `E_PARSE` にします。小数を読むキーが、書き出すときに float と double のどちらで格納するかを決め、書かれた値はその型でいちばん近い値に丸めて書き出します。そのようなキーは整数を同じ数として読むので、`scale=2` と `scale=2.0` は同じ値です。

2 つの値を比べるところでは、数値はその数値が表す数として比べます。`1.5` と `1.50` は同じ値で、`2` と `2.0` も同じ値です。theme のセレクタの属性は、この比べ方でメンバーの値に一致します ([マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット))。アドレスは、それぞれの数値を 1 通りに綴ります ([§5.5](#55-idクラスアドレス))。

小数を読むキーは display の `scale=` で、書き出しはこれを float として格納します ([エンティティ §8.1](/ja/spec/entities/#display))。ほかの種類の値を読むキーは、小数を座標の組 (下記) と同じように扱います。ラベルやサイズのキーは型違いとして拒否し、`height=` や `offset=` のようなメンバーのキーはそのメンバーを `E_INVALID_MEMBER` として拒否し、`sym=` や `overhang=` のように既定値に戻るキーはそのことを `W_IGNORED_ARGUMENT` で知らせます。

**NBT コンパウンド** は、生の NBT を波かっこの中に SNBT で書いたもので、`nbt={variant:"black"}` のように書きます。キーの `=` の後に `{` が続くと、間に空白があってもなくても、キーはそれを NBT コンパウンドとして読みます。それ以外の場所では `{` は本来の意味のままなので、裸の `{a:1}` と値のリストの中のコンパウンドは `E_PARSE` になります。コンパウンドは開いた行の中で閉じます。下の行へ続けられるのは真理値表の波かっこだけで、行末で開いたままのコンパウンドはその位置で `E_PARSE` になります。中に書けるのは、Cairn がターゲットにするどの Java のバージョンも同じように読む SNBT の範囲です。

- コンパウンドは `{}` か、2 つの間にちょうど 1 つの `,` を挟んで並べた `key:value` のエントリです。キーは引用符で囲むか、英字、数字、`_`、`-`、`.`、`+` の並びで書き、1 つのコンパウンドの中で同じキーは 1 回しか書けません。
- リストは `[]` か、2 つの間にちょうど 1 つの `,` を挟んで並べた値で、値はすべて同じ型です。配列は `[B;`、`[I;`、`[L;` で始まり、この 3 文字の間には何も挟まず、それぞれ接尾辞付きの数値で書いた byte、int、long だけを持ちます。
- 数値は、省略できる符号、数字、省略できる `.` と数字、省略できる接尾辞の順に書きます。接尾辞は大文字でも小文字でもよく、`b`、`s`、`l` が byte、short、long を、`f`、`d` が float、double を表します。接尾辞がなければ int で、`.` があれば double です。byte、short、int、long は `.` も先頭の 0 も持たず、どの数値もその型の範囲に収まります。
- 文字列は `"` か `'` で囲み、エスケープできるのは `\` と自身の引用符だけです。`true` と `false` は byte の `1b` と `0b` で、それ以外の引用符のない単語は拒否するので、文字列になるのは引用符で囲んだ値だけです。`variant:black` は `variant:"black"` と書きます。
- コンパウンド、リスト、配列の入れ子は、いちばん外のコンパウンドを含めて 64 段までです。

それ以外のものは、どれもそれが始まる位置で `E_PARSE` になります。指数、16 進や 2 進の数、数字の間の `_`、`\n` のようなエスケープ、`bool(...)` のような関数、コメントもこれにあたります。パーサはコンパウンドを波かっこごと書かれたとおりに保ち、中のフィールドをターゲットに照らして検査することはありません。フィールドの意味と、コンパウンドを書く行が置かれる `@edition` ガードは、[エンティティ §8.1](/ja/spec/entities/#81-2-つの段階) で定めます。`nbt=` を読むキーワードは、エンティティのキーワードと `raw_block` です。ほかの行では、`nbt=` はその行が読まないほかのキーと同じ扱いになります。ヘッダやメンバーでは `E_UNKNOWN_ARGUMENT` になり、theme のセレクタの束縛としては `W_IGNORED_ARGUMENT` になります。ほかの種類の値を読むキーは、コンパウンドを小数と同じように扱います。

サイズのリテラルは、0 でない寸法をちょうど 2 つ持つ `WxH` です。`2x2x9` や `2x2y` のように 2 つ目の寸法より先に続く並びは、サイズとその後ろの何かとして読むのではなく、そのリテラルの位置で拒否します。

**座標の組** は、3 つの整数を間に何も挟まずに `,` でつないだ `x,y,z` で、`at=4,3,2` や `from=1,1,1` のように書きます。座標の組は、それを書いたスコープの 1 つのセルを、そのスコープのメンバー行を測るのと同じ座標系で指します ([未決事項](/ja/spec/open-issues/))。`x` は `size=` の敷地の `W` に沿って `x` が小さい側の角から、`z` は `H` に沿って `z` が小さい側の角から測り、`y` は基準面から、`level y=N` の下ではその `level` の基準面から上へ数えます。こうして指したセルも、ほかのメンバーと同じく屋根の `overhang=` の分だけずれます。小さい側の角より手前を数える成分はないので、負の成分はありません。各成分の上限は、ほかの整数と同じです。`raw_repeat` の `step=` ([エコシステム連携](/ja/spec/ecosystem-interop/)) のように、後の章がセルではなく距離として定めるキーは、同じ 3 つの整数を、ある繰り返しから次の繰り返しまでの距離として読みます。

座標の組は `key=` の値です。キーの `=` の後に整数、`,`、もう 1 つの整数が続くと、キーはそれを座標の組として読みます。どちらかの整数の前に `-` があっても座標の組として読み始め、その `-` の位置で拒否します。そのため `from=-1,2,3` と `from=1,-2,3` には、成分が負にならない理由が示されます。それ以外の場所では、カンマは本来の意味のままです。値のリストではカンマが要素を区切るので、`[1,2,3]` は 3 つの整数です。裸の値と `->` の束縛は整数を 1 つしか読まないので、`fill 1,1,1` は最初の `,` で `E_PARSE` になります。セレクタの中では、後ろにキーが続く `,` はこれまでどおり属性を区切ります。`[y=2,side=front]` は 2 つの属性で、`[at=1,2,3, y=2]` は座標の組と属性です。組の中の `,` の前後にある空白、2 つだけの成分、4 つ目の成分、成分の前の `-` は、どれもそのリテラルの位置で拒否します。

敷地の外のセルや、書かれたとおりのスコープが届く最上段より上のセル ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出)) は、スコープの外です。その座標の組を読むメンバーは、壁の長さ以上の `offset=` を拒否するのと同じく、これを `E_INVALID_MEMBER` として拒否します。`fill` ([ブロックステート §6.3](/ja/spec/blockstate/#63-waterlogged)) と `raw_fill` の `from=` と `to=`、`raw_block` ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))、Tier 0 の部品 ([レッドストーン §14.1](/ja/spec/redstone/#tier-0-の部品))、`trapdoor`、`note_block`、`sign`、`bed` ([ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する))、エンティティ ([エンティティ §8.1](/ja/spec/entities/#81-2-つの段階)) の `at=` は座標の組を読みます。座標の組を読むキーはほかにありません。ほかの種類の値を読むキーは、座標の組を種類の違うほかの値と同じように扱います。ラベルやサイズのキーは型違いとして拒否し、`side=` や `height=` のようなメンバーのキーはそのメンバーを `E_INVALID_MEMBER` として拒否し、`sym=` や `overhang=` のように既定値に戻るキーはそのことを `W_IGNORED_ARGUMENT` で知らせます。

座標の組の外では、カンマは構造ではなく、**省略できる区切り** です。`@intended_targets ["1.20.4", "1.21.4"]` と `@intended_targets ["1.20.4" "1.21.4"]` は同じ 2 つのバージョンを表し、`[side=front, y=2]` と `[side=front y=2]` も同じです。ただし、どこまで記号を許すかは 2 種類のリストで異なります。

- `[selector]` の属性リストは、カンマをどこで見つけても読み飛ばすので、`[side=front, , y=2]` もパースできます。
- 値のリストは、要素の間にカンマを 1 つまでしか読まず、`[a, , b]` は拒否します。

正規トークンには、`@oak_log[axis=x]` や `@oak_stairs[half=top, facing=north]` のように **ブロックステートのリテラル** を付けられます。`[` はトークンに接していなければなりません。空白の後の `[` は、トークンとは別の次の要素として読みます。値のリストでは、`[@a [b]]` はこれまでどおりトークンと入れ子のリストですが、`[@a[b]]` は `b` がプロパティではないので拒否します。リテラルの中の各組は `property=value` で、値は単語、数字の並び、`true` / `false` のいずれかです。これは Cairn のリストではなく Minecraft 自身のブロックステートの構文なので、2 つの組の間にはちょうど 1 つのカンマを書きます。空のリテラル、末尾のカンマや重なったカンマ、同じプロパティの 2 回目の指定は拒否します。`@floor.wood` のようなドットを含むトークンは抽象トークンです。ブロックを選ぶのはそのトークンを割り当てるテーマなので、リテラルは付けられず、これに接する `[` も、空白の後の `[` と同じく別の次の要素として読みます。

トークンに接する `[` をリテラルとして読んでも、ほかの読み方ならビルドできたはずのソースを拒否することにはなりません。`[` を別の次の要素として読むと、`mat_slot=@a[1]` は位置引数を読まないメンバーの行に裸の値を残すので `E_UNEXPECTED_POSITIONAL` に、`mat_slot=[@a[b]]` はラベルを書くべき場所にリストを置くので `E_TYPE_MISMATCH_LABEL` になるからです。

**ブロック ID** は、名前空間とパスを、間に何も挟まずに `:` でつないだもので、`mat=minecraft:stone` のように `namespace:path` と書きます。どちらの半分も識別子です。テーマが割り当てる意味ではなく、Minecraft が綴るとおりのブロックを名指し、これを読むのは生のメンバーの `mat=` だけです ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))。正規トークンと同じブロックステートのリテラルを接して付けられ、`minecraft:light[level=15]` のように書きます。座標の組と同じく `key=` の値です。それ以外の場所では `:` はもとの意味を保つので、テーマのルール `slot wall -> minecraft:stone` は `E_PARSE` になります。テーマが割り当てるのは正規トークンです ([マテリアルとテーマ §7.2](/ja/spec/materials-themes/#72-正規トークン))。`:` の前後に空白を入れた場合も `E_PARSE` で、ラベル、トークン、整数を読むキーは、ほかの種類の違う値を拒否するのと同じようにブロック ID を拒否します。

バージョンを固定したビルドは、リテラルのプロパティと値を、そこでブロックが取るステートと照らし合わせるので、`@oak_log[axis=q]` は `E_STATE_DOMAIN` ([Lint](/ja/spec/lint/)) になり、`x`、`y`、`z` を示します ([バージョンとエディション](/ja/spec/versioning-editions/#ステートはターゲットでのブロックのステートと照らし合わせる))。

このリテラルと座標の組を除くと、カンマが意味を持つのは `assert truth(...)` の入力リストだけです。そこではカンマが信号を区切り、その信号の数と行の幅を照合します。行には入力の信号 1 つにつき 1 文字 (`0`、`1`、`-` のいずれか) を書きます。`truth(a, b -> out)` の行は 2 文字幅になり、`{ 2->0 }` や `{ 0->0 }` は拒否します。

`-` は **don't-care** です。その入力がどちらの値でもよいという意味で、`0- -> 1` は `00->1` と `01->1` の 2 行を合わせたものを表します。これは独立した構文ではなく、行をまとめて書くための省略形なので、2 つの行が同じ入力の組を受け持つことはできません (下の表を参照)。

`-` と `->` は同じ文字を使うので、字句解析ではできる限り矢印として読みます。最後の入力が don't-care の行は、`11--> 0` か `11- -> 0` と書きます。どちらも同じ 3 文字幅の行です。空白はパターンの終わりを表すので、`0- 1 -> 1` は 3 文字幅の行ではなく、2 文字幅のパターンと余分な `1` になります。

行の**出力**にも `0`、`1`、`-` を書けますが、出力の `-` は意味が異なります。その行が受け持つ入力の組については、意図的に何も制約しないという意味です。`--0 -> -` は、3 つ目の入力が low であるどの組についても、表は何も主張しないことを表します。これで、作者が意図していない 4 つの出力を主張せずに `W_TRUTH_TABLE_PARTIAL` を解消できます。この時点で矢印はすでに読み終えているので、`-> -` と `->-` は同じ行です。すべての行の出力が `-` である表は何も制約しないので、行が 1 つもない表と同じく `E_TRUTH_TABLE_EMPTY` になります。

行を囲む表も、同じ考え方で読みます。

| 状況 | コード |
|---|---|
| 1 つの信号を 2 つ以上の入力として並べている | `E_TRUTH_TABLE_DUPLICATE_INPUT` (各信号を 1 回ずつにするまで、その表についてほかの指摘はしない) |
| 行が 1 つもない、または出力が `0` か `1` の行が 1 つもない | `E_TRUTH_TABLE_EMPTY` |
| 2 つの行が、同じ入力の組に異なる出力を割り当てている | `E_TRUTH_TABLE_CONFLICT` (後の行で報告) |
| 2 つの行が同じ入力の組を受け持ち、互いに矛盾していない | `W_TRUTH_TABLE_DUPLICATE_ROW` (後の行で報告) |
| 割り当てのない入力の組がある | `W_TRUTH_TABLE_PARTIAL` |

最後の 2 つが警告なのは、書いてある行は、書かれたとおりの意味をそのまま持つからです。入力が 4 つの表は 16 行になります。途中まで書いた作者を止める理由はありません。

波括弧の中では、表の行の前後、表の行を終える `;` の後、`}` の前のどこで改行してもかまいません。表は `assert` と同じ行に収めても、表の行ごとに行を分けてもかまいません。

```
assert truth(sig.a, sig.b, sig.enable -> sig.out) {
  001 -> 0
  011 -> 1
  101 -> 1
  111 -> 1
}
```

波括弧の中の行はインデントを持ちません。表の行と閉じる `}` はどの深さに置いてもよく、その間の空行とコメント行は読み飛ばします。ただし、表の行や `}` の前のタブは、コマンドの前のタブと同じく拒否します。表の行は 1 行に収めるものなので、パターン、`->`、出力の間で改行すると拒否します。`{` は `assert` と同じ行に置きます。`;` は同じ行にある直前の表の行を終えるものなので、`;` で始まる行は書けません。`}` が欠けた表は、最後の表の行の次に来るもの (次のコマンドなど) の位置で拒否します。次に何も来なければ、最後の表の行の行末で拒否します。

インデントは 1 段につきスペース 2 つで、一度に 1 段ずつしか深くできません。幅が 2 の倍数でない場合と、2 段以上いっぺんに深くした場合は別の誤りなので、別々に報告します。真理値表の波括弧の中の行はインデントを持たないので、そこではどちらの誤りも起こりません。

改行の前のスペースは行に含めないので、行末にスペースがあってもかまいません。スペースだけの行は空行として扱います。空行の先頭のスペースもほかの行と同じように数えますが、行ごと捨てるので、その幅はインデントにも誤りにもなりません。

ファイルの先頭にある UTF-8 の BOM は無視します。それ以外の位置にある BOM は、ただの余計な文字として扱います。

行の終わりは `\n`、`\r\n`、単独の `\r` のどれでもよく、3 つとも同じ改行として扱います。VS Code や Monaco と同じ規則なので、診断の行番号とカーソルのある行の番号は一致します。位置は常に誤っているテキストそのものを指すので、行末のエラーはその行の行末で報告し、次の行の 1 桁目で報告することはありません。

tree-sitter の文法は、3 つの点で既知の例外です。1 つ目に、そのランタイムは `\n` でしか行を進めないので、単独の `\r` だけで改行したファイルは、正しくパースできていても 1 つの長い行としてハイライトされます。2 つ目に、パーサが拒否する次の 15 の形を受け付けます。寸法が 0 のサイズ (`0x3`)、3 つ目の寸法が続くサイズ (`2x2x9`)、単語が続くサイズ (`2x2y`)、2^63 − 1 を超える整数 (単独のものも、座標の組の成分も)、2^32 − 1 を超えるアサーションの `within` や `<=` の上限やマクロの段数、0 の段数、最後の成分がサイズにつながった座標の組 (`1,2,3x4`)、幅が入力の数と合わない真理値表の行、同じプロパティを 2 回指定したブロックステートのリテラル、単語が続く小数 (`1.5e3`)、double の範囲を超える小数、そして同じキーを 2 回書いたもの、型の混ざったリストを持つもの、型の範囲を超える数値を持つもの、64 段より深く入れ子にしたものの 4 つの NBT コンパウンドです。どれも、その規則を tree-sitter では表せないためです。3 つ目に、`site` と `theme` のヘッダの名前のあとにある裸の値を拒否します。パーサはこれを読んで `E_UNEXPECTED_POSITIONAL` として報告します。文法が拒否するのは、ここで裸の値を受け付けると、エラー回復のときに、深くインデントしすぎた本体の最初の行をヘッダに取り込んでしまうからです。

## 5.2 ネスト

ネストは浅く保ちます (`struct` / `def` / `level` / `theme` / `site`)。ネストが深いほど、LLM の生成の誤りが増えるからです。(`room` はこの一覧にありません。まだ決まっていないので、今書くと `E_UNKNOWN_KEYWORD` になります。[未決事項](/ja/spec/open-issues/)を参照してください。)

本体の中でほかのメンバーをまとめられるのは `level y=N` だけで、それも `struct` か `def` の中に限ります。`site` の本体は `place` と `connect` の行を平らに並べたもので、まとめるための構文はありません。それ以外の場所でインデントした本体を書くと、黙って捨てるのではなく `E_UNSUPPORTED_NESTING` にします。その本体はブロックを生成せず、何も配置せず、通路も敷きません。

この規則はメンバーについてのものなので、メンバーを持つ本体にしか適用されません。`theme` の本体が持つのはルールです。ルールは素材を割り当てるだけで、本体を開かないので、その下にインデントした行はネストの診断ではなく構文エラーになります。ディレクティブの下にインデントした行も同じです。ディレクティブは 1 行で完結し、その下の行はどの構文にも属しません。

`@edition` ガードもその下の行をインデントさせますが、メンバーではなく、何もまとめません。ガードの行は周りの本体に属し、ガードが持てるのはエスケープハッチの層だけです。つまり生のメンバー、`spawn`、Tier 0 の部品、そして `nbt=` を書くエンティティの行です ([バージョンとエディション §10.7](/ja/spec/versioning-editions/#edition-ガードはエスケープハッチを囲む))。

`y=N` がまとめられた各メンバーにとって何を意味するかは、[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) で定めています。

**本体がどのキーワードを受け付けるか** も、同じ区別に従います。`struct` / `def` の本体は 1 棟の建物の形を記述します (`floor`、`walls`、`fill`、`door`、`window`、`roof`、`stair`、`beam`、`level`、`pressure_plate`、`lever`、`button`、`daylight`、`observer`、`lamp`、`piston`、`dispenser`、`chest`、`trapdoor`、`note_block`、`sign`、`bed`、`painting`、`item_frame`、`armor_stand`、`villager`、`trade`、`text_display`、`block_display`、`item_display`、`hologram`、`spawn`、`repeater`、`comparator`、`redstone_torch`、`redstone_dust`、`circuit`、`raw_block`、`raw_fill`)。`site` の本体は配置を記述します (`place`、`connect`)。キーワードの表はグローバルなので、一方のキーワードをもう一方の本体に書いても、パースも分類も通ってしまい、そのうえでどこにも使われません。これが `E_MISPLACED_MEMBER` で、問題の行で 1 回だけ報告し、その下にインデントした行もまとめて捨てます。`level` は `struct` / `def` の本体のほかのメンバーをまとめますが、スコープ全体にわたって領域を確保する `circuit` 行はまとめません。`level` の下に書いた `circuit` 行もどこにも使われず、その行で `E_MISPLACED_MEMBER` になります ([レッドストーン §14.5](/ja/spec/redstone/#145-配置配線-place-and-route))。

`logic` と `assert` の行はメンバーではないので、この規則は適用されません。`logic` の行は、どちらの本体にあってもレッドストーンの合成が読みます。`assert` の行については、それ自身の形と、名指す信号を検査します。真理値表は `cairn check` が検査し ([リテラルと区切り](#511-リテラルと区切り))、名指す信号はレッドストーンの合成が解決します (`E_LOGIC_UNBOUND_SIGNAL`)。レイテンシの上限は敷いた回路に沿って数え、`truth` と `always` はその回路を動かして検査します ([レッドストーン §14.7](/ja/spec/redstone/#147-検証))。

**トップレベルの名前は、種類ごとに別々のスコープを持ちます。** `theme` / `def` / `struct` / `site` はそれぞれ別の名前空間なので、同じ名前を種類ごとに 1 回ずつ使えます。同じ種類で同じ名前を 2 回宣言すると `E_DUPLICATE_ITEM` です。`theme` / `def` / `struct` では名前で割り当てが決まるので、最初の宣言だけが使われます。エラーにしなければ、2 回目は何の知らせもなく消えてしまいます。同じ名前の `site` ブロック 2 つは、代わりに統合され、1 つの `site::NAME::` 名前空間を共有します。しかし `east_of=` はブロックをまたいで参照できないので、統合は中途半端で、やはりエラーにします。

## 5.3 ヘッダ

メタデータは、意味を記述する本体ではなく、ヘッダに書けます (MAY)。

```
@cairn 2026.06                           # このファイルが対象とする Cairn 言語のバージョン
@requires version>=1.20                  # Minecraft のターゲットに求める機能の下限
@intended_targets ["1.20.4","1.21.4"]    # ヒントであり、検証の記録ではない
```

**`@cairn`** は Cairn 言語そのもののバージョンで、Minecraft に関する 2 つのヘッダとは別の軸です。書くかどうかは任意で、将来のコンパイラが正しくパースし、適切に警告できるようにするための来歴 (provenance) として存在します。どのパスもこの値で処理を分けませんが、値は読みます。形式は `YYYY.M` か `YYYY.M.PATCH` で、年は 4 桁、月は `1 … 12` です。月の先頭のゼロは受け付けるので、`2026.06` と `2026.6` は同じバージョンです。それ以外の形は `W_INVALID_CAIRN_VERSION` に、読んでいるコンパイラより新しいバージョンは `W_FUTURE_CAIRN_VERSION` になります。後のコンパイラが読めない来歴では、このヘッダの役目を果たせないからです。

**`@requires`** は、ターゲットに求める機能の下限です。式は、省略できるエディション、主語の `version`、演算子の `>=`、バージョンのラベルからなります。演算子の前後の空白は省略できるので、`version>=1.21` と `version >= 1.21` は同じ要求です。一方、エディションの後には空白が必要で、`javaversion>=1.21` は `E_INVALID_REQUIRES` になります。演算子が `>=` だけなのは、もっとも厳しいものにまとめて合成できる制約が下限だけだからです。それ以外の式は、何も宣言しない行として黙って残すのではなく、`E_INVALID_REQUIRES` にします。消えてしまう下限は、下限がないよりも悪い結果になります。読む人はそれが効いていると信じてしまうからです。

```
@requires version>=1.21                  # ビルドするエディションに対する下限
@requires java version>=1.21.4           # Java の番号体系での下限。Bedrock のビルドでは効かない
@requires bedrock version>=1.21.40
```

エディションを書けるのは、Java のリリースが `1.20.4 / 1.21 / 1.21.4 / 26.3`、Bedrock のリリースが `1.21.0 / 1.21.40 / 1.21.60 / 1.26.60` のように進むからです。`1.21.4` は Java のリリースで、Bedrock のどのリリースも指しません。ラベルは、ドットで区切った要素の並びです。各要素は数字で始まり、英字と数字だけからなります。その後ろに、`-` と、ドットで区切った英字と数字からなるプレリリースタグを続けてもかまいません。`1.21.4`、`1.21.4-rc1`、`24w14a` はどれもラベルです。そのうちどれを *ターゲットのエディション* が順序付けられるかは構文の問題ではないので、ここでは扱いません。[バージョンとエディション](/ja/spec/versioning-editions/)を参照してください。

**`@intended_targets`** は、ファイルをどの Minecraft のバージョン向けに設計したかを示します。検証済みであるという主張ではありません。検証の記録はロックにしかありません。

ヒントであっても、同じファイルの下限とは照らし合わせます。`@intended_targets` に挙げたバージョンのうち、ターゲットのエディションでビルドできるものを、`@requires` がすべて拒否するファイルがあるとします。このファイルは、誰かがその意図に従って動いた瞬間にコンパイラが拒否するような意図を表明していることになります。これが `E_INTENDED_TARGET_CAP` です。一部だけが下限を下回るリストは `W_INTENDED_TARGET_CAP`、ターゲットのエディションではそもそもビルドできないバージョンは `W_INTENDED_TARGET_UNSUPPORTED` になります。[バージョンとエディション §10.4](/ja/spec/versioning-editions/#ヒントは下限と突き合わせる) を参照してください。

`@cairn` と `@intended_targets` は 1 つのモジュールに 1 回までで、2 回目は `E_DUPLICATE_HEADER` です。`@requires` は例外です。下限は合成されるので、繰り返すと制約を置き換えるのではなく、制約が追加されます。

`def` と `theme` は、同じ式を本体の行として持てます。その場合は `@` を付けずに `requires` と書きます。これはファイルではなくその部品に対する下限で、その部品を実体化するすべてのビルドに引き継がれます。先頭の `@` はファイルのディレクティブであることを表す記号で、部品の下限はファイルのディレクティブではありません。[バージョンとエディション](/ja/spec/versioning-editions/)を参照してください。本体の中で `@` が始めるのは `@edition` ガードだけで、これもディレクティブではありません。ガードは、その下の行を残すビルドのエディションを選びます ([§10.7](/ja/spec/versioning-editions/#edition-ガードはエスケープハッチを囲む))。

## 5.4 セレクタ

壁のセレクタは `front` (+z)、`back`、`left`、`right` です。`offset` は壁に沿った位置で、`y` は床 (`y = 0`) から測ります。内側の面には接頭辞を付けます (`inside.front`)。ブロック、ブロックエンティティ、エンティティは、どれも同じセレクタの文法を使います。

**`offset` の原点。** `offset=0` は、その壁を外から見たときの左端です。`front` と `back` の壁は `x` の小さい側を基準にします。`front` は +z 側から見た向きで、`back` は x 方向に鏡映するので、`sym=true` の開口は建物のどちら側から見ても対称に見えます。`left` と `right` の壁は `z` の小さい側を基準にし、同じように鏡映します。

**`anchor=` による窓の位置。** `offset=` と `y=` は窓の 1 つのセルを置き、`anchor=` は、壁の外から見てどのセルかを名指しします。

| 位置 | 窓の最初の列からの列 | 最も低い段からの段 |
|---|---|---|
| `bottom_left`、`middle_left`、`top_left` | `0` | `0`、`size_h / 2`、`size_h - 1` |
| `bottom_center`、`center`、`top_center` | `size_w / 2` | `0`、`size_h / 2`、`size_h - 1` |
| `bottom_right`、`middle_right`、`top_right` | `size_w - 1` | `0`、`size_h / 2`、`size_h - 1` |

3 つの段は、最初の列に挙げた位置の順に対応します。たとえば `top_center` は列 `size_w / 2`、段 `size_h - 1` です。割り算は切り捨てなので、幅や高さが偶数なら中央は真ん中の 2 つのセルのうち後ろの方になります。偶数の長さの壁で `at=center` が選ぶ列と同じです。`anchor=` のない窓は `bottom_left`、つまり最初の列と最も低い段で置きます。`anchor=bottom_center offset=4 size=3x3` は、`anchor=` のない `offset=3` と同じく、列 `3` から `5` を切り抜きます。ほかの値は `E_INVALID_MEMBER` です。窓の最初の列を壁の左端より前に、または最も低い段を struct か `level` の基準の段より下に置くアンカーも、`E_INVALID_MEMBER` です。以下の `offset` は窓の最初の列を指します。`anchor=` がそれより後ろの列を名指ししない限り `offset=` そのもので、`repeat=` の連なりもこの列から進みます ([エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約))。

`sym=true` は、開口を壁の中点で鏡映します (`mirror_offset = wall_length - offset - size_w`)。鏡映した開口が元の矩形と重なる場合は `W_DEFERRED_MEMBER` で拒否し、元の側だけを描きます。壁の中点に対して対称に置いた窓 (`2 * offset + size_w = wall_length`) の鏡映もこれに当たり、元の矩形とぴったり重なります。一方、鏡映が元の矩形に接するだけの場合、つまり元の最後の列の次の列から始まる場合 (`2 * (offset + size_w) = wall_length`) や、元の最初の列の前の列で終わる場合 (`2 * offset = wall_length`) は、元の矩形とセルを共有しないので、拒否も報告もしません。両方が描かれ、窓の 2 倍の幅の 1 つの開口に見えます。

`sym=` には裸の `true` か `false` を書き、`sym=` のない窓は鏡映しません。それ以外の値 (`sym=yes`、`sym="true"`、`sym=1`) は読み取れない値として扱います。窓は鏡映なしで描き、その値は `W_IGNORED_ARGUMENT` として報告します ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。ただし、`repeat=` が 1 より大きい窓は例外です。連続する窓の鏡映は将来の拡張のために予約しているので、`sym=true` の連続はまだ切り抜かず、`W_DEFERRED_MEMBER` として報告します。読み取れない `sym=` もそこでは `false` とは読まず、その窓も切り抜かずに、`W_IGNORED_ARGUMENT` とあわせて `W_DEFERRED_MEMBER` として報告します。

**ドアがどの列に立つか。** ドアを壁のどの列に置くかは、`at=` の名前付きの位置か `offset=N` で決まります。名前付きの位置は次の 3 つです。

| 位置 | 列 |
|---|---|
| `at=center` | `u = floor(wall_length / 2)`。長さが奇数の壁には中心が 1 つあり、偶数の壁では中点の右側の列を選びます。 |
| `at=left` | 壁の座標軸の原点 `u = 0`。 |
| `at=right` | 反対側の角 `u = wall_length - 1`。 |

`offset=N` の数え方は窓の `offset=` と同じで、外から見た壁の左端を 0 とします。数値が指すのは壁の角と角の間の列 `1 … wall_length - 2` です。角の列は隣の壁と接する場所です。そこにドアを立てるのは `at=left` と `at=right` なので、`offset=` が 0 や `wall_length - 1` なら拒否し、`wall_length` 以上も拒否します。長さが 3 未満の壁には、角と角の間の列がありません。`at=` が取るのは名前付きの位置だけなので、`at=3` は拒否します。診断では、列 3 が角と角の間にあれば `offset=3` と、角なら `at=left` か `at=right` と書くよう案内し、どちらでもなければ `offset=` が取る列を示します。

ドアは列を 1 回だけ指定します。どちらのキーもないドア、両方を書いたドア、どの位置も指さない `at=` を書いたドア、角と角の間の列ではない `offset=` を書いたドアは `E_INVALID_MEMBER` になり、何も切り抜きません。ドアと、このドアにつながる `connect` の通路 ([§9.3.5](/ja/spec/components-editing-sites#935-ポートと-connect)) は、どちらもこの同じ列を使います。

**ドアがどの段を開けるか。** `level y=N` の下にあるドアは、その level の基準面の 1 つ上、段 `N + 1` から開け、2 段の高さで立ちます。ドアのブロックが、その段と 1 つ上の段を占めるからです ([ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する))。2 段はどちらも、石積みの 1 つの層の中になければなりません (MUST)。書かれたとおりの壁が 2 段を 1 つの層に収めないドアは `E_INVALID_MEMBER` になり、何も切り抜きません。同じ本体の `window` が受けるのと同じ指摘です。1 段だけの層の下にあるドアもこれにあたります。その上の段は屋根のもの、あるいは何もない段だからです。何も塗らない `walls` の層にあるドアや、配置されない `level` の下の `walls` の脇にあるドアは、代わりに `W_DEFERRED_MEMBER` になります。直すべきなのはその `walls` かその `level` だからです (`walls` がどの層を描くかは [§9.3.5](/ja/spec/components-editing-sites#935-ポートと-connect) で定めています)。

**ドアを何で組むか。** ドアの `mat_slot=` はドアのブロックを指し、`mat_slot=` のないドアはレジストリパックの `@door.default` で組み上げます ([マテリアルとテーマ §7.2](/ja/spec/materials-themes/#tier-1-のトークン))。ブロックはドア、つまり ID が `_door` で終わるブロックでなければなりません (MUST)。それ以外は、階段の系統の外を割り当てた傾斜屋根と同じく `E_INCOMPATIBLE_MATERIAL` になり ([Lint](/ja/spec/lint/))、ドアはエラーとあわせて `@door.default` で組み上げます。

## 5.5 ID、クラス、アドレス

**変更の余地あり。** アドレスでメンバーを選ぶ `edit` のパッチ DSL は、まだ組み上げられません ([互換性ティア](/ja/spec/compatibility/#変更の余地あり))。現時点では、トップレベルに `edit` を書くと `E_PARSE` になります。

重要なメンバーは `id=` を宣言でき (MAY)、`class=` はメンバーをグループにまとめます。さらに `struct` や `def` の本体のメンバーには、どれにも **アドレス** が付きます。アドレスは、メンバーが立つ位置 (親・ロール・side・level・offset) と行に書いたものからコンパイラが導くもので、行を書いた順番からは導きません ([コンポーネント・編集・複数建築 §9.2](/ja/spec/components-editing-sites/#92-編集モデル))。

アドレスは、本体からメンバーまでの段ごとに 1 つのセグメントを、外側から順に `.` でつないだものです。`window@front[0]`、`level` の下の窓なら `level[1].window@front[0]` のようになります。セグメントは `ROLE@SIDE[N]` の形です。

- `ROLE` はメンバーのキーワードです。
- `@SIDE` は行が指す壁を、書いたとおりに表します。`side=` があればそれ (`door@front[0]`)、なければドットを含む `at=` です (`chest@inside.back[0]`、`button@front.outside[0]`)。開口の上に渡す `beam` も `at=` を書いたとおりに表し、壁の代わりに開口の `id=` が入ります (`beam@entry.top[0]`)。壁を指さない行には `@SIDE` がありません (`walls[0]`、`level[1]`)。
- `N` は、同じ親の下で `ROLE` と `@SIDE` が同じメンバーの中での番号で、0 から数えます。並びは立つ位置の順です。
  1. まず壁に沿った位置です。`offset=`、なければ `at=` のドアのアンカーが、行が指す壁の上で指す列です ([§5.4](#54-セレクタ))。壁の長さは、`front` と `back` なら `size=` の `W`、`left` と `right` なら `H` です。どちらも書かない行と、`at=` が壁やセルを指す行は 0 に立ちます。窓は書かれたとおりの `offset=` で数えます。`anchor=` があれば、それは最初の列ではなく、アンカーが指すセルの列です。
  2. 次に高さ、つまり `y=` です。書かなければ 0 なので、`level` は低いものから数えます。窓の `y=` も書かれたとおりに数えます。
  3. 次に座標の `at=X,Y,Z` が指すセル、なければ `from=` と `to=` が張る箱です。どちらの端を先に書いても同じで、低い角、次に高い角の順に、それぞれ `y`、`z`、`x` の順で比べます。どれも書かない行は `0,0,0` に立ちます。

  これらの段で整数として読めない値は、どの数値よりも後に並びます。別の種類の値を書いた `offset=`、`y=`、`from=`、`to=`、ドアのアンカーでも壁でもセルでもない `at=` (たとえば [§5.4](#54-セレクタ) が予約している数値)、測る壁の長さがない `center` と `right` がこれにあたります。長さがないのは、`front`、`back`、`left`、`right` のどれも指さない行と、`size=` のない `def` の行です。

  同じ位置に立つメンバーどうしは、行に書いたもののうち、`id=`、`class=`、`[selector]` 以外で並べます。まず `key=value` の組を比べます。キーの順に並べ、組ごとにキー、次に値を比べます。次に、書いた順の裸の値、`->` の後の値、行を囲む `@edition` ガードのエディション、最後に、その下にあってアドレスを持つメンバーを比べます。下のメンバーは、本体ごとにキーワード、次に `@SIDE` (壁を指さない行が先) の順に並べ、その後はこのリストの順で並べてから、1 つずつ比べます。どの段でも、先に尽きた行、`->` のない行、ガードのない行が先に並びます。キー、値、エディションは Unicode のコードポイント順にテキストとして比べます。値の綴りは 1 通りに決めます。整数は 10 進の数字、小数は整数部の先頭の 0 と小数部の末尾の 0 を除き、`.` の後に何も残らなければ `.` も除いたもの、文字列は二重引用符で囲んだもの、トークンは `@` を付け、ブロックステートのリテラルがあれば空白を除いたもの、リストは要素を `, ` でつないで `[` と `]` で囲んだもの、`mat_slot=` はスロットの名前で、それ以外は書いたとおりです。この綴りで比べるので、`height=10` は `height=9` より前に、`frame="oak"` は `frame=oak` より前に並び、`scale=02.50` と `scale=2.5` は、`scale=2.0` と `scale=2` と同じく差がつきません。どの段でも差がつかないメンバーどうしは、行を書いた順のままです。

アドレスは `id=` の有無にかかわらず付くので、行に `id=`、`class=`、`[selector]` を足しても番号は変わりません。`@edition` ガードの下のメンバーは、ガードが置かれた本体のメンバーとして数えます。アクチュエータのパッチ (`door[id=front] opened_by=sig.x`) はどこにも立たず、セレクタが選ぶメンバーに作用するだけなので、アドレスがなく、番号も取りません。パッチの下の行にもアドレスはありません。ほかのキーワードの行に付いた `[selector]` はパッチにならず、その行はほかの行と同じように数えます。

行を並べ替えてもアドレスは変わりません。ただし、どの段でも差がつかないメンバーどうしは、行を入れ替えるとアドレスも入れ替わります。ロールの違うメンバー、別の壁のメンバー、別の親の下のメンバー、壁のもっと先に立つメンバーを足しても、アドレスは変わりません。壁の上で同じロールのメンバーより手前にメンバーを足すと、その後ろの番号がずれます。そうした変更の後も編集が指し続けなければならないメンバーには、`id=` を付けます。

`cairn parse --format json` はメンバーの行ごとにアドレスを出力し、`cairn lower` の ASCII の出力は、セルを組み上げたメンバーとエンティティを置いたメンバーのアドレスを一覧にします。そうしたメンバーの `resolved_state` の記録は、struct の `circuit` のものも含め、アドレスを持ちます ([ブロックステート §6.2](/ja/spec/blockstate/#62-intent_state-と-resolved_state))。そうしたアドレスが `resolved_ir_hash` に入ります ([バージョンとエディション §10.6](/ja/spec/versioning-editions/#106-来歴-provenance-とロック))。

`site` の本体の行にはアドレスがありません。代わりに `place` 行は `id=` が必須で、省略すると `E_INCOMPLETE_PLACE` になります。アドレスは、そのメンバーがある本体の外では何も指しません。一方、`place` の `id=` は `east_of=` と `connect` が参照する名前で、その `.nbt` を書き出すときの名前でもあります。コンパイラが勝手に名前を作ると、作者が書いてもおらず、参照もできない名前になってしまいます。

## 5.6 キーワード一覧

トップレベル項目とメンバーのキーワード、およびメンバーの行が受け付ける `key=` を、それぞれ 1 行で説明し、規定している節を添えます。規範になるのはその節で、この一覧はその索引です。``cairn docs spec/syntax "`door`"`` で 1 項目をその下に入れ子になったキーとともに表示でき、言語サーバーはホバーでその項目自身の行を表示します。

**トップレベル項目。**

- **`struct`。** 1 つの建物です。行で宣言した `size=WxH` のフットプリントの上に、本体から組み上げます。[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) を参照してください。
- **`def`。** スロットを持つ再利用できる建物で、`site` の `place` 行が配置します。[コンポーネント・編集・複数建築 §9.1](/ja/spec/components-editing-sites/#91-コンポーネントを定義する-def) を参照してください。
- **`theme`。** スロット名ごとにマテリアルトークンを割り当てます。[マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット) を参照してください。
- **`site`。** 複数の `def` を並べて配置し、その間に通路を敷きます。[コンポーネント・編集・複数建築 §9.3](/ja/spec/components-editing-sites/#93-site-による複数建築) を参照してください。

**どのメンバーも受け付けるキー。**

- **`id=`。** メンバーの名前です。セレクタ、ポート、`connect` 行がこの名前で参照します。[§5.5](#55-idクラスアドレス) を参照してください。
- **`class=`。** メンバーが属するグループです。テーマのセレクタ行でこのグループを選べます。[§5.5](#55-idクラスアドレス) を参照してください。
- **`mat_slot=`。** メンバーを組み上げるマテリアルのスロットです。[マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット) を参照してください。

**メンバー。**

- **`floor`。** 基準面の上に、フットプリント全体へマテリアルを 1 層敷きます。[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) を参照してください。
- **`walls`。** フットプリントの外周を、床の 1 段上からマテリアルで囲みます。[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) を参照してください。
  - **`height=`。** 壁が立ち上がる段数です。
- **`fill`。** 箱の範囲をマテリアルで満たすか、水を入れられるブロックを置き終えてから水を注ぎます。[ブロックステート §6.3](/ja/spec/blockstate/#63-waterlogged) を参照してください。
  - **`from=`。** 箱の一方の角で、座標の組です。
  - **`to=`。** 箱の反対側の角で、座標の組です。
  - **`fluid=`。** マテリアルの代わりに注ぐ液体で、`water` です。
  - **`kind=`。** 注ぐ水の種類で、`source` です。
- **`door`。** 壁に切り込む、高さ 2 段のドアです。[§5.4](#54-セレクタ) を参照してください。
  - **`side=`。** 切り込む壁で、`front`、`back`、`left`、`right` のいずれかです。
  - **`at=`。** 壁のどこに切り込むかで、`center`、`left`、`right` のいずれかです。
  - **`offset=`。** `at=` の代わりに書く、切り込む列です。壁の両端の角の間の列で、外から見た壁の左端から数えます。
  - **`opened_by=`。** ドアを開く信号です。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`hinge=`。** 蝶番の側で、`left` か `right` です。導出した側の代わりに使います。
  - **`open=`。** 開いた状態 `true` で組み上げるか、閉じた状態 `false` で組み上げるかです。
- **`window`。** 壁に切り込む開口部です。`mat_slot=` のマテリアルで埋め、それがなければ開けたままにします。[§5.4](#54-セレクタ) を参照してください。
  - **`side=`。** 切り込む壁で、`front`、`back`、`left`、`right` のいずれかです。
  - **`y=`。** `anchor=` が名指すセルの段で、床から数えます。`anchor=` がなければいちばん下の段です。
  - **`offset=`。** `anchor=` が名指すセルの壁に沿った列で、外から見た壁の左端から数えます。`anchor=` がなければ最初の列です。
  - **`size=`。** 幅と高さで、`WxH` と書きます。
  - **`sym=`。** `true` なら、壁の中点で鏡映した複製も切り込みます。
  - **`repeat=`。** 壁に沿って切り込む窓の数で、最初の窓も数えます。
  - **`step=`。** 各窓が 1 つ前の窓から何列後に始まるかです。
  - **`shape=`。** 開口部の輪郭です。まだどのパスも読みません。[エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約) を参照してください。
  - **`anchor=`。** `offset=` と `y=` が置く窓のセルで、ないときは `bottom_left` です。[エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約) を参照してください。
- **`roof`。** 壁の上に、`kind=` が名指す形の屋根を架けます。[コンパイルモデル §4.3](/ja/spec/compilation/#43-切妻屋根のボクセル規則) を参照してください。
  - **`kind=`。** 屋根の形で、`gable`、`shed`、`hip`、`flat` のいずれかです。
  - **`overhang=`。** 屋根が四方で壁の外へ張り出す列数です。
  - **`slope_to=`。** `shed` の屋根が高くなっていく側の壁です。
  - **`footprint=`。** 屋根が覆うセルで、struct の `size=` の範囲を表す `struct` だけを取ります。[エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約) を参照してください。
  - **`bounds=`。** 軒の出が本体に及ぼす扱いで、本体のブロック配列を広げる `expand` だけを取ります。[エンティティ §8.2](/ja/spec/entities/#82-アンカーの規約) を参照してください。
- **`stair`。** 軒です。1 つの壁の外側、軒の出の範囲に階段を帯状に並べます。[コンパイルモデル §4.3](/ja/spec/compilation/#43-切妻屋根のボクセル規則) を参照してください。
  - **`kind=`。** 階段の種類で、`stairs` です。
  - **`side=`。** 帯を外側に並べる壁です。
  - **`half=`。** 階段が収まるセルの半分で、`top` か `bottom` です。
  - **`facing=`。** 階段の向きで、壁から離れる `out` か壁に向かう `in` です。
  - **`shape=`。** 階段の形で、`straight`、`inner_left`、`inner_right`、`outer_left`、`outer_right` のいずれかです。
  - **`y=`。** 帯がある段です。
  - **`waterlogged=`。** 階段のステートに書き込む `true` か `false`、または水の `fill` に決めさせる `auto` です。[ブロックステート §6.3](/ja/spec/blockstate/#63-waterlogged) を参照してください。
- **`beam`。** 壁のいちばん上の段に沿って、または開口の上に横たえる柱状ブロックの列です。[ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する) を参照してください。
  - **`kind=`。** 梁の種類で、`pillar` です。
  - **`at=`。** 渡す場所で、その壁のいちばん上の段に沿う `<side>.top` か、その `id=` を持つ `door` か `window` の上に渡す `<id>.top` です。
  - **`axis=`。** ブロックを並べる軸で、`x`、`y`、`z` のいずれかです。壁に沿う軸の代わりに使います。
- **`level`。** 配下のメンバーをまとめ、そのすべてを基準面から `y=` 段上に持ち上げます。[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) を参照してください。
  - **`y=`。** メンバーを基準面から何段上に立てるかです。
- **`pressure_plate`。** 壁のそばに置く感圧板で、センサーです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
- **`lever`。** 壁に付けるレバーで、センサーです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
- **`button`。** 壁に付けるボタンで、センサーです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
- **`daylight`。** 壁のそばに置く日照センサーで、信号を出すセンサーです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
- **`observer`。** 壁のそばに置くオブザーバーで、センサーです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
  - **`facing=`。** 壁から離れる向きの代わりに向ける方向で、`in`、`out`、`left`、`right`、`up`、`down` のいずれかです。[ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する) を参照してください。
- **`lamp`。** 壁のそばに置くレッドストーンランプで、アクチュエーターです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
  - **`lit_by=`。** ランプを点ける信号です。
- **`piston`。** 壁のそばに置くピストンで、アクチュエーターです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
  - **`powered_by=`。** ピストンを動かす信号です。
  - **`facing=`。** 壁から離れる向きの代わりに押し出す方向で、`in`、`out`、`left`、`right`、`up`、`down` のいずれかです。
  - **`sticky=`。** `true` なら粘着ピストンです。
- **`dispenser`。** 壁のそばに置くディスペンサーで、アクチュエーターです。[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
  - **`fired_by=`。** ディスペンサーを作動させる信号です。
  - **`facing=`。** 壁から離れる向きの代わりに撃ち出す方向で、`in`、`out`、`left`、`right`、`up`、`down` のいずれかです。
- **`chest`。** 壁のそばに置くチェストで、隣にチェストがあれば対になります。[ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する) を参照してください。
  - **`at=`。** 壁とその面で、`inside.<side>` か `<side>.outside` です。
  - **`offset=`。** そばにある壁の列です。
  - **`y=`。** 置く段です。
  - **`facing=`。** 壁から離れる向きの代わりに向ける方向で、`in`、`out`、`left`、`right` のいずれかです。
  - **`size=`。** `single` なら、チェストを対にしません。
  - **`waterlogged=`。** チェストのステートに書き込む `true` か `false`、または水の `fill` に決めさせる `auto` です。[ブロックステート §6.3](/ja/spec/blockstate/#63-waterlogged) を参照してください。
