## 5.1 字句

1 行が 1 つのコマンドで、`#` から行末まではコメントです。行はコマンドのキーワードで始まり、**それ以降の引数はすべて `key=value` の形でなければなりません (MUST)**。コマンドが次の行以降に続いてよいのは、真理値表の波括弧の中だけです ([リテラルと区切り](#511-リテラルと区切り))。

```
window side=front mat_slot=glass offset=2 y=2 size=2x2 sym=true   # OK
window front G 2 2 2x2                                            # 禁止 (位置引数)
```

位置引数を使うと、引数の順番を覚えておく必要があります。LLM は順番を取り違えたり、引数を書き落としたりします。`mat_slot=` や `side=` のようなキーは、モデルの注意を向ける目印 (attention のアンカー) になり、生成を安定させます。キーに使うトークン以上の価値があります。

位置引数を読まない行に裸の値があると、`E_UNEXPECTED_POSITIONAL` になります。位置引数を読む形式は `connect FROM.PORT to TO.PORT` だけで、その形は代わりに `E_CONNECT_ARITY` が検査します。

パーサは、`key=`、`-> binding`、`[selector]` のどれでもないトークンを、すべて位置引数のリストに入れます。`=` を書き忘れた引数も、ここに入ります。`walls mat_slot=wall height 3` は、高さが低い `walls` になるのではなく、まったく作られません。

現時点で位置引数のリストを持つのは、メンバーの行 (`struct`、`def`、`site` の本体の行) だけです。`struct`、`def`、`site`、`theme` のヘッダ行、`theme` のルール、`logic` と `assert` の行はまだ持たないので、そこでの同じ書き落としは `E_PARSE` になり、パースはそこで止まります。`struct s size 3x3` は「expected `=`」で拒否されます。

### 5.1.1 リテラルと区切り

**変更の余地あり。** ほかの章が書く小数 (`scale=1.5`)、座標の組 (`at=4,3,2`)、`nbt={...}` の値は、まだパースできません ([互換性ティア](/ja/spec/compatibility/#変更の余地あり))。

`key=` の値は `-` で始まらないので、負の数はパースできません。`offset=-1` は `E_PARSE` です。現時点のパーサは、数値を 10 進の数字の並びとしてしか読みません。上限は 2^63 − 1 で、`assert` の `within` の上限だけは 2^32 − 1 です。`scale=1.5` ([エンティティ](/ja/spec/entities/)) のような小数も、パーサが読むようになるまでは `E_PARSE` になります。

サイズのリテラルは、0 でない寸法をちょうど 2 つ持つ `WxH` です。`2x2x9` や `2x2y` のように 2 つ目の寸法より先に続く並びは、サイズとその後ろの何かとして読むのではなく、そのリテラルの位置で拒否します。

カンマは構造ではなく、**省略できる区切り** です。`@intended_targets ["1.20.4", "1.21.4"]` と `@intended_targets ["1.20.4" "1.21.4"]` は同じ 2 つのバージョンを表し、`[side=front, y=2]` と `[side=front y=2]` も同じです。ただし、どこまで記号を許すかは 2 種類のリストで異なります。

- `[selector]` の属性リストは、カンマをどこで見つけても読み飛ばすので、`[side=front, , y=2]` もパースできます。
- 値のリストは、要素の間にカンマを 1 つまでしか読まず、`[a, , b]` は拒否します。

正規トークンには、`@oak_log[axis=x]` や `@oak_stairs[half=top, facing=north]` のように **ブロックステートのリテラル** を付けられます。`[` はトークンに接していなければなりません。空白の後の `[` は、トークンとは別の次の要素として読みます。値のリストでは、`[@a [b]]` はこれまでどおりトークンと入れ子のリストですが、`[@a[b]]` は `b` がプロパティではないので拒否します。リテラルの中の各組は `property=value` で、値は単語、数字の並び、`true` / `false` のいずれかです。これは Cairn のリストではなく Minecraft 自身のブロックステートの構文なので、2 つの組の間にはちょうど 1 つのカンマを書きます。空のリテラル、末尾のカンマや重なったカンマ、同じプロパティの 2 回目の指定は拒否します。`@floor.wood` のようなドットを含むトークンは抽象トークンです。ブロックを選ぶのはそのトークンを割り当てるテーマなので、リテラルは付けられず、これに接する `[` も、空白の後の `[` と同じく別の次の要素として読みます。

トークンに接する `[` をリテラルとして読んでも、ほかの読み方ならビルドできたはずのソースを拒否することにはなりません。`[` を別の次の要素として読むと、`mat_slot=@a[1]` は位置引数を読まないメンバーの行に裸の値を残すので `E_UNEXPECTED_POSITIONAL` に、`mat_slot=[@a[b]]` はラベルを書くべき場所にリストを置くので `E_TYPE_MISMATCH_LABEL` になるからです。

リテラルのプロパティと値は、まだターゲットに照らして検査していません。`E_STATE_DOMAIN` ([バージョンとエディション](/ja/spec/versioning-editions/)) は未実装なので、Java のビルドは `@oak_log[axis=q]` を書いたとおりに出力します。ただし、ビルドが読むリテラルには、トークンの位置にそれぞれ `W_STATE_LITERAL_UNCHECKED` ([Lint](/ja/spec/lint/)) が付くので、検査していないことは報告されます。

このリテラルを除くと、カンマが意味を持つのは `assert truth(...)` の入力リストだけです。そこではカンマが信号を区切り、その信号の数と行の幅を照合します。行には入力の信号 1 つにつき 1 文字 (`0`、`1`、`-` のいずれか) を書きます。`truth(a, b -> out)` の行は 2 文字幅になり、`{ 2->0 }` や `{ 0->0 }` は拒否します。

`-` は **don't-care** です。その入力がどちらの値でもよいという意味で、`0- -> 1` は `00->1` と `01->1` の 2 行を合わせたものを表します。これは独立した構文ではなく、行をまとめて書くための省略形なので、2 つの行が同じ入力の組を受け持つことはできません (下の表を参照)。

`-` と `->` は同じ文字を使うので、字句解析ではできる限り矢印として読みます。最後の入力が don't-care の行は、`11--> 0` か `11- -> 0` と書きます。どちらも同じ 3 文字幅の行です。空白はパターンの終わりを表すので、`0- 1 -> 1` は 3 文字幅の行ではなく、2 文字幅のパターンと余分な `1` になります。

行の**出力**にも `0`、`1`、`-` を書けますが、出力の `-` は意味が異なります。その行が受け持つ入力の組については、意図的に何も制約しないという意味です。`--0 -> -` は、3 つ目の入力が low であるどの組についても、表は何も主張しないことを表します。これで、作者が意図していない 4 つの出力を主張せずに `W_TRUTH_TABLE_PARTIAL` を解消できます。この時点で矢印はすでに読み終えているので、`-> -` と `->-` は同じ行です。すべての行の出力が `-` である表は何も制約しないので、行が 1 つもない表と同じく `E_TRUTH_TABLE_EMPTY` になります。

行を囲む表も、同じ考え方で読みます。

| 状況 | コード |
|---|---|
| 1 つの信号を 2 つ以上の入力として並べている | `E_TRUTH_TABLE_DUPLICATE_INPUT` (各信号を 1 回ずつにするまで、その表についてほかの指摘はしない) |
| 行が 1 つもない、または出力が `0` か `1` の行が 1 つもない | `E_TRUTH_TABLE_EMPTY` |
| 2 つの行が、同じ入力の組に異なる出力を割り当てている | `E_TRUTH_TABLE_CONFLICT` (後の行で報告) |
| 2 つの行が同じ入力の組を受け持ち、互いに矛盾していない | `W_TRUTH_TABLE_DUPLICATE_ROW` (後の行で報告) |
| 割り当てのない入力の組がある | `W_TRUTH_TABLE_PARTIAL` |

最後の 2 つが警告なのは、書いてある行は、書かれたとおりの意味をそのまま持つからです。入力が 4 つの表は 16 行になります。途中まで書いた作者を止める理由はありません。

波括弧の中では、表の行の前後、表の行を終える `;` の後、`}` の前のどこで改行してもかまいません。表は `assert` と同じ行に収めても、表の行ごとに行を分けてもかまいません。

```
assert truth(sig.a, sig.b, sig.enable -> sig.out) {
  001 -> 0
  011 -> 1
  101 -> 1
  111 -> 1
}
```

波括弧の中の行はインデントを持ちません。表の行と閉じる `}` はどの深さに置いてもよく、その間の空行とコメント行は読み飛ばします。ただし、表の行や `}` の前のタブは、コマンドの前のタブと同じく拒否します。表の行は 1 行に収めるものなので、パターン、`->`、出力の間で改行すると拒否します。`{` は `assert` と同じ行に置きます。`;` は同じ行にある直前の表の行を終えるものなので、`;` で始まる行は書けません。`}` が欠けた表は、最後の表の行の次に来るもの (次のコマンドなど) の位置で拒否します。次に何も来なければ、最後の表の行の行末で拒否します。

インデントは 1 段につきスペース 2 つで、一度に 1 段ずつしか深くできません。幅が 2 の倍数でない場合と、2 段以上いっぺんに深くした場合は別の誤りなので、別々に報告します。真理値表の波括弧の中の行はインデントを持たないので、そこではどちらの誤りも起こりません。

改行の前のスペースは行に含めないので、行末にスペースがあってもかまいません。スペースだけの行は空行として扱います。空行の先頭のスペースもほかの行と同じように数えますが、行ごと捨てるので、その幅はインデントにも誤りにもなりません。

ファイルの先頭にある UTF-8 の BOM は無視します。それ以外の位置にある BOM は、ただの余計な文字として扱います。

行の終わりは `\n`、`\r\n`、単独の `\r` のどれでもよく、3 つとも同じ改行として扱います。VS Code や Monaco と同じ規則なので、診断の行番号とカーソルのある行の番号は一致します。位置は常に誤っているテキストそのものを指すので、行末のエラーはその行の行末で報告し、次の行の 1 桁目で報告することはありません。

tree-sitter の文法は、2 つの点で既知の例外です。1 つ目に、そのランタイムは `\n` でしか行を進めないので、単独の `\r` だけで改行したファイルは、正しくパースできていても 1 つの長い行としてハイライトされます。2 つ目に、パーサが拒否する次の 6 つの形を受け付けます。寸法が 0 のサイズ (`0x3`)、3 つ目の寸法が続くサイズ (`2x2x9`)、単語が続くサイズ (`2x2y`)、2^63 − 1 を超える整数、幅が入力の数と合わない真理値表の行、同じプロパティを 2 回指定したブロックステートのリテラルです。どれも、その規則を tree-sitter では表せないためです。

## 5.2 ネスト

ネストは浅く保ちます (`struct` / `def` / `level` / `theme` / `site`)。ネストが深いほど、LLM の生成の誤りが増えるからです。(`room` はこの一覧にありません。まだ決まっていないので、今書くと `E_UNKNOWN_KEYWORD` になります。[未決事項](/ja/spec/open-issues/)を参照してください。)

本体の中でほかのメンバーをまとめられるのは `level y=N` だけで、それも `struct` か `def` の中に限ります。`site` の本体は `place` と `connect` の行を平らに並べたもので、まとめるための構文はありません。それ以外の場所でインデントした本体を書くと、黙って捨てるのではなく `E_UNSUPPORTED_NESTING` にします。その本体はブロックを生成せず、何も配置せず、通路も敷きません。

この規則はメンバーについてのものなので、メンバーを持つ本体にしか適用されません。`theme` の本体が持つのはルールです。ルールは素材を割り当てるだけで、本体を開かないので、その下にインデントした行はネストの診断ではなく構文エラーになります。ディレクティブの下にインデントした行も同じです。ディレクティブは 1 行で完結し、その下の行はどの構文にも属しません。

`y=N` がまとめられた各メンバーにとって何を意味するかは、[コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出) で定めています。

**本体がどのキーワードを受け付けるか** も、同じ区別に従います。`struct` / `def` の本体は 1 棟の建物の形を記述します (`floor`、`walls`、`door`、`window`、`roof`、`stair`、`level`、`pressure_plate`、`circuit`)。`site` の本体は配置を記述します (`place`、`connect`)。キーワードの表はグローバルなので、一方のキーワードをもう一方の本体に書いても、パースも分類も通ってしまい、そのうえでどこにも使われません。これが `E_MISPLACED_MEMBER` で、問題の行で 1 回だけ報告し、その下にインデントした行もまとめて捨てます。`level` は `struct` / `def` の本体のほかのメンバーをまとめますが、スコープ全体にわたって領域を確保する `circuit` 行はまとめません。`level` の下に書いた `circuit` 行もどこにも使われず、その行で `E_MISPLACED_MEMBER` になります ([レッドストーン §14.5](/ja/spec/redstone/#145-配置配線-place-and-route))。

`logic` と `assert` の行はメンバーではないので、この規則は適用されません。`logic` の行は、どちらの本体にあってもレッドストーンの合成が読みます。`assert` の行については、それ自身の形と、名指す信号を検査します。真理値表は `cairn check` が検査し ([リテラルと区切り](#511-リテラルと区切り))、名指す信号はレッドストーンの合成が解決します (`E_LOGIC_UNBOUND_SIGNAL`)。組み上がった回路に照らして `assert` を検証するものは、まだありません。

**トップレベルの名前は、種類ごとに別々のスコープを持ちます。** `theme` / `def` / `struct` / `site` はそれぞれ別の名前空間なので、同じ名前を種類ごとに 1 回ずつ使えます。同じ種類で同じ名前を 2 回宣言すると `E_DUPLICATE_ITEM` です。`theme` / `def` / `struct` では名前で割り当てが決まるので、最初の宣言だけが使われます。エラーにしなければ、2 回目は何の知らせもなく消えてしまいます。同じ名前の `site` ブロック 2 つは、代わりに統合され、1 つの `site::NAME::` 名前空間を共有します。しかし `east_of=` はブロックをまたいで参照できないので、統合は中途半端で、やはりエラーにします。

## 5.3 ヘッダ

メタデータは、意味を記述する本体ではなく、ヘッダに書けます (MAY)。

```
@cairn 2026.06                           # このファイルが対象とする Cairn 言語のバージョン
@requires version>=1.20                  # Minecraft のターゲットに求める機能の下限
@intended_targets ["1.20.4","1.21.4"]    # ヒントであり、検証の記録ではない
```

**`@cairn`** は Cairn 言語そのもののバージョンで、Minecraft に関する 2 つのヘッダとは別の軸です。書くかどうかは任意で、将来のコンパイラが正しくパースし、適切に警告できるようにするための来歴 (provenance) として存在します。どのパスもこの値で処理を分けませんが、値は読みます。形式は `YYYY.M` か `YYYY.M.PATCH` で、年は 4 桁、月は `1 … 12` です。月の先頭のゼロは受け付けるので、`2026.06` と `2026.6` は同じバージョンです。それ以外の形は `W_INVALID_CAIRN_VERSION` に、読んでいるコンパイラより新しいバージョンは `W_FUTURE_CAIRN_VERSION` になります。後のコンパイラが読めない来歴では、このヘッダの役目を果たせないからです。

**`@requires`** は、ターゲットに求める機能の下限です。式は、省略できるエディション、主語の `version`、演算子の `>=`、バージョンのラベルからなります。演算子の前後の空白は省略できるので、`version>=1.21` と `version >= 1.21` は同じ要求です。一方、エディションの後には空白が必要で、`javaversion>=1.21` は `E_INVALID_REQUIRES` になります。演算子が `>=` だけなのは、もっとも厳しいものにまとめて合成できる制約が下限だけだからです。それ以外の式は、何も宣言しない行として黙って残すのではなく、`E_INVALID_REQUIRES` にします。消えてしまう下限は、下限がないよりも悪い結果になります。読む人はそれが効いていると信じてしまうからです。

```
@requires version>=1.21                  # ビルドするエディションに対する下限
@requires java version>=1.21.4           # Java の番号体系での下限。Bedrock のビルドでは効かない
@requires bedrock version>=1.21.40
```

エディションを書けるのは、Java のリリースが `1.20.4 / 1.21 / 1.21.4`、Bedrock のリリースが `1.21.0 / 1.21.40 / 1.21.60` のように進むからです。`1.21.4` は Java の最新リリースで、Bedrock のどのリリースも指しません。ラベルは、ドットで区切った要素の並びです。各要素は数字で始まり、英字と数字だけからなります。その後ろに、`-` と、ドットで区切った英字と数字からなるプレリリースタグを続けてもかまいません。`1.21.4`、`1.21.4-rc1`、`24w14a` はどれもラベルです。そのうちどれを *ターゲットのエディション* が順序付けられるかは構文の問題ではないので、ここでは扱いません。[バージョンとエディション](/ja/spec/versioning-editions/)を参照してください。

**`@intended_targets`** は、ファイルをどの Minecraft のバージョン向けに設計したかを示します。検証済みであるという主張ではありません。検証の記録はロックにしかありません。

ヒントであっても、同じファイルの下限とは照らし合わせます。`@intended_targets` に挙げたバージョンのうち、ターゲットのエディションでビルドできるものを、`@requires` がすべて拒否するファイルがあるとします。このファイルは、誰かがその意図に従って動いた瞬間にコンパイラが拒否するような意図を表明していることになります。これが `E_INTENDED_TARGET_CAP` です。一部だけが下限を下回るリストは `W_INTENDED_TARGET_CAP`、ターゲットのエディションではそもそもビルドできないバージョンは `W_INTENDED_TARGET_UNSUPPORTED` になります。[バージョンとエディション §10.4](/ja/spec/versioning-editions/#ヒントは下限と突き合わせる) を参照してください。

`@cairn` と `@intended_targets` は 1 つのモジュールに 1 回までで、2 回目は `E_DUPLICATE_HEADER` です。`@requires` は例外です。下限は合成されるので、繰り返すと制約を置き換えるのではなく、制約が追加されます。

`def` と `theme` は、同じ式を本体の行として持てます。その場合は `@` を付けずに `requires` と書きます。これはファイルではなくその部品に対する下限で、その部品を実体化するすべてのビルドに引き継がれます。先頭の `@` はファイルのディレクティブであることを表す記号で、部品の下限はファイルのディレクティブではありません。[バージョンとエディション](/ja/spec/versioning-editions/)を参照してください。

## 5.4 セレクタ

壁のセレクタは `front` (+z)、`back`、`left`、`right` です。`offset` は壁に沿った位置で、`y` は床 (`y = 0`) から測ります。内側の面には接頭辞を付けます (`inside.front`)。ブロック、ブロックエンティティ、エンティティは、どれも同じセレクタの文法を使います。

**`offset` の原点。** `offset=0` は、その壁を外から見たときの左端です。`front` と `back` の壁は `x` の小さい側を基準にします。`front` は +z 側から見た向きで、`back` は x 方向に鏡映するので、`sym=true` の開口は建物のどちら側から見ても対称に見えます。`left` と `right` の壁は `z` の小さい側を基準にし、同じように鏡映します。

`sym=true` は、開口を壁の中点で鏡映します (`mirror_offset = wall_length - offset - size_w`)。鏡映した開口が元の矩形と重なる場合は `W_DEFERRED_MEMBER` で拒否し、元の側だけを描きます。壁の中点に対して対称に置いた窓 (`2 * offset + size_w = wall_length`) の鏡映もこれに当たり、元の矩形とぴったり重なります。一方、鏡映が元の矩形に接するだけの場合、つまり元の最後の列の次の列から始まる場合 (`2 * (offset + size_w) = wall_length`) や、元の最初の列の前の列で終わる場合 (`2 * offset = wall_length`) は、元の矩形とセルを共有しないので、拒否も報告もしません。両方が描かれ、窓の 2 倍の幅の 1 つの開口に見えます。

`sym=` には裸の `true` か `false` を書き、`sym=` のない窓は鏡映しません。それ以外の値 (`sym=yes`、`sym="true"`、`sym=1`) は読み取れない値として扱います。窓は鏡映なしで描き、その値は `W_IGNORED_ARGUMENT` として報告します ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。ただし、`repeat=` が 1 より大きい窓は例外です。連続する窓の鏡映は将来の拡張のために予約しているので、`sym=true` の連続はまだ切り抜かず、`W_DEFERRED_MEMBER` として報告します。読み取れない `sym=` もそこでは `false` とは読まず、その窓も切り抜かずに、`W_IGNORED_ARGUMENT` とあわせて `W_DEFERRED_MEMBER` として報告します。

**`at=` によるドアの位置。** ドアを壁のどの列に置くかは、3 つの名前付きの位置で決まります。

| 位置 | 列 |
|---|---|
| `at=center` | `u = floor(wall_length / 2)`。長さが奇数の壁には中心が 1 つあり、偶数の壁では中点の右側の列を選びます。 |
| `at=left` | 壁の座標軸の原点 `u = 0`。 |
| `at=right` | 反対側の角 `u = wall_length - 1`。 |

開口の切り抜きと、このドアにつながる `connect` の通路 ([§9.3.5](/ja/spec/components-editing-sites#935-ポートと-connect)) は、どちらもこの同じ列を使います。数値のオフセット (`at=N`) は、将来の拡張のために予約しています。

**ドアがどの段を開けるか。** `level y=N` の下にあるドアは、その level の基準面の 1 つ上、段 `N + 1` から開けます。ドアは戸口に必要な 2 段を開けますが、その段から数えて壁の層に 1 段しか残っていなければ、1 段で止めます。たとえば、1 段だけの層の下にあるドアは、屋根を切り抜かずに 1 段だけ開けます。開け始める段は、石積みの層の中になければなりません (MUST)。届かない壁に対して書いたドアは `W_DEFERRED_MEMBER` になり、何も切り抜きません。同じ本体の `window` が受けるのと同じ指摘です (`walls` がどの層を描くかは [§9.3.5](/ja/spec/components-editing-sites#935-ポートと-connect) で定めています)。

## 5.5 ID、クラス、アドレス

**変更の余地あり。** `id=` のないメンバーにコンパイラが与えるアドレスと、それを使う `edit` のパッチ DSL は、まだ組み上げられません ([互換性ティア](/ja/spec/compatibility/#変更の余地あり))。現時点では、そうしたメンバーにはアドレスがなく、トップレベルに `edit` を書くと `E_PARSE` になります。

重要なメンバーは `id=` を宣言でき (MAY)、`class=` はメンバーをグループにまとめます。`id=` を持たないメンバーには、親・ロール・side・level・offset から導いた、意味に基づく安定したアドレスをコンパイラが割り当てます ([コンポーネント・編集・複数建築 §9.2](/ja/spec/components-editing-sites/#92-編集モデル))。

`place` 行は例外で、`id=` が必須です。省略すると `E_INCOMPLETE_PLACE` になります。自動で割り当てたアドレスは、そのメンバーがある本体の外では何も指しません。一方、`place` の `id=` は `east_of=` と `connect` が参照する名前で、その `.nbt` を書き出すときの名前でもあります。コンパイラが勝手に名前を作ると、作者が書いてもおらず、参照もできない名前になってしまいます。
