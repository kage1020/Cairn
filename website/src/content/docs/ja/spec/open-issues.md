## 15.1 実装時に決めること

**来歴 (provenance) をどこに置くか。** `.crn` のヘッダか、ロックか。これは決まりました。`.crn` が持つのは、ヒントである `@intended_targets` と、書いたときの言語のバージョンを示す `@cairn` だけで、`verified` のような記録はコンパイラがロックに書きます ([バージョンとエディション §10.6](/ja/spec/versioning-editions/#106-来歴-provenance-とロック))。

**座標系。** 角を原点とし `front = +z` とする今の規約を続けるか、中心を原点にする、入口を基準に向きを決める、といった仕組みに移るか。これは決まりました。ビルドの原点はその範囲の低い側の角で、`y` は床から上へ増え、`front` / `back` / `left` / `right` はそれぞれ `+z` / `-z` / `-x` / `+x` を向きます ([構文 §5.4](/ja/spec/syntax/#54-セレクタ)、[コンポーネント・編集・複数建築 §9.3.1](/ja/spec/components-editing-sites/#931-座標規約))。ストラクチャファイルは低い側の角から置かれるので、この原点はファイルの原点そのものです。辺の長さが偶数だと、原点にできる中心のボクセルがありません。建物はワールドに置くときに回すもので、入口は `front` がすでに名指ししているので、入口を基準にした座標系を足しても得るものがありません。階ごとにローカルな `y=0` は `level y=N` が提供します ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出))。座標の組 (`from=1,1,1`、`at=4,3,2`) は、仕様に入るときにこの座標系で読みます。

**逆変換で使う IR の型。** 情報の一部を欠いた状態も表せる単一の IR にするか、Intent IR と Raw Geometry IR を別の型にするか。暫定の方針は、「block-array の層は共有し、その上のメンバーの層で型を分ける」です ([アーキテクチャ](/ja/spec/architecture/))。

**旧形式の `.schematic`** (1.13 より前) は、v1 では扱いません。数値 ID の対応付けは、将来オプションとして検討する余地があります。

## 15.2 まだ検討していない話題

**プリミティブへの昇格。** 柱やアーチなどを意味プリミティブに昇格させるか。判断は [評価フレームワーク](/ja/spec/evaluation/) の実験データに基づいて行います。

**内装。** `inside.front` という接頭辞で足りるのか、より上位の `room` という概念が必要なのか。また、家具を `def` のライブラリでまかなえるのか。

## 15.3 言語の進化の方針

Cairn の進化に伴う破壊的変更をどう扱うかは、まだ決めていません。選択肢は、Rust のような「エディション」の仕組み (年単位のオプトイン) か、リリースごとに CHANGELOG で告知するだけにするかです。ただし Cairn では「エディション」がすでに Java / Bedrock を指しているので、前者を採るなら別の用語が必要です。当面は後者、つまり CalVer と `@cairn` による来歴の記録で足ります。
