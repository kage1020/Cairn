---
title: "14. レッドストーン (論理回路)"
---

Cairn はレッドストーンを **論理レベル** で記述します。信号のグラフを宣言すると、コンパイラが実際のダスト、リピーター、トーチ、コンパレーターを合成し、配置し、配線して、ボクセルに落とし込みます。

P1 の効果が最も大きいのがここです。信号の減衰、クロストーク、遅延の計算は、AI がボクセル建築以上に苦手とする物理ですが、どれも論理記述から決定的に導けます。

論理層で第一級に扱う対象は、挙動ではなく **信号の依存グラフ** です。時間は言語のコアには持ちません ([§14.4](#144-時間モデル))。

## 14.1 2 つの層と v1 の範囲

- **Tier 0: 物理配置。** `repeater facing=north delay=2` のように部品を置き、ブロックステートは導出されます。挙動はモデル化しません ([ブロックステート](/ja/spec/blockstate/))。
- **Tier 1: 論理。** この章で扱います。信号グラフを宣言すると、コンパイラが合成、配置、配線を経てボクセルにします。

新しいキーワードは `logic` / `circuit` / `assert` の 3 つだけです。論理プリミティブは組み込みの `def` ライブラリとして提供し、語彙は小さく閉じたまま保ちます (P3)。

Verilog で言えば、v1 が許すのは `assign` に相当するものだけで、クロック付きの代入は許しません。

| | 範囲 |
|---|---|
| **組み合わせ回路** | `and` / `or` / `not` / `xor` / `nand` / `nor` / `mux` |
| **厳選した順序マクロ** | `latch` / `pulse` / `delay` / `edge_rising` / `edge_falling` / `counter` |
| **対象外** (→ Tier 0 か `raw`) | `always` / `process` / `state` / `case` / FSM / クロック付きの代入 / CPU |

## 14.2 信号バインディング

センサーが信号を発し、アクチュエーターがそれを受け取ります。どちらも、先行するフェーズで配置される物理メンバーです ([コンポーネント・編集・複数建築](/ja/spec/components-editing-sites/))。

```
# センサー → 信号
lever      id=sw   side=front offset=2 y=1 -> sig.power
button     id=bt   side=front               -> sig.ring
daylight   id=dl   at=..                     -> sig.day
observer   id=ob   at=.. facing=down         -> sig.tick
pressure_plate id=pp at=front.outside offset=0 y=0 -> sig.step

# アクチュエーター ← 信号
lamp       id=l1   at=..  lit_by=sig.lamps
piston     id=p1   at=..  powered_by=sig.mem facing=up sticky=true
door       id=d1   ..     opened_by=sig.power
dispenser  id=ds   at=..  fired_by=sig.pulse facing=south
```

この対応は規範です。末尾の `-> sig.X` はセンサーのもので、アクチュエーターの各キーは、それを読む 1 種類のコンポーネントのものです。ほかの場所に書かれたバインディングは回路を何も記述しておらず、受け付けると、コンポーネントのないポートがネットリストに載ってしまいます。

これを報告するコードは 2 つあり、どちらになるかは、判定に何が必要かで決まります。センサーでないメンバーに付いた末尾の `->` は `E_MISPLACED_BINDING` です。あるキーワードが信号を発せるかどうかはメンバー行についての事実なので、`check` が判定し、どのコマンドでも報告します。それを読まないコンポーネントに付いたアクチュエーターのキーは `E_LOGIC_MISPLACED_BINDING` で、synth パイプラインが出します。

**上の例のうち、現在受け付けるのは `door` と `pressure_plate` だけです。** `lit_by=` / `powered_by=` / `fired_by=` にはまだそれを読むコンポーネントがなく、どこに書いても拒否されます。

**`at=inside.<side>` のプレートを置ける位置。** プレートは `offset=` の位置にある壁のセルを基準に、そこから 1 ボクセル内側に置かれます。そのボクセルは、壁のリング (敷地の最も外側の行と列で、`walls` が各段を塗る場所) より厳密に内側でなければなりません。つまり `offset` は 1 から「壁の長さ − 2」までで (長さは `front` と `back` では `size.w`、`left` と `right` では `size.h`)、そもそも内側があるためには、両方の軸で `size` が 3 以上必要です。リングは `walls` メンバーが塗るかどうかに関係なく敷地から決まり、この規則は床の段 `y = 0` を含むすべての `y` で成り立ちます。範囲外のプレートは置かれません。

**置けないプレート。** 自身の行の指定ではどのボクセルにも置けないプレートは `E_UNPLACEABLE_PLATE` になり、ビルドは止まります。行がそうなるのは、`at=` がないか `<side>.outside` でも `inside.<side>` でもない場合、`offset=` や `y=` が非負整数でない場合、`offset=` が壁の長さ以上の場合、段が struct の高さ以上の場合 ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出))、`y = 0` より上の `at=<side>.outside` で脇に外側のボクセルがない場合 (屋根が軒の出を作らない struct では、そのすべて)、`at=inside.<side>` が内側の外にある場合です。別のメンバーが建っていれば struct に収まったはずのプレートは、代わりに `W_DEFERRED_MEMBER` になります。直すべきなのは、そのメンバーの指摘のほうです。何も塗らない `walls` が、塗っていれば届いたはずの段や、`overhang=` 付きで書かれながら何も描かない `roof` の脇の `at=<side>.outside` がその例です ([Lint](/ja/spec/lint/#lowering))。プレート自身の行を先に判定するので、行の指定がそもそもプレートをどこにも置けないなら、そうしたメンバーが欠けていてもエラーです。合成はボクセルではなくメンバー行を読むので、どちらの場合もプレートの `->` バインディングは読まれます。信号はそれを駆動するプレートがないままネットリストに残り、そのことは指摘に示されます。

**信号名。** センサーは `sig.` 名前空間へ信号を発し、アクチュエーターはそこから読むので、名前空間の外の名前は誰にも読まれません。`logic` 行の左辺でも、センサーの末尾の `->` でも、アクチュエーターのキーの値でも同じで、`E_LOGIC_INVALID_SIGNAL` になります。名前は `sig.` とそれに続く 1 つのセグメントです。`opened_by=a` は `a` という信号への配線にはならず、`opened_by=sig.a.b` も何も指しません。

値より先に、それを持つメンバー (ホスト) を検査します。`walls -> a` の誤りは 1 つで、それはホストの誤り、つまり上の `E_MISPLACED_BINDING` です。センサーに付いていれば値に付くはずの `E_LOGIC_INVALID_SIGNAL` は付きません。値をどう書き直しても、`walls` はセンサーにならないからです。

**バインディングは `[selector]` の後に書き、中には書きません。** `door[id=front] opened_by=sig.power` はバインディングになり、`door[id=front,opened_by=sig.power]` はなりません。角括弧は行が作用するメンバーを選ぶためのもので、その中に書いたものはバインディングとして読みません。括弧の中の組には、括弧の外に出しても残る指摘が付きます。問題がそれだけなら角括弧を指す `E_LOGIC_MISPLACED_BINDING`、そうでなければホストやキーに対する指摘です。

**セレクタ行は、角括弧が選ぶメンバーにバインディングを付けます。** `door[id=front] opened_by=sig.power` は、同じスコープのトップレベルか `level` の直下に `door id=front ...` と宣言されたドアにバインディングを付けます。`id=` は、角括弧なしで書かれたそうしたドアをちょうど 1 つ指す必要があります。パッチは単独で 1 行を占め、対象のドアの前にも後ろにも、トップレベルにも `level` の直下にも書け、ドアがどこにあっても構いません。セレクタに `id=` がないパッチ、その id を持つドアがないパッチ、同じ id を持つドアが 2 つあるパッチは `E_LOGIC_UNRESOLVED_PATCH` です。どのドアにも作用しないので、受け付けるとコンポーネントのないポートがネットリストに載ってしまいます。セレクタ行が運ぶバインディングはドアのパッチだけなので、`pressure_plate[id=p]` に付いた末尾の `->` は、センサーでないメンバーの末尾と同じく `E_MISPLACED_BINDING` です。

**アクチュエーターは、1 つのキーにつき 1 つのバインディングしか取りません。** ドアの `opened_by=` は、ドア自身の行に書いても、パッチで書いても、両方に書いても 1 つです。2 つ目は `E_LOGIC_DUPLICATE_BINDING` になります。バインディングが 2 つあると 1 つのドアへの配線が 2 本になり、論理層に書かれていないワイヤード OR になってしまうからです。信号は論理層で組み合わせます。`logic sig.open = sig.a or sig.x` と書き、ドアを `sig.open` に結び付けてください。

4 つのアクチュエーターのキー以外のキーに `sig.` の値が付いている場合は、`E_LOGIC_UNKNOWN_BINDING_KEY` です。値は「信号を配線するつもりだった」と言い、キーは「誰にも読まれない」と言っている状態で、これは打ち間違いの典型です (`oepend_by=sig.power` など)。

## 14.3 論理層は依存関係の DAG

論理層には、信号どうしの依存関係を書きます。ブール演算の組み合わせとマクロの適用です。時間を含まない純粋なデータフローで、コンパイラの内部では Logic IR になります。

```
logic sig.lamps = sig.power and not sig.day
logic sig.mem   = latch(set=sig.a, reset=sig.b)   # RS ラッチ (マクロ)
logic sig.pulse = pulse(sig.ring, 4)              # 単安定: 4 段
logic sig.fire  = edge_rising(sig.tick)
logic sig.sel   = mux(sel=sig.s, a=sig.x, b=sig.y)
```

式には時間の演算がありません。`pulse(sig.ring, 4)` の `4` は tick 数ではなく **段数** です。

## 14.4 時間モデル

v1 で時間を持つのはマクロ (`delay` / `pulse` / `edge` / `latch` / `counter`) だけです。`delay(3)` は内部でリピーター 3 個に展開されるセルマクロです。tick を扱う演算子はありません。

**遅延は Logic IR にも Netlist IR にも現れず、Placement IR で初めて確定します** ([§14.8](#148-ir-とフェーズの関係))。`and` は論理的には遅延ゼロですが、何 tick かかるかは、セルの選択 (Java なら `and → ComparatorAND`) と、配置後の実際の配線長が決まるまで分かりません。

数値が tick として現れるのは、検証のアサーション ([§14.7](#147-検証)) だけです。論理式の中で tick の計算をすることはありません。

## 14.5 配置配線 (place-and-route)

DSL が見せるのは 2D のメンタルモデルです。純粋な 2D のフロアプランでは行き詰まるので、内部実装は疑似 2.5D で、`plane` / `via` / `bridge` という概念を持ちます (DSL には出てきません)。純粋な 2D では扱えない回路には、ファンアウト、バス、交差、コンパレーターのフィードバック、オブザーバーの連鎖があります。

```
circuit region=basement void=3       # 高さ 3 のサービス層を確保し、ここに回路を配線する
```

この行は `struct` または `def` に 1 つだけです。同じ本体にある 2 つ目は `E_DUPLICATE_CIRCUIT` です ([Lint §11.1](/ja/spec/lint/#111-診断コード))。確保が 2 つ以上必要なロジックは、2 つ以上のスコープに分けます。

この行は、本体自身のメンバーの間に置きます。確保はスコープの `size=WxH` 全体に及び、どの `level` の `y=` も取らないので、配置配線は `level` の下の `circuit` 行を読みません。そうした行は `E_DUPLICATE_CIRCUIT` ではなく、その行の `E_MISPLACED_MEMBER` になります。

内部のアルゴリズムは 5 段階です。

1. **配置**: トポロジカル順に左から右へ並べ、セルとセルの間に 1 列の空きを置きます。セルの行は入力パッドの列の次の列から始まり、遅くともアクチュエーターのパッド列の手前の列で終わるので、`n` 個のセルの行には `2n + 1` 列が必要です。最後の 1 列はアクチュエーターのパッド自身の列です。`2n` 列だと最後のセルがその列に立ち、`z = 0` と `z = 2` のパッドと面で接してしまいます。どちらのパッド列も、セルの行にはパッドを置かないので、パッド列の隣に立つ端のセルは、そこにある隣の座標を空いた隣接座標として持ち続けます。セル本体はブロックなので、ネットは隣接する座標を通ってセルに届きます。2 入力のゲートには 3 つの異なるネット (2 本のドライバと自分の出力) が接するので、空いた隣接座標が 3 つ必要です。セルを詰めて並べると、行の途中のセルには領域をいくら広げても 2 つしか残りません。行に空きを入れるのはそのためで、これがあって初めて、ショートのない配線が可能になります。

   セルの行は、さらに領域の手前の端から 1 行内側に置きます。セルのあるスコープでは、I/O パッドは `z = 0` から、セルの行を飛ばして並びます。セルのないスコープにはセルの行がないので、パッドは `z = 0` からすべての行を使います。セルの行にパッドがあると、セルの行がその列まで届いたときに端のセルと面で接し、そのセルとは無関係かもしれないネットの端子が、セルの面を 1 つ取ってしまいます。パッドをその行から外し、セルの行をアクチュエーターのパッド列の手前で終えれば、行の検査が受け付けるどの幅でも、パッドがセルに接することはありません。ダストは隣の座標のダストとつながるので、空いた座標のレーンは、どれだけ長くても 1 本のネットしか運べません。端に接したセルにはレーンが 1 本しかなく、2 入力のゲートに接する 3 つのネットはそれを共有できません。1 行内側に置けば、どのセルにも両側にレーンが 1 本ずつできます。これに要るのはネットリスト全体で 1 行で、セルごとに 1 行ではないので、列の空きと違ってセルの数に比例して増えません。

   どちらの空きも、ショートのない配線を *可能にする* だけで、保証はしません。通り抜けるネットが最後の空き面を取ってしまうこともあり、そのスコープはショートさせずに拒否します。次のような領域は、2 段階先で到達できないシンクとして落ちるのを待たずに、ここで拒否します。セルの行が収まらない領域 (`n` 個のセルに `2n + 1` 列と 3 行が必要)。パッドを置く行が足りない領域 (パッドの多い側の辺で、センサーかアクチュエーター 1 つにつき 1 行。セルのあるスコープでは、その辺にパッドが 2 つ以上あれば、セルの行の分としてさらに 1 行)。センサーとアクチュエーターの両方を持つスコープで、2 つのパッド列の分の 2 列がない領域 (1 列では両者が同じ列になってしまう)。
2. **Steiner 配線**: マンハッタン経路で、すでに立っているものと、すでに敷いたネットのダストを避けて配線します。コンポーネントは信号を発するか受け取るかのどちらかなので、セル本体と I/O パッドは予約済みで、その上にダストは引けず、信号がその中を *通り抜ける* こともできません。すべてのシンクはネットの木の葉になり、ファンアウトはシンクを数珠つなぎにするのではなく、行の脇に幹を通して各シンクへ枝を出す形になります。障害物がなければ、配線はまっすぐな直角経路です。障害物があれば回り込み、回り込む場所がなければ、`void=<N>` の予算内で `bridge` 層へ登ります。

   1 つの座標に 2 つのネットが乗ると、2 つの信号を運ぶ 1 本のダストになってしまいます。同じ平面で 1 歩隣り合う 2 本も同じです。ダストは隣のダストとつながるからです。そこでネットは 1 本ずつ敷き、後のネットは、先に敷いたダスト *とその隣の座標* を避けます。これが交差の回避で、登った分を測るために、段階 4 ではなくここで行います。`wire_length` も、遅延のパスが数える tick 数も、この配線の木から読み取ります。ネットを敷く順番は、ファンアウトの多い順、次にネット自身のキーの順です。これは全順序なので、1 つのレイアウトに対する答えは、何度問い合わせても 1 つに決まります。

   「隣」は同じ平面の中だけで考えます。層をまたいだ 2 本が互いにつながるかどうかは、その間に何が立っているかで決まりますが、このモデルはそれを持っていません。内部モデルは疑似 2.5D で、ボクセルとしての実現は物理タイルの層が担当します。層をまたいで 1 歩以内にある 2 本を隔てるのは、ルーターではなくその層の義務です。真上に重なった組も、斜めに 1 歩ずれた組も対象です。後者はレッドストーンの階段で、こちらのほうが多く現れます。ある座標の真下は 1 つですが、斜め下は 4 つあり、レーンを避けて登った経路は、そのレーンと平行に走る間ずっと、1 歩ずれた位置を通るからです。タイルの層はこの義務を、`bridge` の座標を何として実現してよいかという要件として負います ([§14.6](#146-エディションの違い))。

   この義務は推測させず、明示します。交差の回避によって、層をまたいで 1 歩以内に *ダスト 2 本* が残ったスコープには `W_ROUTE_CROSS_LAYER_CLEARANCE` が付き、座標とネットを列挙します。これで、そうした組はレイアウトから導き出すものではなく、読み取れるものになります。この警告は助言で、何も削りません。レイアウトに落ち度はなく、ルーターがここで独自の規則を作れば、自分のモデルでは確かめようのない理由でレイアウトを拒否することになるからです。示せる対処もありません。領域を広げても、この組は消えません。セルの両側のレーンが埋まっていて、ネットが自分の出口ですぐに登るしかない場合、広げた分は、登った後に上の層を走る距離が伸びるだけです。

   ```text
   W_ROUTE_CROSS_LAYER_CLEARANCE line 46 circuit=floor:
     routed netlist for struct `crossbar` leaves 12 pairs of dust within one step of each other
     across layers (2 stacked, 10 staircase).
     note: (4,1,1) on cell #0 stands directly over (4,0,1) on cell #1
     note: (5,1,1) on cell #0 stands directly over (5,0,1) on cell #1
     note: (1,1,1) on cell #0 stands a layer over, and one step across from, (1,0,0) on sig.a
     Fix: nothing in the source is wrong — the pairs are what the escape costs, and enlarging
     the region is not a remedy.
   ```

   セグメントの上限も、配線を 1 本も敷く前に、この段階で検査します。ドライバとシンクのマンハッタン距離は、両者を結ぶどの経路の長さよりも短いか等しいので、直線距離ですでに上限を超えているシンクは、ルーターがどう回り込んでも超えます。そうしたスコープには、段階 3 ではなくこの段階で `E_ATTENUATION_LIMIT` が付きます。これは下限による判定で、実測ではありません。段階 3 よりも厳密に少ないものしか拒否せず、段階 3 の検査を置き換えるものでもありません。幅 256 の領域では、パッドがドライバから 255 ブロックの位置に置かれ、そこへ 257 ブロックの配線を敷くことがあります。これは上限を超えていますが、この検査には掛かりません。Fix 行が段階 3 と異なるのも同じ理由です。直線を縮める方法はないので、ここでは領域を広げても解決になりません。

   ルーターの探索も同じ上限で打ち切ります。ネットの配線からシンクへの経路はそのシンクのセグメントの一部なので、探索は上限より先を見ません。到達できなかったシンクは、その後 1 つずつ判定します。ルーターがそのシンクを塞がれていると証明できる場合は、後述の `E_ROUTE_CONGESTION` です。証明できるのは、シンクのどの面からも到達できない場合、上限で何かを切り捨てる前に探索する座標が尽きた場合、シンクから続く空き座標がすべてシンクから上限以内にあり、その中にネットの配線がない場合です。それ以外の場合は、この段階で `E_ATTENUATION_LIMIT` が付きます。わかるのは、上限内の経路がないことだけです。上限より広い空き領域の中で塞がれたシンクもこちらです。両方の種類のシンクを持つスコープでは、メッセージは塞がれたシンクについて述べます。この打ち切りがあるので、シンクを諦めるまでの手間は、確保した領域の大きさではなく上限に比例します。打ち切りがなければ、ネットが到達できる空き座標をすべて訪れてからでないと拒否できません。
3. **遅延の挿入**: ダストが減衰の限界である 15 ブロックを超えて続くセグメントにだけ、バッファとしてリピーターを入れます。強度 15 の信号源から延びるダストは、15 ブロック目でも強度 1 で、その先のシンクを駆動できます。セグメントはドライバからシンクまでの **実際の配線** に沿って測り、バッファはその経路の上に立ちます。2 点間の直線が、常に配線になるとは限りません。v1 の上限である 256 歩を超えるセグメントにはバッファを入れず、拒否します。コードは段階 2 と同じ `E_ATTENUATION_LIMIT` です。違うのは、このパスが実際に敷いた配線を測っている点です。

   リピーターは背後のブロックを読み、正面のブロックを自分と同じ高さで駆動するので、リピーターを立てられるのは、配線が同じ高さのまま座標をまっすぐ通り抜け、そこから何も分岐しない場所だけです。また、リピーターがつなぐ背後と正面の 2 つ以外に、同じネットのブロック (別の道筋で経路が届いているダストや、そのネットのセルやパッド) が 6 面のどれかで接している座標にも立てられません。そこにリピーターを立てると、そのブロックを切り離してしまうからです。強度 15 の信号源から延びるまっすぐな区間なら、リピーターは 15 ブロックのダストに続く 16 ブロック目ごとに、ダストの代わりに立ちます。その座標が曲がり角、層の上り下り、分岐のいずれかであれば、リピーターはその手前で、まっすぐ通り抜ける最後の座標に立ちます。経路によっては、長さだけから決まる数より 1 個多くリピーターが必要になります。手前へ戻る元の座標が分岐なら、戻った先は幹の上にあるので、1 個で先のすべての枝をまかなえます。分岐がそれより手前にあれば、枝ごとに 1 個ずつ立てます。リピーターはシンクごとではなく、ネットの実際の配線の木の上に置き、各シンクには自分の経路上にあるリピーターを計上します。減衰の限界を超える区間に、リピーターを立てられる座標が 1 つもなければ、`E_ATTENUATION_LIMIT` で拒否します。

   限界は、各セグメントの始点からではなく、強度を回復する最後の部品 (センサーのパッド、リピーター、トーチ) から数えます。セルのうち 2 つは、受け取った強度を回復せずにそのまま渡します。Bedrock の OR はダストの合流です。Java のコンパレーター AND は、一方のオペランドを反転して側面に入れるコンパレーターで ([§14.6](#146-エディションの違い))、オンの間は後ろの入力が運ぶ強度を出力します。このパスは、コンパレーターのどの入力が後ろの入力かを追跡しません。どちらのセルでも、入る配線と出る配線は、間にセルが立っていても 1 続きのダストとして数え、最も強度を消費した入力から測ります。セルがオンの間、その出力がこの入力より弱くなることはありません。合流は点いている入力のうち最も強いものを、コンパレーターは後ろの入力を渡すからです。反転するオペランドの配線は、強度を回復する反転で終わるので、それをセルが割ける分に収めるのは、セルが必要とする以上に厳しい条件です。その 1 続きの区間に必要なリピーターは、累計が 15 を超える位置に置きます。そうしたセルに入る配線の上では、出る配線が残りを使うので、セルが割ける分を累計が超える位置に置きます。その位置がダストのブロックなら、リピーターはダストの代わりに立ち、手前のダストを読みます。まっすぐな区間と同じです。その位置がシンクなら (こうしたセルもシンクです)、リピーターはその代わりには立てないので、手前の配線に立ちます。リピーターが立つのはセルから出る配線の上で、セルの近くに立てられる座標がそこになければ、セルに入る配線の上です。
4. **交差の合法化**: 段階 3 が数えたバッファのリピーターに、座標を割り当てます。この時点で、配線を合法化する必要はもうありません。リピーターは自分のネットの実際の配線の上に立ち、その経路はそのネットだけのもので、ほかのどのネットも 1 歩以内を走っていないので、取り除くべきショートも、奪い合う座標もないからです。このパスも自分でネットを敷くので、直線距離の上限を適用します。前の段階が渡したネットリストから、スコープがここに到達することがあるためです。同じ理由で、リピーターを立てられる座標のない区間も、段階 3 と同じく拒否します。
5. **エディションの合法化**: [§14.6](#146-エディションの違い) を参照してください。

配線は `circuit` の領域の中に閉じ込めます。収まらなければ、はっきりエラーにします。ドライバからの経路がすべて塞がれているシンクも、理由は違いますが同じ拒否になります。塞いでいるのは、コンポーネント、先に敷いたネットのダストとその隣の座標、あるいは確保した領域の端です。メッセージには、結べなかった 2 つの座標と、面を取っていたネットが示されます。

```text
E_ROUTE_CONGESTION line 21 circuit=basement:
  synthesized netlist needs ~3.2x the reserved area (void=3, region 9x7).
  Fix: increase `void`, enlarge region, or split the logic across several scopes, each with its
  own `circuit` line.
```

これらのパスが出すもう 1 つの拒否が `E_ATTENUATION_LIMIT` で、4 つの形で起きます。段階 2、3、4 は、どれも共通の 1 つの手順でネットを敷きます。この手順は、経路を敷く前にドライバとシンクを結ぶ直線を上限と比べ、ルーターが探索した後で、上限内の経路が届かないシンクを拒否します。段階 3 はさらに、実際の配線のセグメントを上限と比べます。段階 3 と 4 はどちらも、減衰の限界 15 を超えるダストの区間に、リピーターを立てられる座標が 1 つもなければ拒否します。どちらも同じ配線の木から同じ規則でリピーターの位置を求めるので、どの区間かについて両者の判断は一致し、メッセージは信号が届かなくなるノードを示します。どの段階が拒否するかは、どれが先にそのスコープに到達したかだけで決まります。primary はそのパスが読んだネットリスト (段階 2 なら `placed`、段階 3 なら `routed`、段階 4 なら `delayed`) を示すので、パイプラインのどこで測った形なのかがメッセージから分かります。

```text
E_ATTENUATION_LIMIT line 13 circuit=floor:
  placed netlist for struct `wide_pack` puts output pad #0 299 steps from its driver in a
  straight line — exceeds the v1 attenuation limit of 256 steps, and no route between two coords
  is shorter than the straight line between them.
  Fix: split the logic across several scopes, each with its own `circuit` line, or reserve a
  `region=` whose pad column sits within the cap of the cells it serves — a larger reservation
  cannot help, because the straight line between these two is already over the cap.
```

## 14.6 エディションの違い

3 層のセルライブラリが、エディションの違いをライブラリの中だけに閉じ込めます。

```
Logical Cell → Edition Cell → Physical Tile
  AND        → Java:    ComparatorAND → block array
             → Bedrock: TorchAND      → block array
```

Java の `ComparatorAND` は減算モードのコンパレーターで、一方のオペランドを反転し、最大強度で側面に入れます。そのオペランドがオンの間は側面が 0 を読み、コンパレーターは後ろの入力が運ぶ強度を出力します。オフの間は側面が 15 を読み、後ろの入力が何を運んでいても出力は 0 です。どちらのオペランドもネットリストが運ぶとおりにセルに届くので、反転はセル自身が行い、そのうえで AND を計算するのが減算モードです。比較モードでは、側面が 15 を読んでいる間も、強度 15 の後ろの入力がそのまま通ってしまいます。

タイルの層は、配置配線から生じる義務を 1 つ自分で負います。`bridge` の座標は、**ほかのネットの** 真下の座標にも、ほかのネットの斜め下の座標にも導通しないタイルとして実現します。自分のネットの真下の座標は、そこへ登ってきた経路そのもので (via を別に置くことはありません)、導通しなければなりません。段階 2 ([§14.5](#145-配置配線-place-and-route)) は 2 つのネットを同じ平面で 1 歩以上離し、回り込めないものは登って避けるので、ある 1 本がほかのネットの真上に来るのは必ず交差の回避の結果で、その 2 本を隔てるのはタイルの仕事です。

これは作者ではなくカタログに対する要件で、それを知らせる指摘よりも広い範囲に及びます。`W_ROUTE_CROSS_LAYER_CLEARANCE` が示すのはダストどうしの組、つまり 2 つの信号が 1 本を共有しかねない箇所だけです。一方、上の義務は、`bridge` タイルの下にあるほかのネットの座標すべてに及びます。セル本体や I/O パッドも含みます。コンポーネントの上を登るのは、それを越えるためのふつうの手段なので、それらまで示す指摘を出すと、未解決の問題ではなくレイアウトそのものを報告することになってしまいます。

- **吸収するもの**: リピーター、オブザーバー、コンパレーター、向き。どれもセルの実装の違いです。
- **吸収しないもの**: QC (準接続)、BUD、更新順序。ブロック更新順序という暗黙の意味論に依存しており、エディション間で移植できる実装が存在しません。

更新順序の意味論を必要とする論理は、気付かないうちに壊れるのではなく、コンパイルエラーになります。「変換ではなく再コンパイル」という方針と一致します。

```text
E_NO_PORTABLE_IMPL line 15:
  this circuit requires update-order (quasi-connectivity / BUD) semantics.
  No portable redstone implementation exists for the target edition.
  Fix: redesign the logic to be order-independent, or drop to Tier 0 with an @edition guard.
```

手で置いたレッドストーンは、エディションをまたぐと壊れます。論理として記述しておけば、コンパイラがエディションごとに正しい回路を出力できます。部品ではなく論理を書く、最大の理由です。

## 14.7 検証

意図を宣言し、合成した回路を tick 単位でヘッドレスにシミュレーションして照合します。アサーションは 3 種類です。

```
# 組み合わせ: 真理値表
assert truth(sig.a, sig.b -> sig.out) { 00->0; 01->1; 10->1; 11->0 }

# レイテンシ: 配置配線で遅延が変わるので重要
assert latency(sig.in -> sig.out) <= 4

# 時相: 完全な LTL ではなく、有界の eventually のみ
assert always(sig.button -> eventually sig.door_open within 8)
```

自己修正のループ (P5) は **synth → sim → diff → patch** で、検証はターゲットのエディションごとに走ります。パッチが変更するのは、配置配線のヒント、リピーター、バッファだけです。**Logic IR は決して書き換えません。** 論理を自動で書き換える自己修正は危険だからです。

```text
E_SIM_ASSERTION_FAILED edition=bedrock:
  assert latency(sig.in -> sig.out) <= 4, but measured 6 (extra repeaters from crossing legalization).
  Patch target: placement hint / route. (logic is never auto-modified)
  Suggested: relax to <=6, enlarge circuit void to shorten routes, or pin cell placement.
```

## 14.8 IR とフェーズの関係

Intent IR と block-array IR の間に、HDL と同じ分け方で 3 つの IR 層が入ります。

```
Intent IR        logic 宣言 / circuit 領域 / 信号バインディング
   ↓ logic_synth
Logic IR         論理式と依存 DAG。エディション中立、遅延ゼロ
   ↓
Netlist IR       セルとネット。Logical Cell の選択。まだ遅延なし
   ↓ logic_place
Placement IR     セル座標 + 実際の配線長。ここで遅延が確定する
   ↓ logic_route
block-array IR   ダスト・リピーター・トーチ・コンパレーターのボクセル実体
```

フェーズモデル ([コンパイルモデル](/ja/spec/compilation/)) では、`fixtures` の直後を `logic_synth → logic_place → logic_route` に分けます。センサーとアクチュエーターが 3D 空間に配置されるまで、I/O ポートの座標が決まらないからです。

## 14.9 逆変換

schematic から取り込んだ手作りのレッドストーン ([エコシステム連携](/ja/spec/ecosystem-interop/)) は、v1 では Tier 0 の raw として保持します。ダストの塊から論理を逆合成することは対象外です。生成を優先し、情報の欠落を許容する方針と一致します。
