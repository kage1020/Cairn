title: "14. レッドストーン (論理回路)"
---

Cairn はレッドストーンを **論理レベル** で記述します。信号のグラフを宣言すると、コンパイラが実際のダスト、リピーター、トーチ、コンパレーターを合成し、配置し、配線して、ボクセルに落とし込みます。

P1 の効果が最も大きいのがここです。信号の減衰、クロストーク、遅延の計算は、AI がボクセル建築以上に苦手とする物理ですが、どれも論理記述から決定的に導けます。

論理層で第一級に扱う対象は、挙動ではなく **信号の依存グラフ** です。時間は言語のコアには持ちません ([§14.4](#144-時間モデル))。

## 14.1 2 つの層と v1 の範囲

- **Tier 0: 物理配置。** `repeater at=3,1,2 facing=north delay=2` のように部品を自分で置き、ブロックステートはコンパイラが導出します。挙動はモデル化しません ([ブロックステート](/ja/spec/blockstate/))。部品は[後述](#tier-0-の部品)します。
- **Tier 1: 論理。** この章で扱います。信号グラフを宣言すると、コンパイラが合成、配置、配線を経てボクセルにします。

新しいキーワードは `logic` / `circuit` / `assert` の 3 つだけです。論理プリミティブはキーワードではなく、組み込みのライブラリとして提供し、語彙は小さく閉じたまま保ちます (P3)。

Verilog で言えば、v1 が許すのは `assign` に相当するものだけで、クロック付きの代入は許しません。

| | 範囲 |
|---|---|
| **組み合わせ回路** | `and` / `or` / `not` / `xor` / `nand` / `nor` / `mux` |
| **厳選した順序マクロ** | `latch` / `pulse` / `delay` / `edge_rising` / `edge_falling` / `counter` |
| **対象外** (→ Tier 0 か `raw`) | `always` / `process` / `state` / `case` / FSM / クロック付きの代入 / CPU |

**組み込みの論理ライブラリ。** ライブラリの各項目は、プリミティブの名前とその書き方です。前置のプリミティブは 1 つのオペランドの前に置きます。中置のプリミティブは 2 つのオペランドの間に置き、結合の強さを順位で表します。順位が高いものから先にまとまり、同じ順位どうしは左から順にまとまります。呼び出し形式のプリミティブは、名前の後の括弧の中にオペランドを取ります。各オペランドは `name=式` の形で 1 回ずつ名前を付けて書き、順序は自由で、オペランドの間にはカンマを 1 つ置き、最後のオペランドの後には置きません。適用形式のプリミティブは、名前の後の括弧の中に 1 つのオペランドを位置で取ります。段数を数えるプリミティブは、オペランドの後にカンマと段数を取ります。段数は 1 から 4294967295 までの整数です。パーサは式の形をライブラリから読むので、これらの書き方のどれかであれば、プリミティブがライブラリに加わっても新しい構文は要りません。ライブラリにあるプリミティブは 13 個です。

| プリミティブ | 書き方 |
|---|---|
| `or`、`nor` | 中置、順位 0 |
| `xor` | 中置、順位 1 |
| `and`、`nand` | 中置、順位 2 |
| `not` | 前置 |
| `mux` | 呼び出し、`mux(sel=…, a=…, b=…)` |
| `latch` | 呼び出し、`latch(set=…, reset=…)` |
| `edge_rising`、`edge_falling` | 適用、`edge_rising(…)` |
| `delay`、`pulse`、`counter` | 段数付きの適用、`delay(…, N)` |

順位はビット演算子のふつうの順序に従い、`and` が `xor` より、`xor` が `or` より先にまとまります。否定形はそれぞれ、否定する元のプリミティブと同じ順位です。前置のプリミティブはどの中置のプリミティブよりも強く結合するので、`sig.a or sig.b and not sig.c` は `sig.a or (sig.b and (not sig.c))` と読み、`sig.a nor sig.b xor sig.c nand sig.d` は `sig.a nor (sig.b xor (sig.c nand sig.d))` と読みます。括弧は書いたとおりにまとめます。呼び出しは信号と同じく 1 つのオペランドなので、`not mux(sel=sig.s, a=sig.x, b=sig.y) and sig.z` は `(not mux(…)) and sig.z` と読みます。呼び出しの中の各オペランドは、それぞれ 1 つの完全な式です。適用も同じで、`delay(sig.a and sig.b, 2)` は `and` を遅らせます。

`mux` は、`sel` がオフの間は `a`、オンの間は `b` です。オペランドを位置で渡す呼び出し、オペランドを書き漏らす呼び出し、同じオペランドを 2 回書く呼び出し、プリミティブが取らないオペランドを書く呼び出しは `E_PARSE` になり、メッセージはプリミティブが取るオペランドを挙げ、位置で渡したオペランドと書き漏らしたオペランドについては、まだ書かれていないオペランドを挙げます。`mux(sel=sig.s, sig.x, sig.y)` は 2 つ目の `sig` で止まり、`a=` か `b=` を求めます。

適用形式のプリミティブは逆に、名前を付けたオペランドを拒否します。`pulse(in=sig.x, 4)` は `in` で止まります。段数の誤りも、誤った位置で `E_PARSE` になり、メッセージはそのマクロの書き方を示します。段数を書き漏らすと、`delay(sig.x)` は `)` で止まって `,` を求めます。カンマを書き漏らすと、`delay(sig.x 2)` は `2` で止まります。段数を数えないプリミティブに段数を渡すと、`edge_rising(sig.x, 2)` は `,` で止まります。段数が 1 から 4294967295 の範囲になければ、`pulse(sig.x, 0)` は `0` で止まります。各マクロが何を計算するかは、時間モデル ([§14.4](#144-時間モデル)) で定めます。

ライブラリにない語は、その語の位置で `E_PARSE` になり、メッセージはそこに置けるものを挙げます。`sig.a xnor sig.b` は `xnor` で止まり、`toggle(sig.x)` は `(` で止まって、ライブラリが呼び出しや適用として持つプリミティブを挙げます。

### Tier 0 の部品

4 つのキーワードが、レッドストーンの部品を手で置きます。`repeater`、`comparator`、`redstone_torch`、`redstone_dust` です。どれも 1 つのブロックを置き、そのブロックステートは、ほかのメンバーと同じようにコンパイラが導出します。部品が何をするかはモデル化しません。部品はネットリストに載らず、何を動かすか、何に動かされるかを検査するものはなく、信号バインディングも持たないので、部品に付いた末尾の `->` は `E_MISPLACED_BINDING` です ([§14.2](#142-信号バインディング))。部品は `struct` か `def` の本体に、直接または `level` の下に書きます。`@edition` ガードは `raw_block` と同じように部品を囲めます ([バージョンとエディション](/ja/spec/versioning-editions/#edition-ガードはエスケープハッチを囲む))。`site` の本体では `E_MISPLACED_MEMBER` です。

```
repeater       at=3,1,2 facing=east delay=2
comparator     at=4,1,2 facing=east mode=subtract
redstone_torch at=inside.back offset=2 y=2
redstone_torch at=5,1,2 facing=east
redstone_dust  at=6,1,2
redstone_dust  at=6,1,4 connect=none
```

**部品を置く位置。** `at=x,y,z` は、`raw_block` の `at=` と同じようにセルを指し ([マテリアルとテーマ §7.4](/ja/spec/materials-themes/#74-生のブロック))、部品は `raw_block` が拒否または保留される場所で拒否または保留されます。`at=<side>.outside` か `at=inside.<side>` に `offset=` と `y=` を添えると、`pressure_plate` と同じように壁のそばに置きます ([§14.2](#142-信号バインディング))。3 つ組はセルをそれだけで指すので、3 つ組と並べた `offset=` や `y=` は `E_INVALID_MEMBER` です。

**部品の向き。** `repeater` と `comparator` は、後ろのセルを読んで前のセルを駆動し、`facing=` は駆動する向きです。壁のそばでは `observer` と同じく `in`、`out`、`left`、`right` を取り、行に書かれていなければ壁から離れる向きに駆動します。3 つ組の位置では `north`、`south`、`east`、`west` を取ります。north は `back` の壁の方向、east は `right` の壁の方向です。そばに壁がなく、離れる向きを決められないので、行に必ず書く必要があります。`redstone_torch` は、壁のそばでは壁の面に掛かり、壁から離れる向きを指します。3 つ組の位置では下のブロックの上に立ちます。方角の 4 語のどれかを `facing=` に書くと、後ろのブロックの側面に掛かってその向きを指します。これが [ブロックステート §6.1](/ja/spec/blockstate/#61-既定では導出し上書きで昇格する) のトーチと壁付きトーチの置き換えで、トーチが何に付いているかから読み取ります。壁のそばのトーチには、`facing=` で選べるものがありません。`redstone_dust` には向きがないので、`facing=` を取りません。部品の位置の指定がそこで取らない語は、壁のそばの方角、3 つ組の位置での壁からの語、壁のそばのトーチの `facing=` も含めて `E_INVALID_MEMBER` になり、部品は置かれません。

**部品のステート。** `delay=` はリピーターの遅延で、1 から 4 までの整数です。行に書かれていなければ 1 です。`mode=compare` か `mode=subtract` はコンパレーターのモードで、書かれていなければ `compare` です。ダストの 4 つの側は、すべてのメンバーを塗り終えてから導出します ([ブロックステート、つながり](/ja/spec/blockstate/#つながり))。ただし `connect=none` はどの側ともつながらない点として、`connect=all` は 4 つの側すべてとつながる十字として置きます。どの部品も、何にも動かされていない状態で置きます。リピーターは動力もロックもなし、コンパレーターは動力なし、トーチは点灯、ダストは強度 0 です。ブロック更新が届けば、ゲームがそれぞれを落ち着かせます。`facing=`、`delay=`、`mode=`、`connect=` の値が、そのキーが取る種類でないとき (語を書く場所の数や、数を書く場所の語) は `W_IGNORED_ARGUMENT` で ([リント §11.3](/ja/spec/lint/#113-エラーと警告の区分))、書かれていないものとして部品を置きます。種類は合っていても、ここに挙げたものを指さない値 (`delay=5` など) は `E_INVALID_MEMBER` です。

**部品の材料。** 部品はそれぞれ、置くブロックが 1 つに決まっています。それが部品の tier-1 トークンで ([マテリアルとテーマ](/ja/spec/materials-themes/#tier-1-のトークン))、部品に付けた `mat_slot=` は `W_IGNORED_ARGUMENT` です。部品が何の上に立ち、何に掛かっているかは、レバーと同じく検査しません。下にブロックのない部品や、後ろにブロックのないトーチは、ブロック更新が届いた時点で落ちます。

**部品と回路。** Tier 0 の部品はネットリストの外にあるので、部品が何をするかは誰も読みません。両者がセルを共有することはありません。`circuit` の確保はスコープの基準面の下にあり ([§14.5](#145-配置配線-place-and-route))、Tier 0 の部品を含むどのメンバーも基準面かその上に立つからです。部品が何に動力を与えるかを記した表はないので、回路は部品の下にも、その隣のセルの下にもダストを通さず、ライザーが部品に動力を与えてしまうアクチュエーターは拒否します。

## 14.2 信号バインディング

センサーが信号を発し、アクチュエーターがそれを受け取ります。どちらも、先行するフェーズで配置される物理メンバーです ([コンポーネント・編集・複数建築](/ja/spec/components-editing-sites/))。

```
# センサー → 信号
lever          id=sw at=inside.front offset=2 y=1 -> sig.power
button         id=bt at=front.outside offset=5 y=1 -> sig.ring
daylight       id=dl at=back.outside offset=3 y=0 -> sig.day
observer       id=ob at=inside.left offset=2 y=1 facing=down -> sig.tick
pressure_plate id=pp at=front.outside offset=1 y=0 -> sig.step

# アクチュエーター ← 信号
lamp      id=l1 at=inside.back offset=3 y=2 lit_by=sig.lamps
piston    id=p1 at=inside.right offset=2 y=1 powered_by=sig.mem facing=up sticky=true
door      id=d1 side=front at=center opened_by=sig.power
dispenser id=ds at=front.outside offset=6 y=1 fired_by=sig.pulse facing=out
```

この対応は規範です。末尾の `-> sig.X` はセンサーのもので、アクチュエーターの各キーは、それを読む 1 種類のコンポーネントのものです。ほかの場所に書かれたバインディングは回路を何も記述しておらず、受け付けると、コンポーネントのないポートがネットリストに載ってしまいます。

これをどのコードで報告するかは、判定に何が必要かで決まります。センサーでないメンバーに付いた末尾の `->` は `E_MISPLACED_BINDING` です。あるキーワードが信号を発せるかどうかはメンバー行についての事実なので、`check` が判定し、どのコマンドでも報告します。それを読まないコンポーネントに付いたアクチュエーターのキーも、メンバー行についての事実です。キーがそのメンバーの語彙にないので、`walls opened_by=sig.power` は `E_UNKNOWN_ARGUMENT` になり ([Lint](/ja/spec/lint/#構文と構造))、`check` が報告して、どのコマンドもそこで止まります。このとき、キーの持ち主のコンポーネントを注記で示します。同じコンポーネントを示す synth パイプラインの `E_LOGIC_MISPLACED_BINDING` に届くのは、`theme` のセレクタがそのキーをメンバーの語彙に加えた場合だけです ([Lint](/ja/spec/lint/#113-エラーと警告の区分))。

**`door` 以外のコンポーネントは、プレートと同じ方法で位置を決めます。** `lever`、`button`、`daylight`、`observer`、`lamp`、`piston`、`dispenser` は、どれも壁のそばに置く 1 つのブロックで、`pressure_plate` と同じ `at=`、`offset=`、`y=` で書きます。以下の規則はプレートについて述べますが、これらすべてに同じように当てはまります。どれも、プレートが置かれる場所に置かれ、プレートが拒否または保留される場所で拒否または保留されます。指摘には、そのコンポーネントの名前が出ます。

**`at=<side>.outside` のプレートを置ける位置。** プレートは `offset=` の位置にある壁のセルを基準に、そこから 1 ボクセル外側、屋根の `overhang=` の分だけ壁の周りに広がるリングの中に置かれます ([コンパイルモデル §4.3](/ja/spec/compilation/#43-切妻屋根のボクセル規則))。struct の外側はこのリングだけなので、軒の出を描く屋根がなければ、床の段 `y = 0` を含むどの段にもプレートのセルはありません。代わりに壁自身の柱に置くことはしません。そこに置くと上の壁に埋もれ、信号が出ることはないからです。

**`at=inside.<side>` のプレートを置ける位置。** プレートは `offset=` の位置にある壁のセルを基準に、そこから 1 ボクセル内側に置かれます。そのボクセルは、壁のリング (敷地の最も外側の行と列で、`walls` が各段を塗る場所) より厳密に内側でなければなりません。つまり `offset` は 1 から「壁の長さ − 2」までで (長さは `front` と `back` では `size.w`、`left` と `right` では `size.h`)、そもそも内側があるためには、両方の軸で `size` が 3 以上必要です。リングは `walls` メンバーが塗るかどうかに関係なく敷地から決まり、この規則は床の段 `y = 0` を含むすべての `y` で成り立ちます。範囲外のプレートは置かれません。

**置けないプレート。** 自身の行の指定ではどのボクセルにも置けないプレートは `E_INVALID_MEMBER` になり、ビルドは止まります。行がそうなるのは、`at=` がないか `<side>.outside` でも `inside.<side>` でもない場合、`offset=` や `y=` が非負整数でない場合、`offset=` が壁の長さ以上の場合、段が、書かれたとおりの struct が届くどの段よりも上にある場合 ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出))、1 以上の `overhang=` を持つ屋根がない struct の `at=<side>.outside` の場合、`at=inside.<side>` が内側の外にある場合です。別のメンバーが建っていれば struct に収まったはずのプレートは、代わりに `W_DEFERRED_MEMBER` になります。直すべきなのはそのメンバーのほうだからです。何も塗らない `walls`、何も描かない `roof`、配置されない `level` の下の `walls` が建っていれば届いたはずの段や、何も描かない `overhang=` 付きの `roof` の脇の `at=<side>.outside` がその例です ([Lint](/ja/spec/lint/#lowering))。プレート自身の行を先に判定するので、行の指定がそもそもプレートをどこにも置けないなら、そうしたメンバーが欠けていてもエラーです。合成はボクセルではなくメンバー行を読むので、どちらの場合もコンポーネントのバインディングはネットリストに届き、信号はコンポーネントのないまま残ります。そのことは、コンポーネントの行の指摘に示されます。このバインディングは、センサーの末尾の `->`、アクチュエーターのキー、アクチュエーターにバインディングを付けるパッチのキーのうち、`sig.` の信号を指すものです。アクチュエーターに付いた末尾や `sig.` の外の値のように、合成が拒否するバインディングはネットリストに届かず、指摘もそれには触れません。

**コンポーネントの向き。** `lever` と `button` は、位置で指定した壁のセルの面に掛かり (`face=wall`)、その壁から離れる向きを向きます。`inside.<side>` なら struct の内側、`<side>.outside` なら外側です。`observer`、`piston`、`dispenser` も、`facing=` で向きを変えない限り壁から離れる向きを向きます。`in` と `out` は struct の内側と外側、`left` と `right` は壁に沿って `offset=0` に近づく向きと遠ざかる向き、`up` と `down` は上下です。これは前面が向く方向で、オブザーバーが見張るセル、ピストンが押す向き、ディスペンサーが発射する向きです。ほかの語は、方角も含めて `E_INVALID_MEMBER` になり、コンポーネントは置かれません。メッセージは使える語を挙げ、方角が書かれていれば、その壁からその方角を向く語を示します。方角は壁ごとに意味が変わってしまうからです。`daylight` と `lamp` には向きがなく、`facing=` を取りません。

`sticky=true` の `piston` は粘着ピストンとして、`sticky=false` か `sticky=` のない `piston` は通常のピストンとして建ちます。語でない `facing=` や、`true` でも `false` でもない `sticky=` は `W_IGNORED_ARGUMENT` になり ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))、コンポーネントはそれを書かなかったものとして建ちます。

どのコンポーネントも、動力のない状態で建ちます。レバーはオフ、ボタンは押されておらず、ランプは消え、ピストンは縮み、ディスペンサーは作動していません。ワールドで動力を与えるのは回路なので、こうした状態は行に書かず、意図 (intent) に昇格する状態は `facing=` だけです ([ブロックステートモデル §6.2](/ja/spec/blockstate/#62-intent_state-と-resolved_state))。

**コンポーネントの材料。** `button` は `mat_slot=` を読み、そのスロットはボタンに割り当てる必要があります。ほかのブロックなら `E_INCOMPATIBLE_MATERIAL` で、ボタンは代わりに `@button.default` で建ちます。`mat_slot=` がなければ `@button.default` で建ちます。ほかのコンポーネントは、それぞれの tier-1 のトークン ([マテリアルとテーマ](/ja/spec/materials-themes/#tier-1-のトークン)) で建ちます。ピストンは `@piston.default` で、`sticky=true` なら `@piston.sticky` で建ちます。そのどれを使うかを `mat_slot=` が選ぶことはないので、`mat_slot=` を書くと `W_IGNORED_ARGUMENT` になります。

**レバーやボタンが掛かるブロックは検査しません。** レバーやボタンは、壁のセルに何があってもそこに掛けて書き出し、そのブロックにゲームが掛けさせるかどうかは確かめません。そのセルを `walls` が塗っていないか、それを支えられない面のブロックで塗っている場合、ブロック更新が届いた時点でゲームはレバーやボタンを落とします。

**信号名。** センサーは `sig.` 名前空間へ信号を発し、アクチュエーターはそこから読むので、名前空間の外の名前は誰にも読まれません。`logic` 行の左辺でも、センサーの末尾の `->` でも、アクチュエーターのキーの値でも同じで、`E_LOGIC_INVALID_SIGNAL` になります。名前は `sig.` とそれに続く 1 つのセグメントです。`opened_by=a` は `a` という信号への配線にはならず、`opened_by=sig.a.b` も何も指しません。

値より先に、それを持つメンバー (ホスト) を検査します。`walls -> a` の誤りは 1 つで、それはホストの誤り、つまり上の `E_MISPLACED_BINDING` です。センサーに付いていれば値に付くはずの `E_LOGIC_INVALID_SIGNAL` は付きません。値をどう書き直しても、`walls` はセンサーにならないからです。

**バインディングは `[selector]` の後に書き、中には書きません。** `door[id=front] opened_by=sig.power` はバインディングになり、`door[id=front,opened_by=sig.power]` はなりません。角括弧は行が作用するメンバーを選ぶためのもので、その中に書いたものはバインディングとして読みません。括弧の中の組には、そのキーを括弧の外に出したときに付く指摘が付きます。メンバーの語彙にないキーなら `E_UNKNOWN_ARGUMENT`、メンバーが読むがアクチュエーターのキーではないキーに `sig.` の値が付いていれば、後述の `E_LOGIC_UNKNOWN_BINDING_KEY` です。コンポーネント自身のアクチュエーターのキーを角括弧の中に書いた場合は、値が何であっても、角括弧を指す `E_LOGIC_MISPLACED_BINDING` になります。

**セレクタ行は、角括弧が選ぶメンバーにバインディングを付けます。** `door[id=front] opened_by=sig.power` は、同じスコープのトップレベルか `level` の直下に `door id=front ...` と宣言されたドアにバインディングを付けます。`lamp[id=l1] lit_by=`、`piston[id=p1] powered_by=`、`dispenser[id=ds] fired_by=` も同じように、ランプ、ピストン、ディスペンサーにバインディングを付けます。`id=` は、角括弧なしで書かれた、パッチと同じキーワードのコンポーネントをちょうど 1 つ指す必要があります。パッチは単独で 1 行を占め、対象のコンポーネントの前にも後ろにも、トップレベルにも `level` の直下にも書け、コンポーネントがどこにあっても構いません。セレクタに `id=` がないパッチ、その id を持つ同じキーワードのコンポーネントがないパッチ、それが 2 つあるパッチは `E_LOGIC_UNRESOLVED_PATCH` です。どのコンポーネントにも作用しないので、受け付けるとコンポーネントのないポートがネットリストに載ってしまいます。セレクタ行が運ぶバインディングはアクチュエーターのパッチだけなので、`pressure_plate[id=p]` や `lever[id=sw]` に付いた末尾の `->` は、センサーでないメンバーの末尾と同じく `E_MISPLACED_BINDING` です。センサーはほかのどんなパッチも取りません。`lever[id=sw] at=inside.front offset=2 y=1` のようなセレクタ形式のセンサーの行は、角括弧がほかの場所で宣言されたメンバーを選ぶので何も置かず、`E_INVALID_MEMBER` になります。

**アクチュエーターは、1 つのキーにつき 1 つのバインディングしか取りません。** ドアの `opened_by=`、ランプの `lit_by=`、ピストンの `powered_by=`、ディスペンサーの `fired_by=` は、コンポーネント自身の行に書いても、パッチで書いても、両方に書いても 1 つです。2 つ目は `E_LOGIC_DUPLICATE_BINDING` になります。バインディングが 2 つあると 1 つのコンポーネントへの配線が 2 本になり、論理層に書かれていないワイヤード OR になってしまうからです。信号は論理層で組み合わせます。`logic sig.open = sig.a or sig.x` と書き、ドアを `sig.open` に結び付けてください。

メンバーが読むキーのうち、4 つのアクチュエーターのキー以外のものに `sig.` の値が付いている場合は、synth パイプラインが出す `E_LOGIC_UNKNOWN_BINDING_KEY` です (`walls height=sig.power` など)。値は「信号を配線するつもりだった」と言い、キーは「このキーから信号を読むコンポーネントはない」と言っている状態です。`oepend_by=sig.power` のようにアクチュエーターのキーを打ち間違えた場合は、キーがメンバーの語彙にないので、`check` が先に `E_UNKNOWN_ARGUMENT` を報告します。

## 14.3 論理層は依存関係の DAG

論理層には、信号どうしの依存関係を書きます。ブール演算の組み合わせとマクロの適用です。時間を含まない純粋なデータフローで、コンパイラの内部では Logic IR になります。

```
logic sig.lamps = sig.power and not sig.day
logic sig.mem   = latch(set=sig.a, reset=sig.b)   # RS ラッチ (マクロ)
logic sig.pulse = pulse(sig.ring, 4)              # 単安定: 4 段
logic sig.fire  = edge_rising(sig.tick)
logic sig.sel   = mux(sel=sig.s, a=sig.x, b=sig.y)
```

式には時間の演算がありません。`pulse(sig.ring, 4)` の `4` は tick 数ではなく **段数** です。

マクロは 1 つのノードで、`latch` と `counter` が状態を保つための帰還はそのセルの内側に閉じている ([§14.6](#146-エディションの違い)) ので、グラフは非巡回のままで、配置はトポロジカル順を保ちます。信号が自分自身を読み返すと、マクロを通していてもいなくても `E_LOGIC_CYCLE` のままです。`logic sig.q = latch(set=sig.a, reset=sig.q)` は、作者が書いた循環です。

## 14.4 時間モデル

v1 で時間を持つのはマクロ (`delay` / `pulse` / `edge_rising` / `edge_falling` / `latch` / `counter`) だけです。tick を扱う演算子はありません。マクロが数えるのは段の数で、tick 数ではありません。`delay` と `pulse` の 1 段はどちらのエディションでも 2 tick なので、`delay(sig.x, 3)` は、合わせて 6 tick かかるよう直列につないだリピーターに展開され、エッジはどちらも 1 段の間オンになります。`counter` の 1 段はそのリングのフリップフロップ 1 個なので、`counter(sig.x, 3)` はフリップフロップ 3 個でできています。マクロが経路に加える tick 数は、ほかのセルと同じく、その Edition Cell の tick 数として数えます ([§14.6](#146-エディションの違い))。

| マクロ | 出力 |
|---|---|
| `delay(x, n)` | `x` を `n` 段遅らせたもの |
| `pulse(x, n)` | `x` がオンで、かつ `n` 段前にオフだった間オン。`n` 段オフだった `x` がオンになるたびに、最初の `n` 段の間だけオン。それより先に `x` がオフになれば、そこまで |
| `edge_rising(x)` | `pulse(x, 1)`。1 段オフだった `x` がオンになるたびに 1 段の間だけオン |
| `edge_falling(x)` | `x` がオフで、かつ 1 段前にオンだった間オン。1 段オンだった `x` がオフになるたびに 1 段の間だけオン |
| `latch(set=s, reset=r)` | `s` がオンで `r` がオフの間にオンになり、`r` がオンの間にオフになり、両方がオフの間は保つ |
| `counter(x, n)` | `x` が `n` 回目にオンになるとオンになり、`2n` 回目でオフになる。`n` 回ごとに切り替わるので、`counter(x, 1)` はトグル |

`reset` が勝ちます。`set` と `reset` が両方オンの `latch` はオフで、2 つが同時にオフになってもオフのままです。`latch` と `counter` が応じるのは、変化を少なくとも 1 段保つオペランドで、それより早く元に戻るオペランドでどう振る舞うかは定めません。エッジと `pulse(x, 1)` は 1 段の間まるごとオンなので、どちらも `latch` や `counter` を駆動できます。`latch` と `counter` はオフから始まります。どのマクロも、構造物を組み上げた時点ではそうです。タイル層は各セルを、オペランドがすべてオフのときに落ち着く状態で書き出します。

**遅延は Logic IR にも Netlist IR にも現れず、Placement IR で初めて確定します** ([§14.8](#148-ir-とフェーズの関係))。`and` は論理的には遅延ゼロですが、何 tick かかるかは、セルの選択 (Java なら `and → ComparatorAND`) と、配置後の実際の配線長が決まるまで分かりません。マクロの段数はどちらの IR にも、どのセルかの一部として載りますが、その tick 数は載りません。

セルは各オペランドを、それぞれ専用の入力ポートで受け取ります。2 入力のセルでは `a` と `b`、`not` と各適用形式のマクロでは `a`、`mux` と `latch` では呼び出しが名前を付けるオペランドです。入力によっては、ほかの入力よりセルの多くの部分を通ることがあるので、セルの遅延は入力ポートごとに、そのポートからセルの出力までの tick 数として数えます。信号がセルを通るときの遅延は、その信号が入るポートの遅延です。マクロのポートが 1 回変化すると、`pulse` がオンになってからオフになるように、出力が 2 回以上変化することがあるので、マクロのポートは、その変化が出力に起こす最後の変化までの tick 数を数えます。

数値が tick として現れるのは、検証のアサーション ([§14.7](#147-検証)) だけです。論理式の中で tick の計算をすることはありません。

## 14.5 配置配線 (place-and-route)

配置配線は、各スコープのネットリストを実寸の回路として組み上げます。部品 1 つにつきブロック 1 つで、スコープが床下に確保した層に置きます。struct はその層の上へ持ち上がります。

```
circuit region=floor void=3       # 床下に 3 層を確保し、そこに回路を敷く
```

この行は `struct` または `def` に 1 つだけです。同じ本体にある 2 つ目は `E_DUPLICATE_CIRCUIT` です ([Lint §11.1](/ja/spec/lint/#111-診断コード))。確保が 2 つ以上必要なロジックは、2 つ以上のスコープに分けます。

この行は、本体自身のメンバーの間に置きます。確保はどのメンバーも立たない基準面の下にあり、どの `level` の `y=` も取らないので、配置配線は `level` の下の `circuit` 行を読みません。そうした行は `E_DUPLICATE_CIRCUIT` ではなく、その行の `E_MISPLACED_MEMBER` になります。

ロジックに組み立てるセルか駆動するアクチュエーターが 1 つでもあれば、スコープにはこの行が要ります。行のないスコープは、最初のセルで、セルがなければ最初のアクチュエーターのバインディングで `E_NO_CIRCUIT_REGION` になります。何も確保しない行を持つスコープも同じです。`region=` のラベルがない行、`void=` が 1 以上の整数でない行、`size=WxH` のないスコープの行がそれに当たります。`site` は確保する基準面を持たないので、`site` にあるそうしたロジックも `E_NO_CIRCUIT_REGION` です。

**確保。** `void=N` は、struct を組み上げる足元の全体、屋根の `overhang=` が足す外周も含めて、基準面の下に `N` 層を確保します。組み上げた struct は `N` 層高くなり、どのメンバーも地面の上に立っていたとおりに確保の上に立ちます。`site` に置いた `def` は原点が `N` 下がるので、その基準面は `site` が決めた位置のままです。1 つの構造物が持てるブロック数の上限、つまり `W_STRUCTURE_TOO_LARGE` が守る体積 ([Lint](/ja/spec/lint/#lowering)) を struct が超えてしまう `void=` は、`circuit` 行の `E_ROUTE_CONGESTION` です。

回路はそれらの層の上から `min(N, 5)` 層に収まり、その下の層は空のまま残ります。

- **最下層**。全面に回路ブロックを敷き、その上のすべてがここに載ります。
- **セルの層**。各セルのタイルがここに立ちます。`counter` のタイルは 1 層上まで伸びます。
- その上の最大 **2 層**。ある信号のダストが、別の信号のダストを乗り越える層です。
- **最上層**。床のすぐ下にあり、回路が struct と接する層です。

したがって確保には 3 層が要り、ロジックが `counter` を含むなら 4 層が要ります。`counter` のフィードバックは、自分の配線を 1 層上で越えるからです。それより少ない `void=` は `circuit` 行の `E_ROUTE_CONGESTION` で、メッセージが必要な層数を示します。回路ブロックは `@circuit.block` で ([マテリアルとテーマ](/ja/spec/materials-themes/#tier-1-のトークン))、最上層のうち床のブロックの下で回路が空けたボクセルもすべてこれで埋めます。

**回路が struct と接する場所。** 何かがその信号を読むセンサーは、その下の最上層にあるパッドから回路に入ります。バインディングが駆動するアクチュエーターは、ライザーが駆動します。ライザーは直列の 2 本のトーチで、信号をセルの層から最上層まで持ち上げ、上のトーチがアクチュエーターの下に来ます。どちらも床の行より先には届かないので、部品が回路と接するのは、床の行 `y = 0` に立つときか、自分と最上層の間で動力を伝える床のブロックの上、`y = 1` に立つときだけです。

| 部品 | 立つ場所 | 回路側で接するもの |
|---|---|---|
| `pressure_plate` | `y = 0`、またはブロックの上の `y = 1` | `y = 0` では、その下にあって感圧板が動力を与えるブロックと、さらにその下のダスト。`y = 1` では、感圧板が全体に動力を与える足元のブロックの下のダスト |
| `lever`、`button` | `y = 0` | その下のダスト |
| `daylight` | `y = 0` | その下のダストと、続くリピーター。強度が空の明るさに従うため |
| `observer` | 上向き (`facing=up`) で `y = 0`、またはブロックの上の `y = 1` | 背面の下のダスト、または背面が全体に動力を与えるブロックの下のダストと、続く 2 tick のリピーター。1 tick のパルスを 1 段分保つため |
| `door` | 床のブロックの上の `y = 1` | ライザーの上のトーチ。そのブロックの下にあって、ブロックに動力を与える |
| `lamp`、`piston`、`dispenser` | `y = 0`、または床のブロックの上の `y = 1` | ライザーの上のトーチ。部品の下か、部品が立つブロックの下にある |

それ以外の場所にある部品は、その行の `E_ROUTE_UNREACHABLE_COMPONENT` です。メッセージはその種類の部品が床下の層に届く場所を示し、修正案はそこへ移す方法です。下を向いた `piston` も同じで、下のトーチへ押し込んでしまいます。ライザーが別の部品まで駆動してしまうアクチュエーターも同じです。ライザーのトーチが動力を与えるセル、つまり床の行にあるアクチュエーター自身か、`y = 1` のアクチュエーターの下のブロックは、床の行でその隣に立つものとその上に立つものにも動力を与えるので、そこにはほかのアクチュエーターも Tier 0 の部品も raw メンバーも立てません。センサーは立てます。動力でセンサーは動かないからです。

```text
room.crn:8:3: error[E_ROUTE_UNREACHABLE_COMPONENT]: struct=room: the lever `l` at y=2 cannot reach the circuit under the floor: a lever or button reaches the layer under the floor only from the floor row `y = 0`, the row over it
  note: Fix: set `y=0` on it
```

最上層は、struct が動力を与えるものから離しておきます。動力を受けたブロックの下のダストは、その動力を読んでしまうからです。そこにダストを通せるのは、床の行の**静かな**セルの下だけです。静かなセルとは、空気か、どの部品も占めないブロックで、隣にも上にもセンサー、Tier 0 の部品、raw メンバーがないセルです。パッド自身のダストは、自分のセンサーだけが動力を与えるセルの下も通れます。ライザーの上のトーチは、下のトーチが動力を与えるブロックに付き、そのブロックはどの部品も占めないセルの下にだけ置きます。

内部のアルゴリズムはエディションごとに 4 段階で、各段階は前の段階が残したレイアウトに対して動きます。どの選択にも順序が決まっているので、1 つのソースからは 1 つの回路が組み上がります。

1. **配置。** パッドとライザーを最初に置きます。それぞれ自分の部品の下に立つからです。各パッドとライザーは、ほかと並んで収まる向きのうち、回路がつながる端が確保の中央にいちばん近い向きに回します。どの向きでも収まらないパッドやライザーを持つ部品は、その行の `E_ROUTE_CONGESTION` です。続いて各セルのタイルを、ネットリストの順に、そのネットがつなぐタイルにいちばん近い空き場所へ置きます。いちばん近い場所とは、すでに置いたタイルのうちネットを共有するもののポートと出力から、自分のポートと出力までの距離の合計が最小の場所で、同じなら `z` の小さい方、`x` の小さい方、向きは東、南、西、北の順です。空き場所とは、タイルが確保の中で最上層より下に収まり、ほかのどのタイルからも余白の列を空け、それまでに置いたどのポートと出力にも配線が届く面を残す場所です。セルは余白 2、1、0 列で置き、セルとネットを共有するタイルとの距離の合計がいちばん小さいレイアウトを残します。どの余白でも空き場所のないセルは、その `logic` 行の `E_ROUTE_CONGESTION` で、メッセージがそのタイルに要る列を示します。

   25 段を超える `pulse` と 4 段を超える `counter` は、何かを置く前に、その `logic` 行の `E_ATTENUATION_LIMIT` になります。前者はオペランドがリピーターごとに 1 ブロックのダストを通り、後者はすべての段の横を通ります。どちらも 1 本のダストで、15 ブロックを超えると信号が消えます。`delay` はリピーターを 2 段に 1 個ずつ 1 列に並べるので、ポートと出力を含めたその列が struct のどちらの辺よりも長いものは、セルを置く前に、その `logic` 行の `E_ROUTE_CONGESTION` になります。
2. **配線。** 各ネットのダストを、そのネットを駆動するタイルから、ネットが入力するすべての入力まで、層に沿って、また階段で上り下りしながら敷きます。それまでのダストから、まだ届いていないいちばん近い入力までの最も安い経路を取り、層に沿った 1 歩は 1、上りか下りの 1 歩は 2 と数えます。上りでは下のダストの上のセルを、下りでは上のダストの隣のセルを空けておくので、2 つがつながります。下に何もないダストにはブロックを置きます。ダストは最下層より上にだけ敷き、ほかのネットのダストとつながる場所にも、タイル自身のダストの隣にも敷きません。ネットは入力の多い順に、同じならネットリストの順に配線します。道が見つからないネットは先頭へ移してネットを配線し直し、それを 3 回まで繰り返したあと、ほかの余白でセルを置き直します。そのどれでも道が見つからないネットは、それを駆動する行の `E_ROUTE_CONGESTION` です。

   ```text
   crossbar.crn:24:3: error[E_ROUTE_CONGESTION]: struct=crossbar: the sensor's signal finds no way to every input it feeds through the reservation (region 10x8, void=4) without running beside another signal's dust
     note: Fix: widen the struct's `size=WxH`, increase `void`, or split the logic across several scopes, each with its own `circuit` line
   ```
3. **遅延の挿入。** 信号は、強度を回復する部品、つまりパッド、トーチ、リピーター、強度を回復するセル ([§14.6](#146-エディションの違い)) を強度 15 で出て、ダスト 1 ブロックごとに 1 ずつ弱まります。Java の `ComparatorAND` は何も回復せず、後ろの入力が読む強度をそのまま渡します。各入力は、ネットを駆動する部品それぞれが単独でダスト越しに届ける強度を読み、少なくとも 1 を、タイル自身のダストがポートの先へ信号を運ぶ場合はそれ以上を必要とします。必要な強度に届かない入力があれば、入力にいちばん近く、最後に信号を回復した部品へ戻る途中で、リピーターが収まる場所のネット自身のダスト 1 ブロックをバッファのリピーターに置き換えます。収まる場所とは、ダストが 3 ブロックにわたって真っすぐ水平に続き、ほかの何ともつながらず、リピーターへまだ動力を運び、横から駆動されていない場所です。すべての入力が必要な強度を読むまで、リピーターを 1 つずつ入れます。そうした場所ではどこまで持ち上げても足りない入力は、それを読むタイルの行の `E_ATTENUATION_LIMIT` で、メッセージはダストが 15 ブロックを超えて続き、リピーターを置ける真っすぐな区間がないことを伝えます。
4. **合法化。** すべての部品を、組み上げるときのブロックにします。ID は部品のトークンに対するターゲットのもので、ダストは `@redstone_dust.default`、トーチは `@redstone_torch.wall`、リピーターは `@repeater.default`、コンパレーターは `@comparator.default`、それ以外のブロックはすべて `@circuit.block` です。各ブロックは、すべてのセンサーがオフのときに回路が落ち着く状態で書き出します。この段階は、何も変わらなくなるまで回路を動かしてその状態を求めます。ダストは強度とつながる面、トーチは点灯しているかどうか、リピーターは動力を受けているかどうかとロックされているかどうか、コンパレーターは出力する強度で、その強度は構造物がブロックエンティティに保持します。`latch`、`counter` をはじめ、どのマクロもオフから始まります ([§14.4](#144-時間モデル))。Bedrock は消灯したトーチと、動力を受けたリピーターやコンパレーターを、`unlit_redstone_torch` や `powered_repeater` のような別のブロックとして持ち、Bedrock のビルドはそれを書き出します。いつまでも落ち着かない回路は `circuit` 行の `E_ROUTE_CONGESTION` です。前の段階が受け入れたレイアウトでそうなることはないはずなので、メッセージはその struct をバグとして報告するよう求めます。

配線は `circuit` の確保の中に限られます。確保に収まらない回路は拒否され、確保の外に敷かれることはありません。

## 14.6 エディションの違い

3 層のセルライブラリが、エディションの違いをライブラリの中だけに閉じ込めます。

```
Logical Cell → Edition Cell → Physical Tile
  AND        → Java:    ComparatorAND → block array
             → Bedrock: TorchAND      → block array
```

Java の `ComparatorAND` は減算モードのコンパレーターで、一方のオペランドを反転し、最大強度で側面に入れます。そのオペランドがオンの間は側面が 0 を読み、コンパレーターは後ろの入力が運ぶ強度を出力します。オフの間は側面が 15 を読み、後ろの入力が何を運んでいても出力は 0 です。どちらのオペランドもネットリストが運ぶとおりにセルに届くので、反転はセル自身が行い、そのうえで AND を計算するのが減算モードです。比較モードでは、側面が 15 を読んでいる間も、強度 15 の後ろの入力がそのまま通ってしまいます。

`ComparatorAND` は、ポート `a` を後ろの入力にし、`b` を反転して側面に入れます。ポートごとに数えると ([§14.4](#144-時間モデル))、`a` から入る信号はコンパレーターだけを通るので 1 tick、`b` から入る信号は反転とコンパレーターを順に通るので 2 tick です。`and` や `or` のオペランドのうち、どちらをネットリストが `a` に置くかは規定しないので、`ComparatorAND` を通る経路の tick 数は書く順序では決まりません。それを検査するのは `assert latency` ([§14.7](#147-検証)) で、オペランドが実際に入ったポートで数えます。

どの論理セルにも、エディションごとに 1 つの実現があります。ポートの tick 数は、そのポートから出力までのいちばん遅い経路で数えます。マクロでは、そのポートの変化が出力に起こす最後の変化までを数えます ([§14.4](#144-時間モデル))。セルは強度を回復するか (そのときは各ポートへの配線がそこで終わります)、入力の 1 つが運ぶ強度をそのまま渡すかのどちらかです ([§14.5](#145-配置配線-place-and-route))。

| 論理セル | Java | Bedrock | ポートごとの tick 数 | 強度 |
|---|---|---|---|---|
| AND | `ComparatorAND` | `TorchAND`、OR を反転する 2 本のトーチ | Java は `a` が 1、`b` が 2。Bedrock は 2 | Java は後ろの入力の強度を渡す。Bedrock は回復する |
| OR | `RepeaterOR`、共通の線に入る 2 個のリピーター | 同じ | 1 | 回復する |
| NOT | `InverterTorch` | `InverterTorch` | 1 | 回復する |
| NAND | `TorchNAND`、共通の線に入る 2 本の反転トーチ | 同じ | 1 | 回復する |
| NOR | `TorchNOR`、両方のオペランドが動力を送るブロックに付いた 1 本のトーチ | 同じ | 1 | 回復する |
| XOR | `TorchXOR`、`a` と 2 つの NOR のトーチ NOR、`b` と 2 つの NOR のトーチ NOR を共通の線に入れる | 同じ | 2 | 回復する |
| MUX | `TorchMUX`、`sel` と `not a` のトーチ NOR、`not sel` と `not b` のトーチ NOR を共通の線に入れる | 同じ | 2 | 回復する |
| DELAY `n` | `RepeaterDelay`、合わせて `2n` tick になるよう直列につないだリピーター | 同じ | `2n` | 回復する |
| PULSE `n` | `TorchPulse`、`not a` と、`2n + 1` tick のリピーターを通した `a` のトーチ NOR | 同じ | `2n + 2` | 回復する |
| EDGE_RISING | `TorchEdgeRising`、1 段の `TorchPulse` | 同じ | 4 | 回復する |
| EDGE_FALLING | `TorchEdgeFalling`、`a` と、リピーターを通した `not a` のトーチ NOR | 同じ | 3 | 回復する |
| LATCH | `TorchLatch`、互いに動力を送り合う 2 本のトーチ NOR | 同じ | `set` が 4、`reset` が 5 | 回復する |
| COUNTER `n` | `RepeaterCounter`、ロックするリピーターでできた `n` 個のフリップフロップのジョンソンカウンター | 同じ | 3 | 回復する |

`xor` のオペランドは、自分の NOR にはそのまま、もう一方には 2 つの NOR を通って届くので、出力が落ち着くのはその経路が落ち着いたとき、つまりオペランドが変わってからトーチ 2 本分の後です。`mux` の各ポートも同じく、いちばん遅い経路で反転と NOR を通ります。`sel` の場合は、反転して受け取る側の NOR です。

マクロのセルはトーチとリピーターだけでできており、どちらのエディションでも同じです。`latch` と `counter` は帰還を自分のセルの内側に閉じています。

- **`TorchPulse`** は、`not a` がオフになるとオンになり、`a` がリピーターを抜けるとオフになります。リピーターが `n` 段より 1 tick 長いのは反転の分を合わせるためで、オンの長さは `n` 段になります。ポートが数えるのはこのオフになるまでで、リピーターと NOR を合わせて `2n + 2` tick です。先にオンになった `a` がまだリピーターの中にあると出力はオフに保たれるので、パルスを `n` 段まるごと出すには、`a` がオンになる前の `n` 段の間オフである必要があります。
- **`TorchEdgeRising`** は 1 段の `TorchPulse` で、オンの長さは 2 tick、ポートは 4 tick を数えます。**`TorchEdgeFalling`** は、`a` がオフになるとオンになり、`not a` が 1 tick のリピーターを抜けるとオフになります。オンの長さは 1 段、最後の変化までは 3 tick です。
- **`TorchLatch`**: 出力のトーチは `reset` と 2 本目のトーチの NOR で、2 本目のトーチは、出力と、`reset` で閉じた `set` の NOR です。閉じた `set` とは、`not set` と、横に置いたリピーターで立ち下がりから 2 tick 長く保った `reset` のトーチ NOR です。`set` は、`not set`、閉じた `set`、2 本目のトーチ、出力の 4 本のトーチを通って出力をオンにします。`reset` は出力のトーチだけを通って出力をオフにし、`set` がオンの間に `reset` が立ち下がると、リピーターとその後の 3 本のトーチを通って、5 tick 後に出力をオンに戻します。`reset` が勝つのはこの保持のおかげです。`reset` がオンの間と、立ち下がった直後の間は、`set` はどこにも届きません。
- **`RepeaterCounter`**: 各段は 2 個のリピーターでできたマスター・スレーブのフリップフロップで、マスターは `a` がオンの間、スレーブはオフの間ロックされます。各段は次の段に入り、最後の段は反転を通って最初の段に入ります。`n` 段のジョンソンカウンターは、すべてオフの状態から `2n` 個の状態を順にたどるので、最後の段、つまり出力は、`a` が `n` 回オンになるごとに変化します。スレーブのロックは `a` がオンになってから 2 tick で外れ、そのリピーターが 1 tick 後にマスターの値を渡すので、合わせて 3 tick です。マスターは 2 tick でロックされ、読み取る段が変化するより前に値を保ちます。

各 Edition Cell の Physical Tile は、部品を実寸で並べたものです。各ボクセルにブロック、トーチ、リピーター、コンパレーター、ダストのどれかがあり、各ポートが読むボクセルと、出力が出ていくダストを持ちます。配置はこれを 90 度ずつ回して置きます ([§14.5](#145-配置配線-place-and-route))。ポートはオペランドを、動力を受けるブロック、駆動されるリピーター、ダストのいずれかとして読みます。タイルの中でオペランドを先へ運ぶダストは、端まで届く強度を必要とするので、ポートはそこへ入る配線がどれだけの強度で届かなければならないかを持ちます。

- **吸収するもの**: リピーター、オブザーバー、コンパレーター、向き。どれもセルの実装の違いです。
- **吸収しないもの**: QC (疑似接続)、BUD、更新順序。ブロック更新順序という暗黙の意味論に依存しており、エディション間で移植できる実装が存在しません。

更新順序の意味論を必要とする論理は、気付かないうちに壊れるのではなく、コンパイルエラー `E_NO_PORTABLE_IMPL` になります。「変換ではなく再コンパイル」という方針と一致します。ライブラリのセルは、マクロのものも含めてどれも自分のタイミングを自分で保つので、回路が更新順序を必要とするのは、組み上げた構造物のあるコンポーネントが、別のコンポーネントをブロック更新を通して読む場合だけです。そうなる形は 2 つで、どちらもそのエディション向けに組み上げた構造物に照らして検査します。

- **回路を読み返すオブザーバー (BUD)。どのエディションでも。** `->` の付いた `observer` で、その正面が、バインディングが駆動する `lamp`・`piston`・`dispenser`・`door`、または駆動されるピストンのヘッドが入るセルを見ているもの。その信号は回路自身の変化で、ブロック更新が届いた時点で現れます。指摘はオブザーバーの行に出し、バインディングを注記で示します。直し方には、同じパルスを順序に依存せずに書いた形 `edge_rising(sig.x) or edge_falling(sig.x)` を示します。
- **上のセルを通して動力を受けるピストンとディスペンサー (QC)。Java で。** 駆動される `piston` か `dispenser` で、センサーが真上のセルを通して動力を与え、直接は与えていないもの。このとき、ブロック更新が届くまでその動力に反応しません。センサーが真上のセルに動力を与えるのは、そのセルの隣に立つとき、またはその隣のブロックを丸ごと動力源にするときです。`lever` と `button` は取り付いたブロックを、`pressure_plate` は真下のブロックを、`observer` は背面のブロックを丸ごと動力源にします。どのブロックが動力を伝えるかを記録した表はないので、空気、センサー、アクチュエーター以外のブロックはすべて伝えるものとみなします。ピストンは正面からは動力を受けません。Bedrock には疑似接続がないので、そこではこれは指摘になりません。

[Tier 0 の部品](#tier-0-の部品)と生のメンバーは作者が責任を持つものなので、どちらも検査しません。センサーがコンポーネントに直接も動力を与えている場合は順序への依存ではないので、報告しません。回路を組み上げるどのコマンドも、配置配線の前にこれを検査します ([§14.8](#148-ir-とフェーズの関係))。次の例では、ディスペンサーの 2 段上のレバーが、ディスペンサーの真上のセルの隣に立っています。

```
theme t:
  slot wall -> @cobblestone

struct s size=7x5
  floor mat_slot=wall
  walls mat_slot=wall height=4
  roof kind=flat mat_slot=wall overhang=1
  dispenser id=p at=inside.back offset=2 y=1 fired_by=sig.p
  lever id=sw at=inside.back offset=2 y=3 -> sig.a
  logic sig.p = not sig.a
  circuit region=floor void=4
```

```text
dispenser.crn:8:3: error[E_NO_PORTABLE_IMPL]: struct=s: on java, the dispenser `p` also takes power from the lever `sw` through the cell above it, and acts on it only once a block update reaches it: this circuit requires update-order (quasi-connectivity) semantics
dispenser.crn:9:3:   note: the lever `sw` powers the cell above the dispenser `p` from here
  note: bedrock has no quasi-connectivity, so this is no dependence on order there
  note: Fix: move the lever `sw` so that it powers no block beside the cell above the dispenser `p`, or redesign the logic to be order-independent; or drop to Tier 0 with an `@edition java` guard
```

Bedrock では、同じソースが配置配線で止まります。床の行から 3 段上のレバーは床下の回路に届かないからです (`E_ROUTE_UNREACHABLE_COMPONENT`、[§14.5](#145-配置配線-place-and-route))。

手で置いたレッドストーンは、エディションをまたぐと壊れます。論理として記述しておけば、コンパイラがエディションごとに正しい回路を出力できます。部品ではなく論理を書く、最大の理由です。

## 14.7 検証

意図を宣言し、合成した回路をターゲットのエディションごとに照合します。アサーションは 3 種類です。

```
# 組み合わせ: 真理値表
assert truth(sig.a, sig.b -> sig.out) { 00->0; 01->1; 10->1; 11->0 }

# レイテンシ: 配置配線で遅延が変わるので重要
assert latency(sig.in -> sig.out) <= 4

# 時相: 完全な LTL ではなく、有界の eventually のみ
assert always(sig.button -> eventually sig.door_open within 8)
```

どの種類のアサーションも、スコープ内で何も駆動していない信号を挙げれば、synth パイプラインが `E_LOGIC_UNBOUND_SIGNAL` で拒否します。真理値表は、行どうしを照らし合わせて検査します ([Lint](/ja/spec/lint/#真理値表))。

`assert latency(<from> -> <to>) <= N` は、`<from>` の変化が `<to>` を読む場所に届くまでの tick 数に上限を設けます。配置配線は経路に tick を足すだけで、レイアウトが破りうるのは上限なので、書けるのは `<=` と tick の整数だけです。ほかの比較はその位置で `E_PARSE` になります。tick は、バッファリピーターがすべて置かれた合法化済みの Placement IR ([§14.8](#148-ir-とフェーズの関係)) で、ターゲットのエディションごとに数えます。経路は `<from>` を駆動するもの (センサーのパッドかセルの出力) から始まり、セルを通って `<to>` に至ります。入るセルごとに、入ったポートの tick 数 ([§14.4](#144-時間モデル)) を、通る配線上のバッファリピーターごとに 1 tick ([§14.5](#145-配置配線-place-and-route)) を数え、ダストは数えません。`<to>` をその名前で読むアクチュエーターがあれば、経路はその配線上のリピーターを通ってアクチュエーターのライザーまで続き、その 2 本のトーチを上る 2 tick を加えます。複数あれば最も遅いものまでを数えます。なければ、`<to>` を駆動する場所、つまりそのセルの出力かそのセンサーのパッドで終わります。上限が押さえるのは最も遅い経路です。`<from>` の変化が 1 つのセルに 2 つのポートから届くなら、遅いほうのポートで数えます。

最も遅い経路が上限を超えると、そのエディションで `E_SIM_ASSERTION_FAILED` になります。`a` から入る `and` がコンパレーター 1 つだけを通る Java では守れる上限を、トーチ 2 本を通る Bedrock では守れない、ということが同じソースで起こります。この診断は、数えた tick 数を示し、経路が入るセルとそのポート、各配線上のリピーターをそれぞれ注記で挙げます。`<to>` が `<from>` にまったく依存しないなら、一方の変化をもう一方に運ぶ経路がないので、どのエディションでも守れません。これは、エディションを選ぶ前に synth が同じコードで拒否します。依存は Logic IR で判断します。Logic IR では 2 回書いたゲートが 1 つのゲートになり、`logic sig.d = sig.c` が 2 つの名前に 1 つのネットを与えるので、1 つのネットを共有する 2 つの名前は互いに依存し、その間の経路は 0 tick です。配置配線は上限を読まないので、上限はソースの側で守ります。上限を緩めるか、通るセルが少ない経路や、リピーターが少ない配線で守れるようにします。回路を組み上げるどのコマンドも、合法化のあとですべての上限を検査し、1 つでも守れなければ回路を組み上げません ([§14.8](#148-ir-とフェーズの関係))。

```text
reach.crn:13:3: error[E_SIM_ASSERTION_FAILED]: struct=reach: `assert latency(sig.a -> sig.c) <= 1` fails on java: its slowest path from sig.a to sig.c takes 4 ticks, 1 in buffer repeaters on the routed wire and 2 in the torches up to the actuator
reach.crn:10:3:   note: the path enters cell #0 (`RepeaterOR`) by port `a`: 1 buffer repeater on the wire, then 1 tick through the cell
reach.crn:7:3:   note: then the actuator reading sig.c: no buffer repeater on the wire to the torches under it, then 2 ticks up to it
  note: the path's wires carry 1 buffer repeater, one wherever a wire runs past 15 blocks of dust, so laying what reads a signal nearer what drives it needs fewer
  note: Fix: relax the bound to `<= 4`, or shorten the path; the logic is never rewritten to meet a bound
```

`truth` と `always` を回路と照合する仕組みはまだありません。論理と矛盾する真理値表があっても、回路はそのまま組み上がります。自己修正のループ (P5) は **synth → sim → diff → patch** で、ターゲットのエディションごとに走ります。パッチが変更するのは、配置配線のヒント、リピーター、バッファだけです。**Logic IR は決して書き換えません。** 論理を自動で書き換える自己修正は危険だからです。このループはまだ存在しません。守れない上限は報告するだけで、それを守るようにレイアウトを直すものはありません。

## 14.8 IR とフェーズの関係

Intent IR と block-array IR の間に、HDL と同じ分け方で 4 つの IR 層が入ります。

```
Intent IR           logic 宣言 / circuit 領域 / 信号バインディング
   ↓ logic_synth
Logic IR            論理式と依存 DAG。エディション中立、tick を持たない
   ↓
Netlist IR          セルとネット。Logical Cell の選択。まだ遅延なし
   ↓
Edition Netlist IR  同じセルとネット。Edition Cell の選択。まだ配線なし
   ↓ logic_place
Placement IR        各タイルのボクセル。セル、センサーの下のパッド、アクチュエーターの下のライザー
   ↓ logic_route
Placement IR        + 各ネットのダストとバッファのリピーター、続いて各ボクセルのブロック。ここで遅延が確定する
   ↓
block-array IR      その下に敷いた回路の上へ持ち上がった struct
```

Placement IR は、パスごとに順に埋まっていきます ([§14.5](#145-配置配線-place-and-route))。配置が各タイルを置き、続いて配線が各ネットのダストを、遅延の挿入がバッファのリピーターを、合法化が各ボクセルのブロックと状態を加えます。Edition Cell の時点で、各ポートからの tick 数は決まります ([§14.6](#146-エディションの違い))。しかし配線する前には数えるべき配線がないので、遅延が確定するのは Placement IR で、それより前ではありません。`assert latency` は合法化した回路で検査します ([§14.7](#147-検証))。

これらのパスは struct を lowering したあとに走ります。パッドとライザーは、lowering が置いた部品の下に立つからです。順に、合成、組み上げた struct に対する [§14.6](#146-エディションの違い) の順序の検査、配置配線の 4 段階、レイテンシの検査です。エラーを報告したパスで残りは止まり、struct は元のままです。そうでなければ、合法化した各回路をその struct の下に敷き、struct はその上へ `void=` 層だけ持ち上がります。コンパレーターの出力の強度は、そのブロックエンティティに入ります。

`cairn compile` は、コンパイルするエディション向けにすべての回路を組み上げ、パスが報告したエラーは lowering のエラーと同じくコンパイルを拒否します。`cairn lower --edition` は回路を敷いた struct を出力し、`--edition` のない `cairn lower` は回路を敷きません。合成より後のパスはエディションごとだからです。`cairn check` と `cairn info` は、読み取る各エディションでパスを走らせます。1 つに固定すればそのエディションの指摘を、そうでなければどのエディションも同じ場所で出す指摘を報告し、`info` は各エディションに固有の指摘をそのエディションの下に報告します。`cairn synth --experimental-logic-synth` は、途中の各 IR を出力します。

フェーズモデル ([コンパイルモデル](/ja/spec/compilation/)) では、`fixtures` の直後を `logic_synth → logic_place → logic_route` に分けます。センサーとアクチュエーターが 3D 空間に配置されるまで、I/O ポートの座標が決まらないからです。

## 14.9 逆変換

schematic から取り込んだ手作りのレッドストーン ([エコシステム連携](/ja/spec/ecosystem-interop/)) は、v1 では Tier 0 の raw として保持します。ダストの塊から論理を逆合成することは対象外です。生成を優先し、情報の欠落を許容する方針と一致します。
