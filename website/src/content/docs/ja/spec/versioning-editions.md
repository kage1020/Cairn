## 10.1 ターゲットはコンパイル時のパラメータ

ターゲットは `(edition, version)` の組で、どちらもソースには書きません。知っているのはバックエンドだけです ([コンパイルモデル](/ja/spec/compilation/))。

**バージョン文字列は中身を解釈しないラベルとして扱います。** Minecraft のバージョンには、従来の semver 風の `1.21.4` もあれば、最新リリース以降の日付ベースのものもあります。Cairn はバージョン文字列どうしを比べず、Mojang が割り当てる単調増加の整数 **DataVersion** で順序を決めるので、semver から日付ベースへ移っても、`since`/`until`、Vmin/Vmax、`@requires`、`semantic_sensitivity` の境界は壊れません。

バックエンドは「バージョン文字列 ↔ DataVersion」の表を持っているので、`--target` には同じバージョンのどちらの綴りを渡しても構いません。Bedrock も同じように、バージョン文字列を内部の単調なキーに解決します。違いが情報を持たない 2 つのラベルは、同じバージョンです。末尾の成分が欠けていれば 0 とみなし、数値成分の先頭のゼロは桁ではなく桁埋めとみなします。したがって `1.21`、`1.21.0`、`1.021` は 1 つのバージョンです (`1.21.0` は Java の `1.21`、`1.21` は Bedrock の `1.21.0` を指します)。`@requires` と `@intended_targets` もこの規則でラベルを読みます。ビルドとそのロックファイルには、表に載っている綴りでバージョンを記録します。

## 10.2 言語の契約: 変換ではなく再コンパイル

> 仕様は、バージョンやエディションをまたいだ NBT の可搬性を **保証しません**。保証するのは「同じソースを特定のターゲットへコンパイルした結果」だけです。

ソースは設計図で、`.nbt` はターゲットに固定されたビルド成果物、つまりコンパイル済みバイナリに相当します。新しいバージョンや別のエディションで使うときは、ソースを再コンパイルします。

DataFixerUpper は前方向にしか変換できず、情報を失い、対応も不完全です。アイテム、看板、絵画、ブロックエンティティでは欠落がよく起きます。あくまで救済用のツールなので、言語の意味論には含めません。

どうしても解決できない部分は、隠さずに明記します。

- バージョン間の意味の変化 (大釜の分割、アイテムの `tag` → `components`)。
- データテーブルに載らないゲーム挙動 (流体、重力、設置面への取り付け、レッドストーン)。
- 見た目の一貫性 (色温度のずれ)。
- 物理ルールの変更 (1.21 のウィンドチャージが従来のトラップを壊す)。

出力される NBT は幾何的には正しいものの、ゲーム内での体験までは保証しません。

## 10.3 バックエンドはデータテーブル

バックエンドには 2 つの情報源があり、両者は分けて管理します。

**機械的な抽出。** ゲームの `--reports` やレジストリダンプから取り出します。構文とドメインに関する真実はここにあります。ブロックとエンティティの ID、ブロックステートのプロパティとそのドメイン、アイテムとコンポーネントのスキーマ、DataVersion、タグです。誰かの記憶ではなくゲームそのものを真実の源にするので、新しいバージョンについての知識の抜けが根本からなくなります。ただし組み込みパックは、まだ `--reports` から何も抽出していません。上に挙げたもののうちパックが持っているのは、バージョンごとのブロック ID とバージョン表だけです。ブロック表は PrismarineJS/minecraft-data から取り込んでおり、出典は各パックのファイルに記載しています。

**バージョンタグ付きの、手書きの制約カタログ。** データに含まれない事柄を扱います。取り付け (額縁はガラスには掛けられない)、重力と支え (砂利、吊るしたランタン)、流体の挙動、エンティティの AABB、レッドストーンです。新しいバージョンごとに一度定義すれば、すべてのユーザーがその恩恵を受けます。制約カタログはまだ同梱していないので、ロックの `constraint_catalog_hash` はゼロで、意味が変わりうるメンバーとして報告されるものもありません ([§10.5](#105-どのバージョン向けかの答えは-3-つある))。

```yaml
constraints:
  minecraft:item_frame:
    type: entity_attachment
    since: "1.13"
    targets: { solid_full_face: true, glass_pane: false }
    error: "item_frame requires a solid attachable face"
  minecraft:lantern:
    type: support
    states:
      hanging=true:  { requires_above: solid_or_chain }
      hanging=false: { requires_below: solid_top }
```

### `(edition, version)` 行列の畳み込み

正規トークンを主キーにし、各トークンがエディションごとの対応 (id + state_map) を持ちます。バージョンは `inherits + diffs` で畳み込みます。Java が基底で、Bedrock はそれを上書きする差分です。手書きの意味カタログには、違いのある点だけを記録します。

現時点の組み込みパックは、エディションの中でしか畳み込みません。レジストリパックはエディションごとに独立していて、各パックの `pack.json` が自分の `edition` を示し、一方のパックがもう一方を継承することはまだありません。1 つのパックの中では、`blocks` コンポーネントが 1 つのバージョンのブロック ID を持ち、それより後の各バージョンは、継承元のバージョンと、追加・削除した ID を記録します (Java は `1.20.4` → `1.21` → `1.21.4`、Bedrock は `1.21.0` → `1.21.40` → `1.21.60`)。`materials` のエントリは 1 つのトークンを 1 つのブロック ID に対応付け、綴りの違うバージョンを `overrides` に挙げます。次の Bedrock の例では 1.21.0 がそれにあたります。

```json
{ "token": "floor.stone.smooth", "block": "stone_bricks",
  "overrides": [{ "mc_version": "1.21.0", "block": "stonebrick" }] }
```

`state_map` や `sensitivity` を持つパックはまだありません。現在あるステートの変換は階段のファミリのものだけで、Bedrock のバックエンドに直接書かれています ([§10.7](#107-java--bedrock-の可搬性))。

```yaml
"@oak_stairs":
  base: { states: { half: [bottom,top], shape: [straight,inner_left,inner_right,outer_left,outer_right] } }
  mappings:
    java:    { id: minecraft:oak_stairs, base: "1.13" }
    bedrock: { id: minecraft:oak_stairs, state_map: { half=top: {upside_down_bit: true} }, dropped_states: [shape] }
  sensitivity:
    - { edition: bedrock, kind: missing_state, state: shape, reason: "no inner/outer stair shape" }
```

## 10.4 Fail-loud と最小バージョン推定

未知の ID、ドメイン外のステート、パリティの欠落はハードエラーです。黙って置き換えることも、暗黙に落とすことも禁止します。エラーは、ターゲットで有効な候補の閉じた集合、最小バージョン、修正案を返します。モデルを自分の記憶ではなく、レジストリ由来の候補へ引き戻すためです。

ドメイン外のステートは、まだ検査していません。コンパイラが各ブロックのステートの表を持っていないため、下の `E_STATE_DOMAIN` は未実装です。それまでは、ステートリテラル ([構文](/ja/spec/syntax/)) は書かれたとおりに出力され、代わりにどれにも `W_STATE_LITERAL_UNCHECKED` ([Lint](/ja/spec/lint/)) が付きます。下の `E_PARITY_UNSUPPORTED` も未実装です ([§10.7](#代替を書くとき))。最小バージョンを示すエラーもまだありません。表が記録しているのは各バージョンが持つ ID で、ID が最初に現れたバージョンではないからです ([後述](#未知の-id-はどのレジストリに照らして未知なのか))。

```text
E_UNKNOWN_ID line 4: "minecraft:pale_oak_planks" not in java 1.21 registry.
  Nearest: minecraft:dark_oak_planks

E_VERSION_CAP line 2: this file requires version>=1.21.4 (target 1.21).
  Valid java targets: 1.21.4. Fix: --target 1.21.4, or lower the @requires floor

E_STATE_DOMAIN line 18: wall north=true invalid for 1.21.4. Valid: none, low, tall (changed from boolean in 1.16).
  Suggested DSL: wall_segment id=yard_wall connect_north=low

E_PARITY_UNSUPPORTED line 8: text_display is Java-only (since 1.19.4); Bedrock has no display entity.
  Suggested: sign side=front text="Inn", or slot+theme fallback, or @edition java guard
```

### 未知の ID はどのレジストリに照らして未知なのか

ID は、エディション全体ではなく、コンパイルが固定した 1 つの `(edition, version)` のブロック表と照合します。Bedrock 1.21.0 は石レンガを `stonebrick` と綴り、1.21.40 は `stone_bricks` と綴ります。エディション単位で判定すると、どちらの綴りもどこでも通ってしまい、どちらの誤りも捕まえられません。表はレジストリパックの `blocks` コンポーネントに入っており、[§10.3](#103-バックエンドはデータテーブル) の `inherits + diffs` の規則で畳み込まれます。

したがってこの検査は、バージョンを固定した場所でしか走りません。`cairn compile --target`、同じ組を固定して同じパスを走らせ、何も書き出さない `cairn check --edition E --target V`、そしてサポート対象の各バージョンを順に固定する `cairn info` の `buildable targets` 行の 3 つです。ファイルの下限が拒否するターゲットに対する `compile` は、何も固定しません。ID は 1 つも照合せず、代わりに下限で拒否します ([§10.4](#宣言した下限は強制される))。一方 `check --target` は下限に縛られないので、その場合でもターゲットを固定します。`buildable targets` 行は、各バージョンの `E_UNKNOWN_ID` をそのバージョンの下に報告し、終了コードは変えません ([§10.5](#buildable-targets-の行))。`info` のほかの行はもともと範囲全体について報告するためのもので、`cairn lower` はターゲットなしで lowering するので、どちらもバージョンを固定しません。作者の代わりにバージョンを選ぶことはせず、比較そのものを飛ばします。`--target` を付けない `cairn check` は、ターゲットなしで lowering します。バージョンを固定せず、各抽象トークンはそれをビルドするターゲットのパックに任せるので、この検査も `E_UNKNOWN_ABSTRACT_TOKEN` も `W_ABSTRACT_TOKEN_DEFERRED` も発生しません ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。

エディションが出荷する *すべての* バージョンと照合し、どれにも存在しない ID だけを拒否する方式なら、フラグは要りません。ただしそれは別の問いへの答えです。`stone_bricks` は Bedrock のどこかには存在するので、1.21.0 に固定したビルドには何も知らされません。答えを「いま作っているビルドについての真実」にしているのは、固定です。

ID の誤りには 2 通りの経路があるので、修正案も 2 つに分かれます。**タイポ** には、同じ表に対する距離検索で答えます。`oak_plank` には `oak_planks` を返します。**リネーム** はタイポではありません。Bedrock は Java の `light` を `light_block_0` … `light_block_15` と綴り、編集距離は 8 です。タイポ検索の精度を保つ閾値では、この 2 つが結び付くことはありません。リネームにはレジストリパックの `aliases` コンポーネントで答えます。ただし、パックにその行がある場合に限ります。行がなければ、無関係な最寄りのブロックを示すのではなく「候補はない」と答えます。

`aliases` の 1 行は **綴りのグループ** です。1 つのブロックがこれまでに名乗ってきた名前を、エディションをまたいで、また 1 つのエディションのサポート範囲内でも並べたものです。古い 1 つの綴りが分かれてできた複数の ID も含みます。

```json
{ "spellings": ["light", "light_block", "light_block_0", "light_block_1"] }
```

行には、どの綴りがどの `(edition, version)` のものかは書きません。それは `blocks` コンポーネントがバージョンごとに知っているので、照合は「グループを取り出し、固定したターゲットが宣言している綴りだけを残す」という手順になります。このおかげで、同じ行の集まりで Java → Bedrock (`oak_sign` → `standing_sign`) にも、Bedrock 1.21.0 → 1.21.40 (`stonebrick` → `stone_bricks`) にも答えられます。答えは §10.4 が求める閉じた候補集合であり、そこから 1 つを選んだものではありません。Bedrock 1.21.60 での `@light` には、16 段階の明るさすべてを返します。1 つを選べば、この節が禁じるサイレント置換になるからです。

このキーで表せないのは、両方のエディションが宣言していながら別のブロックを指す綴りです。Bedrock の `snow` は Java の `snow_block` で、Java の `snow` は Bedrock の `snow_layer` です。こうした組には行を作らず、その場合もタイポ検索は引き続き働きます。

同じバージョン単位の扱いは、パック自身のマテリアル対応にも当てはまります。エントリは、綴りの違うバージョンを列挙する `overrides` を持てます。これによって、1 つの `@floor.stone.smooth` が、途中にリネームを含む範囲でも解決できます。`since` の側はまだ保留です。表が記録しているのは、あるバージョンがどの ID を *持っているか* であって、どのバージョンで初めて導入されたかではありません。上の `E_VERSION_CAP` の例も、レジストリからの推定ではなく、`@requires` の下限によるものです。

### 構成要素は自分の下限を宣言できる

`def` と `theme` は、独立した行で `requires version>=X` を宣言できます。合成したものの最小バージョンは、構成要素の最小バージョンの最大値です。

```
def cottage size=9x7:
  requires version>=1.21.4
  walls mat_slot=wall height=4
```

式は `@requires` と同じで、エディションスコープも書けます。2 つの書き方の違いは、何を述べるかではなく、何を制約するかです。モジュールレベルの `@requires` は *ファイル* に対する下限で、こちらは *構成要素* に対する下限なので、`place use=cottage` はこの下限を引き継ぎます。テンプレートのライブラリは、利用する側がいちいち書き直さなくても自分の要件を持ち運べます。

**ビルドが下限を引き継ぐ構成要素。** `place use=` が名指す `def` と、スコープに割り当てられた `theme` です。どこからもインスタンス化されない構成要素は、何も寄与しません。どの `place` にも名指されない `def` はボクセルを 1 つも作りません (すでに `W_UNUSED_DEF` の対象です)。それを理由にターゲットを拒否するのは、作者がファイルに残しておいただけのテンプレートを理由に拒否するのと同じです。

**テーマの下限は、テーマを割り当てた時点で適用します。** メンバーがそのテーマからスロットを読むかどうかは問いません。テーマを割り当てることは、そのテーマが宣言する内容を引き受けることだからです。ルールが実際に発火したときにだけ下限を課す方式も考えられますが、それでは下限が、どのセレクタがマッチしたか、固定がどのバリアントを選んだかに左右されます。すると同じソースが、エディションとは関係のない理由で、Java では 1.21 を要求し、Bedrock では何も要求しないことがありえます。しかもこの方式は危険な側に倒れます。過剰に適用された下限は、それを設定した行に対して報告され、1 か所直せば済みます。適用され損ねた下限は、ファイル自身が除外しているビルドを検証済みにしてしまいます。

テーマを割り当てるものは 2 つあり、どちらもビルドが lowering するスコープです。1 つは `place ... theme=NAME` の参照です。`place` には `theme=` が必須なので、これは配置する `def` をインスタンス化するものでもあります。もう 1 つはモジュールレベルの自動選択で、配置を伴わずにビルドが lowering する唯一のスコープである `struct` に対して読まれます。自動選択は唯一のテーマをすべての `def` スコープにも割り当てますが、下限はそこまでは追いかけ *ません*。どの `place` にも名指されない `def` は何も作らないので、そうした `def` があることを理由にテーマの下限を課すと、同じ `def` を「テーマの下限を引き受ける程度にはインスタンス化されている」と読み、同時に「自分の下限を課されるほどにはインスタンス化されていない」と読むことになります。配置される `def` は、その配置自身の `theme=` を通じてテーマに到達します。

`struct` と `site` はこの行を持てません。どちらも何かからインスタンス化されるものではなく、それ自体がビルドなので、内側に書いた下限は、それが置かれたファイルそのものを制約することになります。それは `@requires` がすでに述べている内容です。メンバー自身のインデントされた子も同じです。下限は構成要素に属するもので、`walls` の行は構成要素ではありません。拒否は 3 種類でメッセージも 3 つですが、修正は 2 通りです。一方は `@requires` を、もう一方はインデントを戻すことを示します。`def` の中にあるメンバーの子には、インデントを戻す修正を示します。`struct` や `site` の中では、インデントを戻しても行はやはりそれを拒否する本体に入るだけなので、`struct` や `site` 自身と同じく `@requires` を示します。下限かどうかは行より後を読む前に式で判定するので、下にインデントされた行を持つ下限も、メンバーとしては読まれず、下限として拒否されます。いずれの場合も、語だけを理由には拒否しません。下限を読まない本体では `requires` はふつうのキーワードなので、そう綴ったメンバー行は、`struct`、`site`、メンバーの下で、下限の行という仕組みがない場合とまったく同じようにパースされます。

`def` と `theme` の本体はその逆で、語の後に何が続いてもその語を受け取ります。行は下限として扱い、下限として読めない式はメンバーではなく `E_INVALID_REQUIRES` になります。これで失うものはありません。`requires` はもともとメンバーのキーワードではないので、下限の仕組みがなくても同じ行は `E_UNKNOWN_KEYWORD` になるからです。

`E_VERSION_CAP` は、数値だけでなく、下限を課した構成要素も名指します。テンプレートの中に書かれた下限で拒否されたターゲットは、バージョン番号だけを示されても対処できません。直すべき場所は、それを引き継いだ `place use=` の向こう側にあるからです。

### 宣言した下限は強制される

モジュールの下限は積で合成します。`cairn compile --target` は、そのビルドに適用されるすべての `@requires` 行と照らし合わされ、どれか 1 つでも下回れば `E_VERSION_CAP` です。これは成果物を準備する前に報告するので、拒否されたビルドは構造ファイルもロックも残しません。この順序には意味があります。ロックは検証した内容を記録するものなので、ソース自身が除外しているターゲットに対して `verified: true` と書いてはならないからです。

下限を下回るターゲットには、たいていファイルが使っているブロックも存在しません。ターゲットより後に追加されたブロックを使うことが、下限を宣言するよくある理由だからです。そこで `cairn compile` は、下限が拒否するターゲットではバージョンを固定しません。下限を下回るターゲットと、このエディションの表で位置づけられないバージョンを下限が名指しているときのすべてのターゲット ([§10.4](#順序はエディションごとに-dataversion-で決める)) がこれにあたります。ターゲットがすべての下限を満たすまでは、ソースが名指す ID を 1 つも照合しません。どのバージョンにも存在しない ID も同様です。ビルドは代わりに下限を理由に `E_VERSION_CAP` か `E_REQUIRES_UNORDERABLE` で拒否されます。下限を宣言した理由であるブロックを置き換えるよう促す `E_UNKNOWN_ID` は出ません。バージョンを必要としない指摘は、それでもこの拒否より先に報告します。`E_INVALID_REQUIRES` のような check パスの指摘や、`E_UNKNOWN_ABSTRACT_TOKEN` のような lowering の指摘です。その中にエラーがあれば、拒否にたどり着く前にビルドは止まります。`cairn check --edition E --target V` は下限に縛られないので、下限が拒否するターゲットでも、そのターゲットにない ID を報告します。同じターゲットで `compile` が報告するのは下限のほうです ([Lint](/ja/spec/lint/#マテリアルとターゲット))。

### ヒントは下限と突き合わせる

`@intended_targets` ([§5.3](/ja/spec/syntax/#53-ヘッダ)) は検証の記録ではなく願望で、その上にある下限は制約です。ファイルには、両立しない形で両方を書けてしまいます。`@requires version>=1.21` の隣に `@intended_targets ["1.20.4"]` を書く場合です。下限だけを検査すると、一方はビルドを決め、もう一方は決めないことになります。指示のように読めるヘッダのほうが無視されるので、これは最悪の組み合わせです。

そこで、ヘッダが名指す各バージョンをターゲットのエディションの表に位置づけ、次の 3 通りのいずれかで答えます。

| バージョン | 指摘 |
|---|---|
| そのエディションのどの `--target` でも指定できない: パックがブロックデータを同梱していないリリース (Java の `1.19`)、または表で位置づけられないラベル (Java の `1.21.40`) | `W_INTENDED_TARGET_UNSUPPORTED` |
| そのエディションでビルドできるが、ファイルが宣言する下限を下回る | ビルドできるもの *すべて* が該当すれば `E_INTENDED_TARGET_CAP`、*一部* だけなら `W_INTENDED_TARGET_CAP` |
| そのエディションでビルドでき、すべての下限以上 | なし |

この順序は意図的です。コンパイラがビルドできないバージョンは、下限が何であれ、まずそのこととして報告します。作者が対処すべきなのは `--target 1.19` が存在しないという事実で、その隣に cap を並べると、ビルドを止めているわけではない下限を直させることになるからです。2 つの cap コードを分けるのは、種類ではなく及ぶ範囲です。「対象だと書いたものが 1 つもビルドできない」は、2 つの宣言の矛盾として最も強い読み方で、そう意図する作者はいません。一方、片側の端だけが下限を越えているリストは、願望を広く書きすぎただけで、下限より上に挙げたものは問題なくビルドできます。

**「すべて」に数えるのは、そのエディションがビルドできるバージョンだけです。** どの `--target` にも載らない名前は、リストのどの部分の答えにもなりません。たとえば `version>=1.21` のもとでの `@intended_targets ["1.20.4", "1.19"]` は、2 つ目ではなく 1 つ目のケースです。Java がビルドできるのは 2 つのうち 1 つだけで、それを下限が拒否しているからです。`1.19` を数に入れると、もともとビルドできないバージョンのせいで、何もビルドできないファイルが「半分だけの問題」として報告されてしまいます。`1.19` は unsupported として別に報告され、その修正もそちらにあります。

どの下限が効くかは、[§10.4](#構成要素は自分の下限を宣言できる) で定めた合成の畳み込みで決まります。ファイルの `@requires` 行と、ビルドがインスタンス化するすべての構成要素です。ライブラリの `def` が、それを配置するファイルの意図を拒否することもあり、その場合の指摘はその構成要素を名指します。もう一方のエディションにスコープを限った下限は、ほかの場面と同じくここでも効きません。このエディションの表で位置づけられない下限は、何も拒否しません。それは `E_REQUIRES_UNORDERABLE` で、直すべきは意図ではなく `requires` の行です。

`cairn check` を通過条件にするすべてのコマンド (`check`、`info`、`lower`、`compile`、`synth`) が 2 つの cap コードを報告し、それぞれ自分が対象とするエディションの表でヘッダを照らします。`--edition` が指定した 1 つ、`cairn info --editions` が挙げたもの、どちらの指定もなければ両方です。どちらかのエディションで出た指摘は報告します。矛盾は、後でどうビルドするかに関係なく、ファイルの 2 行の間にあるからです。また、1 つのスパンが持つ cap の指摘は 1 つだけです。及ぶ範囲について 2 つのエディションの判断が食い違えば、エラーを報告します。一方がリストの一部をまだビルドできると判断しても、もう一方の「1 つもビルドできない」が弱まるわけではないからです。

`W_INTENDED_TARGET_UNSUPPORTED` は、対象のエディションがちょうど 1 つのときにだけ報告します。Java でビルドできないバージョンが、作者の意図する Bedrock のターゲットであることはよくあるからです。`cairn info --editions bedrock` は対象が 1 エディションなので、Bedrock の表だけで照らします。1 つのエディションに絞ったレポートが、もう一方のエディションの答えで拒否されることはありません。

`E_REQUIRES_CONFLICT` は **予約済み** です。宣言された下限が、レジストリから *推定した* 範囲と矛盾することと定義されていますが、パックが `since` / `until` を持たないため、推定範囲はまだ導出していません。2 つの `@requires` 行の衝突ではありません。下限は最も厳しいものに畳み込まれるので、積が空になることはないからです。`version<1.20` のような上限が必要な制約は言語として受け付けない形で、`E_INVALID_REQUIRES` になります。

### 順序はエディションごとに DataVersion で決める

[§10.1](#101-ターゲットはコンパイル時のパラメータ) は `DataVersion` を順序の基準と定めており、`@requires` もそれを使います。下限は **ターゲットのエディションの** バージョン表 (`registry-data/{java,bedrock}/data_versions.json`) の中に位置づけ、ターゲット自身の `DataVersion` と比べます。

この表には、そのエディションの **リリース系列** のうち、表が収録しているものが載っています。パックが *ビルド* できるバージョン、つまりブロックとマテリアルのデータを同梱している各エディション 3 つずつとは、別の集合です。各行がどちらなのかは `targetable` が示します。Java の行は `1.14` 以降のリリースです。Bedrock の行はリリース系列で、10 刻みで採番され (`1.21.0`、`1.21.20`、`1.21.40`)、その間のホットフィックスは含みません。2 つの集合を分けておくことで、「表の範囲内にあるが、どの行にも当たらない」が「この表では順序付けられるリリースがない」を意味するようになります。たとえば下限 `1.21.1` は、パックがビルドできない Java のリリースですが、順序付けは問題なくできます。一方 `1.21.4` は Bedrock のどの行にも当たらず、ホットフィックスの `1.21.42` も同様です。

それでも下限にはどの表にもないものを書けるので、位置づけは単純な表引きでは済みません。答えは 4 通りあり、厳密なのは最初の 1 つだけです。

| 下限 | 位置づけ | 理由 |
|---|---|---|
| 表の行を名指す (末尾の欠けた成分は 0、数値成分の先頭のゼロは桁埋め: `1.21` は Bedrock の `1.21.0`、`1.020` は Java の `1.20`) | その行の `DataVersion` | 厳密。 |
| 表の行のプレリリースを名指す (`1.21.4-rc1`) | その行の `DataVersion` | リリース候補と正式リリースの間には何も出荷されないので、その間に対応するターゲットも存在しない。 |
| すべての行より下、またはすべての行より上にある | すべてのターゲットが満たす、またはどのターゲットも満たさない | 下限のラベルを最初と最後の行の *ラベル* と比べて決めるが、どの行が最初と最後かは *キー* で決まる。この判定は、表のラベルの並びがテキスト順とキー順で一致するとき、かつそのときに限り正しい。レジストリパックのローダーが読み込み時にこれを検査する。下限のラベル自体も、ドット区切りの 10 進数でなければ比較できない。 |
| それ以外 (表の範囲内にあるが、どの行にも当たらない) | 位置づけない | `DataVersion` を持たず、与えようもない。`E_REQUIRES_UNORDERABLE`。 |

最後の行は推測ではなく拒否です。Bedrock に対する `@requires version>=1.21.4` がまさにこれにあたります。この Java のリリースは Bedrock のどのリリースにも当たらず、`1.21.0` と `1.21.20` の間に位置します。ラベルどうしを比べる方式では、`40 > 4` を理由に満たされたと判断し、下限より前のバージョンに向けた Bedrock のビルドを通してしまいます。下限を強制して取り除こうとしている欠陥と同じものが、隣のエディションで起きるわけです。

この拒否は「駄目」と言うだけでは終わりません。このエディションでは位置づけられず、*もう一方の* エディションが名指すラベル、つまり相手の表の行やそのプレリリースは、相手の採番で書かれた下限です。`E_REQUIRES_UNORDERABLE` はそのことを指摘し、スコープを付けるよう提案します。もう一方のエディションも名指さないラベルには、スコープを提案しません。提案すれば推測を勧めることになり、それを名指さないエディションにスコープを付けると、下限はそこで効力を失い、制約が消えてしまうからです。これには、どちらのエディションでも位置づけられないラベル (スナップショット) と、もう一方のエディションでもすべての行より下か上としか位置づけられないラベルが含まれます。この 2 つの位置づけはリリースではなく比較の結果であり、作者がどちらの採番を意図したかについては何も語りません。そのエディションにスコープを付けると、下限はそのエディションのすべてのターゲットが満たすか、どれも満たさないかのどちらかになります。

### 下限にはエディションを指定できる

Java のリリースは `1.20.4 / 1.21 / 1.21.4`、Bedrock のリリースは `1.21.0 / 1.21.40 / 1.21.60` と進みます。2 つは別の尺度で、一方の採番で書いた下限は、もう一方では何の意味も持ちません。そこで下限には、どちらの採番で書いたかを指定できます。

```
@requires java    version>=1.21.4
@requires bedrock version>=1.21.40
```

**スコープ付き** の下限は、自分のエディションのビルドだけを制約し、もう一方のエディションでは効力を持ちません。違反ではなく効力を持たないだけなので、上の 2 行は両方のエディションでビルドできます。**スコープなし** の下限は、ビルドするものに対する下限で、ほかの下限と同じくそのエディションの表で解決します。これにより `@requires version>=1.21` は両方のエディションが守れる下限になり (Java の `1.21`、Bedrock の `1.21.0`)、一方のエディションのリリースだけを名指してもう一方にはない下限は、黙って通るのではなく前述のエラーになります。

`cairn info` の `registry compatibility` 行 ([§10.5](#registry-compatibility-の行)) が読むのは、スコープなしの下限だけです。この行は、両方のエディションについて同時に報告されることもあるファイルに対して 1 行しかありません。Java の採番で書いた下限は、そのファイルの Bedrock での範囲については何も言いません。エディションごとの答えは `buildable targets` 行が担います。

`theme` が宣言する下限にも同じ検査を行います。ただし対象は行に書かれた語ではなく、それを引き継ぐ *構成要素* です。エディション別のテーマバリアント ([§10.7](#107-java--bedrock-の可搬性)) があると、1 つの `theme=` 参照に対して 2 つのエディションが別々のテーマを割り当てることがあるので、テーマがこの行に寄与するのは、両方のエディションが同じテーマを割り当てるときだけです。そうでなければ、その下限はエディションスコープを持たないまま、エディション固有の事実になってしまいます。`def` にはこの検査は要りません。`place use=NAME` が名指すのは 1 つの def で、バリアントの集まりではないからです。この行が読まなかったものは理由とともに stderr に出力するので、バージョンを拒否する `buildable targets` 行の隣に `0.0` が並んでいても、読み手が理由を推測する必要はありません。

### 下限に書けるラベル

[§10.1](#101-ターゲットはコンパイル時のパラメータ) が存在を認めるラベルの形は、すべてディレクティブで受け付けます。semver 風の `1.21.4`、プレリリースの `1.21.4-rc1`、スナップショットの `24w14a`、そして日付ベースの採番で使われる綴りです。形の規則は、各成分が数字で始まり英数字だけからなるドット区切りの列で、その後に `-` と同じ形のプレリリースタグを続けてもよい、というものです。`1.a` や `x` はどの体系でもバージョンを表さないので、`E_INVALID_REQUIRES` です。

ラベルを受け付けることは、それを順序付けられると主張することではありません。あるラベルが `DataVersion` を持つかどうかは表が答えることで、エディションごとに問います。`cairn compile --target` はビルドを拒否し、`cairn info --editions` はそのエディションにビルドできるターゲットがないことと、その理由を報告します。`cairn check` はこの問いを発しません。`--edition` と `--target` を固定しても、下限をターゲットと照らし合わせることはないからです ([§10.4](#宣言した下限は強制される))。

## 10.5 「どのバージョン向けか」の答えは 3 つある

「対応バージョン」は 1 つには決まりません。`cairn info` は 3 つの軸を報告します。

1. **宣言されたレジストリ範囲 `[Vmin, Vmax]`**: ファイルがエディションを指定せずに宣言した下限を合成したものと、開いた上端です。使っているブロックから導いた事実ではなく、ソースとそれがインスタンス化する構成要素が宣言した内容を読み返したものです。詳しくは [`registry compatibility` の行](#registry-compatibility-の行)を参照してください。
2. **意味が変わりうるメンバー**: ID は有効なまま、意味、挙動、見た目が変わる箇所です。範囲よりもこちらが重要です。挙動の変化は ID の消滅よりはるかに頻繁に起きるので、レジストリだけで Vmax を決めるのは危険です。制約カタログは `since`/`until` とは別に `semantic_sensitivity` (境界のバージョンと理由) を持ち、その境界をまたぐコンパイルは警告を出します。例: 1.17 の大釜の分割、1.16 で壁の接続が bool から `none/low/tall` に変わった件、1.20.5 のアイテムフォーマット。制約カタログはまだ同梱していないので ([§10.3](#103-バックエンドはデータテーブル))、`semantic-sensitive` の行は常に `(none)` で、警告を出すコンパイルもありません。
3. **検証済みのロックターゲット** ([§10.6](#106-来歴-provenance-とロック))。`cairn info` はロックファイルを読まないので、この軸はまだ報告しません。ロックのターゲットとビルドするターゲットを比べるのは `cairn compile` で、違いがあれば `W_PREVIOUSLY_VERIFIED_TARGET` で知らせます。

```text
$ cairn info build.crn --editions java,bedrock
registry compatibility:  1.21.40 .. latest
edition portability:     Java: portable: 42  degraded: 0  unsupported: 0   Bedrock: portable: 38  degraded: 3  unsupported: 1
buildable targets:       Java: none (1.20.4, 1.21, 1.21.4 all refuse)   Bedrock: 1.21.40, 1.21.60 (1.21.0 refuses)
intended targets:        1.21.40, 1.21.60
semantic-sensitive:      yard_water(cauldron split @1.17), fence(wall conn @1.16)
```

名前が出てくるバージョンは、どれも組み込みパックが宣言しているものです。この出力のもとになったファイルは `@requires version>=1.21.40` を持っているので、Java のすべてのターゲットと Bedrock 1.21.0 が下限を下回っています。`semantic-sensitive` の行は、制約カタログがあれば加わる内容を示したもので、現在は `(none)` と表示します。

`intended targets` はファイル自身の `@intended_targets` 行をそのまま写したもので、答えではなく宣言である唯一の行です。`buildable targets` の隣にあるのは、矛盾しうる相手がその行だからです。判定できる半分の比較は [§10.4](#ヒントは下限と突き合わせる) が自動で行い、残りは読み手が突き合わせます。何も宣言していないファイルでも行は消えず、`(none declared)` と表示します。

5 行は stdout に、それぞれの数値の内訳は stderr に `note:` 行として出ます。行を読むパイプラインは、`cairn info` が最後まで完了するかぎり、毎回同じ 5 行を受け取ります。完了しない場合は別です。指摘がどの行も計算する前にコマンドを拒否するので、stdout は 1 行欠けるのではなく空になります。

### `registry compatibility` の行

この行は宣言を読み返すだけで、ソースが使っているブロックは見ません。`Vmin` は、エディションを指定しない下限のうち最も厳しいもので、1 つもなければ `0.0` です。対象は `@requires version>=X` のヘッダと、ビルドがインスタンス化する `def` と `theme` のうち、この行に寄与するものの `requires version>=X` 行です ([§10.4](#構成要素は自分の下限を宣言できる))。`theme` が寄与するのは、両方のエディションが同じテーマを割り当てるときだけです。*どの* 構成要素がインスタンス化されるかを割り出すのは、ソースに対する実際の処理です。ただし、それらがどのブロックを塗るかを読むことは、その処理に含まれません。

「最も厳しい」はラベルどうしの比較なので、すべてがドット区切りの 10 進数である間しか厳密ではありません。数値として読めないラベルは、読めるラベルのどれよりも上に並びます。この並びに意味はなく、決まっているというだけです。`version>=1.21.4` と `version>=24w14a` の両方を宣言したファイルは、スナップショットのほうを報告します。この順序がビルドを決めることはありません。ビルドを決める判定は、どれも各下限をターゲットのエディションの表と個別に照らします ([§10.4](#順序はエディションごとに-dataversion-で決める))。

この行はエディションに依存しないので、スコープなしの下限だけを読みます (理由と、除外した下限を stderr に出す note は [§10.4](#下限にはエディションを指定できる) を参照)。下限を 1 つも宣言していないファイルも、宣言した下限がすべてエディションを指定しているファイルも、`0.0` になります。行ではこの 2 つを区別できませんが、stderr の note では区別できます。

`Vmax` はリテラルの `latest` です。上端は *導出した* 範囲の片方で、この行が持つのは宣言のほうなので、パックが `since` / `until` を持つようになっても、その答えはこの欄を埋めるのではなく `buildable targets` に入ります。

**この行は宣言であり、どのバージョンでビルドできるかの答えではありません。** この 2 つは同じものとして読まれやすく、ソースによっては見分けがつかなくなります。次の例は、サポートするどのバージョンも満たす下限を宣言しつつ、Java が 1.21.4 で追加したブロックを使っています。

```text
$ cat hut.crn
@cairn 2026.06
@requires version>=1.20.4

theme pale:
  slot floor -> @pale_moss_block
  slot wall  -> @cobblestone

struct hut size=5x5
  floor mat_slot=floor
  walls mat_slot=wall height=3

$ cairn info hut.crn --editions java
registry compatibility:  1.20.4 .. latest
edition portability:     Java: portable: 2  degraded: 0  unsupported: 0
buildable targets:       Java: 1.21.4 (1.20.4, 1.21 refuse)
intended targets:        (none declared)
semantic-sensitive:      (none)
```

`1.20.4 .. latest` は答えのように読めますが、2 行下の行がそれを否定しています。しかも拒否されたリストには `1.20.4` 自身が入っています。宣言した下限が間違っているのではなく、別の問いに答えているのです。`minecraft:pale_moss_block` が 1.21.4 で追加されたことはパックについての事実で、この行が読むのはファイルが宣言した内容だけです。

**導出した答えは 2 行下の `buildable targets` の行です。** この行は、サポートするすべてのバージョンに対してソースを試し、ビルドが受け付けるバージョンをエディションごとに報告します。`since` / `until` の積で近似しようとしていた答えを、推定ではなく実際に問い合わせて得たものです。しかも積では表せない形をしています。答えはエディションごとに異なり、連続しているとは限らないので、`[Vmin, Vmax]` の組で表そうとすると、見えていない隙間まで含んでしまいます。

宣言された下限を独立した行として残すのは、種類の違う事実だからです。下限は作者が書いた **入力** で、`cairn compile --target` が受け付ける範囲と、ファイルが読み手に約束する内容を決めます。対して `buildable targets` は、たまたま出荷されているパックについての **出力** です。`E_REQUIRES_CONFLICT` ([§10.4](#104-fail-loud-と最小バージョン推定)) は、この 2 つを比べられるようになる日のために予約しています。宣言された下限が、レジストリから *推定した* 範囲と矛盾する場合です。パックが `since` / `until` を持つまでは、このコードは発生しません。

### `edition portability` の行

この行はパレットのエントリを数えます。エントリが `unsupported` になる理由は 2 つあります。

| 理由 | 直し方 |
|---|---|
| そのエディションに、そもそもそのブロックがない。 | マテリアルを変えるか、パックでのそのマテリアルの対応を変える。 |
| ブロックはあるが、intent が持つステートに対する対応を Cairn が持っていない ([§10.7](#107-java--bedrock-の可搬性))。 | 今のところない。対応を追加するのは Cairn の側。 |

1 つ目は ID の問題、2 つ目はステートの問題です。`degraded` になりうるのは 2 つ目だけです。存在しないブロックには、失う詳細がないからです。

1 つの数値の裏に 2 通りの直し方が隠れるので、数えた各エントリは理由とともに stderr に出力します。ID の問題には `E_UNKNOWN_ID` と同じ方法で、同じ 2 つの手段で答えます。`aliases` コンポーネントに行があれば、このエディションが別の名前で持っているエントリを、行き止まりとしてではなくその名前で報告します (Java での `standing_sign` は `oak_sign`)。行がなければ `did you mean` を付けます。この 2 つは択一で、順番に試すものではありません。行はどのブロックかについてのパックの言明であり、その横に距離による推測を並べると、読み手にどちらを信じるかを選ばせることになるからです。ここでもエイリアスはエディションに対して問います。サポートする *いずれかの* バージョンが宣言する綴りなら答えになります。固定したビルドなら、自分のバージョンの綴りだけを残します。`--format json` では `edition_portability[].unsupported_entries` として、数値 1 につき 1 要素、パレット順で出力します。

この行は互換範囲全体について報告するので、どちらの問いもバージョンではなく *エディション* に対して発します。範囲の一部でしか有効でない ID は `unsupported` になりません。Bedrock が 1.21.40 で `stonebrick` を `stone_bricks` にリネームした件がその例です。実際にビルドするバージョンがその ID を持っているかどうかは、固定したターゲットが `E_UNKNOWN_ID` として答えます。`cairn compile --target` か、ビルドせずに同じ答えを得られる `cairn check --edition E --target V` です ([§10.4](#104-fail-loud-と最小バージョン推定))。

#### degraded になったエントリと失われたもの

`degraded` も、コマンドが名指しできるエントリを数えたもう 1 つの数値で、名指しの仕方も同じです。理由は `unsupported` ほど強くありません。degraded になる理由は 1 つ、直し方も 1 つなので、読み手が直し方を選ぶ必要はないからです。共通しているのは「N 個のうちどれなのか」という問いです。`roof-hip` は `degraded: 4` と報告します。この問いに答えるもう 1 つの場所はビルド時の `W_INTENT_DEGRADED` ですが、`cairn info` はまさにそのビルドの *前に* 読むためのコマンドです。

数えた各エントリは stderr に出力し、`--format json` では `edition_portability[].degraded_entries` として、数値 1 につき 1 要素、パレット順で出力します。1 件は `{id, states, dropped}` です。

| フィールド | 内容 |
|---|---|
| `id` | パレットのエントリのブロック ID。lowering が intern したそのままの形。 |
| `states` | エントリの `key=value` をカンマでつないだもの。`states_unmapped` の理由と同じ綴り。 |
| `dropped` | エディションに表現のない intent ごとに 1 件の `{key, value}`。`key` は閉じた集合 (`shape`) で、新しい種類の損失は既存の `key` の変更ではなく新しい `key` として追加する。 |

カテゴリのタグを付けた 1 つのリストにはせず、2 つのリストに分けています。また ID だけでなく `states` も持たせています。degraded はブロックについての事実ではなく、*ステートの組み合わせ* についての事実だからです。1 つの ID が、詳細を失う組み合わせの数だけこのリストに現れます。`roof-hip` の 4 件は、`minecraft:spruce_stairs` の 4 通りの綴りです。ID だけをキーにしたリストでは、同じ行が 4 回出力されてしまいます。ビルド時の `W_INTENT_DEGRADED` も、構造のスコープの後に `id[states]` という同じ形で、各エントリを 1 行に 1 回ずつ名指すので、警告はそれぞれ区別でき、同じエントリについての note と対応します。

`dropped` は、文ではなくプロパティと値を持ちます。`unsupported` の理由と同じ考え方で、これを読むプログラムが、どのステートが失われたかを知るために英文を解析しなくて済むようにするためです。エディションが表現 *できる* 値は損失ではないので、ここには現れません。Bedrock の階段は `straight` なので、`shape=straight` はエントリを作らずに落ちます。note と `W_INTENT_DEGRADED` が出力する文章は 1 か所で書かれています。しかもペア全体ではなく `key` ごとに書かれています。`shape` が落ちたときの文章は階段についての話だからです。intent を落とす 2 つ目のブロックファミリが現れたら、この文章を流用するのではなく、自分の `key` と文章を持ちます。

#### パックが弾くべきだったブロックステートは数に入れない

ステートの変換器には、ほかに 2 種類の失敗が届くことがあります。Java のドメイン外のステート値 (階段の `facing=up`) と、変換器が読まないステートキーです。どちらもエディションについての答えではありません。検証済みのレジストリパックからはどちらも生まれないので、出どころは、まだターゲットに照らして検査していないソースのステートリテラル (`W_STATE_LITERAL_UNCHECKED`、[§10.4](#104-fail-loud-と最小バージョン推定)) か、パックまたは Cairn の欠陥のどちらかです。

したがって、これらは `unsupported` の 3 つ目、4 つ目の理由ではありません。パレットにこうしたエントリを含むエディションについては、`cairn info` は可搬性の数値を **一切** 報告しません。数値そのものは計算できますが、通常の可搬性の数値として読まれてしまいます。`facing=up` を `unsupported: 1` と数えると、Bedrock に角の形のステートがないだけの階段と見分けがつきません。それこそ、読み手に導かせてはならない結論です。コマンドはそうしたエントリを 1 つずつ、変換器自身のメッセージとともに stderr に出力します。メッセージはソースのブロックステートの直し方を示し、続く note は、各エントリがソースのステートリテラルか、パックまたは Cairn からの漏れのどちらかであることを伝えます。そのうえで行を出さずに非ゼロで終了します。コマンドを拒否するほかの指摘と同じ振る舞いです。

今のところこれを観測できるのはステートの変換器だけなので、規則もステートの問いについてだけ定めています。これは、ほかの場所の検証漏れに `unsupported` と答えてよいという意味ではありません。検証済みのパックからは生まれないはずのパレットで計算した数値は、何がそれを生んだにせよ、可搬性の答えではありません。

### `buildable targets` の行

カウンタだけではわからないことがあります。2 つのエントリがそれぞれ *互いに素な* バージョンの集合で宣言されていても、どちらも「エディションは持っている」と答えます。どのバージョンも両方を宣言していないのに、行には問題が出ません。

`buildable targets` はバージョン単位の答えです。指定されたエディションごとに、ターゲットを固定した lowering がエラーを出さないサポート対象のバージョンを並べ、拒否したバージョンをその横に示します。`[Vmin, Vmax]` の範囲ではなく集合にしているのは、バージョンの集合が入り組んだ 2 つの ID は、範囲では埋まってしまう隙間を残すからです。

導出には、サポート対象のバージョンごとに 1 回ずつ lowering する方法を使います。`cairn compile --target` と同じ検査です。範囲全体のパレットの ID 集合の積を取る方法は **健全ではない** ので使いません。ターゲットを固定しないと、すべてのマテリアルが *既定の* 対応を取るので、ターゲットが別の綴りにするトークンが、誤った ID として比べられてしまいます。

カウンタと同じく、この行も報告するだけで拒否はしません。どのサポート対象バージョンでもビルドできないソースでも、`cairn info` は 0 で終了します。拒否するのはビルドの役目です。拒否した各バージョンの指摘はそのバージョンの下に出力するので、`E_UNKNOWN_ID` が、それを出したターゲットと切り離されて表示されることはありません。

#### リストが空になる理由

`buildable` が空になる原因は 4 つあり、どれも同じ修正で直るわけではありません。2 つは `@requires` の行で、3 つ目はボクセルを 1 つも作らなかったメンバーで、4 つ目は固定した lowering が名指したもので直します。リストだけではこれらを区別できないので、`--format json` では `reason` を一緒に出力します。ビルドできるバージョンが 1 つでもあれば、このキーは **出力しません**。通常のレポートは変わりません。

`reason` はオブジェクトで、当てはまる原因をすべて報告します。4 つのうち 2 つは **エディション** についての事実で、どのリリースでも同じ内容になり、リリースごとの判定より前に決まります。これらは `reason` 自身のフィールドです。残りの 2 つはリリースによって異なるので、その隣のバージョン別のリストに入ります。中身のないフィールドは出力しません。

| フィールド | 内容 | 作者が直す場所 |
|---|---|---|
| `unplaceable_floors` | 下限 | `@requires` の行。下限がこのエディションのどのリリースも名指していないので、どのバージョンとも照らし合わせられず、どれも認められない。 |
| `dropped_scopes` | スコープキー。通路の場合は `site::SITE::FROM ↔ TO` | ボクセルを作らなかったメンバーまたは `connect` 行。部分的なビルドは認められないので、ID の表を参照する前にすべてのバージョンを拒否する。 |
| `versions` | 拒否されたターゲット | 自分自身の理由で拒否されたバージョンごとに 1 エントリ。 |

どちらか一方ではなく、両方を並べます。このエディションで位置づけられない下限を宣言し、*しかも* いずれかのリリースに存在しない ID を使っているファイルはありえます。前者だけを報告する形だと、作者は前者を直した後で初めて後者に出会い、1 回の実行で 1 つの原因しか分からない往復を繰り返すことになります。この行はその往復をなくすためにあります。

上のエディション単位の答え以外に問題のないリリースはエントリを持たないので、`versions` は `considered` の **部分列** になり、位置が対応する配列ではありません。利用する側は、位置ではなく `version` で突き合わせます。各エントリは `version` と `refusal` タグを持ちます。

| `refusal` | 内容 | 作者が直す場所 |
|---|---|---|
| `below_floor` | `floors` | `@requires` の行。*そのバージョン* を拒否している下限だけを載せる。下限を複数宣言しているファイルでも、直すのはすべてではなく 1 行で済むから。 |
| `lowering_refused` | `findings` | 指摘が名指すもの。たいていはマテリアルか ID で、バージョンごとに異なる。 |

この 2 つは同時には起きません。下限を下回るバージョンは lowering しないからです。下限はソースとターゲットの関係なので、ID の表が何であっても変わりません。

下限の 1 件は `{declared, line, col, declared_by?}` で、作者が書いたままの下限 (スコープを含む) と、その位置を表します。`declared_by` は構成要素から引き継いだ下限の場合の `{keyword, name}` で、`keyword` は `def` か `theme` のどちらかです。ファイル自身の下限には付きません。位置がすでにその行を指しており、その行はファイルのものだからです。

`findings` は [Lint §11.2](/ja/spec/lint/#112-機械可読ペイロード) が指摘を表すのと同じ形で、実行時にそのバージョンの下に stderr へ出力するものと同じ指摘です。この行によって同節の内容は変わりません。これらは `{"diagnostics": [ ... ]}` の文書ではなくレポートの中に入り、レポートは拒否ではないからです。

テキストの行からは、これらは何もわかりません。`buildable targets: Bedrock: none (1.21.0, 1.21.40, 1.21.60 all refuse)` は 4 つの原因のどれでも成り立ちます。どの原因も stderr には出ますが、形は同じではありません。下限に関する 2 つの原因は行の位置を持つ `note:` として、落ちたスコープは位置を持たずスコープ名だけを示す `note:` として、拒否された lowering はそのバージョンの下に指摘そのものとして、それぞれの位置とともに出力します。`reason` が補うのは、この情報を読み取れない JSON の側です。

5 つ目の行 `recommended test targets` もこの軸に属し、また別の問い (どのバージョンでテストする価値があるか) に答えます。まだこれを出力するコードはありません。

## 10.6 来歴 (provenance) とロック

`.crn` が持つのは、書かれた言語のバージョン (`@cairn`) と、ターゲットについてはヒントである `@intended_targets` だけです。`verified: true`、DataVersion、各種ハッシュはロックにだけ存在し、ビルドが成功したときにコンパイラが書き込みます。手で書くことはありません。

```yaml
# build.crn.lock (コンパイラが生成)
lock_schema_version: 1        # この文書自身のスキーマの改訂番号
source_hash: sha256:...
cairn_version: 2026.10.0      # 書き出した Cairn のリリース。`cairn --version` の表示と同じ
target: { edition: java, mc_version: 1.20.4, data_version: 3700 }
inputs: { registry_pack_hash: sha256:..., constraint_catalog_hash: sha256:... }
resolved_ir_hash: sha256:...
verified: true
member_version_sensitivity: [ { id: yard_water, reason: "cauldron split at 1.17" } ]
```

コンパイルは、`--lock` で別のパスを指定しないかぎり、ロックをソースの隣に `<source>.lock` として書き出します。制約カタログはまだ同梱していないので ([§10.3](#103-バックエンドはデータテーブル))、現在の `constraint_catalog_hash` はゼロで、`member_version_sensitivity` は `[]` です。

`resolved_ir_hash` が再現性の中心です。マクロ展開、デフォルト値の補完、アドレスの自動割り当てを終えた後の IR を固定します。ただしアドレスの自動割り当ては未実装で、アドレスを持つのは `id=` を書いたメンバーだけです ([§9.2](/ja/spec/components-editing-sites/#92-編集モデル))。

`lock_schema_version` を先頭に置くのは、読み手が残りをパースする前に、内容を理解できるかどうか判断できるようにするためです。バージョン `1` は、上の形に、空でないときにだけ書き出す 2 つのキーを加えたものです。`placements` は各 `place` 行の解決済みの原点と大きさ、`walkways` は各 `connect` 行の解決済みの通路と経路のマテリアルです。`lock_schema_version` を省いた文書もバージョン `1` とみなします。より高いバージョンを宣言する文書は、フィールド名の意味が変わっていないと仮定して読むのではなく、拒否します。スキーマが宣言していないキーは、どこにあっても拒否します。

別のターゲットで再コンパイルすると、検証済みのターゲットとの違いをはっきり報告します。

```text
$ cairn compile build.crn --edition java --target 1.21.4 --lock build.crn.lock
W_PREVIOUSLY_VERIFIED_TARGET: verified for 1.20.4/DataVersion 3700, now 1.21.4/4189.
W_SEMANTIC_SENSITIVITY: 2 members may resolve differently: yard_water, fence
```

2 つ目の警告は前のロックに記録されたメンバーを読むものなので、現在のコンパイルが書き出すロックからは出ません。

## 10.7 Java / Bedrock の可搬性

導出規則はエディションごとに異なります。**`intent_state` は中立で、`resolved_state` はエディション別です。** 契約は「同じ intent から、エディションごとに最も近い正しい表現へ解決する」ことであり、「同じ結果を保証する」ことではありません。

```yaml
intent_state: { primitive: stairs, corner: inner_left, facing: east }   # エディション中立
resolved_state:
  java:    { facing: east, half: bottom, shape: inner_left }
  bedrock: { weirdo_direction: 0, upside_down_bit: false }              # shape が無いので角がつながらない
```

解決結果の違いが見た目や機能の違いになるときは、ビルドがそれを知らせます。`themed-tower` の軒の階段は `shape=outer_left` です。

```text
$ cairn compile examples/themed-tower.crn --edition bedrock
warning[W_INTENT_DEGRADED]: struct::keep: minecraft:dark_oak_stairs[facing=south,half=top,shape=outer_left]: Bedrock has no `shape` state; its stairs render straight, so corners show visual gaps
```

トークンで吸収できるのは、ID、ステート、シリアライズの違いだけです。**概念がないことと、ゲーム挙動の違いは吸収しません。** 吸収できない代表例は次のとおりです。

- display エンティティ (Bedrock にはない)
- 階段の `shape` (Bedrock にはこのステートがない)
- 防具立て (armor_stand) のポーズ
- レッドストーン信号の伝わり方
- アイテムコンポーネント ↔ Bedrock のアイテム NBT
- 光源ブロック (light) の内部挙動

### 代替を書くとき

意味層で `@edition` による条件分岐を書くことは禁止です。代替が必要なときは、次の階層を上から順に検討します。

1. 閉じた意味プリミティブ (中立) を使います。表現できなければ `E_PARITY_UNSUPPORTED` で失敗させます。
2. **スロット + エディション別テーマ** でフォールバックします。たとえば `floating_text` スロットを、Java では `text_display` に、Bedrock では光る看板に解決します。
3. エスケープハッチの層でだけ、`@edition` でガードします。生の ID や NBT は、もともとエディション固有のものです。

```
@requires bedrock version>=1.21.40   # 下の Bedrock 分岐は平坦化後の ID で書いている

hologram id=shop_sign text="Weapon" mat_slot=floating_text   # 意味層は常に中立
theme shop_java:    slot floating_text -> text_display scale=2.0
theme shop_bedrock: slot floating_text -> sign glowing=true   # Bedrock のフォールバック

@edition java    { raw_block mat=minecraft:light[level=15] at=4,3,2 }
@edition bedrock { raw_block mat=minecraft:light_block_15 at=4,3,2 }
```

現時点のパーサがこのスニペットで受け付けるのは、`@requires` の行だけです。`hologram` はトップレベルにありますが、トップレベルで項目を始められるのは `theme`、`def`、`site`、`struct` だけなので `E_PARSE` になり、パースはそこで終わります。後続の行も、それぞれ単独で失敗します。`theme` のルールはヘッダの下にインデントして書くので、1 行の形は `slot` の位置で `E_PARSE` です。インデントしても、`slot` のルールが割り当てるのは 1 つのトークンで、その後には何も書けないので、`scale=2.0` と `glowing=true` は `E_PARSE` になります。`@edition` は未知のディレクティブ (`E_PARSE`) で、本体の中に書いた `hologram` と `raw_block` は `E_UNKNOWN_KEYWORD` です。`E_PARITY_UNSUPPORTED` も未実装です。

### `@edition` はエディションを固定し、バージョンは固定しない

ガードが決めるのは、どちらの分岐をビルドするかだけです。分岐の中の ID は、やはりコンパイルが固定した 1 つの `(edition, version)` と照合するので ([§10.4](#104-fail-loud-と最小バージョン推定))、エディションが自分のサポート範囲の中でブロックの綴りを変えている場合、分岐を選ぶのは `@edition bedrock` で、綴りを決めるのはファイルの下限です。なお、ガードはまだパースできません ([上記](#代替を書くとき))。この節が前提とするそれ以外のもの、つまりバージョン単位の ID の照合、`aliases` による答え、`E_VERSION_CAP`、`E_INTENDED_TARGET_CAP` は現在の挙動です。

Bedrock の光源ブロックがまさにその例で、上のスニペットに下限がある理由でもあります。1.21.0 はこのブロックを `light_block` と綴り、明るさは `block_light_level` ステートとして別に持ちます。1.21.40 で明るさが ID の中に移ったため、1.21.40 と 1.21.60 では同じブロックを `light_block_0` … `light_block_15` と綴り、`light_block` という ID はもう存在しません。これらの綴りをまとめている `aliases` の行 ([§10.4](#104-fail-loud-と最小バージョン推定)) が答えるのは、診断であってソースではありません。その答えは、固定したターゲットが宣言している閉じた集合です (Bedrock 1.21.60 に対する `light` は 16 段階すべてが返ります)。16 個の集合は綴りではありません。そこから 1 つを選ぶことこそ同節が禁じるサイレント置換なので、選ぶのは作者の役目のままです。2 つの形のどちらかに向けて分岐を書くことが、その選択にあたります。そして、どちらの形なのかを示すのが下限です。この下限はスコープ付きなので Java のビルドでは効力を持たず ([§10.4](#下限にはエディションを指定できる))、Java はもう一方の分岐が受け持ちます。

下限を省いても誤りにはならず、はっきり失敗するだけです。Bedrock 1.21.0 に対する `light_block_15` は、検査がバージョン単位なので `E_UNKNOWN_ID` になります。下限を書くと、2 つのものが加わります。1 つは別の拒否です。下限があれば同じコマンドは `E_VERSION_CAP` になり、ブロックではなく `--target` と下限を指し示します。下限が拒否するターゲットでは、コンパイルは ID を照合しないからです ([§10.4](#宣言した下限は強制される))。もう 1 つは宣言です。分岐がどのバージョン向けかというもう半分の情報を、ファイルのほかの制約と同じ場所に書くことになり、ほかのヘッダもそれと照らし合わせられます。1.21.40 の下限を宣言したファイルで `@intended_targets` が 1.21.0 を挙げていれば、ターゲットを選ぶ前の `cairn check` の時点で `E_INTENDED_TARGET_CAP` になります ([§10.4](#ヒントは下限と突き合わせる))。下限のない同じファイルは、ターゲットを選ぶまで何も言いません。両方の綴りに対応しなければならないなら、ビルドを 2 つに分けます。`@edition` と組み合わせられるバージョンの条件分岐はありません。

### バリアントはソースではなくビルドが選ぶ

`theme NAME_java` と `theme NAME_bedrock` は、論理テーマ `NAME` の 2 つのバリアントを宣言します。`--edition` を固定すると、そのエディションのバリアントを割り当て、なければ接尾辞のない `NAME` にフォールバックし、そこで止まります。*もう一方の* エディションのバリアントを割り当てると、そのスロット値がこのエディションの出力に流れ込みます。これは [§10.4](#104-fail-loud-と最小バージョン推定) が禁じるサイレント置換です。どちらもなければ、要求された範囲を空気で埋めてビルドするのではなく、`E_THEME_VARIANT_MISSING` でコンパイルを止めます。

`place ... theme=NAME` は **論理** テーマを名指し、まさにこの規則に従うので、1 つの site で、同じ def を、ビルドが必要とするバリアントで配置できます。ここでバリアントを名指しても (`theme=shop_bedrock`) 解決はします。固定が選んだバリアントを割り当て、代わりに何を割り当てたかを `W_THEME_VARIANT_REBOUND` で知らせます。ただし、意味層に書くべきなのは中立な綴りです。

`--edition` を固定していなければ、作者が名指したバリアントを選び直すことはありません。宣言された名前はそのまま割り当てます。接尾辞 *なし* で書かれた名前は、モジュールレベルの選択と同じ、固定なしの順序で解決します。モジュールが宣言していない接尾辞 *付き* の名前は `E_UNRESOLVED_THEME_REF` です。

### バージョンをまたいだ適用

意図的に非対称にしています。

- **ダウングレード** (新しいバージョンの NBT を古いバージョンのワールドへ) はハードエラーです。未知のコンポーネントは、クラッシュやデータ破損の原因になります。
- **アップグレード** (古いバージョンの NBT を新しいバージョンのワールドへ) は、目立つ警告と DataVersion の刻印を伴い、DFU に依存します。明示的な `--allow-cross-version` が必要です。

ただし、構造ファイルをワールドに適用するコマンドはまだないので、どちらの規則も強制されず、`--allow-cross-version` を受け付けるコマンドもありません。

すべてのビルドがエディション間で可搬である必要はありません。コンパイラの役目は、何が可搬性を損なうかを明示することです。

## 10.8 Cairn 自身の公開面の互換性ティア

ここまでの `(edition, version)` の軸が扱うのは、Cairn が *出力するもの* です。これと直交するもう 1 つの軸が、Cairn が自分自身の進化について約束する内容です。対象は `.crn` の構文、ロックファイル、CLI フラグ、Rust API です。CalVer には約束を読み取れる「メジャー」の軸がないので、約束は [互換性ティア](/ja/spec/compatibility/) に明記しています。`Stable` な面は `W_DEPRECATED` (最初の非推奨化とともに追加する予約済みのコード) で 1 リリース分の猶予を設け、`Evolving` な面は毎月のマイナーリリースのどれでも変わることがあり、`Internal` は何も約束しません。
