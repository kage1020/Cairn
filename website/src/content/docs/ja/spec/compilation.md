## 4.1 フェーズ評価
ソースは行指向、フラット、順不同で書いてかまいません。コンパイラは各コマンドを暗黙のフェーズに
振り分け、**固定順** で評価します:

```
massing (shell: floor/walls/volume)
  → envelope (roof/exterior)
  → openings (door/window)
  → fixtures (装飾物: sign/painting/frame/bed/sensors & actuators)
  → logic_synth (レッドストーン合成: Logic IR → Netlist IR)
  → logic_place (セル配置)
  → logic_route (配線 → Placement IR、ディレイ決定)
  → raw (エスケープハッチ)
```

- ソース内で `roof` の後に書かれた `window` も、壁の開口として適用されます (順序事故が消えます)。
- **last-wins は同一フェーズ内のローカル上書きにのみ適用されます**。`raw` (fill など) は危険ゾーン
  であり、常に最後に適用されます。同一フェーズ内で *別々の* メンバが 1 つのボクセルを奪い合う場合も
  同じ規則で解決され、そのうえで報告されます (§4.8)。
- 所属は上の一覧のとおりです。`floor` と `walls` は massing、`roof` は envelope で、軒が外装である
  `stair` (軒は外装なので) も同じです。`door` と `window` は openings、`pressure_plate` はセンサなので
  fixtures です。`circuit` は論理フェーズ向けの配線領域を確保するだけでボクセルを書かないため、
  どのフェーズにも属しません。
- レッドストーン論理 ([レッドストーン](redstone)) は `fixtures` の直後を 3 フェーズに分割します。
  センサ/アクチュエータが 3D に配置されて初めて I/O ポートの座標が確定し、配置と配線が可能になり
  ます。

```
struct keep size=11x9
floor  id=base   mat_slot=floor
walls  id=shell  mat_slot=wall height=5
roof   id=roof   kind=gable mat_slot=roof overhang=1
window id=front_windows side=front y=2 offset=2 size=2x2 mat_slot=glass   # roof の後でも開口を切る
door   id=entry  side=front at=center
```

## 4.2 ターゲット軸
ターゲットは **二軸 `(edition, version)`** です。バージョンとエディションは **DSL ソースには書きません**。
バージョン/エディションを知るのはバックエンドのみです ([バージョンとエディション](versioning-editions))。

```sh
cairn compile build.crn --edition java    --target 1.21.4
cairn compile build.crn --edition bedrock --target 1.21.40
```

- `--target` 単独は **禁止** です。`--edition` は **必須** です。
- 同じ「1.21」も Java と Bedrock では異なる意味を持ち、Java の DataVersion は Bedrock の block_version
  とは無関係です。

## 4.7 level グループ化と体積の導出

`level y=N` はメンバをグループ化し、その各メンバを struct の基準面から `N`
ボクセル上に置きます。これ自体はメンバではなくグループ化構文で、`level` の行
はブロックを一切生みません。配下の各メンバは、それぞれが元から持つ垂直座標に
`N` を足した上で、本体に直接書かれたのと同じように立体化されます。

struct が立体化される体積は書くものではなく、導出されるものです。

```
Dims.x = size.W + 2 × overhang
Dims.z = size.H + 2 × overhang
Dims.y = 1 + wall_top + roof_extra
```

各項が数えるのは、実際に塗るメンバだけです。`overhang` は実際に描かれる roof
(コンパイラが知っている `kind=` を持ち、`shed` ならば `slope_to=` もあるもの) の
うち最大の `overhang=`、`wall_top` は `mat_slot=` が解決する
walls のうち最大の `N + height` (`N` は囲っている level の値、本体直下なら `0`)、
`roof_extra` は kind ごとの寄与 (gable / shed / hip / flat) のうち最大のものです。
`1` はどの struct にもある基準面で、どのメンバの寄与でもありません。`level` の中の
メンバもこの 3 つすべてに数えられます — walls が `level y=5` の下にしかない
struct は、それを本体に直接書いた struct と同じ高さになります。

オフセットが 0 でないときの立体化規則を、すべてのロールが持つわけではありません。
`walls` / `door` / `window` / `stair` / `pressure_plate` は `N` を自身のジオメトリ
の基準として読みます。`floor` と `roof` は struct が 1 枚だけ持つ面で、落とすべき
2 枚目の床も、置くべき 2 枚目の屋根もありません。したがって `N > 0` の `level y=N`
の下では `W_DEFERRED_MEMBER` を出し、ブロックを生みません。

上の規則で落とされたメンバは、導出される体積にも何も寄与しません。level 配下の
roof の `overhang=` は footprint を広げませんし、その高さも `Dims.y` を上げません。
逆も成り立ちます — 塗られるメンバは必ず、その体積が収めるつもりで大きさを決めた
メンバです。この 2 つは 1 つのリストを両側から読んだものであり、渡された配列の外
にメンバが描き込むことを防いでいるのはこの一致です。

この規則は `level` のグループ化についてではなくリストについてのものなので、メンバが
脱落するあらゆる場面で成り立ちます。描かれない `roof` (`kind=` が無い、あるいは
`slope_to=` の無い `shed`) は footprint を広げません。材質が解決できない `walls` は
何も塗らないので `Dims.y` を上げません。

材質の側は `walls` に効いて `roof` には効きません。壊れ方が違うからです — `mat_slot=` が
解決しない roof は自前の材質にフォールバックして描かれるので、描かれる roof として体積を
形作ります。テーマが束縛されていない struct はこの非対称のいちばん分かりやすい例で、壁は
空気に落ちて何も確保しませんが、その上の `roof kind=gable` は描かれ、棟はやはり壁より
上に座ります。

「材質が解決するか」は、ビルドが固定されている target に対して問われます。したがって
一部のバージョンしか宣言していないブロックは、`--target` の違いで `Dims.y` を変えます。
どちらの答えも正直です — その配列こそ、そのバージョンが作れるものだからです。固定した
target が宣言しない id は `E_UNKNOWN_ID` (エラー) なので、その形から成果物は出ません。

以上が成り立つには、体積が導出される前にそれらの失敗が判明していなければなりません。
だからこそ材質の問いは、範囲を決める場所と、ブロックを置く場所の両方で発せられます —
同じ 1 つの関数を通すので、2 つが違う答えを返すことはありません。両者が食い違いえた頃、
余分な範囲は空気でした — 内側へ寄った壁のまわりを囲む空気の輪と、1 つも塗られなかった
壁の高さぶんだけ背の高い配列です。

## 4.8 同一フェーズ内の衝突とパレット

2 つのメンバが別々のフェーズに属するなら、どちらが勝つかはフェーズ順が決めます。
`walls` を貫く `door` は massing に続く openings であり、穴が開くことこそが目的です。
同一フェーズ内では、2 つのメンバを分けるものは行の書かれた順序しか残っておらず、
§4.1 はそれを「同一フェーズ内のローカル上書き」に対して認めています。

この許可は、作者が同じメンバを書き直す場合のためのものです。たまたま footprint が
交差しただけのものはグリッド上では同じ形に見えますが、意味はまったく別です。そこで
コンパイラは最後の書き込みを残したうえで、両方のメンバ名と入れ替わったボクセル数を
示す `W_PHASE_CONFLICT` を出します。警告によってビルド結果は変わりません。変わるのは、
動かせる 1 行が結果を決めていることが作者に伝わる点です。

値が変わらないセルは衝突ではありません (同じ材質の `walls` 2 枚が共有する段で重なって
も、結果は順序に依存しません)。`repeat=` / `step=` のスタンプが重なる `window` が自分の
ガラスを同じガラスで塗り直す場合のように、1 つのメンバが自分自身の上に書く場合も同様
です。

フェーズが評価する本体 — `struct`、`def`、およびそれらを実体化する各 `place` — の
パレットは、その本体が含むブロックを各フェーズが最初に塗った順で並べたものであり、
スロット `0` は空気です (walkway の配列はフェーズではなく `connect` パスが敷くもので、
この節は対象にしていません)。途中で intern された履歴ではありません。最後の
1 ボクセルを後続フェーズに覆われた材質は削除され、残りのスロットは詰め直されます。
そうしなければ敗者は `.nbt` に紛れ込み、`cairn info` に数えられ、`resolved_ir_hash` に
含まれてしまい、「どちらのメンバが負けたか」だけが異なる 2 つのソースが同じビルドに対して
別々の成果物を生むことになります。
