## 4.1 フェーズ評価

コマンドは、順番を気にせず並べて書けます。コンパイラが各コマンドをフェーズに振り分け、フェーズを次の決まった順番で評価します。

```
massing     floor / walls / volume
envelope    roof / stair
openings    door / window
fixtures    sign / painting / frame / bed / センサー / アクチュエーター
logic_synth レッドストーンの合成: Logic IR → Netlist IR (Edition Cell の選択を含む)
logic_place セルの配置 → Placement IR
logic_route Placement IR 上での配線、遅延の挿入、交差の合法化。遅延が確定
raw         エスケープハッチ
```

ただし、今のところすべての行が動くわけではありません。`volume`、`sign`、`painting`、`frame`、`bed`、`raw` はまだキーワードではなく、どれも `E_UNKNOWN_KEYWORD` として拒否されるので、ブロックを置くフェーズは `massing`、`envelope`、`openings`、`fixtures` の 4 つで、`fixtures` に属するのは `pressure_plate` だけです。また、`cairn compile` は 3 つの `logic_*` フェーズを実行しないので、`logic` 行を書いても成果物にレッドストーンは置かれません。これらのフェーズを実行できるのは `cairn synth --experimental-logic-synth` だけです。

`roof` の後に書いた `window` も、壁の開口として切り抜かれます。ソース上の順番がメンバーの意味を決めることはありません。成果物の内容も同じで、ソース上の順番には左右されません ([§4.8](#48-同一フェーズ内の衝突とパレット))。ボクセルを共有しない 2 つのメンバーを入れ替えても、ボクセルだけでなく、パレットの番号付けを含めた `BlockArray` 全体が変わりません。

`circuit` は配線のための領域を確保するだけで、ボクセルを書かないので、どのフェーズにも属しません。3 つの `logic_*` フェーズが `fixtures` の後にあるのは、センサーとアクチュエーターを 3D 空間に配置するまで、ポートの座標が決まらないからです ([レッドストーン](/ja/spec/redstone/))。

後勝ちになるのは **同じフェーズの中での局所的な上書き** だけで、`raw` は常に最後に評価します。同じフェーズの中で別々のメンバーが 1 つのボクセルを取り合う場合も、同じ規則で決着し、そのことを報告します ([§4.8](#48-同一フェーズ内の衝突とパレット))。

```
theme stone:
  slot floor -> @oak_planks
  slot wall  -> @cobblestone
  slot roof  -> @spruce_stairs
  slot glass -> @glass_pane

struct keep size=11x9
  floor  id=base   mat_slot=floor
  walls  id=shell  mat_slot=wall height=5
  roof   id=roof   kind=gable mat_slot=roof overhang=1
  window id=front_windows side=front y=2 offset=2 size=2x2 mat_slot=glass   # それでも開口として切り抜かれる
  door   id=entry  side=front at=center
```

## 4.2 ターゲット軸

ターゲットは `(edition, version)` の組です。どちらもソースには書かず、知っているのはバックエンドだけです ([バージョンとエディション](/ja/spec/versioning-editions/))。

```sh
cairn compile build.crn --edition java    --target 1.21.4
cairn compile build.crn --edition bedrock --target 1.21.40
```

`--edition` は必須で、`--target` だけを指定すると拒否されます。同じ「1.21」でも、Java と Bedrock では意味が違います。Java の DataVersion と Bedrock の block_version にも関係はありません。

## 4.3 切妻屋根のボクセル規則

`roof kind=gable [overhang=N] mat_slot=...` は、棟で向かい合わせに出会う 2 つの階段の斜面になります。

屋根の 4 種類 (`gable` / `shed` / `hip` / `flat`) は、以下で説明する軒の出 (overhang) と壁の上端の規約を共有します。各種類の形は、この節と続く 3 つの節で説明します。`overhang=` はどの種類でも読みます。`slope_to=` は `shed` 専用です。ほかの種類に書いても何にも使われず、`W_IGNORED_ARGUMENT` として報告されます ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。

**マテリアル。** 傾斜のある屋根は `mat_slot=` から材質を取ります。この材質は、階段の系統 (パスが `_stairs` で終わる id) でなければなりません (MUST)。屋根の形状は、置くブロックに `facing`・`half`・`shape` を付けますが、フルブロックはこれらを持てないからです。階段の系統以外を割り当てると `E_INCOMPATIBLE_MATERIAL` になり、ビルドが止まります。`mat_slot=` がまったくなければ、`minecraft:spruce_stairs` を代わりに使います。レジストリパックの 4 種類の屋根材 (`roof.dark_wood` / `roof.light_wood` / `roof.warm_wood` / `roof.cool_wood`) は、どれも階段の系統に解決されます。

階段の系統でも、独自のブロックステートを持つ割り当ての場合は、id はそのまま使い、ステートは屋根の形状が決めた値で置き換えて、`W_DEFERRED_MEMBER` を出します。軒に置く `stair kind=stairs` も同じ材質の規則に従いますが、ステートは自分の引数から取ります。

その引数は `facing=out | in`、`half=top | bottom`、`shape=straight | outer_left | outer_right` で、どれも裸の識別子です。既定値はそれぞれ `out`、`top`、`straight` です。一覧にない識別子はまだサポートしていないので、その階段は `W_DEFERRED_MEMBER` で保留になります。識別子ではない形の値 (`half="bottom"`、`facing=1`) は読み取れない値として扱います。階段はそのキーの既定値で作られ、その値は `W_IGNORED_ARGUMENT` として報告されます。階段が別の理由で拒否された場合も、この値は報告されます。その際は、どちらにしても階段は作られないという注記が付きます ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。

**棟の向き。** 棟は、敷地 (footprint) の長いほうの水平軸に沿って走ります。正方形の敷地 (`size=WxW`) では `x` 軸を選び、東西方向の棟になります。

**棟の高さ。** 切妻屋根は、壁の上端から `ceil(short_span / 2)` ボクセル立ち上がります。`short_span` は、軒の出で広げた後の `min(dims.x, dims.z)` です。

**段。** 段 `0` は壁の上端に載り、左右の斜面の行の組になります (`short_span` が 1 のときは 2 つが重なって 1 行になります)。その上の段は、左右それぞれ 1 ずつ内側に寄ります。いちばん上の段が頂部です。

- スパンが奇数のとき: 中央の行に `half=top` の階段を 1 つ置きます。
- スパンが偶数のとき: 中央で隣り合う 2 行に `half=top` の階段を 2 つ置きます。棟に V 字の隙間を残さないためです。

`short_span` が 1 か 2 なら、立ち上がりはちょうど 1 段、つまり段 `0` だけで、頂部の段はありません。

**軒の出。** `overhang=N` は、ボクセルの格子を水平の 2 軸それぞれについて `N` ずつ広げます (`Dims.x = size.w + 2N`、`Dims.z = size.h + 2N`)。floor / walls / door / window は、書いた座標のまま `+N` だけ内側にずれます。屋根は広げた後の箱いっぱいに張るので、軒と妻側の端が壁の外にはみ出します。

**階段の向き。** 斜面の行は `half=bottom, shape=straight` で、`facing` は棟のほうを向きます。棟が x 軸に沿う場合、`-z` 側の斜面は `south`、`+z` 側の斜面は `north` を向きます。棟が z 軸に沿う場合は、これを鏡映して `east` / `west` になります。

スパンが偶数のときの頂部の 2 つの階段は、それぞれ棟から *外* を向きます (棟が x 軸に沿う場合、`-z` 側の行は `north`、`+z` 側の行は `south`)。内向きにすると、屋根の全長にわたって両側の外面に 0.5 × 0.5 のえぐれが残ります。外向きにすれば、その空洞は棟の下に移ります。

スパンが奇数のときの頂部の 1 つの階段は `half=top` で、低い側の斜面と同じ向きです。1 つのセルに外面が 2 つあり、階段はそのうち片方しか埋められないので、空洞はどうしても残ります。この規則は、どちらを埋めるかを固定するためのものです。

## 4.4 片流れ屋根のボクセル規則

`roof kind=shed slope_to=front|back|left|right [overhang=N] mat_slot=...` は、`slope_to=` で指定した壁に向かって高くなる 1 枚の階段の斜面になります。各行の形は切妻屋根の低い側の斜面と同じ (`half=bottom, shape=straight`) です。ただし斜面は片側だけなので、反対側の壁は書いた高さのままです。

- **傾斜の向き。** `slope_to=front|back` は `z` 方向に、`slope_to=left|right` は `x` 方向に高くなります。高い側の辺が指定した壁に、低い側の辺が反対側の壁に載ります。
- **高さ。** 片流れ屋根は、壁の上端から `slope_span` ボクセル立ち上がります。`slope_span` は、`front|back` なら `dims.z`、`left|right` なら `dims.x` で、どちらも軒の出で広げた後の値です。`y` が 1 上がるごとに、低い側の辺から 1 ずつ内側に寄ります。
- **階段の向き。** 斜面の階段はすべて高い側の辺を向きます。`front` なら `facing=south`、`back` なら `north`、`left` なら `west`、`right` なら `east` です。いちばん上の段は、同じ向きの `half=top` の 1 行でふさぎます。
- **`slope_to=` は必須です。** 既定値はありません。指定がない場合や未知の値の場合は、向きを推測せず `W_DEFERRED_MEMBER` にします。

## 4.5 寄棟屋根のボクセル規則

`roof kind=hip [overhang=N] mat_slot=...` は、四方から階段を積んだピラミッドになります。4 つの面すべてが、中央の棟に向かって内側に傾きます。

- **棟の向きと高さ。** `gable` と同じです (長いほうの軸、正方形なら `x`、壁の上端から `ceil(short_span / 2)`)。
- **段の構成。** 段 `L ∈ 0..extra_height` は、内側に寄せた矩形の枠 `[L, dims.x − 1 − L] × [L, dims.z − 1 − L]` です。段 `0` は壁の上端に載り、それが最後の段であっても、常にこの枠の形になります。

  | 辺 | ステート |
  |---|---|
  | 北の行 (`z = L`) | `facing=south, shape=straight` |
  | 南の行 (`z = dims.z − 1 − L`) | `facing=north, shape=straight` |
  | 西の列 (`x = L`) | `facing=east, shape=straight` |
  | 東の列 (`x = dims.x − 1 − L`) | `facing=west, shape=straight` |
  | 北西 / 北東の角 | `facing=south` で `outer_left` / `outer_right` |
  | 南西 / 南東の角 | `facing=north` で `outer_right` / `outer_left` |

- **頂部。** 頂部は下の枠が立ち上げた部分をふさぐものなので、`extra_height > 1` のときだけ現れます。いちばん上の段では、内側に寄せた矩形の全体を `half=top` の階段で埋めます。正方形の敷地では、階段を 1 つ (短いほうのスパンが奇数のとき) か、`2x2` のかたまり (偶数のとき) を置きます。長方形の敷地では、長いほうの軸に沿った帯になり、その幅は短いほうのスパンが奇数なら 1 行、偶数なら 2 行です。偶数のときは内側に寄せた矩形が 2 行の幅を持つので、1 行ではもう 1 行が開いたまま残ります。頂部の向きは切妻屋根の規則に従います。短いほうのスパンが奇数なら、頂部は低い側の斜面と同じ向きで、棟が x 軸に沿う場合は `south`、z 軸に沿う場合は `east` です。偶数なら 2 行がそれぞれ棟から外を向き、棟が x 軸に沿う場合は `-z` 側の行が `north`、`+z` 側の行が `south`、z 軸に沿う場合は `-x` 側の行が `west`、`+x` 側の行が `east` です。正方形は x 軸の棟になるので、`2x2` の頂部は x 軸の棟の組 (`-z` 側の行が `north`、`+z` 側の行が `south`) になります。
- **軒の出。** `gable` と同じです。

## 4.6 陸屋根のボクセル規則

`roof kind=flat [overhang=N] mat_slot=...` は、`y = wall_top + 1` にフルブロックを 1 層敷きます。この屋根面は、広げた後のバウンディングボックス全体を覆います。

- **マテリアル。** 屋根面の各セルには、`mat_slot=` に割り当てた id をブロックステートなしで置きます。割り当てがなければ `minecraft:spruce_planks` を使います。屋根面はフルブロックなので、傾斜のある屋根なら拒否されるような id も有効です。階段を指定した場合は、既定のステートの階段が並ぶだけです。
- **高さ。** 陸屋根は敷地の形にかかわらず `Dims.y` に `1` を足します。`size=WxH` で `walls height=K` なら、 `Dims.y = 1 + K + 1` です。
- **傾斜の引数はありません。** `slope_to=`、種類ごとの向き、棟の向きは、どれも適用されません。

## 4.7 level によるまとまりと体積の導出

`level y=N` はメンバーをまとめ、それぞれを struct の基準面から `N` ボクセル上に置きます。`level` の行自体はブロックを生成しません。その下にある各メンバーは、自分の垂直方向の座標に `N` を足したうえで、本体に直接書いた場合と同じように lowering されます。ただし `level` は、スコープ全体にわたって領域を確保する `circuit` 行をまとめることはできません。`level` の下に書いた `circuit` 行は `E_MISPLACED_MEMBER` になります ([レッドストーン §14.5](/ja/spec/redstone/#145-配置配線-place-and-route))。

struct が lowering される体積は、自分で書くものではなく、導出されるものです。

```
Dims.x = size.W + 2 × overhang
Dims.z = size.H + 2 × overhang
Dims.y = 1 + wall_top + roof_extra
```

それぞれの項が数えるのは、実際にブロックを置くメンバーだけです。

- `overhang`: 実際に描かれる屋根 (コンパイラが知っている `kind=` を持ち、`shed` なら `slope_to=` も持つもの) の `overhang=` のうち、最大の値。
- `wall_top`: `mat_slot=` が解決できる walls の `N + height` のうち、最大の値。`N` はそれを囲む level のオフセットで、本体に直接書いた場合は `0` です。
- `roof_extra`: 種類ごとの寄与 ([§4.3](#43-切妻屋根のボクセル規則)–[§4.6](#46-陸屋根のボクセル規則)) のうち、最大のもの。
- `1`: どの struct にもある基準面。

`level` の中のメンバーも、この 3 つの項すべてに、level のオフセットを含めて数えます。`walls height=3` を本体に直接書けば `Dims.y = 4` ですが、同じ walls を `level y=5` の下に書くと `Dims.y = 9` (`1 + 5 + 3`) になります。

**すべての種類のメンバーが、0 以外のオフセットで lowering できるわけではありません。** `walls` / `door` / `window` / `stair` / `pressure_plate` は、`N` を自分の形状を測る基準として読みます。`floor` と `roof` は struct に 1 つしかない面なので、`N > 0` の `level y=N` の下に書くと `W_DEFERRED_MEMBER` を出し、ブロックを生成しません。

**ブロックを置かないメンバーは、体積も決めません。** `N > 0` の `level y=N` の下に書いた屋根の `overhang=` は敷地を広げず、その高さも `Dims.y` を上げません。`level y=0` の下に書いた屋根は描かれるので、本体に書いた屋根と同じように敷地を広げ、`Dims.y` も上げます。メンバーが脱落するどの場合も同じです。`kind=` のない `roof` や `slope_to=` のない `shed` は敷地を広げず、材質が解決できない `walls` は `Dims.y` を上げません。

ただし、材質による脱落が起きるのは `walls` だけで、`roof` には起きません。`mat_slot=` が解決できない屋根は、自分の既定の材質を代わりに使って描かれるからです。テーマのない struct を見ると、この違いがよく分かります。壁は作られず、高さも占めませんが、その上の `roof kind=gable` は描かれ、壁がまったくない場合と同じ位置に載ります。

「材質が解決できるか」は、指定したターゲットについて判断するので、一部のバージョンにしか存在しないブロックを使うと、`--target` によって `Dims.y` が変わることがあります。指定したターゲットに存在しない id は `E_UNKNOWN_ID` になるので、その場合は成果物が出力されません。

## 4.8 同一フェーズ内の衝突とパレット

フェーズが異なるメンバー同士では、フェーズの順番で決まります。`walls` を貫く `door` は massing の後の openings なので、壁に穴が開くのは狙いどおりです。同じフェーズの中で 2 つのメンバーを区別するのはソース上の順番だけで、[§4.1](#41-フェーズ評価) はこれを「同じフェーズの中での局所的な上書き」として認めています。

この上書きは、作者が同じメンバーを書き直すことを想定したものです。たまたま敷地が重なっただけのメンバー同士は事情が違います。この場合、コンパイラは最後の書き込みを残し、両方のメンバー名と、入れ替わったボクセルの数を示す `W_PHASE_CONFLICT` を出します。ビルドの結果は変わりません。動かせる 1 行が結果を左右していることを、作者に知らせるためのものです。

次の 2 つは衝突として扱いません。

- 値が変わらないセル。たとえば、同じ材質の `walls` 2 つが共通の行で重なる場合です。
- メンバーが自分自身の上に書く場合。たとえば、`window` の `repeat=` / `step=` で複製した窓同士が重なる場合です。

**パレット** は、評価する本体 (`struct`、`def`、それらを実体化する各 `place`) ごとにあり、書き込みの履歴ではなく、*決まった並べ方を持つ集合* です。パレットにはその本体に含まれるブロックを並べ、並び順は 1 通りに固定されます。スロット `0` は空気で、それ以外は `(id, properties)` の昇順に並べます。

まず id で順番を決めます。id が同じ 2 つのエントリでは、それぞれのプロパティを名前順に並べたうえで、2 つのリストを先頭から 1 組ずつ比べます。つまり、名前が一致したら次は**値**で決まり (`facing=north` が `facing=south` より前)、短いプロパティの組は、それを先頭に含む長い組より前に来ます (`oak_stairs[facing=north]` が `oak_stairs[facing=north,half=top]` より前)。プロパティを名前順に並べるのは、ステートのリテラルにプロパティをどの順で書いたかに、並び順が左右されないようにするためです。`@oak_stairs[half=top,facing=north]` と `@oak_stairs[facing=north,half=top]` は同じブロックで、テーマがどちらの順で書いたかによってスロットが動いてはならないからです。

「その本体に含まれるブロック」には例外が 2 つあります。1 つはスロット `0` の空気で、何があっても残るので、すきまなく埋まった体積にもこのエントリはあります。もう 1 つは一度もブロックを置かなかったスロットで、これは意図的に残します。削除すると、出力されない形状のためにジェネレータが材質を登録 (intern) したという事実の、リリースしたビルドに残る唯一の手がかりを消すことになるからです。

ここから 2 つの規則が導かれます。どちらの規則も、この番号付けが `.nbt`、`cairn info` のエントリごとの行、`resolved_ir_hash` にまで影響するために必要です。

- 最後の 1 ボクセルが後のフェーズで覆われた材質は**削除**し、残りのスロットを詰めて番号を振り直します。そうしなければ、「どちらのメンバーが上書きされたか」だけが異なる 2 つのソースが、同じビルドに対して別々の成果物を生むことになります。
- ボクセルを共有しない 2 つのメンバーの間には、順序を付けません。完成した格子がどちらの行が先かに左右されない以上、成果物も左右されてはなりません。これが §4.1 の冒頭で約束したことで、ボクセルだけでなくバイト列についての約束です。それを実現するのがソートです。パレットは完成した格子だけから導くので、格子を変えないソースの並べ替えは `BlockArray` 全体を変えません。

ソートの対象は解決済みのステートです。ソース上の位置、メンバーの id、フェーズ、ブロックを置いた順番のどれも参照しないという意味で、エディションやバージョンが変わっても安定しています。ただし、2 つのターゲットが同じパレットを持つという意味ではありません。そこに並ぶ id 自体が、ターゲットごとに同じとは限らないからです。

`.mcstructure` のパレットはこのパレットから書き出し、やはり集合のままです。Bedrock に変換すると、複数のエントリが 1 つの Bedrock のブロックになることがあります (たとえば `shape` だけが異なる階段は、`shape` を落とすと同じブロックになります)。その場合は最初のエントリのスロットを共有するので、空気は `0` のままで、同じ Bedrock のブロックが 2 回並ぶことはありません。

通路 (walkway) のブロックは、フェーズではなく `connect` パスが敷くもので、この節の対象外です。
