## 9.1 コンポーネントを定義する `def`

`def` は、スロットを持つコンポーネントを定義します。`theme` や `site` と同じ仕組みで統一されているので、編集、テーマの適用、複数の建物の配置のどこでも、参照の仕方がばらばらになりません。

パラメータ化 (可変のサイズなど) は許し、再帰は禁止します。`def` は `requires version>=X` を宣言でき、部品を組み合わせたものの最低バージョンは、部品の最低バージョンのうち最大のものになります ([バージョンとエディション](/ja/spec/versioning-editions/))。

パラメータの仕組みが決まるまで、ヘッダに書けるキーは限られています。`def` のヘッダに書けるのは、lowering が読む `size=` と、まだどのパスも読まない `class=` の 2 つで、`struct` のヘッダも同じです。どちらでも、それ以外のキーは `E_UNKNOWN_ARGUMENT` として拒否します。ヘッダの `class=` は `W_IGNORED_ARGUMENT` として報告するので ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))、下の例にはこの警告が出ます。

```
def cottage class=house size=9x7:
  floor  id=floor mat_slot=floor
  walls  id=walls class=outer mat_slot=wall height=4
  door   id=door  class=entry side=front at=center
  roof   id=roof  kind=gable mat_slot=roof
```

## 9.2 編集モデル

重要なメンバーは `id=` を持ちます。`id=` を持たないメンバーには、生成した順番ではなく、親・ロール・side・level・offset から導いた **意味に基づく安定したアドレス** が付きます。struct に行を追加しても、このアドレスは変わりません。

編集は、セレクタやアドレスに対するパッチの DSL で書きます。

```
edit window[class=vent][level=floor2] set shape=arch
edit window@front[0]                  set mat_slot=accent_glass
edit door[id=entry]                   set side=front at=center
```

「2 階の窓だけをアーチにする」のような概念レベルの編集が、全体を壊さずにできなければなりません。編集の差分は `intent_state` だけを見るので ([ブロックステート](/ja/spec/blockstate/))、導出した結果が変わっても編集の安定性は損なわれません。

## 9.3 `site` による複数建築

AI に絶対座標を計算させてはいけません。配置は位置関係の制約として書き、それを座標に解決するのはコンパイラの仕事です。

```
site village:
  place id=home1 use=cottage theme=medieval at=origin
  place id=home2 use=cottage theme=medieval east_of=home1 gap=4
  connect home1.door to home2.door path=@gravel
```

各 struct はポート (位置・法線・幅) を公開し、`connect` がそれらを結びます。ストラクチャーブロックの 48³ という上限を超える村や城は、複数の struct を組み合わせて表現します。

### 9.3.1 座標規約

`east` は `+x` 方向に進み、`north` は `-z` 方向に戻ります。これは [§5.4](/ja/spec/syntax#54-セレクタ) の「front は `+z`」と一致します。`front` が南を向く建物は正面が `+z` 側にあり、`north_of=X` は次の配置をその建物の裏側に置きます。

Y 軸は位置関係のセレクタの影響を受けません。今のところ、すべての配置は `y = 0` に置かれます。

### 9.3.2 原点セレクタ

各 `place` は、`at`、`east_of`、`north_of` のうち **ちょうど 1 つ** を持ちます。下の式で、`prior` は `ID` が指す配置、`new` はこれから置く配置です。原点は配置の `x` と `z` が小さい側の角です。`dims` は配置全体の広がりで、`size=WxH` の敷地の両側に屋根の `overhang=` の列を足したものです。これはロックファイルに記録される広がりと同じです。

| セレクタ | 効果 | 備考 |
|---|---|---|
| `at=origin` | ワールドの `(0, 0, 0)` に固定します。 | `at=` に書ける値はこれだけです。暗黙の既定値はないので、site の最初の `place` は必ずこれを使います。 |
| `east_of=ID gap=N` | 新しい原点 = `(prior.x + prior.dims.x + N, prior.y, prior.z)`。 | `ID` は、同じ `site` の中で先に宣言した place を指す必要があります。`gap` は、向かい合う 2 つのバウンディングボックスの面 (それぞれ壁とその `overhang=` の列) の間のブロック数です (`0` ならボックス同士が接します)。既定値は `0` です。 |
| `north_of=ID gap=N` | 新しい原点 = `(prior.x, prior.y, prior.z − new.dims.z − N)`。 | `ID` と `gap` の規則は `east_of` と同じです。原点は `z` が小さい側の角なので、戻る量は新しい配置自身の奥行きになります。これにより、どちらの配置が奥行きが深くても、新しい配置の `+z` 面と前の配置の `−z` 面の間がちょうど `N` ブロックになります。 |

セレクタを併用した場合と、`at=` に `origin` 以外の値を書いた場合は `E_INVALID_PLACE_ORIGIN` です。

`gap=` は 2 つの相対セレクタのためのものです。`at=origin` の行は絶対位置に固定され、距離を読まないので、同じ行に書いた `gap=` はどこにも使われず、`W_IGNORED_ARGUMENT` として報告されます ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。引数自体は実在するので、どちらのつもりだったのかを決めるのは書いた人です。

相対セレクタの行では、`gap=` は 0 以上の整数を取ります。2 つの本体の間に空けるセルの数なので、どちらの本体も相手の中に入り込みません。負の値はパースできません。`-` で始まる `key=` の値はないので、`gap=-3` は `E_PARSE` になります。それ以外の値 (`gap=wide`、`gap="4"`) は読み取れない値として扱い、その行は `gap=0` と同じ位置に置きます。その値は `W_IGNORED_ARGUMENT` として報告します。

原点は 32 ビット符号付きの座標として記録するので、原点か本体の反対側の端がこの範囲を超える行は配置せず、`W_DEFERRED_MEMBER` として報告します。その行を基準に置くすべての行も同じ扱いです。範囲の端に丸めずに拒否するのは、丸めた原点はソースが求める原点ではなく、同じ端に丸められた 2 つの行が同じ座標に重なってしまい、範囲外のセルにはそもそも座標がないからです。

原点や反対側の端が原因で拒否した行でも、その `def` の本体が出す指摘は報告します。基準にした行が拒否されたために拒否された行も同じです。`E_INCOMPATIBLE_MATERIAL` や `W_NO_THEME_BOUND` は、行がどこに置かれるかにかかわらず、`def` やテーマの欠陥だからです。配置されない行の読み取れない `gap=` も、配置されないという注記を付けて報告します。

### 9.3.3 スコープをまたぐ参照

すべての `place` 行は `id=`、`use=`、`theme=` を宣言します。どれかが欠けた行は配置になれません。`.nbt` の名前がない、実体化する `def` がない、`mat_slot=` を解決するテーマがない、のいずれかになるからです。これが `E_INCOMPLETE_PLACE` で、メッセージは欠けているキーをすべて挙げ、その行は捨てます。キーはあるもののラベルではない場合 (`use=3`) は、代わりに `E_TYPE_MISMATCH_LABEL` になります。

[§9.2](#92-編集モデル) の形状のメンバーと違って `id=` が自動で割り当てられず必須なのは、それが `east_of=` と `connect` が参照する名前であり、`.nbt` を書き出すときの名前でもあるからです ([§9.3.4](#934-出力ファイル名))。

| コード | 原因 |
|---|---|
| `E_UNRESOLVED_PLACE_REF` | `use=NAME` がトップレベルの `def` を指していない。最も近い候補の提案が付きます。 |
| `E_UNRESOLVED_THEME_REF` | `theme=NAME` が同じファイルの `theme` を指していない。最も近い候補の提案が付きます。 |
| `E_DUPLICATE_PLACE_ID` | 同じ site の 2 つの `place` 行が同じ `id=` を使っている。診断は最初の宣言も指します。 |
| `W_UNUSED_DEF` | どの `place use=NAME` からも参照されない `def`。助言です。`use=` 側の書き間違いで、空のビルドが黙って出力されないようにします。 |

### 9.3.4 出力ファイル名

コンパイラは `place` ごとに `.nbt` を 1 つ、`id=` の名前で出力ディレクトリの直下に書き出します (`home1.nbt`、`home2.nbt`)。次のような id は `E_INVALID_PLACE_ID` にします ([Lint](/ja/spec/lint/))。

- `/` や `\` を含む id。ファイルではなくパスを指してしまいます。
- Windows のファイル名に使えない文字を含む id。Windows では書き出せません。
- `CON` や `NUL` のように Windows が予約しているデバイス名の id。Windows ではデバイスとして開かれることがあります。

ファイル名に site の名前は含めません。同じディレクトリには、すべての `struct` (自身の名前で書き出し、その名前がこうしたデバイス名なら `E_INVALID_STRUCT_NAME`) と、すべての通路 ([§9.3.5](#935-ポートと-connect)) も書き出します。大文字と小文字を区別せずに比べて同じファイル名になる 2 つの成果物は、`E_OUTPUT_NAME_COLLISION` です。`struct` と同じ名前の `place` や、2 つの site に置いた同じ `id=` は、片方でもう片方を上書きするのではなく拒否します。

各配置のワールド座標での原点と `(site, def, theme)` の来歴は、`build.cairn.lock` の `placements` に記録するので、下流のツールは座標の計算をやり直さずに配置を再現できます。

### 9.3.5 ポートと `connect`

`connect FROM.PORT to TO.PORT path=@MATERIAL` は、同じ `site` の中にある 2 つの配置の名前付きポートの間に、幅 1 ブロックの通路を敷きます。

**ポートとは。** ポートは、`PLACE.PORT` が解決する `(place, member_id)` の組です。ポートは、参照先の `def` の本体に直接宣言した `door` と `window` のメンバーが公開します。階段と屋根のポート、および level の中のメンバーのポートは、将来の拡張のために予約しています。

**ポートの位置。** ポートは、メンバーの `side=` が示す壁の 1 ブロック外側、配置の地面の段 (`place_origin.1`) にあります。`front` / `back` / `left` / `right` は、それぞれ `+z` / `-z` / `-x` / `+x` に対応します ([§9.3.1](#931-座標規約))。壁に沿った位置は次のように決まります。

- `door` は `at=` の値 (`center` / `left` / `right`、[§5.4](/ja/spec/syntax#54-セレクタ))。数値のオフセットは予約しています。
- `window` は矩形の中心 `offset + size.w / 2`。`offset=` がない場合は、切り抜きと同じく `0` として読みます。

配置に軒の出があると、ポートは外壁面より外側の、軒の出の範囲まで押し出されます。`window` に書いた `y=` は、ポートを地面の段から持ち上げ **ません**。通路は厚さ 1 ボクセルの平らな帯で、その Y は反対側の端点と一致していなければならないからです。`sym=true` の窓が提供するポートは、元の `offset` 側の 1 つだけです。鏡映した開口がある場合はそれも壁に現れますが、`id=` が指すのは 1 つの座標です。窓と重なる、またはぴったり一致する鏡映は省き ([§5.4](/ja/spec/syntax#54-セレクタ))、窓には元の切り抜きとポートが残ります。

**ポートは、壁に開口がある場所にしか置けません。** ポートを持てる 2 つのロールは、どちらも石積みを貫く開口なので、必要な段まで壁が届いていない配置には、どちらのポートも置けません。`door` は開け始める段が 1 つの層の中に、`window` は矩形全体が 1 つの層の中に収まっていなければなりません。

```
段 1 が 1 つの層の中にある                           # door (ポートになるドアは def 本体のメンバーなので、
                                                 #       開け始める段は常に 1)
offset + size.w ≤ wall_length                    # window、水平方向
y … y + size.h - 1 のすべての段が 1 つの層の中にある  # window、垂直方向
```

ここまでは、ポート自身が確かめる規則です。それに加えて、ポートは開口パスが実際に切り抜いた開口にしか置けません。切り抜きだけが読む引数 (`repeat=` か `step=`。`sym=true` や読み取れない `sym=` と一緒に書いた 1 より大きい `repeat=` も含みます) のために保留された `window` や、自身の `mat_slot=` がブロックに解決できない `window` は、壁をそのまま残すので、そのポートも一緒に拒否されます。鏡映を省いた `sym=true` の窓には、鏡映について `W_DEFERRED_MEMBER` が出ます。ただし窓自身の矩形は切り抜かれるので、ポートは置けます。

`level y=N` の下にある `walls height=H` のメンバーは、ワールドの段 `N + 1 … N + H` を描きます。これは level の基準の段の 1 つ上からで、基準の段はその level の床が置かれるはずの段です。ただし、level の中の `floor` は今のところ保留されるので、実際に床があるのは struct 自身の床の段 `0` だけです。接している層は 1 つにつながります。たとえば `walls height=5` と `level y=5 walls height=4` は段 1 から 9 までの 1 枚の壁になり、つなぎ目をまたぐ窓もその壁の中にあります。間に空気がある層はつながらず、その隙間にかかる窓はどの層の中にもありません。`def` の本体にある `door` のメンバーは段 `1` から開けるので、石積みが `level y=6 walls` しかない配置では、戸口が壁に届きません。同じ本体の `window` も同じ理由で拒否されます。

ポートを判定するときの段は、配置が実際に **描いた** 段です。これは開口パスが切り抜きに使ったのと同じ値で、`def` を読み直して別に求めた値ではありません。`mat_slot=` が解決できない `walls` は何も描かないので、切り抜きは保留され、ポートもそれに合わせて拒否されます。`level` の中で宣言した `walls` はその段を描くので、切り抜きが行われ、ポートもそこに置けます。

ポートを置けなかった行は、`W_DEFERRED_MEMBER` とともに捨てます。この診断には、拒否された端点ごとに note が 1 つ付き、その端点が破った規則を 1 つだけ示します。示すのは、ポートを持てないロール、書いた `side=` や `at=`、欠けているか形の誤った window の引数、矩形が壁からはみ出した量、石積みが覆っている段と覆っていない段、開口パスが切り抜かなかったことのいずれかです。note はそのメンバーの行を指します。原因が `side=`、引数、石積みのどれかにある場合は、その行にメンバー自身の指摘も出ます。両者は引数を同じように読み取って文言を作るので、書いた内容について食い違うことはありません。`place` によって座標の範囲外まで押し出されたポートには指すべきメンバーの行がないので、そのことは `connect` の行にだけ示されます。

**経路の通り方。** 経路は、2 つのポートが共有する Y の高さで、x 軸方向の区間の次に z 軸方向の区間を通る L 字形の直交経路です。階段や複数階にまたがる通路のような 3D の経路探索は、意図的にスコープ外としています。

その L 字が既存の構造の床を横切る場合、コンパイラは地面の平面で迂回路を探します。障害物を避ける最短の経路を選び、同じ長さなら曲がる回数が少ないほうを選びます。それでも決まらない場合も決定的な方法で選ぶので、同じソースからは常に同じ帯が敷かれます。

衝突するセルを飛ばして直線の L 字に戻すのは、障害物のない経路がまったく存在しない場合だけです。次のような場合がこれにあたります。

- ポートが別の配置の床の下に埋まっているか、ポートのセルに自分の配置がブロックを置いている。
- 行き先が完全に囲まれている。
- 探索がルーターの面積の上限を超える。

ルーターは、2 つのポートと、歩く高さにあるすべての配置の床を含む箱の中を探索するので、ポート同士が離れている場合も、床が広い範囲に散らばっている場合も、上限に達することがあります。

このとき `W_WALKWAY_BLOCKED` が 1 件出て、具体的な原因と直し方が示されます。直し方は、埋まっているドアや窓 (またはポートのセルにあるブロック) を動かす、gap を広げる、2 つの構造を近づける、箱を広げている配置を近づける、のいずれかです。`--format json` では `data: { kind: "walkway_blocked", skipped: N }` が付きます。

**マテリアル。** `path=@TOKEN` は、メンバーのマテリアルと同じ `mat_slot=` の処理を通ります。`@gravel` のような具体的なトークンは、レジストリパックがなくても使えます。`@path.gravel` のような抽象トークンにはパックのマテリアルカタログが必要で、見つからなければ `W_ABSTRACT_TOKEN_DEFERRED` か `E_UNKNOWN_ABSTRACT_TOKEN` を出します。

**出力。** 通路を敷いた `connect` 行ごとに、site とポートの名前を付けた `.nbt` を 1 つ書き出します (`hamlet_walkway_home1_entry__home2_entry.nbt`)。ロックファイルには、ワールド座標での原点、寸法、解決済みの経路のマテリアルを持つ `walkways:` のエントリを記録します。

ブロックを 1 つも敷かなかった行は、ソースが求めた通路を失っています。原因は次のいずれかです。

- 端点の `place` が上流で拒否された (`W_DEFERRED_MEMBER`)。
- ポートを置けない。
- 通路の名前に使えない id がある。
- 経路のマテリアルが解決できない。
- 直線の L 字だけでルーターの探索面積の上限を超える。
- 直線の L 字のすべてのセルが配置と重なり、帯が空気だけになる。

このとき `cairn compile` は、スコープを失ったときと同じく `E_PARTIAL_BUILD` でビルドを拒否し、`cairn check --edition E --target V` も同じく拒否します ([Lint](/ja/spec/lint/))。`--target` を付けない `cairn check` は、失った原因となる指摘のうちターゲットを必要としないものは報告しますが、失ったこと自体は報告しません ([Lint §11.3](/ja/spec/lint/#113-エラーと警告の区分))。失った通路は、`site::SITE::FROM ↔ TO` という名前と、行に書いたとおりのポートで示します。

`W_DUPLICATE_WALKWAY` の行は何も失いません。そのポートの組は、前の行がすでに敷いているからです。どちらも敷かなかった同じ組を指す 2 つの行は、1 件の損失として数えます。逆に、1 つの誤りで複数の損失が出ることもあります。`size=` のない def を使う `place` は失われたスコープで、そこに端点を持つ通路もすべて失われます。通路ごとに `E_PARTIAL_BUILD` に note が 1 つ加わり、lowering できなかったスコープの数も 1 つずつ増えます。

**診断。**

| コード | 原因 |
|---|---|
| `E_CONNECT_ARITY` | 行の形が `FROM.PORT to TO.PORT` ではない。端点を読み取れないとその行の通路が失われるので、解決の前に検査します。 |
| `E_UNRESOLVED_PORT` | ドットの右のポート id が、参照先の def の本体のメンバーを指していない。綴りの差の上限に収まる候補があれば、最も近い候補の note を付けます。その id が `level` の下にあるメンバーのものなら、代わりにそのことを示し、そのメンバーを指す note を付けます。level の中のメンバーは、まだポートになれません。 |
| `E_AMBIGUOUS_PORT` | def が同じ `id=` を複数のメンバーで公開している。重複している名前を変えてください。 |
| `E_MISSING_PATH_MATERIAL` | 行に `path=` がなく、通路の lowering で敷くものがない。 |
| `E_UNRESOLVED_PLACE_REF` | 先頭の place の id が、この site で先に宣言した place を指していない ([§9.3.3](#933-スコープをまたぐ参照) と共通)。 |
| `W_WALKWAY_BLOCKED` | 障害物のない経路がない。直線の L 字に戻し、残りの帯は敷きます。直線の L 字のすべてのセルが配置と重なる場合や、直線の L 字だけでルーターの探索面積の上限を超える場合は、何も敷かず、通路は失われます。 |
| `W_DUPLICATE_WALKWAY` | 同じ `(from, to)` のポートの組が、この site ですでに敷かれている。重複した行は捨てます。 |
