コンパイラは、警告とエラーを行番号付きで報告します。どのメッセージも、自己修正のための 3 点、つまり **何が間違っているか / ターゲットで有効な候補 / 修正案** を持たなければなりません (MUST)。この形が、[評価フレームワーク](/ja/spec/evaluation/) のループの入力になるからです。

## 11.1 診断コード

この節は診断コードのカタログです。安定したコマンドが出しうるコードには、必ずここに行があります。行のないコードがあれば、それはカタログ外のコードではなく、この節の不備です。コードの規則が別の章にある場合は、行にコードの意味を書き、規則はその章へリンクします。コードを手にした読者が探すのはこの行で、振る舞いを定義しているのは各章だからです。

レッドストーンのパイプラインが出す `E_LOGIC_*` / `W_LOGIC_*` は、この約束の対象外です。これらに到達できるのは `cairn synth --experimental-logic-synth` だけで、この機能はまるごと Internal ティア ([互換性](/ja/spec/compatibility/)) です。文字列について何も保証していないので、ここに行を置くと、存在しない契約を書くことになります。規則に関わるものは [レッドストーンと論理](/ja/spec/redstone/) で個別に挙げています。

### 重複

| コード | 意味 |
|---|---|
| `E_DUPLICATE_SIZE` | ヘッダに `size=` が 2 つ以上ある。 |
| `E_DUPLICATE_SLOT` | `theme` の本体が同じスロットを 2 回宣言している。 |
| `E_DUPLICATE_ARG` | 1 つの引数リストで `key=` が繰り返されている。 |
| `E_DUPLICATE_ID` | 同じ本体スコープ内の 2 つのメンバーが同じ `id=` を持っている。 |
| `E_DUPLICATE_SELECTOR` | 1 つの `theme` 内の 2 つのセレクタ行が、同じメンバーを選び、同じキーに値を割り当てている。 |
| `E_DUPLICATE_ITEM` | 同じ種類のトップレベル項目 2 つが同じ名前を持っている。 |
| `E_DUPLICATE_HEADER` | 単一値の `@directive` が 2 回以上宣言されている。 |
| `E_DUPLICATE_CIRCUIT` | `struct` または `def` の本体に `circuit` 行が 2 つ以上ある。 |

1 つの `site` の本体にある 2 つの `place` 行については、`E_DUPLICATE_ID` ではなく、site を名指す `E_DUPLICATE_PLACE_ID` ([site と配置](#site-と配置)) が報告します。`E_INVALID_PLACE_ID` で拒否された id でも同じです。同じ id を持つ 2 行目には、自身の `E_INVALID_PLACE_ID` に加えて `E_DUPLICATE_PLACE_ID` が付きます。両方の行を 1 つの使える id に改名しても、新しい指摘が出ることはありません。`place` 行がその本体のほかの行 (`connect` など) と `id=` を共有する場合は、`E_DUPLICATE_ID` のままです。1 つの行の下にインデントされた 2 つの `place` 行も、その本体の行ではないので `E_DUPLICATE_ID` です。

`E_DUPLICATE_SELECTOR` は、セレクタを字面ではなく意味で比べます。属性の順番は問わず、`class=` / `id=` / `mat_slot=` はラベルの文字列として比べるので、`small` と `"small"` は同じ値です。*別々の* キーに値を割り当てる行は合成されるので、報告しません。属性が部分的に重なるだけの行も同じです ([マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット))。セレクタによる割り当てが予約中であってもエラーにする理由は、[§11.3](#113-エラーと警告の区分) で説明します。

`E_DUPLICATE_ITEM` は `theme` / `def` / `struct` / `site` を 4 つの別々の名前空間として扱うので、同じ名前を種類ごとに 1 回ずつ使えます。最初の 3 種類では最初の宣言が有効になり、残りはどこからも参照されません。同名の `site` ブロック 2 つは、代わりに `site::NAME::PLACE_ID` の名前空間を共有して統合されます。`id=` の異なる place はすべてビルドされ、衝突するのは `id=` が重複したときだけです。ただし `east_of=` はブロックをまたいで参照できません。

`E_DUPLICATE_HEADER` の対象は `@cairn` と `@intended_targets` です。`@requires` は対象外です。下限はすべての行のうち最も厳しいものに畳み込まれるので、2 つ目の行は制約を追加することになるからです ([§5.3](/ja/spec/syntax/#53-ヘッダ))。

### 構文と構造

| コード | 意味 |
|---|---|
| `E_PARSE` | ソースをパースできない。 |
| `E_UNKNOWN_KEYWORD` | 文のキーワードが既知のキーワード表にない。 |
| `E_UNKNOWN_ARGUMENT` | メンバーのキーワードの語彙にない `key=`。引数として書かれたものと、メンバー自身の `[key=value]` の中に書かれたものの両方が対象。`struct` / `def` のヘッダが受け付ける `size=` / `class=` 以外の `key=` も対象。 |
| `W_IGNORED_ARGUMENT` | キーワード (または `struct` / `def` のヘッダ) の語彙にはあるが、書かれた行ではどのパスにも読まれなかった `key=`。`theme` のセレクタ行が割り当てる `key=` も、まだどのパスも読まないので対象。 |
| `E_MISPLACED_BINDING` | 信号を発せないキーワードのメンバーに、末尾の `-> value` が付いている ([§14.2](/ja/spec/redstone/#142-信号バインディング))。 |
| `E_MISPLACED_MEMBER` | キーワードは既知だが、囲んでいる本体にそれを読むものがない。`level` の下にある `circuit` 行も対象。 |
| `E_UNEXPECTED_POSITIONAL` | 位置引数を読まない行に、裸の値がある ([§5.1](/ja/spec/syntax/#51-字句))。 |
| `E_UNSUPPORTED_NESTING` | 誰も読まない、インデントされた本体をメンバーが持っている。 |
| `E_TYPE_MISMATCH_LABEL` | ラベル型のキーの値が、識別子でも文字列でもない。 |
| `E_TYPE_MISMATCH_SIZE` | `size=` の値が `WxH` リテラルではない。 |
| `E_CONNECT_ARITY` | `connect` 行が `FROM.PORT to TO.PORT` の形になっていない。 |
| `E_INVALID_REQUIRES` | `requires` の式がバージョンの下限になっていない。`@requires` ヘッダと、`def` / `theme` の本体の行の両方が対象 ([§5.3](/ja/spec/syntax/#53-ヘッダ))。 |
| `W_INVALID_CAIRN_VERSION` | `@cairn` の値が `YYYY.M[.PATCH]` 形式の言語バージョンになっていない ([§5.3](/ja/spec/syntax/#53-ヘッダ))。 |
| `W_FUTURE_CAIRN_VERSION` | `@cairn` の値が、読んでいるコンパイラより新しい言語バージョンを指している。 |

`E_MISPLACED_MEMBER` は、`struct` / `def` の中の `place` / `connect` や、`site` の行に混ざったジオメトリのキーワードで発生します。問題の行で 1 回だけ報告し、その下にインデントされたものも一緒に落とします。

`level` の直下、またはその中に入れ子になった `level` の下にある `circuit` 行でも発生します。確保はスコープ全体に及ぶので、配置配線 (place-and-route) が `circuit` 行を読むのは `struct` / `def` 自身のメンバーの中だけです ([§14.5](/ja/spec/redstone/#145-配置配線-place-and-route))。`level` の下の行は何も確保しません。`E_DUPLICATE_CIRCUIT` が数えるのは本体自身のメンバーだけなので、その行を重ねて報告することはありません。別の `level` の中の `level` のように何もまとめない `level` は、`E_UNSUPPORTED_NESTING` にもなります。こちらはメンバーが失うブロックについての指摘で、`circuit` 行はブロックを書かないからです。

`E_UNSUPPORTED_NESTING`: メンバーをまとめられるのは、`struct` / `def` の中の `level y=N` だけです。`site` の本体は平坦なリストです。落としたサブツリーごとに、その根で 1 回報告します。

`E_TYPE_MISMATCH_LABEL`: ラベル型のキーは `id=` / `class=` / `mat_slot=` / `use=` / `theme=` です。`use=` と `theme=` では、型の合わない値は、リゾルバから見るとキーがないのと区別がつきません。このコードは「キーは行にあるが使えない」を、`E_INCOMPLETE_PLACE` は「キーがない」を表します。

`E_CONNECT_ARITY`: 位置引数を読むのは `connect FROM.PORT to TO.PORT` の形だけです。片側の欠落、`to` キーワードの欠落や別のトークンへの置き換え、末尾の余分な位置引数、ドット 1 つの `PLACE.PORT` 参照になっていない端点が対象です。2 つの端点はそれぞれ別に直す箇所なので、別々に報告します。

`E_INVALID_REQUIRES`: 受け付ける形は、省略可能なエディション、`version`、`>=`、バージョンラベルの並びで、空白は任意です。`version` の前にあるエディションでない語、`>=` 以外の演算子、バージョンの欠落、数字で始まらないか `u32` に収まらない成分、`-` の後に読めるプレリリースタグがないもの、バージョンの後に続くテキストが対象です。形は正しいがターゲットのエディションに `DataVersion` がないラベルは、対象 *外* です。それは構文の問題ではなく、`E_REQUIRES_UNORDERABLE` です。下限の 2 つの書き方、つまり `@requires` ヘッダと、`def` / `theme` の本体に書ける `requires` 行 ([§10.4](/ja/spec/versioning-editions/#構成要素は自分の下限を宣言できる)) は、同じ規則で検査します。どのビルドもインスタンス化しない構成要素も検査します。誤りは行そのものにあり、それを読むものがあるかどうかとは関係ないからです。

`W_INVALID_CAIRN_VERSION`: 受け付ける形は `YYYY.M` または `YYYY.M.PATCH` です。4 桁の年、`1 … 12` の月、省略可能なパッチからなり、どの成分も 10 進数字だけです。月の先頭のゼロは受け付け、値も変わりません。`2026.06` と `2026.6` は同じバージョンで、前者は calver.org の `YYYY.0M`、後者は Cargo の `version` フィールドに書ける `YYYY.M` です。成分が 2 つでも 3 つでもない値、空または数字でない成分、4 桁でない年、暦にない月、`u32` を超えるパッチ、バージョンの後に続く 2 つ目の語が対象です。ヘッダの値は行全体なので、`@cairn 2026.6 draft` はバージョンの後に別の何かを書いていることになります。

これは `@requires` より意図的に厳しくしています。`@requires` は Mojang の名前空間にある Minecraft のラベルを読み、順序が付けばよいだけなので、成分は数字で *始まれば* よく、プレリリースタグもラベルの一部です。`@cairn` は Cairn 自身のバージョンを指すので、成分はすべて数字です。`2026.13` は存在しない月で、`1.2` は年ではなく semver です。

`W_FUTURE_CAIRN_VERSION` は、自分より新しい言語で書かれたファイルについて、コンパイラが言える唯一の有益な情報です。このビルドより後に追加されたキーワードや引数は `E_UNKNOWN_KEYWORD` / `E_UNKNOWN_ARGUMENT` として報告されます。それらの指摘が、その行の誤りではなくバージョンの差によるものかもしれないと知っているのは、ヘッダだけです。この警告が役立つのは、新しい言語が既存の形の *中に* 追加したものに対してです。ディレクティブやトップレベル項目のようなまったく新しい構文は `E_PARSE` になります。パースはすべての検査パスより先に行われるので ([§11.3](#113-エラーと警告の区分))、バージョンの差が最もよい説明になる場面でも、この指摘は出せません。

その場面では、ヘッダをテキストとして読みます。先頭の `@cairn` で見つけ、行末まで読む 1 行です。そして `E_PARSE` に、このファイルは読んでいるビルドより新しい言語を宣言している、という注記を付けます。2 つ目の指摘ではなく注記にするのは、パースできないソースが報告する指摘は `E_PARSE` 1 つだけ、という決まりを保つためです。注記を付けるのは、値がバージョンとして読めるときだけです。読めない値は `W_INVALID_CAIRN_VERSION` の担当で、無関係なパース失敗の上にそれを重ねても雑音になるだけです。

1 つのディレクティブに両方のコードが付くことはありません。バージョンとして読めない値には、比べるバージョンがないからです。

### マテリアルとターゲット

| コード | 意味 |
|---|---|
| `E_UNKNOWN_ID` | 解決したブロック ID を、固定したターゲットが宣言していない。 |
| `E_VERSION_CAP` | `--target` が、ソースの宣言する `@requires` の下限を下回っている ([バージョンとエディション §10.4](/ja/spec/versioning-editions/))。 |
| `E_REQUIRES_UNORDERABLE` | `@requires` の下限が、ターゲットのエディションの `DataVersion` 表で位置づけられないバージョンを指している ([バージョンとエディション §10.4](/ja/spec/versioning-editions/))。 |
| `E_INTENDED_TARGET_CAP` | `@intended_targets` が挙げるバージョンが、どれも同じファイルの宣言する下限を下回っている。 |
| `W_INTENDED_TARGET_CAP` | そのうちの一部だけが下回っている。 |
| `W_INTENDED_TARGET_UNSUPPORTED` | `@intended_targets` が、そのエディションのどの `--target` でもビルドできないバージョンを挙げている。 |
| `E_INCOMPATIBLE_MATERIAL` | ブロックステートを付けるジオメトリを持つメンバーが、そのステートを持てないマテリアルに割り当てられている。 |
| `E_MISSING_MATERIAL` | ブロックを得る手段が `mat_slot=` しかないメンバーが、`mat_slot=` なしで書かれている。 |
| `E_UNRESOLVED_SLOT` | `mat_slot=` を読む役割のメンバーが、割り当てられたテーマの宣言していないスロットを指している。 |
| `E_UNKNOWN_SLOT_TARGET` | `slot NAME -> VALUE` の値が、正規トークンでも抽象マテリアルトークンでもない ([マテリアルとテーマ](/ja/spec/materials-themes/))。 |
| `E_THEME_SELECTOR_UNMATCHED` | `theme` のセレクタ行が、そのテーマを割り当てたスコープのどのメンバーにもマッチしない。どのスコープにも割り当てられていないテーマは検査しない。 |
| `E_THEME_VARIANT_MISSING` | 固定したエディションに対して、テーマのエディション別バリアントを 1 つも割り当てられない。 |
| `E_INCOMPLETE_PLACE` | `place` 行に `id=` / `use=` / `theme=` のいずれかがない ([§9.3](/ja/spec/components-editing-sites/#93-site-による複数建築))。 |
| `E_UNKNOWN_ABSTRACT_TOKEN` | `mat_slot=` が、渡されたパックのカタログに宣言されていない抽象マテリアルトークンに解決される ([マテリアルとテーマ](/ja/spec/materials-themes/))。 |
| `W_ABSTRACT_TOKEN_DEFERRED` | 同じく抽象マテリアルトークンだが、カタログがまったく渡されておらず、照合できない。 |
| `W_STATE_LITERAL_UNCHECKED` | 正規トークンのステートリテラル (`@oak_log[axis=x]`) を書かれたまま使った。`E_STATE_DOMAIN` が実装されるまで、そのプロパティと値をターゲットと照らし合わせる仕組みがない ([バージョンとエディション](/ja/spec/versioning-editions/))。 |
| `W_NO_THEME_BOUND` | `mat_slot=` を読むスコープにテーマが割り当てられていないので、そこで読む `mat_slot=` はどれもブロックに解決されない。 |
| `W_THEME_VARIANT_REBOUND` | `place theme=` があるエディションのバリアントを名指したが、固定したエディションでは別のバリアントを割り当てた ([バージョンとエディション](/ja/spec/versioning-editions/))。 |
| `W_INTENT_DEGRADED` | パレットのエントリが、固定したエディションでは表せない意図を失った。Bedrock での階段の `shape` がその例で、エントリごとに 1 行出る ([バージョンとエディション §10.7](/ja/spec/versioning-editions/#107-java--bedrock-の可搬性))。 |
| `W_PREVIOUSLY_VERIFIED_TARGET` | 置き換えるロックが、別の `(edition, version)` を検証していた。行には両方が示される ([バージョンとエディション §10.6](/ja/spec/versioning-editions/#106-来歴-provenance-とロック))。 |
| `W_SEMANTIC_SENSITIVITY` | `W_PREVIOUSLY_VERIFIED_TARGET` に続けて、前のロックの `member_version_sensitivity` が挙げるメンバーを、新しいターゲットでは解決が変わりうるものとして示す ([§10.6](/ja/spec/versioning-editions/#106-来歴-provenance-とロック))。制約カタログをまだ同梱していないので、コンパイラが書くロックはメンバーを 1 つも挙げておらず、そうしたロックの上でビルドしても、現時点ではこの警告は出ない。 |

最後の 3 つは `cairn compile` だけが出します。書き出す成果物とロックについての警告なので、スパンを持たず、ほかのコマンドは出しません。

`E_UNKNOWN_ID` と `E_INCOMPATIBLE_MATERIAL` は、block-array lowering の段階で発生します。この lowering は `cairn compile`、`cairn lower`、`cairn info`、`cairn check` のどれでも行われ、言語サーバーでも行われます。ただし `E_UNKNOWN_ID` には固定したターゲットが必要なので、実際に出せるのは `cairn compile --target` と `cairn check --edition E --target V` の 2 つです (`info` と `lower` はバージョンを固定せずに lowering します。ファイルの下限がターゲットを拒否する `compile` も同じです。[バージョンとエディション](/ja/spec/versioning-editions/#宣言した下限は強制される) を参照)。`--target` なしの `cairn check` と言語サーバーはターゲットをまったく持たずに lowering するので、`E_INCOMPATIBLE_MATERIAL` はいずれかの出荷済みバージョンが宣言する正規トークンについてだけ出し、`E_UNKNOWN_ID` は出しません ([§11.3](#113-エラーと警告の区分))。

`W_STATE_LITERAL_UNCHECKED` も同じ lowering で発生します。テーマのスロットや `connect … path=` から読むステートリテラルのそれぞれに付くので、`cairn compile`、`cairn lower`、`cairn info`、`--target` の有無を問わず `cairn check`、そして言語サーバーが、どちらのエディションでも報告します。これは `E_STATE_DOMAIN` の代わりの警告です。コンパイラが各ブロックのステートの表を持つまでは、ブロックにないプロパティやドメイン外の値がそのまま構造ファイルに書き出されます。それを黙って通さないためにこの警告があります。

`cairn check --target` は、CI ジョブが check コマンドを通過条件にしたまま、compile なら拒否する lowering 段階の指摘も見られるようにするためのものです。このフラグがないと、ターゲットが宣言していない ID は `check` を終了コード 0 で通過し、`cairn compile` では終了コード 1 で止まります。それを決める情報、つまり 1 つの `(edition, version)` の組が、`check` のコマンドラインにないからです。このフラグには `--edition` が必要です。[コンパイルモデル §4.2](/ja/spec/compilation/#42-ターゲット軸) が `--target` だけの指定を拒否するのと同じ理由です。ファイルの下限が通すターゲットでは、compile と同じ表に対して同じ lowering パスを走らせるので、スコープを失えば同じ `E_PARTIAL_BUILD` を出します。行わないのは、`compile` が書き出すものすべてです。成果物もロックファイルも作らず、`@requires` の下限の強制も行いません。ロックはビルドを保証する記録なので、`--target` を下限と照らし合わせるのは、ロックを生成するコマンドだけの仕事です (`E_VERSION_CAP`)。下限が拒否するターゲットでは、2 つのコマンドが示す原因が異なることになります。`check` はターゲットを固定して、そのターゲットにない ID を報告し、それでスコープが空になれば `E_PARTIAL_BUILD` も出します。`compile` は ID を照合せず、下限を報告します ([バージョンとエディション](/ja/spec/versioning-editions/#宣言した下限は強制される))。フラグを付けない場合も lowering はしますが、ターゲットは持たず、その行を読むどのターゲットでも出る指摘だけを報告します ([§11.3](#113-エラーと警告の区分))。[バージョンとエディション §10.4](/ja/spec/versioning-editions/#104-fail-loud-と最小バージョン推定) も参照してください。

`E_INCOMPATIBLE_MATERIAL` は、現時点では、階段のファミリ以外に割り当てられた傾斜屋根や軒の `stair` を指します ([コンパイルモデル §4.3](/ja/spec/compilation/#43-切妻屋根のボクセル規則))。

`E_THEME_VARIANT_MISSING` は `--edition` を指定したときだけ発生し、いくつのスコープがそのテーマを読んでいても **論理テーマごとに 1 回** だけ報告します。直す場所は、同じ `theme` ブロックの同じ 1 か所だからです。そのテーマを名指す配置は、その `def` が何を読むかに関係なく、すべて拒否されます。`place` の `theme=` はテーマを割り当て、ロックファイルはその配置に割り当てたテーマを記録し、テーマの下限は割り当てた時点で適用されるからです ([バージョンとエディション](/ja/spec/versioning-editions/#構成要素は自分の下限を宣言できる))。そのテーマをどの `place` も名指さず、`struct` と `def` のメンバーがそこから `mat_slot=` を 1 つも読まないモジュールは報告しません。エディションを固定してもしなくても、ビルド結果が 1 バイトも変わらないからです。`door` に書いたものなど、`mat_slot=` を読まないキーワードに書かれた `mat_slot=` は、ここでいう読み取りに数えません ([§11.3](#113-エラーと警告の区分))。

`E_THEME_SELECTOR_UNMATCHED` は、接頭辞に反して警告です。何にもマッチしないルールは何も上書きしないので、どのメンバーも、ルールを消した場合と同じマテリアルのままです。この指摘が扱うのは、何が作られたかではなく、書き手の意図です。接頭辞はコード文字列の一部で、コード文字列は Stable なので ([互換性ティア](/ja/spec/compatibility/))、書かれたまま変えません。重大度は先頭の 1 文字ではなく、`severity` フィールドから読んでください。

`E_UNKNOWN_SLOT_TARGET` は、逆の理由でエラーです。マテリアルトークン以外に割り当てられたスロットを指す `mat_slot=` は、どれも解決されません。それを名指す `floor` はセルを空気のまま残します。それを名指す `walls` は建たず、段も占めないので、そこを切り抜く `door` や `window` は拒否されます。それを名指す `window` は切り抜かれないので、壁が残ります。それを名指す `roof`、軒の `stair`、`pressure_plate` は既定のブロックで作られます。もしこれが警告なら、スロットがすべて打ち間違っているテーマでも、`roof` のように何かが描かれるスコープは終了コード 0 で建ってしまいます。要求より低く、床も壁もなく、既定のブロックだけでできた構造物です。低くなった構造物に収まらない高さの軒の `stair` や `pressure_plate` は、それすら作られません。

`E_MISSING_MATERIAL` と `E_UNRESOLVED_SLOT` は 1 つの切り分けの両側で、両方が付くメンバーはありません。前者はキーがない場合、後者はキーがあるが使えない場合です。直し方が違うのでコードも分けています。`place` 行における `E_INCOMPLETE_PLACE` と `E_TYPE_MISMATCH_LABEL` と同じ分け方です。この切り分けは、`mat_slot=` を読むキーワードだけに当てはまります。読まないキーワードには、どちらも当てはまりません。キーを読むものがないので、キーがなくても報告せず、名前もテーマで引かれないので、そこに書いたラベルはどのスロットを指していても `W_IGNORED_ARGUMENT` になります ([§11.3](#113-エラーと警告の区分))。

`E_MISSING_MATERIAL` の対象は、マテリアルがないと何も置かない役割のメンバーです。`floor` と `walls` は適用されたテーマのスロット表を通じてパレットに到達し、既定のブロックを持たないので、`mat_slot=` がなければボクセルを 1 つも作りません。`mat_slot=` のない `window` は **開口** で、空気で彫られるので報告しません。樹種を選ばずに壁へ細い狭間を開けるための書き方です。`door` は開口を彫るだけで、自分のブロックはまだ置かないので、マテリアルを読みません。`roof` / `stair` / `pressure_plate` は既定のブロックで塗るので、これも報告しません。この指摘は `cairn check` が lowering の前に出し、テーマも必要としません。テーマを 1 つも宣言しないモジュールでも、どのメンバーがマテリアルを指定していないかがわかります。

`E_UNRESOLVED_SLOT` は **メンバーごと、割り当てられたテーマごとに多くて 1 回** 報告します。`def` の本体は、それ自身のスコープとして 1 回、さらにそれをインスタンス化する `place` ごとに 1 回解決され、そのどれもがテーマを割り当てます。あるメンバーについて報告済みのテーマに対する繰り返しは捨てます。2 つの配置が別々のテーマを名指した場合は、指摘が 2 つになります。それぞれが自分の対象テーマを示し、直す場所も別々だからです。残った指摘がどの解決から出たものかは規定しません。同じテーマを割り当てた 2 つの解決が、同じスロットについて別の判断に至ることがあるからです。

その差は、エディション別バリアントによる緩和から生じます。`--edition` で固定していない場合、選ばれたテーマの兄弟バリアントのいずれかが宣言しているスロットは既知として扱い、報告しません。具体的な割り当てはエディションによって変わり、固定によってテーマが 1 つのバリアントに絞られて初めてスコープに入るからです ([バージョンとエディション §10.7](/ja/spec/versioning-editions/#107-java--bedrock-の可搬性))。バリアント名を書くと、そのバリアントのスロットについて問うことになるので、`place ... theme=NAME` が同じように緩和されるのは、`NAME` が論理テーマ名のときだけです。同じテーマを割り当てる 2 つの配置でも、1 つのスロットについて判断が分かれることがあります。

どこからも配置されない `def` も、モジュールが選んだテーマに対して解決するので、def だけで `site` のないファイルも、モジュールが選べる論理テーマが 1 つであるかぎり検査されます。テーマが 2 つ以上ある場合や 1 つもない場合は、def 自身のスコープにテーマが割り当てられないので、その `mat_slot=` は `place` がテーマを選ぶまで判定されません。

`E_INCOMPLETE_PLACE` は欠けているキーをすべて挙げ、その行をビルドから落とします。

`E_UNKNOWN_ABSTRACT_TOKEN` と `W_ABSTRACT_TOKEN_DEFERRED` は、答えられる相手がいたかどうかで分かれます。パックが渡されていて、そのトークンを宣言していなければ、最も近い既知のトークンを示してビルドを止めます。パックが渡されていなければ、そもそも照合していないので、警告を出したうえでメンバーを欠けた形で作ります。後者に到達するのは、パックを一切渡さずに lowering するライブラリの呼び出し側だけです。ここで拒否すると、パックなしで読んだソースをすべて拒否することになるので、警告にしています。ターゲットを持たないフロントエンド、つまり言語サーバーと `--target` なしの `cairn check` は、どちらのコードも出しません。トークンの判定は、それをビルドするターゲットのパックに任せます ([§11.3](#113-エラーと警告の区分))。

メンバーがどう作られるかは警告に示されます。`floor` はセルを空気のまま残し、`roof`、軒の `stair`、`pressure_plate` は既定のブロックで作られます。`walls` は建たず、段も占めないので、そこを切り抜く `door` や `window` は拒否されます。`window` は切り抜かれないので壁が残り、そのポートも一緒に拒否されます ([§9.3.5](/ja/spec/components-editing-sites/#935-ポートと-connect))。

`W_NO_THEME_BOUND` は、1 段上で起きる同じ形の問題です。どのテーマにも解決されない `mat_slot=` には読むスロット表がないので、メンバーは同じように欠けた形で作られます。テーマがなければ `walls` は 1 つも建たず、段も占めないので、`door` も `window` も切り抜かれず、構造物は要求より低くなります。`floor` はセルを空気のまま残し、`roof` はそれでも既定のブロックで作られます。軒の `stair` と `pressure_plate` も、低くなった構造物に収まれば既定のブロックで作られ、それより高い位置のものは見送られます。判定はスコープごとに行います。テーマが割り当てられておらず、`mat_slot=` も読まないスコープは、モジュールのほかの部分が何を読んでいても報告しません。`door` に書いたものなど、`mat_slot=` を読まないキーワードに書かれた `mat_slot=` は、読んだことになりません。この警告では、`level` が落としたメンバー ([コンパイルモデル §4.7](/ja/spec/compilation/#47-level-によるまとまりと体積の導出)) の `mat_slot=` も読んだことになりません。そのメンバーは、テーマが何であれ何も塗らないからです。`y=0` より上の `floor` や `roof`、本体が `E_UNSUPPORTED_NESTING` になる `level` のメンバーがこれにあたります。

`@intended_targets` の 3 つのコードは、ファイルが表明した意図を、そのファイル自身の下限と照らし合わせます ([バージョンとエディション §10.4](/ja/spec/versioning-editions/#ヒントは下限と突き合わせる))。そのエディションでビルドできないバージョンは `W_INTENDED_TARGET_UNSUPPORTED` で、下限とは照らし合わせません。作者がまず対処すべきなのは「そのターゲットはここには存在しない」という事実で、その隣に cap を並べると、ビルドを止めているわけではない行を直させることになるからです。残り、つまりそのエディションで *ビルドできる* バージョンだけを数えます。そのすべてが下限を下回れば `E_INTENDED_TARGET_CAP` です。ファイルは自分が対象だと言っているどのバージョン向けにもビルドできず、そのいずれかを `cairn compile --target` に渡した時点で `E_VERSION_CAP` になります。*一部* だけなら `W_INTENDED_TARGET_CAP` です。このヘッダはヒントで ([§5.3](/ja/spec/syntax/#53-ヘッダ))、下限より上のバージョンは問題なくビルドできるからです。そもそもビルドできないバージョンは、どちらの数にも入れません。リストのどの部分の答えにもならず、数に入れると、何もビルドできないファイルを「半分だけの問題」として報告することになるからです。1 つのヘッダに cap のコードと unsupported のコードが同時に付くこともあります。挙げたバージョンが、同じ理由で誤っているとは限らないからです。

3 つともエディションごとの答えです。下限とターゲットのラベルは、あるエディションの `DataVersion` 表の中で順序付けるからです。`cairn check` を通過条件にするすべてのコマンド (`check`、`info`、`lower`、`compile`、`synth`) が 2 つの cap コードを報告し、それぞれ自分が対象とするエディションの表でヘッダを照らします。`--edition` が指定した 1 つ、`cairn info --editions` が挙げたもの、どちらの指定もなければ両方です。どちらかのエディションで出た指摘は報告します。矛盾は、後でどうビルドするかに関係なく、ファイルの 2 行の間にあるからです。1 つのスパンが持つ cap の指摘は 1 つだけで、及ぶ範囲について 2 つのエディションの判断が食い違えば、エラーのほうを報告します。`W_INTENDED_TARGET_UNSUPPORTED` は、対象のエディションがちょうど 1 つのときにだけ報告します。Java でビルドできないバージョンが、作者の意図する Bedrock のターゲットであることはよくあるので、両方が対象のうちは、まだその問いを立てられないからです。

### site と配置

| コード | 意味 |
|---|---|
| `E_INVALID_PLACE_ID` | `place id=` が空である。`.` / `:` / `/` / `\` / `*` / `\|` / `?` / `<` / `>` / `"` / 空白 / 制御文字を含む。または、大文字小文字を問わず Windows が予約しているデバイス名 (`CON`、`NUL`、`COM1` など) である。 |
| `E_INVALID_STRUCT_NAME` | `struct` の名前が、大文字小文字を問わず Windows が予約しているデバイス名 (`CON`、`NUL`、`COM1` など) である。 |
| `E_DUPLICATE_PLACE_ID` | 同じ site の 2 つの `place` 行が同じ `id=` を持っている。 |
| `E_OUTPUT_NAME_COLLISION` | ビルドが書き出すはずの 2 つの成果物が、大文字小文字を無視すると同じファイル名になる。同じ名前の `struct` と `place`、2 つの site に置かれた同じ `id=`、平坦化すると同じ名前になる 2 本の通路などで起きる。 |
| `E_INVALID_PLACE_ORIGIN` | `place` に原点セレクタがない、または 2 つ以上ある。`origin` 以外の `at=` を持っている。または `east_of=` / `north_of=` の値がラベルではない ([§9.3](/ja/spec/components-editing-sites/#93-site-による複数建築))。 |
| `E_UNRESOLVED_PLACE_REF` | `place use=`、`east_of=` / `north_of=`、`connect` の端点が、存在しない place や def を指している。 |
| `E_UNRESOLVED_THEME_REF` | `place theme=` が、モジュールの宣言していないテーマを指している。 |
| `W_DEFERRED_PLACE` | `east_of=` / `north_of=` が id を理由に拒否された `place` を指しているので、指している側の行も配置されない。 |
| `W_UNUSED_DEF` | どの `place use=` からも参照されていない `def`。 |

`E_INVALID_PLACE_ID` は好みの問題ではなく、読み戻せるかどうかの問題です。スコープキー `site::SITE::PLACE` と、そこから読み戻すすべての通路のキーは、`.` と `:` を区切りにして組み立てるので、これらを含む id は読み戻せません。id は出力ディレクトリに書くファイルの名前でもあり、`/` や `\` はその名前をパスに変えてしまいます。区切りを含む相対的な id はサブディレクトリに書き込まれ、絶対パスの id は出力ディレクトリそのものを置き換えます。`*` / `|` / `?` / `<` / `>` / `"` と U+0000 から U+001F の制御文字は Windows のファイル名に使えないので、これらを含む id は Linux ではビルドできても Windows では書き出せません。Microsoft の命名規則は、後ろにどんな拡張子が付いても、一連のデバイス名も予約しています。`CON`、`PRN`、`AUX`、`NUL`、`COM0` から `COM9`、`LPT0` から `LPT9`、そして上付き数字を数字とみなす `COM¹`、`COM²`、`COM³`、`LPT¹`、`LPT²`、`LPT³` で、いずれも大文字小文字を問いません。この規則を適用する Windows のリリースは、`CON.nbt` をファイルではなくコンソールとして開きます。どちらもすべてのプラットフォームで拒否するので、id が受け付けられるかどうかは検査するホストに左右されません。残りの制御文字 U+007F から U+009F は Windows のファイル名に使えますが、別の理由で拒否します。何も表示されないか端末のカーソルを動かしてしまうので、id を引用する指摘がその文字を表示できないからです。`id=` は文字列リテラルを受け付けるので、この検査がなければ、これらの値はそのまま通ってしまいます。

`struct` は自分の名前で書き出されるので ([§9.3.4](/ja/spec/components-editing-sites/#934-出力ファイル名))、デバイス名を名前に持つ `struct` も同じ理由で、大文字小文字を問わず `E_INVALID_STRUCT_NAME` です。struct の名前は裸の識別子なので、上の文字はどれも入りません。site の名前とポートの id は、デバイス名であっても拒否しません。どちらも `hamlet_walkway_home1_entry__home2_entry` のような通路のファイル名の一部にしかならず、Windows がファイルをデバイスとして扱うのは、名前の拡張子より前の部分がデバイス名そのものである場合だけだからです。

`E_INVALID_PLACE_ID` で拒否された行の id を、後続の `east_of=` / `north_of=` が指していても、その行を指していることに変わりはないので、打ち間違いを探させる `E_UNRESOLVED_PLACE_REF` ではなく、`W_DEFERRED_PLACE` になります。指している側の行も、基準となる行に位置がないので配置されず、注記は直すべき拒否された行を指します。その行の id を改名するときは、この参照も一緒に改名します。警告にしているのは `W_DEFERRED_CONNECT` と同じ理由です。ビルドは拒否された行の時点ですでに失敗しており、2 つ目のエラーを出すと、書き手を意図どおりの行を指している側の行へ向かわせてしまいます。拒否された行を指す `connect` の端点は `W_DEFERRED_CONNECT` になり、注記も同じくその行を指します。拒否された行より前にある参照は、ほかの id と同じく先行する place を指していないので、`E_UNRESOLVED_PLACE_REF` です。

`E_DUPLICATE_PLACE_ID` は両方のスパンを示します。id を参照するものはすべて最初の行を採り、重複したほうは落とすので、「もう一方」に解決された参照が 2 つ目の指摘になることはありません。

`W_UNUSED_DEF` は、`site` の本体にある `place` 行のうち、`use=` がその def を指すものをすべて数えます。id や原点セレクタで拒否された行も含みます。その行は def を参照しており、直すべき指摘はその行のほうにあるからです。警告に従って def を消しても、行を直したときに `E_UNRESOLVED_PLACE_REF` として戻ってくるだけです。識別子でも文字列でもない `use=` (`use=3`) は def を指さないので、数えません。

`E_OUTPUT_NAME_COLLISION` は、成果物の名前の付け方から生じます ([§9.3.4](/ja/spec/components-editing-sites/#934-出力ファイル名))。`struct` はその名前で、`place` は `id=` だけで、通路は site とポートで名前が付きます。どれも同じ出力ディレクトリに書き出すので、2 つが 1 つのファイルを指すことがあり、両方をビルドすると片方しか残せません。この検査は lowering の前に行います。サイズのない `struct` と、サイズのない `def` を使う `place` は lowering で落とされるので数えません。同じポートの組を結ぶ 2 行の `connect` は、向きによらず、lowering で敷かれるとおり 1 本の通路として数えます。`W_STRUCTURE_TOO_LARGE` で落とされる struct や配置と、探索範囲がルーターの上限を超えて `W_WALKWAY_BLOCKED` が報告し、敷かれない通路は数えるので、指摘は「2 つが同じファイルに書き出されるはず」と述べます。名前は大文字小文字を無視して比べます。macOS と Windows が既定で使う大文字小文字を区別しないファイルシステムでは、`Hut` と `hut` は 1 つのファイルで、ソースをビルドできるかどうかがビルドするホストに左右されるべきではないからです。この指摘はほかの site の指摘と同じく lowering の前に出るので、`cairn check` は `--target` なしでも報告します。同じ名前を 2 回宣言したものは、このコードではありません。2 つ目の `struct hut` は `E_DUPLICATE_ITEM`、同じ site での 2 つ目の `id=` は `E_DUPLICATE_PLACE_ID` です。

`E_UNRESOLVED_PLACE_REF` と `E_UNRESOLVED_THEME_REF` は、綴りの許容範囲に収まる候補があれば、最も近いものを示します ([did you mean](#did-you-mean))。どちらもエラーなのは、名前を何かで代用すると、ソースに書かれていない site を建てることになるからです。

### 接続と通路

| コード | 意味 |
|---|---|
| `E_UNRESOLVED_PORT` | `connect A.PORT to B.PORT` が、参照先の def の本体に直接宣言されたどのメンバーも持たないポート id を指している。`level` の下のメンバーはまだポートになれないので、id がそうしたメンバーのものであれば、診断にそのことが示される。 |
| `E_AMBIGUOUS_PORT` | そのポート id が、参照先の def の複数のメンバーにマッチする。 |
| `E_MISSING_PATH_MATERIAL` | `connect` 行に `path=` がない、または `path=` の値がマテリアルトークンではない (`path=@gravel` のつもりの `path=gravel` など) ので、通路を敷くマテリアルがない。 |
| `W_DUPLICATE_WALKWAY` | 同じ site の先行する行がすでに通路を敷いた 2 つのポートを、`connect` が向きを問わずもう一度つないでいる。 |
| `W_INVALID_WALKWAY_IDENT` | `connect` の site / place / port の識別子が `__` を含む。または place / port の識別子が `_` で始まるか終わる。 |
| `W_DEFERRED_CONNECT` | `connect` の対象の `place` 自体が拒否されており、つなぐものがない。 |
| `W_WALKWAY_BLOCKED` | フォールバック経路のセルが既存の構造物と重なったので、そのセルを落とした。または、直線の L 字だけでルーターの探索面積の上限 (4,000,000 セル) を超えたので、通路を敷かなかった。 |

`E_UNRESOLVED_PORT` が指すのは `place.port` のうちポートの側だけです。place の側は `E_UNRESOLVED_PLACE_REF` です。`E_AMBIGUOUS_PORT` の場合、lowering では最初にマッチしたものを採り、衝突を報告します。直し方は、書き手の代わりにどれかを選ぶことではなく、衝突しているメンバーのどちらかを改名することだからです。

`E_MISSING_PATH_MATERIAL` は、ほかの「マテリアルがない」系の指摘が警告なのに対して、エラーです。空気で敷かれた通路は、ソース上はつながって見える 2 棟を、ワールドではつながないまま残します。しかも、レポートにはそのことが何も現れません。

`W_INVALID_WALKWAY_IDENT` は、`E_INVALID_PLACE_ID` のうち `.` / `:` に関する読み戻しの規則を、別の区切りに当てはめたものです。`__` は通路のスコープキーで `from` と `to` をつなぐので、片側の `b__c` ともう片側の `c__home2` が同じ文字列に符号化されてしまいます。この区切りに接する `_` も、同じように区切りに溶け込みます。`a.p_ to b.p` と `a.p to _b.p` はどちらも `a.p___b.p` に符号化され、`_` という名前の port は、分け直すと port が空になるキーを残します。区切りに接するのは、`from` 側の port の末尾と、`to` 側の place の先頭だけです。ただし `connect` はどちら向きにも書けるので、どの place の先頭も、どの port の末尾も、区切りに接する可能性があります。残りの 4 つの端、つまり place の末尾と port の先頭は、どちら向きに書いても `.` の隣にあるので溶け込みません。それでも規則を「place と port の識別子は `_` で始まることも終わることもできない」という 1 文に保つため、これらも拒否します。site は両側を `::` で区切られるので、端の規則の対象外です。行は落とし、指摘は改名すべき部分を示します。その行が求めた通路は失われるので、何も敷かなかったほかの行と同じく、`cairn compile` は `E_PARTIAL_BUILD` でビルドを拒否します。

`W_DEFERRED_CONNECT` は、`place` を拒否したものに従って発生します。欠けた行、打ち間違えたキー、`E_INVALID_PLACE_ID` で拒否された id (注記はその行を指します)、失敗した原点セレクタ、id を理由に拒否された行を指す原点 (`W_DEFERRED_PLACE`。その注記がその行へ案内します)、解決できない `use=` や `theme=` です。警告にしているのは、直すべき指摘は `place` の側か、その注記が指す先にあるからです。`connect` を 2 つ目のエラーとして報告すると、書き手は正しく書けている行を直しに行くことになります。

### lowering

| コード | 意味 |
|---|---|
| `W_DEFERRED_MEMBER` | block-array パスが lowering しないメンバー。そのスコープは、そのメンバーなしで建つ。 |
| `E_UNPLACEABLE_PLATE` | `pressure_plate` を、自身の `at=`・`offset=`・`y=` では struct のどのボクセルにも置けない ([§14.2](/ja/spec/redstone/#142-信号バインディング))。 |
| `W_STRUCT_NO_SIZE` | `struct` が `size=WxH` を宣言していないので、lowering で範囲を導けず、飛ばした。 |
| `W_DEF_NO_SIZE` | `def` で同じことが起きた。その def を使う `place use=` はすべて飛ばされる。 |
| `W_STRUCTURE_TOO_LARGE` | スコープから導いた範囲が、block-array パスが確保する体積を超えている。 |
| `W_PALETTE_TOO_LARGE` | スコープが空気以外に 65,535 を超える種類のブロックステートを塗っており、1 つのパレットで添字を振れる数を超えている。 |
| `W_PHASE_CONFLICT` | 同じフェーズの 2 つのメンバーが、1 つのボクセルに異なるブロックを書いた ([§4.8](/ja/spec/compilation/#48-同一フェーズ内の衝突とパレット))。 |
| `E_PARTIAL_BUILD` | 要求されたスコープ、または `connect` 行が求めた通路のうち、少なくとも 1 つが lowering されず、求められたより少ないものしか作られなかった。 |

`W_STRUCT_NO_SIZE` と `W_DEF_NO_SIZE` は、1 つの規則を、それが当てはまる対象によって分けたものです。`code` で絞り込むフィルタが、建たない struct と、インスタンス化されないテンプレートを区別できます。

`W_STRUCTURE_TOO_LARGE` は、組み合わせによって発生します。`size=`、`walls height=`、`roof overhang=`、`level y=` はそれぞれ単独で範囲を検査しており、これはその組み合わせが上限を超えた場合です。上の 2 つと同じく、エラーではなく警告です。そのスコープが飛ばされるだけで、ビルドの残りには影響しません。

`W_PALETTE_TOO_LARGE` は、どこに塗るかではなく何を塗るかについての、同じ種類の上限です。後のメンバーが覆い隠すものも含め、メンバーが書いたすべてのブロックステートを数えるので、上限は完成したスコープに残るものではなく、書かれたものにかかります。バニラのレジストリのブロックステートはこれよりはるかに少ないので、ソースがこの上限に届くのは、固定したターゲットが照合しないブロック ID か、ステートリテラルのプロパティを通じてだけです。ブロック ID は、バージョンを固定せずに lowering するところでは照合しません。`cairn lower` と `cairn info`、言語サーバーと `--target` なしの `cairn check`、エディションが出荷していないバージョンを指定した `cairn compile` と `cairn check --edition E --target V`、そしてファイルの下限が拒否するターゲットを渡した `cairn compile` ([バージョンとエディション](/ja/spec/versioning-editions/#宣言した下限は強制される)) がそうです。ステートリテラルのプロパティは、`W_STATE_LITERAL_UNCHECKED` で説明したとおり ([マテリアルとターゲット](#マテリアルとターゲット)) どのターゲットでも照合しないので、lowering を行うどのコマンドでもこの上限に届く可能性があります。解決できるターゲットを渡した `cairn compile` も例外ではありません。上と同じ理由で警告です。

`W_DEFERRED_MEMBER` は、モジュールごと失敗させるのではなく、部分的なビルドを確認できる状態に保つための警告です。スコープの残りは lowering し、指摘は何が欠けているかを示します。

`E_UNPLACEABLE_PLATE` は、`E_MISSING_MATERIAL` と同じ理由でエラーです ([§11.3](#113-エラーと警告の区分))。プレートは代わりのものを置かれずに落とされ、欠けているのはコンパイラではなくその行自身です。影響は block-array の外にも及びます。プレートの `->` バインディングはそれでも読まれるので、信号はそれを駆動するプレートがないままネットリストに残ります。そのことは指摘の注記に示されます。プレートをどこにも置けなくなる行は、[レッドストーン §14.2](/ja/spec/redstone/#142-信号バインディング) に挙げています。別のメンバーが建っていれば struct に収まったはずのプレートは、代わりに同じ注記付きの `W_DEFERRED_MEMBER` になります。何も塗らない `walls` が、塗っていれば届いたはずの段や、`overhang=` 付きで書かれながら何も描かない `roof` の脇の `at=<side>.outside` がその例です。直すべきなのはそのメンバーのほうで、それが建たなかった理由はメンバー自身の指摘か、スコープの `W_NO_THEME_BOUND` が説明しており、プレートの行は正しいからです。行自体も誤っているプレートは、ほかに何が欠けていても `E_UNPLACEABLE_PLATE` になるので、欠けたメンバーがプレート自身の誤りを隠すことはありません。そうした `walls` を切り抜く `door` が見送られるのも同じ理由です。

`E_PARTIAL_BUILD` は、これを実行単位にしたものです。上の指摘が「スコープはそれなしで建つ」と言うのに対し、こちらは「コマンドが求めたスコープのうち建たなかったものがある」と言います。空気だけに lowering されたスコープも、何がそれを空にしたかによらず、建たなかったスコープです。すべてのメンバーが見送られたか拒否された場合も、どのテーマもその `mat_slot=` のメンバーにブロックを与えなかった場合も、メンバーを 1 つも宣言していない場合も同じです。実行ごとに 1 回、失われたスコープの数を示して報告します。出すのは `cairn compile` と、同じ lowering パスを走らせる `cairn check --edition E --target V` です。

`W_PHASE_CONFLICT` は、拒否ではなく「後勝ち」が起きたことを報告します。[コンパイルモデル](/ja/spec/compilation/) は、同じフェーズの中でのローカルな上書きについて後勝ちを認めています。これは書き手がメンバーを言い直した場合を想定したものです。2 つの敷地 (footprint) がたまたま交差した場合は想定していませんが、グリッドからは両者を区別できません。解決は仕様どおりに行われ、どのボクセルで起きたかは指摘に示されます。

### 真理値表

| コード | 意味 |
|---|---|
| `E_TRUTH_TABLE_EMPTY` | 行が 1 つもない、または出力が `0` か `1` の行が 1 つもない `assert truth(...)`。 |
| `E_TRUTH_TABLE_DUPLICATE_INPUT` | `assert truth(...)` が 1 つの信号を 2 つ以上の入力として並べている。 |
| `E_TRUTH_TABLE_CONFLICT` | 2 つの行が、同じ入力の組に異なる出力を割り当てている。 |
| `W_TRUTH_TABLE_DUPLICATE_ROW` | 2 つの行が同じ入力の組を受け持ち、矛盾はしていない。 |
| `W_TRUTH_TABLE_PARTIAL` | どの行も割り当てていない入力の組がある。 |

`E_TRUTH_TABLE_DUPLICATE_INPUT` は、重複した信号ごとに `assert` 全体で 1 回報告し、その表にはほかの真理値表のコードを出しません。ほかのコードはどれも誤った入力リストに照らして行を読むので、入力リストが各信号を 1 回ずつ並べるまで、表の残りの検査は後回しにします。

`E_TRUTH_TABLE_CONFLICT` と `W_TRUTH_TABLE_DUPLICATE_ROW` は、どちらも後ろの行で報告します。各行は、組を共有する先行のすべての行と比べるので、表が拒否されるかどうかは行を書く順番に左右されません。`00 -> 1; 01 -> 0` の後の `0- -> 1` は、前者とは一致していても `E_TRUTH_TABLE_CONFLICT` です。同じ行に両方が当てはまる場合は、重複より矛盾を優先します。その注記は、指摘が示す組にもう一方の出力を割り当てている最初の行に付けます。それ以外の指摘の注記は、指摘が示す組を割り当てている最初の行に付けるので、1 つの組についての指摘はすべて同じ行を指します。矛盾する 2 行のどちらを評価器が読むかは規定しません。直し方は、どちらの行が誤りかを決めることです。

`-` を使うと見た目の異なる行が同じ組を受け持つことがあるので (`0-` と `-1` は、どちらも `01` を割り当てます)、どちらのコードもパターンではなく組について述べます。直し方は形によって変わります。先行する行に含まれる行 (`0-` に対する `01`) は削除します。単に交差しているだけの 2 行は、範囲を狭めます。どちらを消しても、その行だけが割り当てている組が失われるからです。先行する行そのものが、さらに前の行と重なって報告されている場合は、代わりにそちらを先に片付けるよう求めます。`0- -> 1; -0 -> 1; 10 -> 1` では、`-0` に対して `0-` と重ならないよう狭めることを求めます。`-0` が `10` を受け持っているからといって `10` を消すと、`-0` を狭めたときに `10` がどの行にも割り当てられなくなるからです。

出力の `-` だけは、矛盾にも重複にもなりません。その行は、自分の受け持つ組を制約しないと述べているので、矛盾する相手の具体的な出力も、一致する相手もありません。この組み合わせは `W_TRUTH_TABLE_DUPLICATE_ROW` になり、その修正案が非対称性を明示します。2 行のどちらを消すかで、残る表の意味が変わるからです。行はあっても出力が `0` か `1` のものが 1 つもない表は何も制約しないので、これも `E_TRUTH_TABLE_EMPTY` に含めます。直し方は行を足すことではなく行を直すことなので、メッセージは行がない場合とは変えています。

2 つの警告が警告なのは、書かれている行はどれも本物の制約だからです。1 つの表に `W_TRUTH_TABLE_DUPLICATE_ROW` と `W_TRUTH_TABLE_PARTIAL` の両方が付くこともあります。繰り返した行も、先行する行に含まれる行も、表がまだ持っていない組を埋めないからです。ただし交差する 2 行だけは例外で、その場合は網羅性の指摘を出しません。後ろの行を除いて数えると、表が実際には割り当てている組を、未割り当てとして挙げてしまうからです。

### 意味カテゴリ

上のコードに加えて、lint は次の項目を検査します。

| カテゴリ | 検査内容 |
|---|---|
| **ジオメトリ** | AABB の展開。壁の外にある窓、宙に浮いたドア。 |
| **attachment** | 額縁、絵画、看板、ボタン、レバー、松明が、有効な面に取り付けられているか。 |
| **entity_aabb** | エンティティが壁や通路にめり込んでいないか、ドアの開閉範囲を塞いでいないか、過密でないか。 |
| **support** | 吊るしたランタン、松明、焚き火、砂利などの重力ブロックが支えられているか。 |
| **fluid** | 水源、流れ、`waterlogged` が整合しているか。 |
| **version_caps / parity** | ステートやエンティティのスキーマがターゲットで使えるか ([バージョンとエディション](/ja/spec/versioning-editions/))。 |
| **edit_stability** | `intent_state` の変更が、無関係なメンバーの `resolved_state` に波及しないか。 |
| **redstone** | 宣言した真理値表と時相アサーションに対する、tick 単位のシミュレーション。タイミングの衝突、QC への依存、配線の混雑 ([レッドストーン](/ja/spec/redstone/))。 |
| **AABB 干渉** | 重なった場合は、優先度に従って統合するか拒否する。境界のブロックステートの再解決は IR 層が担う。 |

このうち attachment、entity_aabb、support、fluid、edit_stability、AABB の干渉は計画中で、現時点ではどのコマンドも検査しません。本体が重なる 2 つの `place` 行も報告しません。幾何は一部だけ守られます。壁の外にはみ出す door、window、軒の stair は描かずに `W_DEFERRED_MEMBER` として報告し、自分の行の指定でどのボクセルにも乗らない pressure_plate は `E_UNPLACEABLE_PLATE` になります。version_caps / parity は、専用のコードを通じて一部だけ実行します。`E_VERSION_CAP` は `--target` を `@requires` の下限と照らし合わせ、`E_UNKNOWN_ID` は固定したターゲットが宣言していないブロック ID を拒否し、`W_INTENT_DEGRADED` はエディションが表せないものを示します。一方、ステートリテラルは照合しないまま使い (`W_STATE_LITERAL_UNCHECKED`)、エンティティのスキーマは検査しません。redstone の行も一部だけです。真理値表のコードが表そのものの整合性を検査するだけで、回路のシミュレーションは行いません。配線の混雑は `E_ROUTE_CONGESTION` ですが、これに到達できるのは Internal ティアの `cairn synth --experimental-logic-synth` だけです。

### did you mean

閉じた語彙に照らして名前を拒否する診断は、入力の長さに応じた Damerau-Levenshtein 距離の閾値に収まる候補があれば、最も近いものを示します。閾値は、1〜3 文字なら 1 編集以下、4〜6 文字なら 2、それより長ければ 3 です。対象になる名前は、キーワード、引数のキー、`mat_slot=` の名前、place / def / theme / port の参照、抽象トークン、`pressure_plate` の側面、ブロック ID、`--target` のバージョンです。

注記は ``did you mean `X`?`` の形で、`X` はその行に書くべき形で示します (ポートなら `home1.entry`、プレートなら `at=front.outside`)。`E_UNKNOWN_ID` だけは、ターゲットで最も近いブロックとして示し、候補を `data.suggestion` にも持たせます ([§11.2](#112-機械可読ペイロード))。

未知のキーワード、引数のキー、`mat_slot=` の名前には、閉じた語彙の一覧 (`expected one of: ...`) も併せて出力します。未知の `--target` には、指定できたバージョンの一覧 (`supported targets: ...`) を出力します。参照、トークン、ブロック ID には、こうした一覧は付きません。

## 11.2 機械可読ペイロード

`--format json` を受け付けるコマンド (`check`、`info`、`parse`、`lower`) は、**どんな入力に対しても** stdout に JSON 文書をちょうど 1 つ書き出します。`check` の文書は指摘の配列なので、パースできないソースは `E_PARSE` を 1 つ含む配列になります。`info` の文書はレポートです。レポートを出せないとき、つまりパースに失敗したときや、重大度が error の指摘があるときは、代わりに `{"diagnostics": [ ... ]}` を書き出します。レポートとはキーと終了コードで区別できます。どのパスが指摘を出したかによって、この形は変わりません。エディション中立の判定が和集合でまとめてしまうものを、エディションごとの厳密な試行が検出することがあります。そこで出た拒否も、要求されたエディションをすべて調べ終えた後で、同じ文書を書き出します。

ただし、どのパスが指摘を出したかによって、文書に **何を載せるか** は変わります。これは偶然ではなく契約です。エディション中立のパスが拒否した場合、そのパスの警告もエラーと並んで文書の要素になります。エディションごとのパスが拒否した場合、文書にはエラーだけを載せます。中立の警告はすでにテキストで報告済みで、エディションごとの警告はこれから捨てる行に属するので、そのエディションを示す注記の下で stderr に出力されます。レポートを出せる実行での警告は、どちらの形式でも stderr にテキストで報告します。

実行レベルの拒否は、`check` の配列の要素にはなりません。出荷されていない `--target` と、スコープを失った lowering (`E_PARTIAL_BUILD`) は、ファイル中のスパンに結び付く指摘ではなく、コマンドラインとビルドについての事実なので、どちらの形式でも stderr と終了コードで報告します。`compile` での扱いと同じです。配列には実行がたどり着いた指摘がすべて入るので、空の文書ではなく「何を検査したか」のレポートになります。

これは保留中の課題ではなく、決定済みの仕様です。`check --format json` には実行レベルの拒否を機械可読に表す形がなく、利用する側は判定を終了コードから読み取ります。stderr はどちらの形式でも人間向けの文章で、この契約には含まれません。利用する側はそれを解析せず、構造のないテキストとして扱ってください。stderr を読まなくても分かるのは、実行が指摘によってではなく、実行レベルで拒否された *ということ* です。終了コードが `1` で、配列に `"severity": "error"` の要素が 1 つもなければ、まさにそれを意味します。報告することのないソースに対する `[]` でも同じです。なお、ソース自体に重大度 error の指摘がある実行でも、実行レベルの拒否は起こりえます。その場合、配列はほかのエラーによる失敗と同じように見え、実行レベルでも拒否されたことは stderr にしか書かれません。ほかの失敗がこのように見えることはありません。パースできないソースは `E_PARSE` を含む配列になり、読めないファイルは文書を 1 つも書き出しません。2 つの拒否のどちらだったのか、ビルドが何を失ったのかは、stderr にしか書かれません。

`info` の拒否のうち 1 つは、同じ種類の実行レベルの拒否です。レジストリパックが拒否するはずだったブロックステートをパレットが含んでいると、そのエディションの portability の行が出なくなります。この拒否はソース中のスパンに結び付きません。そのようなブロックステートは、作者には直せないパックやコンパイラの漏れか、ソースで階段に書いたステートリテラルのどちらかです。後者は、Java のドメイン外の `facing` や `half` の値 (`@oak_stairs[facing=up]`) か、`facing` / `half` / `shape` 以外のキーで、`E_STATE_DOMAIN` が実装されるまではターゲットと照らし合わせる仕組みがありません。拒否のメッセージは両方の可能性を挙げます。ほかのブロックに書いたリテラルは、代わりに `unsupported` として数えます。どちらの形式でも、stderr にテキストで出力します。それでも文書は書き出します。約束は「入力ごとに 1 文書」であって、「拒否ごとに 1 要素」ではないからです。この拒否以外に拒否のない実行は `{"diagnostics": []}` を書き出し、残りは終了コードで示します。

`parse` の出力は AST、`lower` の出力は block-array IR です。ダンプはレポートではないので、失敗したときに「穴の空いたダンプ」を出すことはありません。どちらも `info` と同じ `{"diagnostics": [ ... ]}` を書き出し、ダンプとはキーと終了コードで区別できます。`lower` は、パースできないソースに対しても、後段のパスで失敗したソースに対しても、これを書き出します。どちらもダンプする価値のある IR を残さないからです。ほかの `--format` では、指摘は stderr にテキストで出力します。

`--format json` は、指摘ごとに 1 つのオブジェクトを返します。

| フィールド | 型 | 備考 |
|---|---|---|
| `code` | string | 安定した `E_*` / `W_*` の識別子。gcc 形式の出力と同じ文字列。 |
| `severity` | string | `"error"` または `"warning"`。 |
| `line` | integer | 主スパンの先頭バイトの行番号 (1 始まり)。 |
| `col` | integer | 同じ先頭バイトの列番号 (1 始まり、Unicode スカラー値単位)。 |
| `end_line` | integer | スパンの終端 (この位置は含まない) の行番号 (1 始まり)。 |
| `end_col` | integer | スパンの終端 (この位置は含まない) の列番号 (1 始まり)。 |
| `primary` | string | 人間向けのメッセージ。 |
| `notes` | array | `[{line?, col?, message}]`。空なら省略。 |
| `data` | object | コード固有のペイロード。なければ省略。 |

`data` は、`kind` で種類を判別する拡張可能なオブジェクトです。`primary` を解析せず、`(code, data.kind)` で照合してください。追加は既存を壊さない形でしか行わないので、未知の `kind` はエラーにせず無視します。下の表にないコードは `data` をまるごと省略します (JSON でも `null` ではなく、キーそのものが存在しません)。

| コード | `data` ペイロード |
|---|---|
| `W_WALKWAY_BLOCKED` | `{ "kind": "walkway_blocked", "skipped": <u64> }`。フォールバックの L 字経路で既存の構造物と衝突し、飛ばしたセルの数。セルを飛ばしたときに付き、ルーターの上限を超えて敷かなかった通路では省略する。 |
| `E_DUPLICATE_SELECTOR` | `{ "kind": "duplicate_selector", "rebound": ["frame"] }`。この行が先行する行から奪う、割り当て対象のキー。末尾の `=` は含まない。必ず空でない。 |
| `E_UNKNOWN_ID` | `{ "kind": "unknown_id", "id", "registry", "origin", "token"?, "suggestion"?, "aliases"? }`。後述。 |
| `E_INCOMPATIBLE_MATERIAL` | `{ "kind": "incompatible_material", "id", "required", "slot"?, "token"? }`。割り当てられたマテリアル、ジオメトリが必要とするファミリ、割り当ての出どころ。 |
| `E_INCOMPLETE_PLACE` | `{ "kind": "incomplete_place", "missing": ["id", "use", "theme"] }`。行に書かれていないキー。必ず空でない。 |
| `E_INVALID_REQUIRES` | `{ "kind": "invalid_requires", "reason", "found" }`。`reason` は `not_a_version_requirement` / `unknown_edition_scope` / `unsupported_operator` / `empty_version` / `component_not_a_number` / `component_too_large` / `prerelease_not_a_tag` / `trailing_tokens` のいずれか。失敗が特定の断片を指さないとき、`found` は空。 |
| `W_INVALID_CAIRN_VERSION` | `{ "kind": "invalid_cairn_version", "reason", "found" }`。`reason` は `component_count` / `component_not_a_number` / `year_not_four_digits` / `month_out_of_range` / `patch_too_large` / `trailing_tokens` のいずれか。`found` はその理由が指す成分。失敗が特定の断片を指さないとき (`component_count` と、成分そのものが空の値 (`2026.`) に対する `component_not_a_number`) は空。 |
| `W_FUTURE_CAIRN_VERSION` | `{ "kind": "future_cairn_version", "declared", "compiler" }`。どちらも書かれたままの文字列。`declared` はファイル中の値、`compiler` は報告したビルドのバージョン。 |
| `W_TRUTH_TABLE_PARTIAL` | `{ "kind": "truth_table_partial", "inputs": 2, "covered": 1, "missing": ["01","10","11"] }`。後述。 |
| `@intended_targets` の 3 コード | `{ "kind": "intended_targets", "edition", "targets": ["1.20.4"], "floor"? }`。指摘の対象となるバージョンをソース順に並べたものと、照らし合わせたエディション。`floor` はそれらを最初に拒否する下限を書かれたまま持つ。下限の問題ではない `W_INTENDED_TARGET_UNSUPPORTED` では省略。 |

**`E_UNKNOWN_ID.origin`** は、誰がその ID を選んだかを示します。直す場所が違うからです。

| `origin` | 意味 | 直す場所 |
|---|---|---|
| `authored` | ソースが ID を直接指定した。 | 作者の行。 |
| `catalog` | レジストリパックがトークンを ID に対応付けた。 | パックの対応付け。 |
| `builtin` | メンバーの既定値に使う行をパックが持たず、コンパイラ組み込みの ID を使った。 | 行を追加すべきパック。 |

`token` は `catalog` と `builtin` のときに付き、`authored` では省略します。`suggestion` は、タイポの閾値に収まる宣言済みの ID がなければ省略します。リネームはふつうこの閾値の外にありますが、2 つのフィールドは互いに独立した規則で埋まるので、置き換え先に綴りが近いリネームは両方を持ちます。

`aliases` はもう半分にあたり、この 2 つは同じ ID についての別種の主張です。`suggestion` は文字列の距離からの推測ですが、`aliases` は、レジストリパックの `aliases` コンポーネントが「2 つの名前は同じブロックだ」と述べたものなので、クイックフィックスは `aliases` なら確認なしで適用してよく、`suggestion` は適用すべきではありません。中身は、ターゲットがそのブロックについて宣言している ID すべて (閉じた候補集合であって、そこから選んだものではない) をパック自身の順番で並べたもので、パックが 1 つも挙げていなければ省略します。表示される注記は先頭のいくつかを並べて残りの数を示し、集合全体はペイロードに入っています。[バージョンとエディション §10.4](/ja/spec/versioning-editions/#104-fail-loud-と最小バージョン推定) を参照してください。

`E_INCOMPATIBLE_MATERIAL` も同じ考え方です。`slot` はメンバーが読んだ `mat_slot=` の名前で、割り当てがなければ省略します。`token` がドット付き (`roof.dark_wood`) なら、直すべきはソースの行ではなくパックの対応付けです。`required` を暗黙にせず名前で持つのは、将来ほかのファミリが加わっても、コードを増やさずにこの値で表せるようにするためです。

`W_TRUTH_TABLE_PARTIAL.missing` は、集合そのものではなく **サンプル** です。入力が 20 本なら、組は 100 万通りあります。件数は `missing.len()` ではなく `2^inputs - covered` で求めてください。総数ではなく `inputs` を持つのは、入力リストに文法上の上限がなく、`2^130` を収められる整数型がないためです。

## 11.3 エラーと警告の区分

- **エラー** は、放置すると意図しない結果になるものです。概念の不在、未知の ID、ドメイン外のステートがこれにあたります。サイレント置換と暗黙の削除は禁止です。
- **警告** は、バージョンやエディション間の意味のずれ、レッドストーンの挙動が保証されないこと、そして block-array パスが報告する部分的なビルドの劣化です。不完全なのがソースではなくコンパイラの側である場合です。

`E_` / `W_` の接頭辞は重大度を表しません。これは両方向に言えます。多くの `W_` コードは部分的なビルドの劣化を表しますが、劣化ではないのに警告のコードもあります。`W_UNUSED_DEF`、真理値表の 2 つの警告、`@cairn` の 2 つのコード、`W_INTENDED_TARGET_CAP`、`W_INTENDED_TARGET_UNSUPPORTED`、`W_THEME_VARIANT_REBOUND`、`W_DUPLICATE_WALKWAY`、そしてリテラルを書かれたまま出力する `W_STATE_LITERAL_UNCHECKED` などです。そして接頭辞が `E_` の次の 2 つは、名前ではなく上の規則で重大度を決めています。

- `E_UNKNOWN_SLOT_TARGET` は **エラー** です。誤りはソースの側にあり、スロットがマテリアルトークンでない値で書かれているからです。参照するメンバーはテーマがないときと同じ形で作られるので、作られるものからは `W_NO_THEME_BOUND` と区別できません。
- `E_THEME_SELECTOR_UNMATCHED` は **警告** です。何にもマッチしないルールは、何も上書きしません。

`E_PARSE` は、パースが失敗するあらゆる形 (未知の文字、奇数のインデント、`i64` を超える整数、項目が来るべき位置にあるキーワード) をまとめた 1 つのコードで、どれが起きたかはメッセージでわかります。形ごとにコードを分けると、パースの失敗の形が増えるたびにこの表が 1 行ずつ増えます。しかも今のところ、形によって処理を分けたい利用者はいません。その代わり、区別するにはメッセージを読む必要があります。また `E_PARSE` は、どの検査パスも出さない唯一のコードです。パースはすべてのパスより先に行われ、パースできないソースはどのパスにも届かないので、ビルドが単独で報告する唯一の指摘です。

block-array lowering の指摘は、ターゲットを固定しているかどうかによらず、ソースを検査するところならどこでも報告します。`--target` がないとき、つまり素の `cairn check` と、何も固定しない言語サーバーでは、ターゲットなしで lowering し、その行を読むどのターゲットでも出る指摘を、固定した check と同じコード、スパン、メッセージで報告します。その際、エディションのいずれかの出荷済みバージョンが宣言するブロック ID は、すべて宣言済みとして判定します。抽象トークンと、どの出荷済みバージョンも宣言しない ID は、見送るのではなく、ターゲットのパックがそれに対して指定するブロックの代わりとして扱い、そのブロックについての判定は行いません。つまり、その代役に対する `E_INCOMPATIBLE_MATERIAL`、代役と別のブロックとの `W_PHASE_CONFLICT`、代役だけが原因になりうる `W_PALETTE_TOO_LARGE` は、どれも出しません。パレットは代役を除いて数えるからです。代役を空気が上書きした場合と、空気を代役が上書きした場合は、どのパックも空気を指定しないので、やはり `W_PHASE_CONFLICT` です。既定のブロックで作られる `pressure_plate` はパックの感圧板を使うので、これも同じ代役です。`W_WALKWAY_BLOCKED` の注記は、固定した check ならブロックの名前を示すところで「a block」と書きます。`E_UNKNOWN_ID` と `E_UNKNOWN_ABSTRACT_TOKEN` はパックによる判定なので出しません。ターゲットでのビルドが失うものを数える `E_PARTIAL_BUILD` も出しません。`--edition` だけを付けると、そのエディションのテーマバリアントを選びます。どちらのフラグもないときは、各エディションのバリアントで lowering します。1 つのエディションのバリアントだけが読む行にある指摘は、そのエディションの判定として報告します。それ以外の指摘は、すべてのエディションが同じスパンに同じコードで出すときに、エディションが付けるメッセージごとに 1 回ずつ報告します。`--target` を付けた check はターゲットに対して 1 回だけ lowering するので、同じ指摘を 2 回報告することはありません。

`E_MISSING_MATERIAL` が **エラー** なのは、上の 2 つの規則のうち 1 つ目によるものです。メンバーはビルドから落とされ、その場所には何も置かれません。これは暗黙の削除で、部分的なビルドの劣化ではありません。不完全なのはマテリアルを指定しなかったソースの側で、コンパイラの側ではないからです。しかも削除はそのメンバーだけでは終わりません。`walls` が落ちると、体積の導出に使う壁の高さが下がるので、構造物そのものが縮み、そこに開けるはずだった `door` や `window` も見送られます。

`E_DUPLICATE_SELECTOR` も同じ理由で **エラー** です。セレクタによる割り当ては予約中で、このコードが扱う 2 つの値はどちらもビルドに使われませんが、それでも変わりません。割り当てが今後どんな意味を持つことになっても、後の行は先の行の値を効かない記述にします。これはソースの誤りで、今の時点ですでに存在し、割り当てを lowering できるようになっても残ります。先の行が選ぶメンバーはすべて後の行にも選ばれるので、メンバーをどう編集しても先の値は効きません。一方、`E_THEME_SELECTOR_UNMATCHED` が報告する行は、マッチするメンバーを足せば効くようになります。コンパイラの側で欠けているのは予約中であることそのもので、それは割り当てごとの `W_IGNORED_ARGUMENT` がすでに報告しています。またこのコードは、2 つの行に対して、`E_DUPLICATE_ARG` が 1 つの行に下すのと同じ判定を下します。1 つの行で同じキーを 2 回書けば拒否されます。同じメンバーを選ぶ 2 つの行は、1 つの割り当ての並びを 2 行に分けて書いたものと同じなので ([マテリアルとテーマ §7.1](/ja/spec/materials-themes/#71-依存性注入としてのスロット))、どこで改行しても、ビルドが拒否されるかどうかは変わりません。

`@cairn` の 2 つのコードは、同じ規則を逆から当てはめた結果、**警告** です。このヘッダは来歴 (provenance) で、どのパスも分岐に使わず、パレットのエントリもここからは生じません。ロックファイルの `cairn_version` が記録するのも、ファイルではなくコンパイラのバージョンです。`@cairn banana` は `@cairn 2026.06` とバイト単位で同じものを建てるので、結果について意図しないことは何も起きません。失われるのはヘッダ自身の役目、つまり後のコンパイラが読めることで、一言伝える価値はあっても、ファイルを拒否するほどではありません。同じ判定で `@requires` がエラーなのは、その下限が入力そのものだからです。下限は `cairn info` の互換範囲を決め、`cairn compile --target` を縛るので、下限が消えると通してはいけないターゲットを通してしまいます。

`E_UNKNOWN_ARGUMENT` は **エラー** です。理由は 1 段上の `E_UNKNOWN_KEYWORD` と同じです。キーワードの語彙にないキーは何も指しておらず、コンパイラがどう成長しても、その値を読むパスは現れません。メンバーは求められたものを持たないまま建ちます。最悪なのは既定値を持つ引数の綴り間違いで、ビルドは既定値のまま成功し、何も言いません。

各キーワードの語彙は閉じています。語彙を広げられるのは、`theme` のセレクタが名指したキーワードの語彙だけです。テーマに `window[tags=...]` と書けば、`tags=` は window で何かに読まれるキーになり、ほかのキーワードではなりません。逆向きの問題は `E_THEME_SELECTOR_UNMATCHED` が扱います。セレクタが作れるのは新しい語です。そのキーワードがすでに持つ語から 1 編集しか離れていない語は、造語ではなく「2 回書かれた綴り間違い」なので、候補付きで拒否します。広げるといっても、語を認めるだけです。マッチによってメンバーに渡るのはその行の割り当てで、割り当ては予約中のままなので ([マテリアルとテーマ](/ja/spec/materials-themes/))、キーワードが定義していてどのパスも読まないキーは、セレクタがそのキーでマッチしていても、まだ届いていないキーのままです。

メンバー自身の `[key=value]` も同じ語彙に従います。`window[clas=outer]` は `window clas=outer` と同じ欠陥です。書き手が何かに読まれると思っている語を何も読まず、どちらにしても `class` は失われるので、同じコードと同じ候補が付きます。そのセレクタが何を *意味* するかは別の問題で、ここでは決めていません。メンバーのセレクタはそのまま運ばれ、新しい id を割り当てているのか、既存のメンバーを参照しているのかは後段のパスが決めます。この検査にはその答えは不要です。どちらに決まっても、その語は何かに読まれるか読まれないかのどちらかだからです。なお、メンバー自身の括弧に書いたキーによって、そのメンバーがその属性を *持つ* ことにはならないので、それを選ぶ `theme` の行はどのメンバーにもマッチしません。

`struct` / `def` のヘッダ行は、[コンポーネント・編集・複数建築](/ja/spec/components-editing-sites/) が定める、ヘッダ自身の閉じた語彙に従います。lowering が読む `size=` と、まだどのパスも読まない `class=` です。セレクタが名指すのはメンバーのキーワードなので、`theme` のセレクタがこの語彙を広げることはありません。この 2 つ以外のキーは、メンバーの場合と同じ欠陥が 1 行上で起きたもので、候補付きで拒否します。`struct s siz=7x7` には `size` を示します。同じ綴り間違いが引き起こすサイズ欠落の警告は、struct にサイズがないと言うだけで、綴り間違いそのものは指摘できません。エラーは警告より先に出力します。

`W_IGNORED_ARGUMENT` は **警告** で、3 種類の問題を扱います。**読めなかった値**: 語彙にはあるが値を読めなかった `key=` は捨て、代わりに既定値を使います。ただし、キーそのものがメンバーを建てるかどうかを決める場合は、代わりにメンバーを拒否します (現在これにあたるのは、`repeat=` が 1 より大きい `window` の `sym=` です。[§5.4](/ja/spec/syntax/#54-セレクタ))。**読まれないキー**: キーワードは受け付けるが、書かれた場所では何も読まない `key=` は、IR まで運ばれても一度も参照されません。これには 2 種類あります。*まだ届いていない* キーは、本仕様が定義していながら、まだどのパスも読まないキーです (現在これにあたるのは、`window shape=` / `anchor=`、`roof footprint=` / `bounds=`、ヘッダの `class=`、そしてドアのブロックそのものを待っている `door` の `mat_slot=` です)。コンパイラが知っているキーワードについての `theme` のセレクタ行で、矢印の右にある `key=value` もすべてこれにあたり、キーや値が何であっても、その割り当ての位置で報告します。セレクタによる割り当てを lowering するパスがまだないからです ([マテリアルとテーマ](/ja/spec/materials-themes/))。*当てはまらない* キーは、すべてのメンバーが受け付けるキーが、それを読むものを何も置かないキーワードに書かれたものです (現在これにあたるのは、`level` / `circuit` / `place` / `connect` の `mat_slot=` です)。どちらの種類の `mat_slot=` もテーマで引かないので、テーマが宣言していないスロット名は `E_UNRESOLVED_SLOT` ではなくこの警告になり、綴り間違いも検出しません。**素通りされたキー**: 同じ行の別の引数の書き方によってだけ読まれるキーが、その引数を別の書き方で書いたメンバーに付いている場合です。境界はキーワードです。コンパイラが知っているキーワードの、仕様で定義されたキーはこの形で報告し、知らない **キーワード** は `E_UNKNOWN_KEYWORD` になり、その引数は判定しません。3 種類とも、ビルドをソースと食い違わせます。規則が禁じているのは *サイレントな* 置換で、3 種類ともそれを告知します。まだ届いていないキーで欠けているのはソースではなくコンパイラの側なので、拒否はしません。当てはまらないキーでは、どこも欠けていません。すべてのメンバーが受け付けるキーで、その値はビルドを何も変えないので、警告はそのキーの削除を勧めます。拒否すると、すべてのメンバーが受け付けるキーを、一部のキーワードだけが拒むことになります。自動修正を提供するかどうかは実装に任せます。

読めなかった値は、そのメンバーが最終的に建つかどうかに関係なく報告します。値はメンバーがどうなっても誤りなので、それだけで 1 つの修正になります。同じ行の拒否が直るまで指摘を保留すると、書き手はコンパイルを 1 回余計に回すことになります。3 つのうちどれが起きたかは注記に示されます。建つメンバーなら、既定値が出力にどう影響したか。どのみち建たないメンバーなら、そのことと、その理由が隣の拒否であること。既定値を使う代わりに拒否されたメンバーなら、そのことと、隣の拒否がこの値によるものであること。現在の例外は、引数を読む前に落とされるメンバー (持ち上げた `level` の下の `roof` など) です。値が読まれないので、落とされたことの指摘の隣に報告することはありません。ほとんどの値は block-array lowering でしか読まれず、読めなかった値の判定にはターゲットが不要なので、`--target` のない `cairn check` と言語サーバーも、固定した check と同じように報告します。

素通りされたキーは、語彙の 2 つ目の軸です。語彙はキーワードごとに閉じており、*さらに*、lowering の規則を選ぶ引数の書き方ごとにも閉じています。`roof slope_to=` を読むのは `kind=shed` の規則だけで、ほかのどの規則も読まないので、

```
roof kind=gable slope_to=front
```

は向きを無視した屋根を建てます。語彙の外のキーで起きる黙った取りこぼしが、引数の 1 段下で起きているわけです。これを `E_UNKNOWN_ARGUMENT` のように拒否せず警告にとどめるのは、直す場所が決まらないからです。このキーは、それを読むキーワードに実在する語です。意図していたのが `kind=` のほうなのか、`slope_to=` が消し忘れなのかは判断できません。メッセージは両方の箇所を示し、どちらも選びません。

この軸の選択肢は、セレクタを *書かないこと* でもありえます。書かないこと自体が 1 つの規則になっている場合です。`place gap=` がその例です。`at=` のない行は、別の place からの相対配置として距離を読みますが、`at=origin` は絶対位置に固定されるので読みません。つまり `at=origin gap=5` でも、同じ黙った取りこぼしが起きます ([§9.3.2](/ja/spec/components-editing-sites/#932-原点セレクタ))。

**セレクタ** がどの規則も指していないとき、つまり lowering の規則が知らない値のときや、「書かない」選択肢を持たない軸で何も書かれていないときは、ここでは何も報告しません。そのメンバーは lowering されず、その拒否が修正のすべてを担うので、その規則なら読まなかったはずの引数について 2 つ目の指摘を出すと、1 つの修正について 2 回知らせることになるからです。その拒否は `W_DEFERRED_MEMBER` で、`pressure_plate` の `at=` なら `E_UNPLACEABLE_PLATE` です。これもターゲットを必要としないので、`--target` のない `cairn check` も、固定した check と同じように報告します。規則を選ぶのでは *なく* 別のキーを無効にするキーは、さらに別の形で、現在は報告しません。`repeat=1` のときの `window step=` は、規則ではなく個数についての条件です。

`E_MISPLACED_BINDING` は、メンバー行の 4 つ目のフィールドに、ほかの 3 つと同じ問いを向けたものです。つまり「この語は何かに読まれるのか」です。末尾の `-> value` を読むのは [§14.2](/ja/spec/redstone/#142-信号バインディング) のセンサの集合だけなので、センサでないメンバーに付いた末尾は IR まで運ばれて捨てられ、そこで指定された信号は誰も発しません。`E_UNKNOWN_ARGUMENT` と同じ基準で **エラー** です。ビルドがソースと食い違い、しかも値をどう直しても解決しないからです。

ここで問うのはホストのキーワードだけです。Logic IR なしで問えるのはホストだけだからです。末尾の値が信号を指しているか、その信号が二重に駆動されていないか、誰にも駆動されていないかは、レッドストーンのパイプラインが判定します ([§14.2](/ja/spec/redstone/#142-信号バインディング))。そしてホストのほうを先に問うので、信号を発せないメンバーに付いた末尾にはこのコードが付き、値の側の指摘は付きません。キーワードが既知のキーワード表にないメンバーは、`E_UNKNOWN_KEYWORD` に任せます。本仕様が挙げているものの、まだ表層の構文が受け付けていないセンサ (たとえば `lever -> sig.a`) について、ホストが誤りだと言わないのはそのためです。
