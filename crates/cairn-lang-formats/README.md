# cairn-lang-formats

This crate's Rust API is in the [Internal tier](https://cairn.kage1020.com/spec/compatibility/#internal) and carries no promise: any release may change it.

Readers and writers around the Cairn block-array IR for existing schematic / structure formats, plus the registry packs that say which block ids, and which states of each, a given `(edition, version)` actually has, and the build every front end runs over a source to reach them, and the Java world a structure file is installed into.

Each format is a serializer or deserializer around the **block-array IR**, which the specification names as the universal pivot ([architecture "The block-array IR is the universal pivot"](https://cairn.kage1020.com/spec/architecture/)). Adding a format means adding a backend here — the parser, lint, and theme machinery in [`cairn-lang-core`](../cairn-lang-core/README.md) are untouched.

## Status

Java vanilla `.nbt`, Litematica `.litematic`, Sponge Schematic `.schem` and Bedrock `.mcstructure` writers ship, and so do the built-in registry packs behind `cairn info` and every id check. The Bedrock writer translates each palette entry's canonical blockstate, which is Java's, into the target version's Bedrock block and `states` through the built-in pack's state map ([`bedrock_state`](src/bedrock_state.rs)). A state the map has no form for, or one the Java block does not have, is a hard error (`BedrockStructureError::State`); intent a version can only approximate (stair `shape` before 1.26.60) is dropped with a `W_INTENT_DEGRADED` parity note rather than in silence; and `waterlogged` becomes the structure's water layer. Each writer saves the block array's block entities, a sign's text, a Bedrock bed's colour and a circuit comparator's output, in its own edition's shape, and the Bedrock writer also fills the block entities that keep a state Java keeps in the block, a chest's pairing and a note block's note. A chest half with no other half beside it stands single on Bedrock, with a `W_INTENT_DEGRADED` parity note. The `.nbt` and `.mcstructure` writers also write the entities the block array's members place into their format's `entities` list, with each one's point and fields in its edition's shape and the `nbt={...}` its line writes over them: the Java writer spells an item and a display's text and block state as the target's `DataVersion` reads them, and the Bedrock writer builds an item frame as the frame block and its block entity, and refuses a display, which Bedrock has no counterpart for (`BedrockStructureError::UnmappedEntity`).

The [`info`](src/info.rs) module builds the `cairn info` report, its JSON document and the `note:` lines behind its rows, once for every front end: the CLI prints it, the language server's `cairn.info` command returns it, and [`cairn-lang-wasm`](../cairn-lang-wasm/README.md) answers it in the browser.

The `.litematic` writer puts each struct in a file of its own and each site in one file, a region per placement and walkway at its site origin ([ecosystem-interop "Litematica"](https://cairn.kage1020.com/spec/ecosystem-interop/)), and streams each region's packed `BlockStates` from the grid. The `.schem` writer writes version 3, one file per struct, placement and walkway like `.nbt`, each with its site origin as its `Offset` ([ecosystem-interop "Sponge Schematic"](https://cairn.kage1020.com/spec/ecosystem-interop/)), and streams the varint `Blocks.Data` from the grid. Every Java writer takes its block entities from the same encoding and placement as `.nbt`'s, so a block entity the IR carries is written by all three, but for a bed's, whose colour Java keeps in its block. Of the Java writers only `.nbt` writes entities: each `.litematic` region's `Entities` is empty, and a `.schem` has none, and `cairn compile` notes how many entities either leaves out. A reader of each format ships too. The `.nbt`, `.litematic` and `.schem` readers return a `BlockVolume`, the `.litematic` reader one region at a time and the `.schem` reader versions 2 and 3; the `.mcstructure` reader returns a `BedrockVolume`, both of its layers as the file stores them, in the Bedrock vocabulary.

[`import`](src/import.rs) is the library half of `cairn import --mode raw` ([ecosystem-interop "Reverse direction: the compiler transliterates, an LLM lifts"](https://cairn.kage1020.com/spec/ecosystem-interop/)). It decodes a file into one block grid per structure it holds, a `.litematic` a grid per region, and stamps it with the shipped target the file's saved version maps onto ([ecosystem-interop "Import stamping and pitfalls"](https://cairn.kage1020.com/spec/ecosystem-interop/)). A Bedrock block is read back into the canonical vocabulary through the target's state map, the inverse of what the writer does. Core's [`transliterate`](../cairn-lang-core/src/transliterate/mod.rs) then writes the grids as raw members and compiles them back against the stamp to check every cell. Each thing the raw members do not carry, block entity data among them, is returned as a `SemanticLoss`, which the CLI prints as `W_SEMANTIC_LOSS`.

The [`world`](src/world/mod.rs) module reads what placing a structure file in a Java world save needs: the version its `level.dat` records, the `DataVersion` a structure file is stamped with, and the file a structure id names in the world's `generated` folder. It walks NBT through [`cairn-lang-nbt`](../cairn-lang-nbt/README.md)'s pull reader, holding only the entries it reads, and tells a Bedrock `level.dat` or `.mcstructure` apart so the command can refuse it by name.

## Registry packs

A pack is the closed vocabulary every id-level answer comes from: which blocks exist in a version and the values each of their states takes, which name a renamed block goes by there, and which canonical token an abstract material resolves to. The Bedrock pack also carries its state maps: `states.json`, how each version writes the canonical states, and the hand-written `sensitivity.json`, what dropping a state no Bedrock state reads costs. Both carry `connections.json`, what each block is to the rules that join panes, fences and walls to their neighbours, the hand-written `paintings.json`, each version's paintings with their sizes in blocks, the hand-written `absent.json`, the other edition's blocks and entities this one has no counterpart for, each with the reason `E_PARITY_UNSUPPORTED` prints, and the hand-written `meanings.json`, each canonical token whose block split into several and the meaning token whose value picks one. A canonical token's meaning token is read through the meaning table first, for the block its value picks, and a token a version does not declare is then read through the others before it is refused: the alias group of a block renamed across the edition gives that version's spelling, and on Bedrock the state map writes a Java block as blocks of its own where no other Java block takes the same forms. `registry-data/<edition>/pack.json` holds the built-in pair, and `load_from_dir` takes an external one. Each table carries a `schema_version` the loader refuses to read past, so a pack written for a newer Cairn fails loudly instead of being half-understood.

Beside the two packs, `registry-data/constraints.json` is the hand-written constraint catalog ([lint "Constraint catalog"](https://cairn.kage1020.com/spec/lint/)): which blocks hang on or stand on a face and what that face must give, which fall, and the Java versions at which a block's meaning changes. One file serves both editions in canonical ids, and the faces it asks about are the connection tables'. It is checked against both packs as it loads, and hashed on its own.

The block tables are extracted from the game, and so is the integer each targetable row of a version table writes, Java's `data_version` and Bedrock's `block_version`: Java's from the server jar's `--reports`, Bedrock's from the block palette GeyserMC ships for the release, pinned by commit and SHA-256. Bedrock's state maps come from GeyserMC's Java-to-Bedrock mappings, pinned the same way, read against the `--reports` of the Java release each one follows. Both editions' connection tables are read off the block tags of the server jar of the Java release each version's states follow, the version itself on Java and the release its state map follows on Bedrock, and the block models of that release's client jar. `pack.json` records the file each table came from, under an `extracted` key the compiler does not read. To regenerate an edition's tables, or check the committed ones with `--check`:

```sh
python3 .github/scripts/extract_registry.py java --java <a Java 25 or later>
python3 .github/scripts/extract_registry.py bedrock --java <a Java 25 or later>
```

Because the tables are closed, a suggestion cannot name a block that does not exist in the target — the "valid candidates" half of a diagnostic is looked up, never generated ([principles P3](https://cairn.kage1020.com/spec/principles/)).

## The build a front end runs

The `build` module holds the passes [`cairn`](../cairn-lang-cli/README.md) and [`cairn-lang-wasm`](../cairn-lang-wasm/README.md) both run over a source, so the CLI and the playground report the same findings and refusals in the same words: the gate `cairn check` applies (`build::gate`), the lowering at a pinned target with each struct's circuit laid (`build::lowering`, `build::circuits`), the run-level refusals and the warnings that name no span, which [lint "Machine-readable payload"](https://cairn.kage1020.com/spec/lint/) keeps apart from the findings (`build::run_level`), each structure checked for its writer (`build::artifact`), and the refusal of a target a version floor rules out (`build::floors`), with the floors the registry contradicts (`build::conflicts`). The `info` report is built on the same passes. The `target` module checks a structure against the backend a resolved target selects. The crate root re-exports none of `build`, `info` and `target`, so the table above does not list them.

## Forward / reverse contract

- **Forward**: block-array IR → serialize. The compile pipeline writes the IR; each backend encodes it for one format.
- **Reverse**: deserialize → block grids plus a provenance stamp `(edition, version)` → raw members. The compiler performs only a *faithful transliteration* into the raw-centric DSL; semantic lifting is the LLM's job ([ecosystem-interop "Reverse direction: the compiler transliterates, an LLM lifts"](https://cairn.kage1020.com/spec/ecosystem-interop/)). The written source compiles back to the same block array, so the reverse direction shares the forward direction's IR rather than having one of its own ([architecture "The block-array IR is the universal pivot"](https://cairn.kage1020.com/spec/architecture/)). Litematica's regions are not flattened: each is a struct of its own, with its corner kept as a comment ([ecosystem-interop "Import stamping and pitfalls"](https://cairn.kage1020.com/spec/ecosystem-interop/)).

## Out of scope

- Pre-1.13 legacy numeric-id `.schematic`. v1 does not support flattening ([overview "Scope and non-goals"](https://cairn.kage1020.com/spec/overview/), [open-issues "Choices to settle at implementation time"](https://cairn.kage1020.com/spec/open-issues/)).
- SNBT printing — Cairn does not round-trip through SNBT.
